# Selective file download

> **Read before touching** `internal/download/manager.go`, `selection_pass.go`, `internal/bittorrent/` piece priorities, or any download client's `SetWantedFiles`/`ListFiles`/`AddTorrent`.
>
> **Covers** — the `download.selective_files` gate, the two grab flows (`.torrent` vs magnet), how `replace_mode` decides the wanted set, `selection_mode` persistence across restarts, each client's selection quirks, and the §4.6 widen rule.
>
> **Not here** — which release wins (`quality-scoring.md`), what happens at import ([`downloads-and-imports.md`](downloads-and-imports.md)).

- `download.selective_files` (default **false**, runtime-toggleable) gates the feature; off is bit-for-bit today's whole-torrent grab. `download.selection_grace` (default `10m`) bounds how long a magnet-sourced selection may sit `pending` before giving up and downloading whole. `schedules.file_selection` (default `30s`) is the pass that resolves `pending` records. **The 5s resolution cadence lives inside the run, not in the schedule** (`jobs.FileSelection`): the job re-runs the pass every `selectionBusyInterval` for as long as it keeps finding pending records, capped at `selectionBusyBudget` (1 min) per run so the scheduler stays in charge. Registering it at 5s instead was thousands of ticks a day finding nothing — the query is indexed and cheap, but a *tick* never is, since the state hook commits a WAL frame through the one SQLite connection every API request queues behind. Folding it into the 30s `download_monitor` tick is still wrong for the opposite reason: that would waste up to 30s of bandwidth per magnet with no fast path at all.
- **The wanted set follows `replace_mode`**, computed one tick earlier by the same predicate the importer uses at import time (`quality.ReplacesFile`), so grab-time and import-time never disagree about what a release is *for*:

  | `replace_mode` | producer | wanted set |
  |---|---|---|
  | `none` | single-episode missing grab (`grabEpisode`), manual grab without replace | missing (`wanted` + aired) episodes only |
  | `upgrades` | RSS gap-fill (`grabPack`), RSS upgrade (`grabUpgrade`), missing-search pack (`grabSeasonPack`, per-grab `UpgradeCandidateShow` context) | missing episodes **∪** episodes whose file the release beats (`beatEpisodes`/`quality.ReplacesFile`) — this union is what keeps "a pack grabbed to fill a gap also replaces what it beats, in the same grab" true once bytes stop being free |
  | `all` | manual replace grab (`grabPackAndMark` with `replaceExisting`) | every episode in the grab's scope — the operator said replace |

  Two producers sit outside the keep-set story and are documented in their own sections: `ReplacePending` stamps `upgrades` (adoption), and the movie feed's `tryUpgrade` stamps `all` (a movie has one file and no keep-set).

  `wantedAiredEpisodes` is what the status-marking loop may ever flip to `downloading` in either mode — a pack can't contain an unaired episode regardless of what was asked to replace — while the `GrabEpisode` wanted-set itself is wider under `all`, since that mode is about the selective-download keep-set, not about which episodes get marked.
- **An anime group may write the absolute number in `SxxExx` form, and the keep-set has to read it.** TLC and Tsundere-Raws list a release as `S02E03` and name the file inside the torrent `S02E15` — TVDB's absolute 15. `library.Parse` reads a real season and episode there, so `AbsoluteNumber` is 0 and `MatchEpisodeInSeason`'s anime arm never fires; the season+episode lookup then finds no `S02E15` in a 12-episode season and `computeKeepSet` returns zero matches, failing the grab with `ErrNoWantedFiles` **before any client is contacted**. The episode is then unfillable no matter how many acceptable releases exist — measured on a homelab where the only non-rejected release for two episodes was refused this way every pass. The fallback runs **only after** the exact season+episode found nothing, so a season that genuinely holds that episode still wins, and it is anime-only.
- **Flow A (`.torrent`)**: `grab` (`internal/download/manager.go`) decodes the metainfo before `AddTorrent` and matches files to episodes with the importer's own matcher (`library.MatchEpisodeInSeason`) — anything the selector can't match, the importer can't match either, so there is no "grab it anyway" fallback. Zero matched episodes fails the grab with `ErrNoWantedFiles` **before any client is contacted** (bumps `grab_failures`, nothing to remove). Every automatic caller counts that against the anchor episode — the RSS/missing single-episode paths, the magnet pass, **and both season-pack arms** (`rss.grabPack`, `rss.grabSeasonPack`); the manual REST grabs surface it as a 422 `grab_rejected` and bump nothing; a season whose only packs all mismatch would otherwise be re-tried every tick and never reach `max_grab_failures`. The pack arms count `ErrNoWantedFiles` only, since any other grab error is the pack's alone and says nothing about the episode. Every candidate matching a wanted episode collapses the grab back to `selection_state: skipped` (not selective, take it whole) rather than applying a no-op selection.
- **Flow B (magnet)**: the file list is unknowable at grab time, so `grab` marks the source `Selective` and parks the record `selection_state: pending`; `RunSelectionPass` (`internal/download/selection_pass.go`) resolves it once `client.ListFiles` reports something. A zero-match resolution here removes the torrent **with its files**, fails the record, and bumps `grab_failures` — same outcome as Flow A's zero-match, one tick later. Past `selection_grace`, an empty or persistently-erroring `ListFiles` gives up and downloads whole (`finalizePending`) rather than hanging the record forever.
- **`selection_mode` is the invariant that keeps a restart from undoing a selection.** The builtin engine's `startWhenReady` calls `applyFilePriorities(t, mode, wanted)` every time a session is (re)armed, including every process restart (sessions restore from `TorrentSession`). `mode` gates what gets bumped off `PiecePriorityNone`: `all` bumps everything (today's behavior — manual adds, adopted torrents, every non-selective grab), `pending` bumps **nothing** (a magnet whose keep-set hasn't resolved — this is also how the builtin engine wastes zero bytes on a selective magnet with no paused-add dance, since anacrolix fetches metadata independently of piece priority), `explicit` bumps exactly `TorrentSession.wanted_files`. Both `pending` and `explicit` are persisted on `TorrentSession` and therefore **survive a restart** — the bug this exists to prevent is a `None`-priority skip (indistinguishable from "nobody decided yet") getting silently bumped back to `Normal` on the next boot, quietly re-downloading everything a selection had excluded.
- **`wantedBytes`/`wantedCompleted`** (`internal/bittorrent/wanted.go`) sum `f.Length()`/`f.BytesCompleted()` over files at priority `!= None` and are the completion/progress/ratio denominator throughout the builtin engine — anacrolix's `BytesMissing` counts every incomplete piece regardless of priority (skipped pieces included) and never reaches zero once a file is skipped, so completion would never fire without this. With nothing skipped these equal the full torrent, so full-torrent behavior needs no special case.
- **Mode `pending` means zero demand, and two places had to stop reading zero demand as "done".** `Engine.status` returns `StatusFetching` for a `pending` torrent before the `wantedMissing == 0` branch — with no file wanted that sum is 0 the instant metadata resolves, which reported a torrent that had downloaded nothing as seeding, i.e. ready to import. `CheckStatus` mirrors the same guard on the record's `selection_state` so a client that scopes progress the same way can't flip a pending record to `importing` either.
- **`ResumeTorrent` is the give-up exit from mode `pending`, for the builtin engine.** Nothing else ever writes mode `all` onto an existing session, so a `pending` torrent that is merely resumed keeps every file at `PiecePriorityNone` and runs forever asking for nothing. Resume therefore persists mode `all`, updates the in-memory state and re-runs `applyFilePriorities` (metadata unresolved is fine — `startWhenReady` reads the state it just wrote). Both callers want exactly that: `finalizePending`'s arms (grace expired on an empty or erroring listing, `ErrNotSupported`, every candidate matched) and a human clicking resume on the Torrents page. `pending` is not a paused state, so nothing is lost by the conflation.
- **§4.6 widen, not duplicate-add.** A re-grab that lands on a hash a **live selective** record already holds (`selection_state` `pending` or `applied`, `selective_files` still on, a non-empty wanted-episode list — it need not add anything new) widens instead of adding: union the new episodes into `wanted_episodes`, recompute the keep-set over the client's own file list, `SetWantedFiles`. A completed record flips back to `downloading` (the `wantedBytes` denominator grew, so the completion predicate stops holding on its own — no un-completion logic needed); the builtin additionally clears `TorrentSession.seed_stopped` and resets `completed_at` so a stale seed-time limit doesn't immediately re-stop the re-completed torrent. `grab_failures` is **never** bumped on a widen — the grab succeeded, it just landed on a torrent already held. Every caller stamps `replace_mode` through `SetDownloadRecordReplaceMode`, which only ever **raises** (`none < upgrades < all`) and silently no-ops a lower: a widen hands the caller a record somebody else's grab created, so an automatic pass stamping `upgrades` onto a hash an operator's replace-grab already holds must not revoke that `all`. Gating on `selection_state` rather than "has `wanted_episodes`" is deliberate: `wanted_episodes` is written unconditionally by every `GrabEpisode` caller, so the state check is what keeps a non-selective duplicate (a plain whole-torrent grab, an `unsupported`/`skipped` client) as an ordinary duplicate-add hit instead. A hash hit on a completed, non-widen-eligible record falls through to a normal grab. The **whole** pre-check — `localInfoHash` + `FindWidenableDownloadRecordByHash`, not just the widen arm — sits behind `selective_files`: its duplicate rejection is behavior this feature introduced, and off has to be the pre-feature path where `AddTorrent` is what detects a duplicate hash.
- **qBittorrent cannot select at add time — this was tried and rejected.** qBittorrent 5.x answers 400 ("Cannot specify filePriorities when uploading torrent files") when `filePriorities` accompanies a `.torrent` upload (container-proven against a real 5.2.1 daemon). The shipped path is **add stopped → `filePrio` (0/1) → start**: `AddTorrent` sends `stopped`/`paused` alongside a selective `.torrent`, `applySelectionAndStart` then issues `filePrio` computed from the locally-decoded metainfo (not a round-tripped `ListFiles`, which can legitimately answer empty while metadata is still settling) and starts the torrent only once every priority call has succeeded. A magnet gets the real mechanism instead — add with `stopCondition=MetadataReceived`, select, start — which is why `selection_state: pending` must suppress the paused-torrent mirror onto episode badges (`CheckStatus`/`SyncSeasonDownloadStateForRecord`) or every qBittorrent magnet grab flashes "paused" for a second.
- **Transmission's `files-wanted`/`files-unwanted` treat an empty array as "everything"** — for all five RPC-spec file fields, not just these two. `SetWantedFiles` and `AddTorrent` both compute the skip-complement and **omit the key entirely** when nothing needs skipping; sending `files-unwanted: []` to mean "skip nothing" would instead mean "skip everything." Transmission has no stop-on-metadata mechanism for a magnet, so it's the one client that relies entirely on the `file_selection` pass — waste is bounded by the pass interval, not zero.
- **Deluge's `set_torrent_options({"file_priorities": ...})` silently succeeds against a pre-metadata torrent and downloads everything** — `torrent.py`'s `set_file_priorities` returns early with no error when the torrent has no metadata yet. `SetWantedFiles` guards this by calling `ListFiles` first and refusing (a plain retryable error, not a client call) when it comes back empty. Deluge's magnet path avoids the trap a different way: `core.prefetch_magnet_metadata` resolves the metainfo **without ever admitting the torrent into the session**, so the keep-set is known and passed in `options.file_priorities` on the same `add_torrent_magnet` call — Flow B collapses into Flow A for Deluge specifically. `manager.go`'s `MagnetMetadataFetcher` interface is how `grab` opportunistically takes this path before falling back to `pending`.
- **The keep-set is written by `CreateDownloadRecord`, not only by the post-add confirmation.** `applied` is decided at create for a Flow A grab, so `selected_files`/`selected_bytes` are stored in the same insert — a confirmation call that fails for any reason other than `ErrNotSupported` leaves the record `applied` and the SPA would otherwise render "0 B of 24 GB selected". The post-add call only *corrects* the pair.
- **Every client refuses an empty keep-set before doing any work** (`SetWantedFiles` with `len(wanted) == 0`): a selective record never wants zero files, and each client's "skip the complement" arithmetic would read it as "skip everything". Same wording across all four (`<client> set wanted files: refusing to skip every file`); the builtin's guard also runs before any state or priority is touched.
- `unsupported` (`ErrNotSupported` from `ListFiles`/`SetWantedFiles`) exists for a client that cannot select at all — none of the four shipped clients' real implementations return it today (only test doubles do), so it's reachable only via edge paths, not the normal four-client surface.
- `selection_state` (`pending | applied | unsupported | skipped`) is omitted from `QueueEntry` API responses when `skipped` — "not a selective download" is the default and the common case. `selected_files_count`/`selected_bytes` are present only when `applied`; the SPA queue row reads "X of Y selected" off them, an "unsupported" hint when the client couldn't select, and renders `pending` unchanged (no special affordance — it's a transient state the pass clears within one tick under normal conditions).
