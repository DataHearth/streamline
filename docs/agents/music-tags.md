# Music tags

> **Read before touching** `internal/library/audiotags/`, `internal/library/music_tags.go`, `internal/media/music/tags.go`, `internal/download/seeding.go`, the album importer's tagging, `library.music_tags`, or the `music-tag-sync` job.
>
> **Covers** — the TagLib wrapper and its write contract, the key set and where each value comes from, the tag state on `MediaFile`, the job and what queues a file, the seeding guard, the modes, and the album dates and genres hydration keeps for them.
>
> **Load-bearing** — a file is never modified in place; the job is the only writer of a file after its import; a file a listed torrent serves is never written; preserve wins over everything; art Streamline did not write — a release's own front cover, a cover file someone left — is never replaced or removed, and Streamline's own copies are never read back as the album's art.

## The library: TagLib through go-taglib
- `go.senan.xyz/taglib` is TagLib 2.x compiled to WebAssembly and run on wazero: CGO-free, so the static binaries, goreleaser's cross builds and the Nix package are unchanged. It replaced `dhowden/tag` (reading) and `bogem/id3v2` + `go-flac` (writing). **Nothing outside `internal/library/audiotags` imports it**; the package re-exports the property keys it writes as `audiotags.Key*` (`keys.go`).
- The keys are TagLib property names, which are MusicBrainz Picard's. TagLib maps them onto ID3v2.4 frames, Vorbis comments and MP4 atoms itself — `MUSICBRAINZ_TRACKID` becomes the ID3 `UFID`, `RELEASETYPE` the `TXXX:MusicBrainz Album Type`, and so on — which is the reason to use it: no per-format writer to keep. Formats: `.mp3 .flac .m4a .ogg .opus` (`AudioExtensions`); TagLib picks the format from the **extension**, so a file is never written under another one.
- It compiles the module once into `os.TempDir()/go-taglib-wasm-<uid>` (about 3 MB). The Helm chart's 64Mi `/tmp` emptyDir carries it; a read-only `/tmp` would fail every read.

## The write contract (`audiotags.Write(path, Tags, Policy)`)
- **Never in place.** It copies the file to a hidden sibling (`.streamline-tags-*<ext>`, same directory so the rename is atomic, the original's permission bits), writes the copy, reads it back and compares every key it wrote (`ErrVerify`), then renames it over the original. A failure leaves the original untouched; **a hard link to the original keeps the old bytes**, which is what lets a hardlinked library file be tagged without touching the torrent's copy.
- It replaces only the keys it is given; a key mapped to no value is **deleted**. Without TagLib's `Clear` option every other property survives, and pictures are not properties at all, so embedded art survives a tag write. The writer before it called `DeleteAllFrames` on MP3s and swapped the whole Vorbis block on FLACs, dropping ReplayGain, lyrics and the cover — and with the cover the resolver's "embedded picture" source.
- `Policy.Strip` deletes existing keys; `Policy.Preserve` keeps a key from being written **or** deleted and wins over both Strip and the keys passed. Patterns are upper-cased, an entry ending in `*` matches as a prefix.
- `TRACKNUMBER`/`TRACKTOTAL` and `DISCNUMBER`/`DISCTOTAL` go in separately; for ID3 and MP4, which have no separate total, `fold` writes `n/total` and deletes any free-form total an earlier tagger left.
- `audiotags.Hash(tags, policy, extra...)` is the SHA-256 of the kept keys in canonical order, the policy and `extra` (the cover's identity). Equal hashes mean a second write would change nothing Streamline owns.
- `WriteWithArt(path, tags, policy, Art{Manage, Front, Ours})` is the same write plus the front cover, in the same copy, check and rename. `Write` is it with `Art{}`, which leaves pictures alone. With `Manage`, `Front` goes in as the front cover when the file has none or the one it has hashes to `Ours` (`audiotags.ArtHash`, SHA-256), and a nil `Front` removes that one; a front cover with any other hash is the release's and is never touched, and every other picture is kept. It returns the hash of the front cover Streamline now owns, which the caller stores as the next `Ours`. **The front cover is the picture typed `Front Cover`, or for MP4 — which keeps no type and no description on a `covr` item — the first one.** That is why ownership is a hash on the database row and never the picture's description: `OwnArtDescription` ("Streamline") is still written where the format keeps one, as a courtesy to whoever reads the file.

## The key set (`library.AlbumTrackTags`)
- Pure, from the database: artist, album (with its tracks, for the totals) and track (with its credits, for the featured artists). **Every key it owns is present**, empty when unknown, so a stale value from an earlier tagger is deleted rather than surviving beside ours.
- Artists: `ARTIST` is the album artist plus `feat. A, B & C`; `ARTISTS` the list; `MUSICBRAINZ_ARTISTID` the artist and the featured artists that have an MBID; `ARTISTSORT` only when there is no guest (no sort name is right for a credit with guests).
- `DATE` is the edition (`Album.edition_date`), else the original; `ORIGINALDATE` is `Album.original_date`, else the **year** of `release_date` — a parsed date cannot tell `1991` from `1991-01-01`.
- `GENRE`: `Album.genres` (up to five, most voted first), else the artist's genre.
- `MEDIA` only when the album holds exactly one medium: the stored media are the union over every release of the group, so with several there is no telling which these files are. `RELEASETYPE` is Picard's spelling (`album; compilation`, `album; live`). `COMPILATION=1` **only under the Various Artists MBID** — players group a compilation-flagged album under Various Artists, which is wrong for one artist's best-of.
- MusicBrainz ids: artist, album artist, release (`MUSICBRAINZ_ALBUMID` = `Album.release_mbid` — Jellyfin and Navidrome group editions by it, not by the release group), release group, recording, release track (`Track.release_track_mbid`, the track's id on the canonical release, read in hydration).
- **Credits** (`creditTags`), Picard's keys and groupings: `COMPOSER`, `LYRICIST`, `WRITER`, `ARRANGER` from the track's writer rows (`MusicCredit.role`; a writer row stored before writers had roles has none and is a `WRITER`); `PRODUCER`, `ENGINEER` (recording and mastering), `MIXER`, `CONDUCTOR`, `REMIXER`, `ARRANGER` from the track's own `credit` rows — its recording's relations — plus the album's **release-level** credits, which are the album rows no track carries (the album folds every recording's credits in with its own, for display, so "the album's credits" would put track 3's remixer on every track); artwork has no tag. `PERFORMER` is the track's own performer rows, one `Name (instrument)` per instrument (`Name` alone when none), never the album's personnel. The writer folds `PERFORMER` for MP3 into one `PERFORMER:<INSTRUMENT>` key per instrument (TagLib's ID3 `TMCL`, where Picard and Navidrome look), keeps Picard's form in Vorbis comments and MP4 (which has no per-instrument key), and owns the family: a `PERFORMER:*` key the write does not carry is deleted, unless preserved.
- **Credit keys are written only when the album's credits are current**: `credits_fetched_at` set and `Album.credits_version` = `library.MusicCreditsVersion` (1: writer roles, the track rows). Otherwise every credit key is left out of the set — not present and empty — so the file keeps what it carries: a heavy call that never succeeded, or credits stored before the track rows existed, must not delete the performer list an earlier tagger wrote in favour of nothing. `SetAlbumHydration` stamps the version with every heavy success; an album holding files with an older one is listed by `ListAlbumsAwaitingDetails` (beside a NULL `genres`), which the sweep's `details` leg and the hydration worker's idle refill drain at background pace, and `HydrateAlbum` fetches it before an import (`detailsStale`). **The worker never refills an album it already fetched in the same run** (`tried`): a refetch that falls back to the light call succeeds without moving the version, and would otherwise be listed again at once, forever. The hydration that lands the credits re-queues the album under `managed` like any other.

## Album dates and genres (hydration)
- `Album.original_date` and `Album.edition_date` are strings as MusicBrainz writes them (`YYYY`, `YYYY-MM`, `YYYY-MM-DD`): the group's `first-release-date` and the canonical release's `date`. `release_date` stays the parsed one sorting and upcoming detection read.
- `Album.genres` comes from `inc=…+genres` on the release-group call hydration already makes. **NULL marks an album hydrated before genres existed**; hydration always writes a list, `[]` when there are none. `HydrateAlbum` fetches such an album best effort (a failure logs and returns nil: the caller has its tracks), the sweep's `details` leg and the worker's idle refill backfill albums **holding files** (`ListAlbumsAwaitingDetails`), and a release group MusicBrainz no longer knows keeps its stored facts and gets `[]` (`storedDetails`) instead of being asked for forever.

## Tag state on `MediaFile`
- `tags_state`: NULL (never asked to write — adopted before tagging, or with tagging off), `pending`, `deferred` (a torrent owns or shares it), `written`, `failed` (after `maxTagFailures`, 5; a format TagLib is not used for fails at once). `tags_hash` is what was last written — **empty forces the next write** even when nothing changed. `tags_mtime`/`tags_size` are the file's after the write (and `size` is updated with them, since the file grew). `tags_checked_at` orders the outside-edit check. `tags_art_hash` is the front cover the writer embedded (`db.TagWrite.ArtHash`); a force mark keeps it, since it is identity, not cache.
- `db.MarkAlbumTags(ids, mark)` / `MarkAllMusicTags(mark)`: `MarkStale` queues written, failed, pending and never-tagged files and keeps their hash, so the job settles a file whose hash still matches **without opening it**; `MarkForce` also empties the hash. A deferred file stays deferred either way (its tags are computed when it is finally written) but loses its hash on a force.

## The job (`music-tag-sync`, `music.Service.SyncTags`)
- **The only writer of a file after its import.** Everything else queues. It lists up to 500 waiting files (pending before deferred — note the **descending** order: `pending` sorts after `deferred`), all of them on a manual run, lists the torrents once, groups files by album so each album's tree is read once, and writes. A write that found the same hash records `unchanged`; anything written triggers one media-server refresh for the music root.
- **The importer tags through the same path**: it records each new file `pending` (`AdoptAlbumFile.TagsPending`) and then calls `TagAlbum(albumID)` synchronously, *before* it refreshes the media servers, so a server indexes the files once, tagged. A file the guard holds is left deferred for the job. With either art setting on, `TagAlbum` first runs `resolveCover` on the album: the import's own art (embedded in its files, or a cover file beside them) reaches the cache now, and a remote cover is fetched when none is cached, so the files are not written coverless only for the background resolve to land a minute later — which under `import` would never be written.
- What queues a file: an import (`pending`), and **under `managed` only** a hydration (tracks, credits, details), a `RefreshOne` (every album of the artist; the hash settles the unchanged ones), a `resolveCover` that changed the cached cover's bytes (compared before and after, so a resolve that re-stores the same art queues nothing), and a `library.music_tags` patch that changes mode, strip, preserve or the art settings (`TagSettingsChanged`). `POST /music/tags/retag` forces every file in either mode (`409 code: music_tags_off` under off).
- Span `music.tag_sync`, one `music.write_tags` per file (outcome, and `tags.deferred_reason`), counter `streamline.music.tag_writes{outcome=written|unchanged|deferred|failed}`.

## The seeding guard
- Only the builtin engine reports a torrent that stopped seeding (`Torrent.SeedingStopped`); qBittorrent, Transmission and Deluge always report false. The signal every client gives is **its listing**: `download.SeedingTorrents` lists every enabled client once and returns the hashes and the content roots (the client's save path through `download.path_mappings`, and the convention path `<library.download_path>/<name>`). A client that cannot be listed makes the set incomplete.
- A file is deferred when a listed torrent's content root contains it (the torrent serves that very path, and a rename over it changes what it serves), when the listing is incomplete and the file lies under the download path or has another hard link, and — under `seeding: defer` — when it has another hard link and a torrent of the album's records (its own grab or a pack that expected it) is still listed. Otherwise it is written: a hardlink whose torrent is gone is split by the write, which is free since the torrent's copy is now an orphan.
- **A paused torrent still listed keeps its files deferred.** Resuming it serves whatever bytes are then at its path.
- `albumImportMode`: `move` while seeding copies (it would pull the file out from under the torrent, tags or not); `hardlink` copies only under a writing mode with `seeding: copy`; with `defer`, or with tags off, a hardlink stays a hardlink — one copy on disk until the torrent goes.

## Managed albums and the import review
- `Album.tags_managed` (default true) is whether the writer **re-queues** an album's files on its own: `MarkAlbumTags` and `MarkAllMusicTags` (managed triggers, settings changes, Retag) reach managed albums only. A file queued explicitly — a new download's `pending` — is written either way.
- The music import review chooses per commit: `POST /library/imports/{id}/commit {write_tags}` (`bulkimport.CommitOptions`, nil = "unless the mode is off"). With it on, every adopted file is recorded `pending` and the album is tagged through `TagAlbum` as it is committed (before the commit's one media-server refresh); an album that held no file before the commit takes the choice as its `tags_managed` — including an `existing` stub of the artist's discography, which a commit adding the artist for another folder creates — and an album that already held files keeps its own. With it off the files keep `tags_state` NULL and the new album is unmanaged.
- The migration that added the column set it false on every album whose files were all adoptions (`source` orphan or wizard): nobody chose to tag those. An album holding a downloaded (`auto`) file stays managed.
- Review rows carry `seeding_files`, read live: the folder's audio files (disc subfolders included, `bulkimport.SeedingFiles`) that a listed torrent's content root contains — the ones the writer will defer.

## Artwork
- The cover is the posters cache's (`albums` kind, whatever `resolveCover` stored); the job reads it **once per album pass** (`albumTagging.artwork`). `embeddableCover` keeps a JPEG or PNG already within `art_max_px` on its long side byte for byte, and scales a larger one down to a JPEG (quality 90) with a box filter written over the stdlib — `golang.org/x/image` is only in the module graph through tools, and pulling it into the binary would move the vendored set and Nix's `vendorHash` for a resample nobody sees at 1000 px. A WebP or GIF cover is not embedded (not every player decodes one from a tag) and logs.
- The art's identity is the hash's `extra`: `art:<sha of the embedded bytes>`, `art:none` (no cover cached — pictures left alone), `art:unusable`, or `art:off` (`embed_art` false — Streamline's own front cover removed). A new cover therefore changes every file's hash and the next pass rewrites them; the same cover settles them without opening.
- **Sidecars** (`sidecar.go`), after the album's files, once at least one of them was written or settled (an album every file of which a torrent holds waits for them): the cached cover, full size, as `cover.jpg` or `cover.png` (by its real type) in the album's folder — the files' **common** directory, so a disc-split album gets one above its disc folders — and the artist photo (`artists` kind) as `folder.jpg` in the folder above, **only when that folder's name equals `library.SanitizePath(artist.Name)`**, as `{Artist}/` renders it (a `{Artist} - {Album}` template puts albums in the root, and nothing is ever written in `music_path` itself), once per artist per pass. `Album.art_sidecar_hash`/`Artist.art_sidecar_hash` record what was written: any `cover|folder|front` (album) or `folder|artist` (artist) image whose bytes hash otherwise is someone else's, and the writer then neither replaces it nor writes beside it. `sidecar_art` false removes only Streamline's. A target a listed torrent owns, or under the download path with the listing incomplete, is skipped. A written or removed sidecar counts as a change for the end-of-pass media-server refresh. `library.PruneEmptyDirs` counts `cover.jpg|png` and `folder.jpg|png` as external metadata, so deleting an album's files still removes its folder.
- An artist photo that changes reaches `folder.jpg` on the next pass over one of the artist's albums; nothing queues for it.
- **A cover file someone adds later is read only when `resolveCover` runs**: the import and adoption paths, `TagAlbum` when either art setting is on (so *Write tags now* is the user's way to have one read), and an album's first hydration. `RefreshOne` re-resolves only albums with **no** cached cover, so a `front.jpg` dropped beside an album that has one waits for the next of those; the wiki says so (Album covers).
- **The resolver never reads Streamline's copies back.** `localCover` skips an embedded picture whose hash is the file's `tags_art_hash` (the downscaled copy would otherwise replace the full-size cache on every resolve, and degrade again on the next), and `folderCover` passes over the album's own sidecar to the next candidate — a `front.jpg` someone adds beside Streamline's `cover.jpg` becomes the album's art.

## The album tag panel, overrides and outside edits
- **`audiotags.Compare(path, tags, policy)`** reads a file and reports every key against the write: `plan` is the one function both `write` and `Compare` take their key set from (the folded `want`, plus the strip and `PERFORMER:*` deletions), so the panel and the edit check judge a file exactly as a write would leave it — in the format's own keys, an MP3's performers as `PERFORMER:<INSTRUMENT>`. `same`/`differs` are keys the write sets, `kept` one it leaves (not given, or preserved); a key absent and set to nothing is omitted. `Edited` is "any `differs`".
- **Overrides** are `Album.tag_overrides` and `Track.tag_overrides` (JSON, key to values, NULL is none), layered by `desiredTags`: library tags, then the album's, then the track's; an empty list removes the key. They ride the hash, so saving one rewrites exactly the files it changes. They win over `strip` (an override of a stripped key is written) and lose to `preserve`, which `Policy.apply` drops before anything else. The handlers validate before storing (`tagOverrides`: `overrideKeyRe` — no wildcard, `:` allowed —, upper-cased, deduplicated, 64 keys, 32 values, 1024 characters). Saving one, or `PATCH tags_managed: true`, queues the album through **`QueueAlbumTags`, which is not scoped to managed albums**: it is a request about that album, unlike the writer's own re-queues (`MarkAlbumTags`, `MarkAllMusicTags`), which reach managed albums only. `POST …/tags/apply` is `QueueAlbumTags(MarkForce)` plus `TagAlbum` in a recovered goroutine; `409 music_tags_off` under off.
- **The outside-edit check** (`checkEdits`) runs at the start of every `music-tag-sync` pass **under `managed` only**, before the write pass, so a file it queues is rewritten in the same run. It lists up to 200 written files of managed albums (every one on a manual run), never-checked first then the longest unchecked (`tags_checked_at`), and stats each: an unchanged size and modification time only stamps `tags_checked_at`; a changed one is read with `Compare` — an owned key changed queues the file with its hash emptied (`SetMediaFileTagsEdited`; the hash still matches what the library wants and would otherwise settle it unopened), anything else (ReplayGain a player added, a preserved key) records the new size and mtime as seen. A missing file is the library scan's business, not the tags'. An unmanaged album is never checked; `import` never checks. At 200 a scheduled pass, a library of N written files takes `ceil(N/200)` passes for a full round, so an edit can stand that long; the batch is a constant (`tagCheckBatch`), not a setting, and the wiki states the delay.
- **Authorization**: `GetMusicAlbumTags`, `ApplyMusicAlbumTags` and `PatchMusicTrack` are `roleMember` in `rbac.go` (and `requireNotRequestOnly` in the handlers), the tier `PatchMusicAlbum` already had — a member could already monitor and grab the album, and overrides only change what its own files carry. `library.music_tags` and `POST /music/tags/retag` stay admin.

## Modes
- `off` writes nothing (the job returns at once, the importer queues nothing). `import` writes each file once. `managed` re-queues on the triggers above and undoes outside edits to managed keys; keys Streamline does not manage are never compared.
