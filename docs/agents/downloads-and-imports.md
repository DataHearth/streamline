# Downloads, imports & adoption

> **Read before touching** `internal/bittorrent/`, `internal/importer/`, `internal/download/adopt.go`, or `internal/mediaserver/`.
>
> **Covers** — which episodes a record is for; the builtin engine's memory bounds, peer-socket ownership and port rebinding; import verification and the `held` record lifecycle; adopting a manually-added torrent (proposals, identify, preview, replace); and the post-import media-server refresh.
>
> **Not here** — which files a grab asks for (`selective-file-download.md`), whether a release beats a file (`quality-scoring.md`).

## A record's episodes
- **A `DownloadRecord` has two episode edges, and they answer different questions.** `anchor_episode` (unique, the column is still `episode_download_records`) is the one episode the record is *filed under*: what the importer resolves the show from, what grab failures and a terminal import failure are counted against, what the queue and event log show. `episodes` (many-to-many through `download_record_episodes`) is every episode the download is *for*, anchor always included — `CreateDownloadRecord` and `IdentifyDownloadRecord` both add it. Every "this record's episodes" question reads `episodes`: the keep-set, the widen, `MarkRecordEpisodesImporting`, `SyncDownloadStateForRecord`, the orphan sweep, `FindSeedingDownloadRecord`, `LatestImportedRecordForEpisode`, and — because the Episode-side name stayed `download_records` — every `episode.HasDownloadRecordsWith` predicate, the missing search's and the upgrade pass's in-flight exclusions included.
- The set held a JSON column (`wanted_episodes`) beside a unique edge until 2026-10, and every consumer picked one half: the orphan sweep reasoned over the edge, saw one episode of a whole-series pack, and declared the other seasons stranded 20 seconds after the grab (Narcos INTEGRALE, 2026-09-20). The sweep now spares exactly what an in-flight record links — the old "its season has an active record" proxy is gone, so **every grab path must link every episode it marks `downloading`**, or the next sweep reverts it.
- **The set includes episodes that are not wanted.** A pack grabbed under an upgrade-permitting profile links the on-disk episodes it beats (`beatEpisodes`), and `grabUpgrade` links nothing else. They keep their `available` status, and nothing mistakes them for in-flight because **every status write over the set filters on the status it moves from** (`downloading`/`paused`, `wanted`, or the in-flight trio for the sweep). The one mover that takes `wanted` rows (`recordEpisodesWanted`, adoption and retry) reads the anchor alone, because an adoption's set can be wider than its torrent. A writer added over `episodes` without such a filter flips files the library holds — and `FailHeldDownloadRecord`/`RecordImportFailure` guard the anchor with `Not(HasMediaFiles())` for exactly that reason, since `grabUpgrade` anchors on an episode it is replacing.

## Builtin torrent engine
- **The peer pool is capped by `applyMemoryBounds` (`internal/bittorrent/bounds.go`), and the caps are constants on purpose.** anacrolix's defaults — 50 established conns per torrent, 100 total half-open, 500 known peers per torrent, 64 MiB of unverified piece data — are sized for a desktop. Each established conn is a 128 KB bufio read buffer + up to 32 KB write + 2 goroutines + 2 timers, so ten seeding torrents at stock is ~500 conns ≈ 80 MB of buffers and a thousand goroutines, against a 256 MB target. Config keys were considered and rejected: raising them past what the host has does not buy throughput, it buys the OOM killer, and a machine with room to spare should run an external client that owns its own limits. `bounds_test.go` asserts each value is *below* the upstream default, so a future anacrolix bump cannot silently turn a cap into a widening.
- **Uploaded bytes are persisted per torrent (`TorrentSession.uploaded`) and ratio is read off `uploadedBase + this process's counter`.** anacrolix's `BytesWrittenData` starts at zero every boot, so a ratio built on it alone forgave everything a torrent had already given back and a `seed_ratio` target receded on every restart — `completed_at` had always been persisted, so the seed-*time* limit worked and only ratio silently didn't. `enforceOnce` writes the total **before** its `Info()`/`wantedMissing`/paused/seedStopped gates, since incomplete and paused torrents upload too and this minute tick is the only pass that runs. `Engine.Close` flushes the counters, so only a hard kill loses up to a minute of upload; the alternative is a write on every stats read.
- **A builtin torrent that has reached its seed limit is removed *with its files*, and that decision is not the enforcer's.** `enforceOnce` stops the upload and sets `seedStopped`; the reaping is `download.RemoveSeedCompleteTorrents` (`internal/download/manager.go`), on the 30s download-monitor tick beside the completion and adoption passes. The engine holds no library state — it cannot tell an imported torrent from one whose import is still parked `held` — so the rule needs the record, and the manager is the only layer that has both. Three conditions, all required: the entry is the **builtin** one (`config.BuiltinDownloadClient`; seed limits are the engine's feature and an external client owns its own ratio handling and its own files), the client reports `Torrent.SeedingStopped` (the generic `download.Torrent` field the builtin `view()` fills from `seedStopped` and every other client leaves false), and `db.FindImportedDownloadRecordByHash` finds a **completed** record for the hash. Everything else is left alone: held and pending records have resolve and adoption flows still waiting on those exact bytes, and an untracked torrent was never ours. Deleting the data is safe in every `library.import_mode` — hardlink and copy leave the library its own directory entry for it, and move already emptied the torrent's directory at import time. There is deliberately no config key: a configured `seed_ratio`/`seed_time` already says "done with this torrent", and without the reap the default `hardlink` + `keep_torrent_seeding: true` pair keeps the download copy on disk forever (the case `transcoding.md`'s `defer_seeding` note used to describe as unfixable). A `RemoveTorrent` failure is a WARN and comes back on the next tick; the sweep never fails the tick. Counted on `streamline.download.seed_complete_removals`, attributed by client name only.
  - **`PurgeOldRecords` never ages out a completed record whose torrent the builtin engine still holds.** The sweep's permission to delete *is* that record, and `completedRecordRetention` (30 days after `imported_at`) used to drop it regardless — so a `seed_time` at or past ~30 days, or a `seed_ratio` a slow swarm takes that long to reach, lost the record first and the torrent then sat `Completed` with its files forever. The homelab's `seed_time: 720h` stranded eleven torrents exactly that way. The purge now lists the builtin engine and passes its hashes as a keep-list (`DeleteCompletedDownloadRecordsBefore`'s `keepHashes`; a hashless record still ages out, which is why the predicate carries an `IsNil` arm beside the `NotIn`). If the engine cannot be listed, the completed purge skips that run rather than purging blind; the failed-record purge runs either way. Torrents stranded before this change have no record to recover and need removing by hand.
- **The engine places a torrent by its info name, and `contentPaths` (`internal/bittorrent/paths.go`) decides whether it may.** The layout stays anacrolix's default, `<download_dir>/<name>[/<path>]`, because that is the location contract adoption and the importer derive `save_path` from. But the name is the torrent author's: an empty one put a single-file torrent at the download dir itself, `.streamline-session` landed on the engine's state, and another live torrent's name landed on its data — anacrolix renames whatever sits there to `.part` on open, and remove-with-files later deletes it. Storage has no hook that returns an error, so a refused torrent is given a file path of `..`, which anacrolix's own sub-path check turns into a failed `OpenTorrent`. `torrentDir` decides (it alone sees the infohash) and claims the name; `filePath` carries the verdict out keyed on the `*metainfo.Info` pointer; `Engine.forget` releases the claim. Data no live torrent owns is judged by size (`fitsOnDisk`): a torrent the engine does not hold may only open where each of its files is absent or already its declared length, with no `.part` leftover — that tells a re-add resuming its own data from a different release under the same name. `restore` calls `paths.trust` for every row it re-adds, since the partial data there is theirs. A `.torrent` add asks `paths.admits` before `AddTorrentSpec`, so the refusal reaches the grab as `download.ErrUnsafeTorrentName` → `grab_rejected`; a magnet's info arrives later and is refused at `OpenTorrent` — and anacrolix swallows that failure, leaving the torrent registered without info, fetching at 0% for good. `torrentDir` therefore reports every refusal through `contentPaths.onRefuse` → `Engine.refuseTorrent`, which logs a warning naming both infohashes and the name, drops the torrent and its session row (`rollbackAdd`) and remembers the reason in `Engine.refusals`. `GetTorrent` then answers `download.ErrTorrentRefused` (reason attached) instead of not-found, and the monitor's `CheckStatus` fails the record with that reason (`failRefusedRecord`: `FailDownloadRecord`, anchor `grab_failures` bump, movie back to wanted; episodes un-strand through `ReconcileStrandedMedia`). The map is in-memory: after a restart the record falls to the 2-minute orphan sweep instead.
- **Tracker, webseed and metainfo-source egress refuses internal addresses; peer dials do not.** `newClientConfig` always installs `TrackerDialContext`/`HTTPDialContext` (a `net.Dialer` whose `Control` hook sees the post-resolution address) and a `TrackerListenPacket` whose conn checks every `WriteTo` — source-bound to `bind_interface` when set, as before. Loopback, link-local (cloud metadata), unspecified and multicast are refused; RFC1918 is allowed, because homelab trackers and indexers live there. Those URLs come from the release, and `checkReleaseSource` only ever guarded the first-hop fetch. Magnet `x.pe` peers and DHT nodes are dropped in `specFromSource` instead of filtered, since peer dials are deliberately unrestricted. The engine also holds at most `maxTorrents` (a `bounds.go` constant, like the peer caps); `AddTorrent` refuses a new hash past it with `download.ErrClientFull`, which the grab handlers answer as `grab_rejected`.
- **`RemoveTorrent` deletes the session row before it drops the torrent.** The other way round, a failed row delete left a torrent no API could reach (every call looks it up live) whose row the next boot restored. `restore` deletes a row whose stored source no longer parses — it fails identically on every boot — but keeps one whose re-add fails, since that can be a download mount not yet ready.
- **A torrent reports `fetching` until its file priorities have been applied, and `prioritize` is the only thing that ends that.** Every file is born at anacrolix's `PiecePriorityNone`, so before the selection lands `wantedBytes` is 0, `wantedMissing` is 0, and `status`'s completed branch calls a torrent holding nothing `seeding` — which the download monitor reads as ready to import, while ratio and progress divide by that same zero. Priorities are applied off the caller's goroutine (`startWhenReady` waits on `GotInfo`), so the window is real on both the add and the restore path: a magnet is covered by the `Info() == nil` check, but a `.torrent` resolves its info synchronously and lands past it. `torrentState.prioritized` is raised by `Engine.prioritize`, the single wrapper every `applyFilePriorities` call goes through, and is deliberately **not persisted** — a restart re-applies priorities from the session row, so carrying the flag across one would claim a pass that has not run. This surfaced as a CI flake in `restores completed torrents across restarts without redownload`, whose post-restart `Eventually(…StatusSeeding)` was being satisfied by the false-seeding window itself and then read `Ratio == 0`.
- **`seeding`/`completed` need every wanted piece hash-verified, not just `wantedMissing == 0`** (`wantedVerified`, `internal/bittorrent/wanted.go`). anacrolix's `File.BytesCompleted` counts dirty chunks — written, not yet hashed — as completed, so the byte count reaches zero while the last pieces are still queued for hash or being marked. A piece reads `Complete` only after `MarkComplete` has returned, which is also what persists it to the bolt store and promotes a finished file off its `.part` name. Reporting seeding before that had two costs: the download monitor imported a file that might still be `payload.bin.part` or fail its hash, and a shutdown in the window dropped the in-flight hash results (`pieceHashed` returns early on a closed torrent, before marking anything), so the bolt store kept the initial check's `incomplete` for those pieces. The next boot trusts a known-incomplete piece and never re-hashes it — `queueInitialPieceCheck` only checks pieces of *unknown* completion — so the restored torrent sat `stalled` with every byte on disk and no peer to fetch it from. That was the second CI flake in `restores completed torrents across restarts without redownload`; the spec now polls its first phase at 1ms to land in that window deliberately and asserts every piece is `Complete` once seeding is reported.
- `e.rates` keeps working on the **session** counter — it is a delta, so folding a constant base in would change nothing but the first sample after boot.
- **The engine owns its own peer sockets — `DisableTCP` + `ListenPacket` — instead of letting anacrolix create them**, because `Client.LocalPort()`, and every tracker announce behind it, reads `cl.listeners[0]`: an anacrolix-created listener has no removal path (`AddListener` only appends), so adding a replacement on a new port would leave the announce still naming the old one. `rebindablePacketConn` and `rebindableListener` are always rebound in step, both landing on the same port — the design leans on that agreement, not on `cl.listeners` ordering staying stable. `rebindablePacketConn.ReadFrom` must swallow the `net.ErrClosed` a rebind produces on the retired socket and retry on the replacement, because `utp.Socket` reads this conn in a loop and treats any error as a dead socket, tearing the uTP stack down for good. A rebind is otherwise selective in what it disrupts: TCP peer connections are each their own kernel socket and survive it; uTP connections all ride the one packet conn and don't.
- **`client.Close()` does reach the packet conn.** anacrolix wraps the `net.PacketConn` handed to `ListenPacket` inside a `utp.Socket` and appends that socket's `Close` to `cl.onClose`, so `Engine.Close`'s own `packetConn.Close()` call is a genuine double-close — safe only because `rebindablePacketConn.Close`/`rebindableListener.Close` are idempotent. The TCP listener is different: `AddListener` only appends to `cl.listeners`, and its doc says the caller owns closing what it registers that way, so `Engine.Close`'s `listener.Close()` is the only thing that ever closes it. `rebind` binds the replacement socket before closing the retired one, so asking a socket to rebind to the port it already holds is a real `EADDRINUSE` — `movePeerSockets` (the locked half of `SetListenPort`) guards each socket individually rather than checking only whether the pair is already correct, which is what lets a *manually retried* call converge on a partial failure (listener moved, packet conn still stuck) instead of wedging on the already-correct socket. Nothing retries automatically, though: the only caller is gluetun's `VPN_PORT_FORWARDING_UP_COMMAND`, fired once per port rotation with no retry of its own, so a partial failure persists — announcing the old port while the TCP listener sits on the new one — until the next rotation or a restart. It's logged at `observability.LevelCritical` with both ports for that reason.
- **A completed port move forces a DHT re-announce; trackers get nothing.** `SetListenPort` ends in `announceToDHT`, which calls `Torrent.AnnounceToDht` for every torrent on every `Client.DhtServers()` entry. That reads the peer port live (`incomingPeerPort`) at announce time, so an announce issued after the rebind carries the new port with no extra plumbing — and unlike the tracker side it is a *real* forced announce. There is none for regular trackers in the pinned anacrolix: `ModifyTrackers` used to force one and no longer does (`torrentRegularTrackerAnnouncer.Stop` is a no-op, and both `modifyTrackers` and the client-level dispatcher key their state by infohash, so restarting a running announcer is a no-op too — measured at 0 announces in 5s against a local tracker). A private tracker can therefore advertise the dead port for up to its whole interval; DHT is the half that can be refreshed at once. The locked rebind lives in `movePeerSockets` **so the announce runs with `e.mu` released** — `AnnounceToDht` takes the anacrolix client lock, and this file otherwise never holds `e.mu` across a call into anacrolix. An empty `DhtServers()` (`entry.DisableDHT` → `cc.NoDHT`) is a configured no-op, and a nil client is the shape `SetListenPort`'s own specs build.
- **`DisableTCP` means the engine must supply its own TCP dialers, on both paths.** `New` calls `client.AddDialer` right after construction: source-bound to `bindIP` (`tcp4`/`tcp6` picked by `bindIP.To4()`) when `bind_interface` is set, a plain unbound `tcp4` + `tcp6` pair otherwise. `cl.dialers` is populated only from sockets anacrolix itself created, so skipping either branch leaves every outbound peer connection uTP-only, silently — no error anywhere names the missing dialer.
- **The unbound path additionally sets `cc.DisableIPv6 = true`** so exactly one UDP network exists — one `ListenPacket` call, one `utp.Socket`, one DHT server, rather than two racing to read the same packet conn. The cost: anacrolix rejects every inbound IPv6 peer and skips `udp6://` trackers, while the unbound `tcp6` dialer above still dials IPv6 peers outbound.

## Import verification & holds
- The importer verifies a probed source against the release claim before any transfer (`verifyFile` in `internal/importer/verify.go`, a pure function) and parks a failing record at `download_record.status = held` with a `hold_reasons` JSON column, returning **nil** — a hold is an outcome, not a failed attempt, so `import_attempts` doesn't move.
- Four checks, each producing one `{file, check, expected, actual}` reason: `corrupt` (probe error — nothing else is evaluable, so it is reported alone), `resolution`, `duration`, `codec`. Plus `always_ask` (`library.probe.always_ask`), which holds an otherwise-clean import and needs no probe, so it fires with ffmpeg off. A source that cannot even be resolved (`ErrNoMedia`) fails the import as a counted attempt instead of holding.
- **Resolution is bucketed by WIDTH**, not height: scope aspect ratios crop height (1920×800 is 1080p). ≥3200 → 2160p, ≥1800 → 1080p, ≥1200 → 720p, else 480p. Only a bucket *below* the claim holds; higher never does, and the claim parses from the payload basename with the release title as fallback — only when both parse nothing is the check skipped. `4K` and odd casing normalize to their bucket.
- `duration` compares against the metadata runtime (movie `runtime`, episode = its show's) scaled by `library.probe.min_duration_ratio` (default `0.5`); runtime `0` skips it. `codec` holds when the profile's `allowed_codecs` is non-empty and the probed video codec isn't in it (case-insensitive); empty = any codec.
- A probe that never ran (ffmpeg disabled/missing) verifies **nothing** — nil info with a nil error must not read as corrupt.
- Season packs are verified **before anything moves**, but only over the files the import actually plans to take: the importer builds a per-file plan first (episode match, existing-file lookup, then probes every matched file — the probe result feeds the `replace_mode` decision via `quality.ReplacesFile` under `upgrades`, since the incoming width/codec come from it) and only runs the verdict/hold-reason pass over the files that plan marked for import — a corrupt file belonging to an episode the import was never going to touch doesn't hold the record. A file matching no episode isn't probed at all. Under `replace_mode: all` the planned set is every matched file, so that mode verifies whole exactly as before. Any planned file's reasons still hold the entire record, reasons itemised per file — importing part of the *planned* set and holding the rest would split a season across two states.
- `POST /api/v1/downloads/{id}/resolve` (admin) takes `{action: import|regrab|delete}`. `import` sets `verification_bypassed` and re-enqueues, so the re-run imports as-is; `regrab` and `delete` both remove the torrent **with its files** and fail the record, differing only in whether the movie goes back to `wanted` for another search. Episodes revert to `wanted` on both. An unknown or missing action is a 400, and 409 when the record exists but isn't held; the queue verbs (pause/resume/cancel) answer 409 on a held record, pointing at resolve. Single-file replace imports verify **before** the existing file is replaced, like packs.
- **A replace places the new file before the old one goes.** `setAside` renames each existing file to `<path>.streamline-replaced` in its own directory (atomic, and it frees the destination when old and new render to the same path); the import runs; a failure `putBack`s the originals, a success deletes the old rows right before recording the new one and then `dropAside`s the files. Deleting first — which every replace path did — cost the library its only copy whenever the import then failed: an unresolvable source, a template the containment check refused, a transfer error. A source that resolves to no media still fails before anything is set aside. A crash between the rename and the record leaves a `.streamline-replaced` file beside a row whose path is missing; drift reports the missing path, and the file is the operator's to rename back.
- **`Worker.Enqueue` coalesces an in-flight ID into a pending requeue; it must never drop one.** An import publishes its outcome to the DB — `HoldDownloadRecord` writes `status = held` — and only unwinds to the `delete(w.inFlight, id)` in `consume` afterwards, so every caller that *reacts* to that outcome enqueues inside the gap: resolve, `RetryFailedImport`, `IdentifyPending`. Treating that as a duplicate stranded the record at `importing` with nothing queued, invisible until the `import_scan` tick (`schedules.import_scan`, 60s) swept it up. The consumer re-enqueues under the same `w.mu` that guards `inFlight`, so the mark is either seen by the running import or lands after its slot is free.
- Held records appear in the live queue (`ListActiveDownloadRecords` includes them) with `status: "held"` and `hold_reasons`, which is what the SPA's ResolveDialog renders.
- **Every import outcome is counted** on `streamline.importer.outcomes` (`succeeded` / `held` / `failed` / `terminal`), and the queue is gauged (`streamline.importer.queued`, `.in_flight`) with `streamline.importer.enqueue_dropped` for what the 100-deep channel throws away. The transitions were logged and nothing else, so a growing review queue, a spike in terminal failures after a library change, or an importer backed up behind a slow probe all degraded silently — each drop wrote one line with nothing aggregating them, and the first real signal was a user noticing imports had stopped.
- **`POST /api/v1/activity/history/{id}/retry` (`RetryFailedImport`, admin) is the only way out of `failed`.** 409 unless the record is `failed`; `db.RetryFailedDownloadRecord` flips it to `importing`, zeroes `import_attempts`, clears `failure_reason`, and walks the media back with it — `RecordImportFailure` set the movie `failed` and the linked episode `wanted` on the terminal write, and leaving either would have the re-run importing into rows claiming nothing is coming while the missing search grabs a duplicate. Only rows the record owns are touched (its episodes, not the season): `MarkRecordEpisodesImporting` skips `wanted` on purpose, but here `wanted` is exactly what this record's own failure wrote. The handler then calls `importer.Enqueue`. Nothing else could reach a failed record — `resolve` takes only `held`, `Worker.Scan` only `importing` — so every transient failure (a mount not up yet, a client that hadn't flushed) was permanently terminal after three attempts, including once the operator had fixed the cause. The re-run reads the record's stored `save_path` unchanged, so the SPA's confirm says as much.
- Deliberate limits: no release blocklist, so a re-grab may re-find the same release; holds are per-record even for packs; `hold_reasons` is cleared on resolve rather than archived.
- Runtime image ships static `ffmpeg`/`ffprobe` binaries (`mwader/static-ffmpeg`, digest-pinned) copied into `/usr/local/bin` — the distroless final stage has no package manager to `apt`/`apk` install into, and static-ffmpeg's binaries have no external deps so a bare `COPY --from=` is enough.

## Album imports
- `runImport` dispatches a record with an `album` edge to `importAlbumRecord` (`internal/importer/album.go`). One record is one album: every audio file under `save_path` (extension in `audiotags.AudioExtensions`, walked recursively) is matched to a track by `library.MatchTrack` — tagged `(disc, track)` with disc 0 read as 1, then a case-insensitive title — and the matches are all imported, unlike the episode flow's single anchor. Two files never fill one track (first in path order wins, the rest are logged unmatched), and a track that already holds a file is skipped unless the record's `replace_mode` is not `none`; there is no quality comparison for audio, so `upgrades` and `all` both replace. Verification and probing are skipped, they are video-specific.
- Placement is `ImportService.ImportAlbumTrack` over the shared `placeFile`, whose `placement.resolve` hook replaces the video-only `findMediaFile` (size floor, `MediaExts`). Naming keys are capitalised and case-sensitive (`BuildAlbumTrackVars`: `Artist`, `Album`, `Year`, `Title`, `Track`, `Disc`, `ext`); `Disc` renders `"<n>-"` on a multi-disc album and is absent otherwise. The template must carry `.{ext}`, nothing appends it.
- **Seeding forces `copy`.** Tags are rewritten in place on the library file, so `import_mode: hardlink` would edit the seeding source through the shared inode, and `move` with `keep_torrent_seeding` would pull the file out from under the torrent. Both import as `copy`; `cleanupTorrent` is then judged on the mode actually used, so a forced copy does not delete a torrent the operator asked to keep. `move` with seeding off is kept.
- **Every file's tier is established, verified and recorded** (`importer/album_quality.go`). With `ffmpeg.enabled` and a resolving ffprobe, `ProbeAudio` (a separate method: `Probe` refuses a file with no video stream) gives codec, bit depth, sample rate and rate, and `audioFactsFromProbe` classifies it; mp3 VBR is read off the average rate because ffprobe cannot see the LAME preset, **and only a rate that is not a constant-rate value (64 96 128 160 192 224 256 320) is taken for VBR** — a CBR 256 file reads exactly 256, and must not be mistaken for V0. Without a probe a `.flac` is `lossless` (never `hires`) and a lossy file takes the tier of the grabbed release's claim, else it is unknown. `MediaFile.quality` stores the tier (empty when unknown) and `format` the extension. **A measured tier the artist's profile does not tick parks the record `held`** (check `tier`, expected the ticked tiers joined by `/`, actual the measured one) before any file is set aside or placed, using the same `hold`/`resolve` machinery as the video checks; a bypassed record (`verification_bypassed`) skips it, and a failed probe is logged and skips it too. Only a measurement can hold: a claim read off a name cannot contradict itself.
- **Replace modes on an album record:** `none` leaves every track that holds a file alone (and fails `ErrDestExists` when nothing else matched), `all` (a grab with `replace_existing`) takes every track the release covers and deletes the old `MediaFile` after the new one is placed, `upgrades` (the RSS arm) takes a covered track only when `MusicProfile.Replaces` says the incoming tier beats the worst file the track holds. An artist's `available` request flips on the first album import, and an album request on that album's import (`MarkRequestsAvailableByMBID`, once with `artist` and once with `album`).
- Tags are written on the imported copy only (`audiotags.Write`: artist, album artist, album, title, track, disc, year, MusicBrainz artist/release-group/recording IDs). A format it cannot write (`ErrUnsupportedFormat`, e.g. `.opus`) or any write error is logged at warn and the file stays imported untagged; it never fails the import.
- `db.RecordAlbumImportSuccess` records one `MediaFile` per track (`source=auto`), completes the record and settles the album: `available` when every track holds a file, else `wanted`. It is not `adoptAlbumFiles`, which writes `source=orphan` and will not move a `downloading` album. A terminal failure (`RecordImportFailureParams.AlbumID`) moves a `downloading` album back to `wanted` unless it already holds a file. `ErrNoAlbumTracks` (nothing matched) is terminal, and so is `ErrDestExists`.

## Discography pack imports
- A pack is one `DownloadRecord` with the `artist` edge and the albums it expects on the `albums` many-to-many (`download.GrabArtistPack`: the albums are `db.ListPackAlbums` — monitored, released, hydrated, wanted or paused — marked `downloading` after the torrent is added, and a pack that would link none is refused with `ErrNoWantedFiles` before the client is contacted). A record has `album` xor `artist`. `ListActiveDownloadRecords` loads the artist and the albums' ids so the queue's `QueueEntry.PackAlbumIDs` can give each album its live progress.
- `runImport` sends an `artist`-only record to `importPackRecord` (`importer/pack.go`): audio files are grouped by `albumDir` (a `CD1`/`Disc 2` subfolder belongs to its parent), each group is matched to a **linked** album by `matchPackDir` — folded title against the folder name with bracket groups and the artist prefix removed, a year in the folder name breaking a tie, two albums of one title with no year matching nothing — and each match runs the ordinary `importAlbumFiles` with `pack=true`, which records the album's files and settles its status through `RecordAlbumImportSuccess{KeepRecord: true}` without completing the record. A hold in any album parks the whole record (`held` returns before the rest are touched). A folder whose tracks all hold files already is a re-run after a partial failure and counts as done; any other album error is joined and returned, so the record retries under the normal attempts rule and the albums already imported are skipped on the way back. At the end `CompletePackRecord` completes the record and moves the linked albums no folder named from `downloading` to `wanted` with no `grab_failures` strike; a pack none of whose folders match fails like an album with no matching track (`ErrNoAlbumTracks`, terminal). A terminal failure reverts every linked album that is still `downloading` and holds no file (`RecordImportFailureParams.PackAlbumIDs`).
- `replace_existing` on a pack sets `replace_mode = all` on the record, applied per album by the same `replacesTrack` rule: an album that already had files has the matched tracks replaced after the new files are placed; one that had none is filled normally.
- **Both album paths hydrate first.** `hydratedAlbum` asks `music.AlbumHydrator` for the tracks of an album whose `metadata_fetched_at` is NULL and reloads it, so a download for a just-added artist does not fail for want of tracks; without the hydrator wired (`Deps.Albums`) the stub simply matches nothing.

## Book imports
- `importBookRecord` (`internal/importer/book.go`) fills one slot per record: an ebook record imports the best-scoring candidate file (`ScoreEbookRelease` over the book's profile; `.cbz` and `.cbr` are ebook extensions), an audiobook record every audio file into one folder. The profile is the book's own, else its series', else the default of its kind (`bookProfile`); the destination is rendered by `library.BookDestination` from `NamingForBook` (the slot edition's title and language, `Book.author_name`, the first-published year, the series title and volume number) under `library.book_series_naming` for an ebook volume and `ebook_naming`/`audiobook_naming` otherwise. **A book that is not ready to be named parks the record `held`** (`bookHoldReasons`, check `metadata`): a series stub the hydration worker has not reached (`last_refreshed_at` unset) or a row with no `author_name`, so the file never lands at a wrong path and `resolve` retries it once the refresh has filled the book in. `MediaFile.quality` is the upper-case profile format (`EPUB`, `M4B`, …; empty for an extension off the ladder such as `.ogg`), `format` the lower-case extension.
- **An audiobook is checked against its profile before anything moves** (`audiobookHoldReasons`, `importer/book_quality.go`): the dominant audio format (most files, ladder order on a tie; an off-ladder extension is not counted, the profile cannot speak for it) must be one the profile ticks (hold check `format`), and with ffprobe available the first file's measured rate must reach `audiobook.min_bitrate` (hold check `bitrate`, `≥ N kbps` against `M kbps`). Either parks the record `held`; a failed probe is logged and skips the rate check; `verification_bypassed` skips both. The first file's probe is written onto its `MediaFile` row (`bitrate` in bits per second, `probed_at` stamped) so the RSS upgrade arm can compare a held folder against the floor later.
- A grab with `replace_existing` makes the record `replace_mode = all`: every file of **that slot** is set aside, the new ones are placed, and only then are the old rows deleted (`ReplacedFileIDs`); a replaced audiobook folder goes whole, a failed import puts it back, and the other slot is never touched. A book request flips to `available` on the first imported slot (`markRequestsAvailable("book", hardcoverID)`); a series request flips off its first imported volume (`"book_series"`, the volume's series' Hardcover id). A record that replaces because the slot's edition was changed (`*_replacing_language`, set by `PATCH /books/{id}`) is flagged `replace_mode = all` by `GrabBookRelease`, and `RecordBookImportSuccess` clears the flag in the transaction that lands the new file.


## Adopting a manually-added torrent
- `download.AdoptManualTorrents` (`internal/download/adopt.go`, run on the `download_monitor` tick) matches every untracked seeding/completed torrent the enabled clients report against the library, and either auto-imports, files a `pending` proposal, or — when the owner's media file has the torrent's exact size and no release fact both sides state disagrees (`sameFile`, resolution/source off `library.ParsedFromMediaFile`; group and codec are left out, since a bulk-imported row parses a template-named file and a probed row says `hevc` for `x265`) — writes the record born `completed` with `imported_at` stamped, so the completed-record sweep ages it like any import. That is the shape a wiped `download_records` table leaves: 84 of the homelab's 113 "already have a file" proposals were the library's own files still seeding, and the only decision anyone could take on them was Ignore. The `DownloadRecord` create hook stays quiet for a record born completed — nothing was grabbed. `ListMoviesForAdoption` eager-loads media files for this, which also retired the per-movie `MovieHasMediaFile` round trip. A show is matched on its title, its original title **and `tv_shows.aliases`** — TVDB's alias list plus every name translation, captured by `GetSeries` and written at add and refresh. A French-titled library with English-named releases ("That Time I Got Reincarnated as a Slime" for *Moi, quand je me réincarne en Slime*) filed 21 torrents as `unidentified` before the column existed; rows added before it fill in on their next metadata refresh. **`classifyMovieAdoption` takes the same set** (`movies.aliases` + `original_title`) and for a long time did not: it was the one matcher in the tree calling bare `library.TitleMatches` against the stored title alone, so with `metadata.language: fr` the homelab proposed `Hellboy.II.The.Golden.Army.2008` as `unidentified` while holding *Hellboy II : Les Légions d'or maudites* with `Hellboy: The Golden Army` sitting unused in its alias list. Three such proposals (Deathly Hallows Pt 1, Hellboy II, the Kaamelott integrale) were dismissed by hand before the cause was found. qBittorrent's `ListTorrents` filters to the `streamline` category and the builtin engine only holds what streamline added, so nothing an operator didn't put there can reach this pass.
- **Adoption stats the payload before it commits, and downgrades to a proposal when it is not there.** `adoptionPath` (`internal/download/adopt.go`) resolves a location in two steps: the convention path `<library.download_path>/<torrent name>` first — what every streamline-grabbed record uses, and what `library.allowed_download_roots` is configured around — then the client's own reported `Torrent.SavePath` translated through `download.path_mappings`, joined with the same (already traversal-checked) name. Neither existing means `autoImport`/`completed` are cleared and the record is filed `pending` with a reason naming the client's path, so the two paths can be compared on the first tick. Before this the fabricated path went straight into the row unverified: the importer stats it as its first act, ENOENT is *retryable* (`classify.go` lists eight terminal sentinels and it is not one), so a wrong path burned all three `library.import_max_attempts` and landed `failed` — which was unreachable until `POST /activity/history/{id}/retry` existed. The trigger on the homelab was a torrent added by hand in qBittorrent and then merely *tagged* `streamline`: **qBittorrent applies a category's save path only under Automatic Torrent Management**, so a Manual-mode torrent keeps whatever path it was added with while the category label says otherwise. Counted as `unsafe_name` on `streamline.download.adoptions` when the name itself is refused.
- **An auto-importing adoption marks its own episodes, and it needs its own method to do it.** `persistAdoption` calls `db.MarkWantedRecordEpisodesImporting` after the create; `MarkRecordEpisodesImporting` (the completion sweep's) cannot serve here because it moves only `downloading`/`paused` — correct for a grab streamline issued, useless for an adopted torrent whose episodes were never grabbed and therefore sit at `wanted`. The new one is record-scoped — the record's **anchor** only, via the shared `recordEpisodesWanted` predicate that `RetryFailedDownloadRecord` also uses: an adopted whole-series pack links every numbered episode of the show, unaired ones and seasons the torrent never held included, and moving all of those to `importing` parked them out of every missing search for as long as a hold lasted — and skips anything already holding a file, since an adopted *upgrade* has no state to walk back to if the import fails. Without it the record read `importing` while every episode behind it read `wanted`, and the series list — which counts a show as importing off `episode.status`, not off the record — showed nothing for the entire run of an adopted import. The record also links its **episodes** (`AdoptionEpisodes` → the `episodes` edge): the matched episode for a single-episode release, and the whole scope `AdoptionEpisode` picked its anchor from for a pack — the two share `adoptionScope`, so anchor and episodes can never disagree about what the release is for. Without them an adopted pack could only ever speak for its anchor, since every write scoped to "this record's episodes" reads that set. Episodes already holding a file stay linked; no writer acts on them, and a set that dropped them would describe the release as smaller than it is. Identifying a proposal by hand re-resolves the set with the anchor in the same write (`IdentifyDownloadRecord` replaces it) rather than carrying it over — the operator may name a different show than adoption guessed, and episode ids from that show would send every record-scoped write into another series' rows; identifying as a *movie* clears it. The set is the release's scope, not a file listing: what the torrent actually contains is still the on-demand `/activity/pending/{id}/preview`'s job. Failure is logged, not returned: the record exists and the import will run regardless.
- **The client's listing is untrusted input, and the pass is bounded on both ends.** An entry needs a 40- or 64-char hex infohash and a name and save path of at most `maxListingField` bytes (checked, never rewritten — records match the client's own spelling); at most `maxAdoptionsPerTick` untracked torrents become work per tick, the rest wait for the next. `DeleteStalePendingAdoptions` diffs the live list in memory and deletes by id in chunks — bound as one `NOT IN`, a client listing over 32,766 torrents made SQLite refuse the statement every tick, switching the prune off for good. `DeleteOrphanedPendingAdoptions` drops the proposals of any client no longer enabled, which the per-client pass never reaches.
- **The sweep is also the reachability probe.** It lists every enabled client on every tick, so both failure arms (`buildClient`, `ListTorrents`) call `d.setReachable(name, false)` and the success path `true`; the observable gauge `streamline.download.client_reachable` reads that map (`internal/download/reachability.go`, registered lazily via `gaugesOnce` on the first sweep — `New` has no ctx to log a registration failure against). Reachability was previously measured only by the Settings page's "Test connection" button, so a client down for hours was indistinguishable from one nobody had asked about; the two sweeps that hit it every tick logged at debug and moved on. Outcomes are counted on `streamline.download.adoptions` (`auto_import` / `proposal` / `unidentified` / `persist_failed`) rather than left as span attributes, which are invisible unless that tick happened to be sampled.
- **A release matching nothing in the library becomes an `unidentified` proposal, not a silent skip.** It is the one proposal carrying **no media edge** (both `DownloadRecord` edges are optional and `events.hooks` skips an owner-less row rather than failing the mutation, so the row inserts cleanly). That last part was a claim before it was true: `downloadRecordOwner` fell through to `m.IDs(ctx)`, which ent refuses outright on `OpCreate`, so the hook failed the insert and *every* unidentified adoption was dropped with one `adopt: persist failed` line at WARN. A create carries its edges in the mutation or not at all — there is no stored row to fall back to — so `OpCreate` now returns the empty owner before that query. Dropping it was what made adding a torrent for an untracked title a dead end: no record, no proposal, nothing above debug in the log, and no way to point at it afterwards. Every `ok == false` from either classifier lands here, so no path through the loop is silent any more.
- `POST /activity/pending/{id}/identify` `{kind, provider_id}` (admin) is how it gets a title: add the movie/series when the library lacks it, then link the record. **Both `movie.GetByTMDBID` and `db.FindTVShowByTVDBID` report "not in the library" as a nil row with a nil error** — testing the error instead of the row is a nil deref, and a mock returning `ent.NotFoundError` hides it through a green suite (it did, and the panic surfaced on the first real click). The anchor episode comes from `download.AdoptionEpisode`, shared with `classifyEpisodeAdoption` so a hand-identified pack lands on the same episode the automatic path would have picked. 409 when the proposal already carries media; 422 when the chosen show has no counterpart for the season the name claims.
- **A pack proposal is filed under one anchor episode, and `GET /activity/pending/{id}/preview` is what stops that from being the whole story.** `AdoptionEpisode` picks the first episode the release can *fill* (a whole-series pack names no season, so `parsed.Season` is 0 — the specials, not "unknown" — `AdoptionEpisode` orders the numbered seasons first with specials last, and `packAnchor` takes the first episode holding no file, falling back to the first episode in scope when every one already does — the pack is then an upgrade); the preview then reads the torrent's own file list off its download client and buckets every file the way the importer will: `imports` (holds no file), `upgrades` (holds a file this release beats), `keeps` (its file wins, or no profile ranks it), `unmatched` (a count — extras, or a name the parser cannot read). It applies the importer's ext/size/sample filters and reaches the per-file verdict through the *same* `qualityctx.Replaces` `takesPackFile` uses, so the counts cannot promise what the import then skips. What it cannot mirror is the probe — the files are still in the client — so `upgrades`/`keeps` are a name-and-size estimate and the SPA says so. 409 for a proposal with no anchor episode, 422 `connection_failed` when the client cannot be listed.
- **The preview decides the pack row's label and its actions**, which is also what repairs a record identified before the anchor fix without migrating anything. The label drops the anchor episode (`Kaamelott · S03`, or `· N seasons`), since naming one episode read as a proposal to import that episode. And the two actions stop being alternatives: a pack can both fill gaps and beat files, so **Import** shows when `imports` is non-empty and **Replace** when `upgrades` is, each hidden when it would do nothing. `has_file` is not consulted for a pack at all — it is the *anchor's*, so it once offered Replace on a pack that was purely filling gaps. Both buttons are disabled while the preview is in flight so neither changes under the cursor; a single-episode record keeps the old `has_file` either/or.
- **`ReplacePending` raises `replace_mode` to `upgrades` and deletes no media file** (it may still remove the *old torrent* when the body asks with `remove_old_torrent`, best-effort and only for a distinct hash). It used to pre-delete the matched media's file in the handler, which was wrong three ways: on a pack it deleted the *anchor's* file — a handle, not necessarily anything the torrent holds — while the record stayed `replace_mode: none`, so the importer then skipped every other episode that had a file; and on every shape the delete ran before anything was probed, so a held import had already destroyed the only copy on disk, the exact ordering `importSingleEpisode`/`importMovieRecord` go out of their way to avoid. `upgrades` rather than `all` because a pack proposal is not a release anyone inspected: `quality.ReplacesFile` decides per episode against that episode's own file, so a better file already there is kept. A movie or single episode has no second opinion to reach, so the importer's `!= none` check reads it as the plain overwrite it is. Replace can therefore legitimately do nothing — which is why the row hides it when `upgrades` is empty.
- Identify leaves the record `pending` — naming it is not accepting it — so the existing Import/Replace/Ignore still decide. `ImportPending`/`ReplacePending` answer **409** on a record with no media edge, since there is nothing to import into or replace. `PendingItem.media` is absent for these and is what the SPA keys the Identify action off; `parsed_title` rides along (present only then) because the raw release name is a useless search seed.
- **`DELETE /activity/pending/{id}` (`ForgetPending`, admin) deletes the record and touches no client**, which is the only way a proposal's torrent gets looked at again. `IgnorePending` sets `dismissed` and keeps the row, and `AllDownloadRecordHashes` — the sweep's "already tracked" set — selects every record carrying a hash **without filtering on status**, so a dismissed proposal locks that hash out for good. That was fine while dismissing meant "I decided", and a dead end the moment a proposal was wrong for a reason the library later fixed: on the homelab, a boot that re-ran adoption 21 seconds before the metadata refresh had recreated any episodes filed 113 correct torrents as `unidentified`, and nothing short of removing them from qBittorrent could undo it. `DeletePendingDownloadRecord` guards on `status = pending`, so an in-flight or completed record — where the row *is* the bookkeeping — is left alone and the handler answers **404**. The SPA offers it as *Forget* on unidentified rows only (`PendingRow`, alongside Identify) plus a bulk *Forget N unidentified* in the needs-attention header, with no confirmation: nothing is destroyed and the torrent keeps seeding.
- Adding a series through identify uses `tvshows.Add` exactly as a hand-add does, so the show arrives monitored and the missing-episode search will start filling its other seasons. That is the same consequence as adding it yourself, deliberately not special-cased.
- The RBAC table (`internal/server/restapi/rbac.go`) is **deny-by-default and keyed by operationId** — a new endpoint 403s with `operation missing from the RBAC table, denying` until it is listed there.

## Media server refresh
- The importer calls `mediaserver.Dispatcher.RefreshAll(ctx, kind, libraryPath)` after every successful import, `kind` being `movie`, `series`, `mediaserver.KindMusic` or `mediaserver.KindBook`. Jellyfin/Emby ignore both args and refresh everything; Plex rescans one section, so the kind picks between `library_section` and `library_section_tv`. Passing only the path meant an episode import poked the *movie* section, and `library_section_tv` was dead config outside the play-on deeplink.
- It is not only the importer: the transcoder after a swap, and the movie/tvshow services after a file delete, a delete-with-files and a rename, and bulk import once per commit that landed anything, all hold the same `mediaserver.Refresher`. Deletes, renames and bulk imports went without one for a long time, so a removed title sat in Plex as "unavailable" until some unrelated import happened to rescan its section. The request-path callers go through `mediaserver.RefreshInBackground` — a detached-ctx goroutine — because an unreachable server holds each call for `otelx.HTTPClient`'s 30s timeout, once per Plex section when none is configured, and the DELETE would hang on it. A rename refreshes from a `defer`, so a plan that fails partway still rescans for what it already moved.
- **Music and books refresh too.** Album and pack imports, the book importer, the music and book bulk-import commits (once per commit that adopted anything; books once per slot root), `music.Renamer`/book renames, `DeleteTrackFile`, and artist/book/series deletes with files all hold a `mediaserver.Refresher` (`music.NewService`, `music.NewRenamer`, `book.NewService` take the dispatcher). `KindMusic` on Plex goes through `Plex.RefreshLibraryOfType("artist")`: the path match first, then only the `artist` sections, and an error when the server has none — it never falls back to `library_section`, which is the movie key. There is no music section config key; discovery is by type. `KindBook` skips Plex entirely (it has no book library type; the refresh is counted `outcome=skipped`) and refreshes Jellyfin/Emby, which rescan everything regardless of path.
- **Plex's path match is a fallback, not the mechanism.** `findSection` compares `libraryPath` against the section locations Plex reports, which are Plex's *own* mount paths: in any containerised install ours is `/srv/streamline/movies` and Plex's is `/data/movies`, so the match finds nothing and the refresh used to fail with `no section found for path …` — imports landed and nobody's library ever saw them. On a miss it now WARNs and refreshes every section, matching what Jellyfin already does. Setting `library_section`/`library_section_tv` skips the lookup and scopes it back to one.
- Both keys are reachable from the settings form; discovery reports each section's Plex type, so each picker only offers sections of the type it names.
- **Discovery has two endpoints, and the saved-server one is not optional.** `POST /media-servers/discover` takes `{server_type, host, api_key}` and serves the *create* form, where the row does not exist yet. A saved server's token never reaches the browser (the read view carries only `api_key_set`), so the edit form has no key to send and that endpoint would be handed an empty one — which is why `POST /media-servers/{name}/discover` (`DiscoverSectionsByName`, mirroring `TestByName`) runs against the stored secret instead. Before it existed the edit form's Discover button was permanently disabled behind `!api_key`, so section keys were unobtainable for any configured Plex server.
- Discovery always fills the pickers — `discover.onSuccess` only assigns `sections`, and the section `Select`s are marked `readOnlyExempt` so they stay usable under `read_only` even though the rest of the form is locked. What `read_only` blocks is *saving*, not picking, so the pickers stay useful for figuring out which section is which. A separate "Show config snippet" button (visible once `lock() && sections.length > 0`) opens `PlexSectionsModal`, which shows the section keys the operator picked plus a paste-ready YAML block to commit by hand — same shape as `PlexCredentialsModal` for the PIN token. Discovery and PIN sign-in deliberately skip `readOnlyLock` — they only read remote state (see the note on the function itself).


## Concurrent grabs of one hash

`grabWith` holds a per-info-hash lock (`hashLocks`, keyed on `localInfoHash`) from the in-flight lookup through `CreateDownloadRecord`, and refuses a hash an in-flight record (`downloading`/`importing`/`held`) already holds as `ErrTorrentAlreadyExists` whether or not `selective_files` is on (on, the widen pre-check does it; off, `FindLiveDownloadRecordByHash`). The builtin engine's `AddTorrent` answers a held hash with success on purpose, so without this two simultaneous grabs (missing search plus RSS, two "search now" clicks) filed two records on one torrent and the second import died on "destination already exists". A completed record stays re-grabbable.
