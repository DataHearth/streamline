# Release-name parsing & bulk import matching

> **Read before touching** `internal/library/` parsing (`Parse`, `ParseSeasonSpan`, `extractTitle`, `SanitizePath`, `ApplyTemplate`), `internal/library/bulkimport/`, `internal/arr/`, the rename services, or the TMDB/TVDB classifiers in `internal/metadata/`.
>
> **Covers** — every parser rule that exists because a real release broke it, title normalization and matching, the classifiers' rank-before-truncate order, commit-time re-resolution, path sanitizing and naming templates, and provider-search quirks.
>
> **Not here** — cross-cutting API conventions (pagination bounds, error codes) which stayed in `../../CLAUDE.md` → API conventions.

- `library.Parse` takes the **last** year token and never one at offset 0, and `extractTitle` cuts at that token's recorded byte offset. Taking the first, and cutting by re-searching the year's *text*, left numeric titles (`1917`, `2001 A Space Odyssey`) with an empty title and no candidates, and ate year-like suffixes (`Blade Runner 2049`, `Fantasia 2000`).
- **`seasonEpRe` takes a third episode digit** (`S(\d{2})E(\d{2,3})`). A season past 99 episodes is rare but real — Kaamelott's first four Livres are 100 shorts each — and pinned at two digits `S01E100` parsed as episode **10**: silently, since nothing about the name looks malformed, so the file matched the wrong episode or none at all and the real one stayed `wanted` forever. The season stays at two digits; widening it makes `S1E1` ambiguous against a regex that carries no `\b` anchor.
- **A release group may carry its own dash**, and `groupRe` stops at the last one — `…x264-tsundere-raws` parsed as `raws`. `expandHyphenatedGroup` walks left from the captured group over further dash-joined words, stopping at a word holding a `.` or a space (a separate token: `WEB-DL.x264-GRP`, `Blu-Ray x264-GRP`) or at a known technical tag. Widening `groupRe`'s character class instead was tried on paper and is wrong: leftmost-match then starts inside `WEB-DL` and `cleanGroup` rejects the whole tail, losing the group entirely.
- **Resolution is normalised at parse time** (`normalizeResolution`: lowercased, `4K` → `2160p`). `quality.resolutionRank` is a plain switch, so a group's `1080P` ranked 0 and `Evaluate` rejected the release as "resolution outside profile band" — a whole release lost to the case of one letter, on a real TR4KER listing. `extractTitle` therefore re-finds the *original* token via `resolutionRe` for its cut marker, the same dance `Source` already does, since the stored value no longer appears in the name as written.
- **A multi-season chain is joined by more than a dash.** `seasonRangeRe`'s separator class covers `-.,+&` and space, because `Demon Slayer S01 & S02 & S03` is a real shape and, read as one season, it surfaced in a season-1 search offering every season. `ParseSeasonSpan` bounds a range with `seasonRangeBounds`, which reads *every* `Sxx` token rather than the pair the regex matched: pairwise matches cannot overlap, so a chain matches `S01 & S02`, resumes past it, and sizes the pack two seasons short.
- **The season token has three spellings and "complete" qualifies whichever noun the name gives it.** `longSeasonRe` reads `Season 4` / `Saison 04` alongside scene's `S04`: without it a French pack (`Breaking Bad Saison 04 Complète Multi …`) named no season at all, which reads as "single episode of nothing" and walked through every scope filter. And `IsWholeSeriesPack` no longer fires on a bare `complete`/`complète`/`intégrale` tag when the name *also* names one season — `Breaking Bad S05 Complete Multi 1080p` is a season-5 pack, and reading it as whole-series dropped it from a search for exactly the season it holds. A season *range* still wins over both, since `COMPLETE S01-S05` spans five. `ParseSeasonSpan` ranks the same way (range → single season → bare complete) and its complete arm moved below the season check for it.
- **A season pack's title is cut at the bare season token**, not at the resolution. `extractTitle`'s marker list only ever held the `SxxExx` match, which is empty for a pack, so everything between the season and the resolution was glued onto the title — `Good.Omens.S03.MULTi.VF2.1080p…` parsed as `Good Omens S03 MULTi VF2`, which `TitleMatches` can never equal the library's `Good Omens`. Manual-torrent adoption dropped every such pack silently (at the time `AdoptManualTorrents` `continue`d on no match; today it would land as an `unidentified` proposal). `rss.releaseShowKey` had been trimming a trailing ` sNN` off its key to compensate; that only covered packs with nothing between the season and the resolution, and the trim is gone now that the parser is right (the function survives to trim an anime absolute number, which `extractTitle` still leaves in the title).
- **Bare `WEB` normalizes to `WEB-DL`**, not to a third source value. Groups spell the same untranscoded stream rip both ways and the *arr parsers fold it the same; kept apart, a `source` custom-format condition written against one scored nothing from the other, in both directions. `WEBRip` stays its own value — that one is a re-encode. The editor's source picker no longer offers `WEB`, and an existing `custom_formats` condition spelling it that way now matches nothing (six values in a dropdown, no migration).
- `library.ParseEmbeddedIDs` lifts `{tmdb-N}`/`{tvdb-N}` out of a path. Both classifiers consult it **first** and treat it as authoritative — the path was rendered from that id, so a title parsed back out of it can only lose information.
- Both classifiers **rank before truncating** (`rank.go`: exact title/alias > year agreement > prefix > provider order). TVDB returns the right series for "Dororo" at index 15 and `showCandidateLimit` is 5; slicing the provider's order first threw away the entry the scoring was meant to find.
- **Identification comes before the existing-library lookup**, in both `Classify` and `ClassifyShow`. Scanning candidates for a tracked id up front resolved ambiguities by whichever tracked row ranked higher: two rows normalising to "Spiral" (TVDB writes the 2017 one's year *inside* its title) made a 2005 folder come back `existing` against the 2017 row, and 76 files were adopted into it as a **success**.
- `normalizeTitle` strips a trailing `(YYYY)` — TVDB's in-title disambiguator — so a disambiguated entry can equal the folder it belongs to. `TitleMatchesAny` also matches TVDB aliases + translations, which is the only way a romaji folder (`Kimetsu no Yaiba`) reaches an entry stored under its English title.
- Confirmation needs **exactly one** match: a unique year among title-matches, else a unique title match. Requiring a parsed year left every year-less series folder ambiguous (104 of 104 across two real scans; the fix confirms 74).
- `ApplyTemplate` runs substituted values through `SanitizePath`. The rendered string is a path whose `/` are structural and callers split on them, so a title carrying its own (`In/Spectre`, `Face/Off`) became two directories — which sanitising the *split segments* afterwards can no longer see.
- `SanitizePath` collapses whitespace runs and trims after replacing: `":" -> " -"` and the outright deletions each double a space they already had beside them (`2001 : L'Odyssée` -> `2001  - L'Odyssée`, `A | B` -> `A  B`). Both rename services `PruneEmptyDirs` the source directory after a move, so a re-rename pass over an existing library doesn't leave one empty folder per affected title.
- **Both rename services read the release facts off the `MediaFile` row (`library.ParsedFromMediaFile`), never off the current basename.** The renamer *writes* that basename from the naming template, and the default keeps only `{quality}` — so the first rename dropped the source, the codec and the group, every pass after it re-parsed a name that no longer carried them, and a file whose quality was never in the name re-rendered `[]` forever while `release_group`, `parsed_resolution` and a full probe sat on the row untouched. Same shape and same fix as `qualityctx.ContextFromRow` on the scoring side. Precedence is probe → stored parse → basename, the basename last but not dropped because it is the only evidence for a row the importer never instrumented (orphan scan, adoption, a bulk import the `media-probe` backfill has not reached). The probe wins outright for **resolution** and only backfills the **codec**: 2160p is 2160p however it was measured, while ffprobe's `hevc` and a release's `x265` are different vocabularies and `{codec}` in a template means the second — so a measurement fills that field only when nothing claimed it, rather than rewriting every name that has one.
- **An empty token wrapped in a bracket pair takes the pair, and the whitespace before it, with it** (`templateTokenRe` captures `(\s*)([\[(])?…([\])])?`; `bracketPair` requires the two halves to match). Punctuation in a template delimits a value and with no value there is nothing to delimit — without this, fixing the paragraph above still left `13 Hours (2016) [].mkv` for every file that genuinely has no quality anywhere, and the name never converged because the next pass re-planned it. A **bare** token is deliberately left alone: `{title}-{group}` has no pair to remove and inventing a rule for the separator would rewrite names nobody complained about. One unmatched half is literal text the template author wrote for some other reason and survives untouched.
- `commitAttach` honours `scan.Mode`: a rename scan relocates `existing` entries too. Attaching them where they lay split the library across two roots and took an inode sweep to find.
- Commit **re-resolves against current state** instead of trusting scan-time classification: `addOrFindMovie` / `resolveShow` return the existing row when the tmdb/tvdb id is already in the library. Otherwise a scan that sat in review while another added the title failed with a UNIQUE violation, and pointing a row at an existing show — the normal way to fix a bad match — was impossible.
- `commitShow` matches the **whole folder before anything moves** (`planEpisodes`), and fails the entry when at most half the files match an episode. Adopting anyway is what wrote 7 of 76 files into the wrong series. A show already in the library reports `outcome: attached`, not `created`. **A file whose basename matches no episode is retried on its parent folder's name.** `SanitizePath` once let a slash through, so an episode titled `White Hat/Black Hat` was written as a folder named for the episode with the title's tail as the only file inside — 33 such files across the homelab's library were invisible to a re-import after the FK-cascade wipe, and the missing search re-grabbed every one of them. Folder-per-episode releases have the same shape.
- Episodes have their **own size floor**, `library.MinEpisodeSize` (5 MiB) against `MinMediaSize`'s 50 MiB. The feature floor is a movie-shaped assumption: Kaamelott's first four seasons are 3-minute shorts, so it hid 228 of a 248-file folder and the scan reported `file_count: 20` — which then failed `planEpisodes` because the survivors weren't episodes. `findMediaFile` takes the floor as a param, `placement.minSize` carries it per media kind, and `ListVideoFilesRecursive` (four series-only callers: the bulk-import scanner and committer, the hygiene series scanner, the importer's pack path) uses the episode one. `file_count` and the `only N of M` denominator are the same list, so anything that filters one moves the other.
- The zero-match guard also fires on a **re-numbered release** — `S02E23` for a season with 22 episodes — and is right to. `have=212/214` is not evidence the two files are the missing pair; check the season rows.
- `TVDB.SearchSeries` retries an **empty** result with each half of the query (`queryHalves`, ≥4 words, leading then trailing). TVDB's scorer returns nothing for a show's own full title while returning it for substrings — `Zom 100 Bucket List of the Dead` finds nothing, `Zom 100 Bucket List` and `Bucket List of the Dead` both find it, and no rule separates the substrings that work. Native-script titles rank best (15/15 in a real sample, `日常` first of 44) but aren't known before matching. A query that returns *junk* rather than nothing (`Baki` → `Bali`) is not helped: the show is absent from the result set, so ranking can't recover it.
- **Season names need one request each** (`TVDB.translateSeasons`). The extended series record carries season names only in the series' original language, and its `?meta=translations` covers the series, not its seasons — so an anime's arc names stayed Japanese (`柱稽古編`) on a French install while everything around them was translated. `GET /seasons/{id}/translations/{lang}` is the only form TVDB offers, hence the per-season cost and hence capturing `seasons[].id` from the extended payload. A miss is ordinary and comes in two shapes — 404 for a language TVDB holds no record for, and a record holding only an overview (`"name": null`) — and both keep the original name, so the error is dropped rather than surfaced: one untranslated season must not fail a refresh.
- Series searches query **both** `show.Title` and `show.OriginalTitle`, mirroring movies — all four call sites (`BrowseEpisodeReleases`/`BrowseSeasonReleases`/`BrowseSeriesReleases`, `rss.searchShow`). `show.Title` is the *local* title, so on a non-English install it is the name a scene release is least likely to carry; `dedupTitles` collapses the pair when a show has no language override, so a translated show costs one extra query per indexer and an untranslated one costs nothing.
- Series `type` is inferred by `metadata.inferAnime`: the literal `anime` genre, **or** an animation genre plus a Japanese origin language/country. It drives absolute-number matching, so a miss silently mis-matches every file. `PATCH /series/{id}` takes a `type` override and `UpdateTVShowMetadata` deliberately **does not refresh** `type`, so the override survives.
- **A multi-disc music album is one candidate.** `walkAlbumFolders` keys audio files by their folder, except a file in a disc folder (`library.DiscFolderNumber`: `CD1`, `CD 2`, `Disc 2`, `Disk1`) is keyed by its parent — unless that parent is the scan root, where a lone `CD1` stays its own candidate. The row's `folder_path` is the parent, so the pending-folder skip and the commit both see the album, not a disc. `planAlbumFiles` reads the parent's files plus those of its direct disc subfolders; a file whose tags carry no disc takes its folder's number before `MatchTrack`, so tracks keep tagged `(disc, track)` matching.
- **Music and book scans adopt in place only.** `StartScan` answers `ErrRenameUnsupported` (422) for `mode=rename` on either kind, before the Hardcover key check so the answer does not depend on configuration; the committers never move or rewrite a file, and a book's rename is `POST /books/{id}/rename` after the fact. The review rows carry what the scan already read: the music scanner takes the majority year tag, the stat'd size and a format label (`library.MusicFormatLabel`, from one `ProbeAudio` of the folder's first file when `ffmpeg.enabled`, else the extension), and `artist_id` is **derived on read** from `ArtistIDsByMBID` so a library change between scan and commit cannot leave it stale. A committed row that was `existing` ends `attached`, not `created` (a reviewer's pick of another release group is still `created`). The album picker is `GET /music/search/releases`; a candidate carries the release-group `type`, never a track count (a MusicBrainz search hit has none).
- `POST /library/imports/{id}/decisions` applies one decision across a scan, narrowed by `classification` and/or `ids`, dispatching on the scan's kind. Reviewing a 465-file scan through the per-row PATCH cost 465 requests.
- `pathmigrate.WarnOnDrift` logs CRITICAL at boot for a root whose stored paths all sit elsewhere. Nothing else notices a remount. For movies/series the message warns of pruning (`drift-check` deletes those records after `drift_grace_ticks`); the downloads root warns about imports instead — nothing prunes download rows on drift — and counts only **live** rows (downloading/importing/held/pending), because terminal rows (dismissed adoption tombstones included) keep their creation-time save_path forever and would hold the warning on for a legitimately moved root.
- Movie matching compares the parsed title against **both** `Title` and `OriginalTitle` (`TitleMatchesAny`), mirroring the series alias path. TMDB answers in `metadata.language`, so a French install is offered `2001 : L'Odyssée de l'espace` and nothing else — the right film under a title an English folder can never equal.

## Radarr / Sonarr migration (`source` axis)

- **`ImportScan.source` is `filesystem | radarr | sonarr`.** An *arr scan fetches identified titles (`scanner_arr.go`) instead of walking and classifying files: no metadata provider is searched, the tmdb/tvdb id is taken as given, `source_path` is empty, and `kind` is derived from the app (radarr → movie, sonarr → series), never trusted from the request. The scan stores its `mappings` (root folders → local paths, source profile ids → streamline profile names) so a commit weeks later still has them. **The API key is never persisted** — it reaches the fetch goroutine by value from `StartScanParams.APIKey` and lives nowhere else, so a migration scan cannot be re-fetched without the caller sending it again. The instance URL is stored as scheme, host and path only (`storedSourceURL`) — a basic-auth proxy's userinfo or a pasted `?apikey=` would otherwise sit in the scan row, shown to every admin — and the fetch gets the URL as given, by value, beside the key.
- **`internal/arr` is a leaf**: the v3 client plus pure translation into `config` entries. It must not import `ent/schema`, which is why `arr.RootMapping` and `schema.RootMapping` are separate types (`rootMappings` converts). `TestConnection` checks `appName` because a Radarr migration pointed at a Sonarr reaches every shared route and returns plausible results. Every route but two decodes through `otelx.DecodeJSON` under `maxSmallResponse`; `GET /movie` and `GET /series` — one unpaged answer for the whole library, several KB a title — go through their own `otelx.NewHTTPClient` (minutes, not 30 s; 1 GiB, not 64 MiB) and are decoded one element at a time under `maxLibraryItems`. Sonarr honours `includeEpisodeFile` only from 4.0.10: on 3.x and earlier 4.0 builds `Episodes` fills the files the episodes name by `episodeFileId` from `GET /episodefile?seriesId=`, or every show would migrate with no files and its whole library wanted. Source paths are compared in the source's own style (`SourcePath`, `UnderSourceRoot`, `IsAbsSourcePath`): a Windows *arr reports `D:\Movies\…` or `\\nas\share\…`, which this host's `filepath` rules never match.
- **Containment is checked per mapped root at start** (`validateArrScanParams`, `ErrRootOutsideLibrary`) with the filesystem scan's rule: in_place targets inside the library root, rename targets outside it. An in-place migration outside the root records a library the orphan scan and drift check never walk. **Per file**, `fileUsable` (exists here, and inside the root for in_place) decides: a row whose file fails it is classified `ambiguous` rather than auto-committed, and accepting it commits the title **without** that file — never a media file at a path this process cannot open.
- **A movie row with an empty `source_path` is a title the source tracks with no file** (`commitTitleOnly`): it adds the movie and links nothing. Every migrated movie arm then runs `applyMovieState` — monitored is not an `Add` parameter, and an existing movie keeps its own profile through `Add`. `migratedProfile` checks the mapped profile **by exact name** before use: `ResolveQualityProfile` falls back to the default for an unknown name, so a profile deleted between review and commit would otherwise be stored verbatim and silently read as the default forever; it falls back explicitly and says so in `outcome_message`. `applyMovieState` runs whenever the title exists, a failed file step included: `commitRename`/`commitAdoptInPlace` add the movie before they touch its file, and a title left at `Add`'s defaults is monitored even where the source had it unmonitored. `commitAttach` (and the series adoption loop) compare the tracked file and the scanned one with `sameFile` (`os.SameFile`), not as strings: a folder scan records symlink-resolved paths and a migration the mapped spelling, and the replace step would otherwise delete the only copy.
- **A migrated show resolves files by the source's episode numbers** (`planFromSource`), never by filename, and the half-match guard does not run for it: that guard exists because a parsed folder name is weak evidence for which show a folder belongs to, and here the source states the tvdb id and the episode of every file. Entries naming an episode this library lacks (the source's metadata ahead of TVDB's) or failing `fileUsable` are skipped and counted in `outcome_message`; a show with files of which none could be adopted fails — with the source's monitoring still applied, since `resolveShow` may already have added it. A multi-episode file (one `EpisodeFile` embedded under every episode it covers) is bound to the first of them only and the rest are named in the note, the way the importer binds one file to one episode: twin rows on one path break deletes, upgrades, renames and transcodes, and a rename would transfer it once per episode. A row the reviewer re-pointed at another show (`rematched`: a `DecisionTvdbID` differing from the source's, on a row not resolved through `ExistingTvshowID`) commits as a folder-scan row — files matched by name under the guard, none of the source's flags applied — because the source's numbers describe a different series; a re-pointed title-only row has nothing to match and is added bare.
- **The series type is applied before any episode resolves** (`applySeriesType`), since it decides absolute-number matching. Monitoring is applied after: the show flag through `tvshow.Service.Update` (which cascades and records the **one** series-scope monitoring event), then only the seasons and episodes that differ, straight through `CascadeSeasonMonitored` / `SetEpisodeMonitored` — the service would write an activity row per call. `ShowMonitoring.Episodes` stores only episodes whose flag differs from their season's.
- **`config.AddResources` writes profiles, indexers and clients in one `config.Update`**, so a migration's config copy lands whole or not at all. `StartImport` validates the body's enums and the instance URL (`arr.ParseBaseURL`) before anything else, then hands the profile write to `StartScan` as `StartScanParams.BeforeCreate`, which runs only once every check `StartScan` makes has passed (mappings, the library root, a running scan) and before the scan row is written — the profiles land before the row, and a refused start leaves none behind. One that already exists **identically** is skipped, so retrying a start whose scan insert failed after its profiles landed is not a collision with itself. The handler's own `CountActiveImportScans` answers 409 before the collision check; the race with `StartScan`'s re-check is harmless because the write is idempotent. Every differing same-name profile (and, in apply-config, every taken indexer and client name) is collected and named in **one** 422; `AddResources`' own duplicate check stays as the backstop and stops at the first.
- **Format names resolve case-insensitively and store streamline's spelling** (`resolveFormat`, the closure `arr.TranslateProfile` takes): exact builtin/custom match first, then `strings.EqualFold` over `quality.Builtins()` and `custom_formats`, returning the stored name. The *arr apps spell formats their own way (`REMUX`, `Repack`), and config invariants compare format names exactly, so storing the source's spelling would fail validation on write. Two source items folding to one name keep the first. A non-zero `minUpgradeFormatScore` has no equivalent and lands in `notes`. The cutoff becomes `preferred_resolution`, a hard ceiling here, while an *arr cutoff only stops upgrades; when the source allows a higher band than that, a note names the releases that will be refused and the value to raise it to (the stock `Any` and `HD - 720p/1080p` profiles do).
- **Every diagnostic 422 of the migration routes carries `code: migration_rejected`** (`errMigrationRejected`): the StartImport arr arm (missing url/key, a sample that does not resolve, a profile collision, an `AddResources` refusal `migrationWriteRejected` accepts, `ErrRootOutsideLibrary`/`ErrMissingSourceURL`/`ErrInvalidPath` for an arr source) and apply-config (unknown or unsupported selection, missing secret, collision). Connection problems keep `connection_failed`; a filesystem scan's 422s stay uncoded. Any other `AddResources` failure is not the caller's to fix: the config lock answers 403, a write fault 500.
- **The preview's profile rows** carry the source `id`/`name`, `in_use` (titles per `qualityProfileId`, counted on the same walk as the counts) and `existing` (`""` when no exact-name profile exists). A download client that cannot come across reads `client_type: unsupported` with its `reason`, so the field is always present.
- **Indexer and client translation** (`TranslateIndexers` / `TranslateDownloadClients`): every Prowlarr-synced indexer (`baseUrl` path `…/<id>/`) collapses into one `prowlarr` entry per instance, its URL base kept in `Path`; a Torznab endpoint is `baseUrl + apiPath`. An all-asterisk secret is the mask newer *arr releases return for a secret that is **set**, and counts as missing (`needs_secret`); an unset one comes back empty, so a download client without authentication is carried with an empty password and needs no secret (an indexer's empty key still does — `api_key` is required). A client whose `urlBase` is not its type's default (Transmission's `/transmission/`, the root otherwise) is refused with a reason: streamline's clients use fixed API paths and an entry has nowhere to keep one, so it would come across pointing at the wrong endpoint at the source's top priority. Names are made unique (`uniqueIndexerNames`, ` (2)` …): every collapsed instance is `Prowlarr` and the ` (Prowlarr)` trim can collide a synced indexer with a manual one, while the name keys the preview row, the selection and the config entry — a repeat threw in the wizard's keyed list. Priority is inverted — an *arr ranks 1 best, streamline picks the highest number.
- The commit metric `streamline.bulkimport.commits` carries `source` beside `kind` and `outcome`; `scan.classified` carries it on a migration.
- **The wizard sends root mappings only for roots holding a file** (`ArrImportWizard` filters on `sample_path`), because `validateArrScanParams` refuses any mapping whose target does not exist here and a title with no file maps nothing — an empty or wanted-only root left at its identity default blocked a whole migration on a folder it never reads. The Sonarr preview samples a root against its shows with files until one answers with a file (up to three), so a root holding files does get its sample. Its refusals name the mapping (`root folder X maps to Y`) rather than the bare sentinel, which reads as a filesystem scan's `source_path`.
