# Quality scoring

> **Read before touching** `internal/quality/`, `internal/quality/qualityctx/`, `internal/config/resources.go` (profile assembly), the RSS feed/missing-search scanners (`internal/rss/`), or any handler under `handler_quality_profiles.go` / `handler_custom_formats.go`.
>
> **Covers** — the scoring engine and its condition semantics, release-vs-file evidence asymmetry, band/score gating, indexer result filtering, custom formats and profile presets, `ReplacesFile` and the upgrade paths, `file_score` on the API.
>
> **Not here** — selective download keep-sets (`selective-file-download.md`), transcode policy on the profile (`transcoding.md`), release-name parsing internals (`bulk-import-matching.md`).

- `internal/quality` is the pure scoring engine (no config/db imports): `Format`/`Condition` (Radarr-compatible matching — every `required` condition must pass, and if any non-required conditions exist at least one of those must pass too; `negate` inverts a single condition; **input that was never recorded matches nothing, negated or not**), `Profile`/`Evaluate` (band check → sum matched-format scores → `min_score` check), `ShouldUpgrade`/`UpgradableFrom`. Context builders (`ContextFromRelease`/`ContextFromRow`/`ContextFromFile`, wrapping `library.Parse` + probe data) live one level up in `internal/quality/qualityctx`, not in `quality` itself — `library` imports `config`, so `config` (which needs `quality.Profile` to build `ResolveScoredProfile`) can only import the leaf `quality` package, not anything that pulls `library` in behind it. `ContextFromRelease` reports `HasSeeders` as `seeders > 0`, not as an unconditional true: Torznab leaves the attribute at 0 when the indexer omits it, and a `negate: true` seeders condition would otherwise score every silent indexer's results as confirmed-low.
- **`Condition.eval` returns `(ok, known)`, and `known` is the whole point.** `negate` inverts only a known result, so a condition reading a field nobody filled in matches nothing rather than scoring a positive out of ignorance. Forced by the idiomatic `no-release-group` format (`release_group`, pattern `.`, `negate: true`): `mediaFileScore` re-parsed `filepath.Base(f.Path)`, which the renamer writes from the naming template (the default keeps only `{quality}`), so every imported file parsed as group-less and took the format's -100 — while `release_group` sat on the row all along. `ReplacesFile` compares that against a full release score, so the RSS scanner read the entire library as upgradable. **Unknown is a property of how the context was built, not of the field being empty**: `ReleaseContext.EmptyIsUnknown` is set by `ContextFromRow` only — a release parse saw the whole name, so an empty `Group` there is a real absence and still matches, while a column is empty both when the release had none and when nothing filled it in. `HasSeeders` was already this flag and now reads unknown rather than false. An unknown `required` condition fails the format (it cannot be proven); an unknown optional counts toward neither the quorum nor against it.
- **`ContextFromRow(*ent.MediaFile)` is how a file already in the library is scored** — `release_group` + `parsed_source`/`parsed_resolution`/`parsed_codec` + `size`, with the probe's `width`/`video_codec` winning where non-zero (so an ffmpeg-off install degrades to what the release name claimed), plus the three stream fields below. Eight of the ten condition types answer off the row; `seeders` is meaningless for a file, and `release_title` is the one that should answer but cannot. `ContextFromFile`/`ContextFromPackFile` survive for files *inside* a torrent, which have no row, and take a `*ffmpeg.Info` rather than loose width/codec so those files answer the stream types too. All six library-file call sites use `ContextFromRow`: `restapi.mediaFileScore`, `rss.feed`/`tv_feed` ×3, `importer.takesPackFile`, `restapi.replacesEpisodeFile`.
- **`release_title` is the one condition type a library file cannot answer, and `ContextFromRow` says so.** A `release_name` column was built and reverted: the name *is* in the DB (`DownloadRecord.title`, `ImportScanFile.source_path`, `TorrentSession.name`) but unreachable from an arbitrary file — a pack has one record and one `.Unique()` episode edge so episodes 2..N reach nothing, wizard/orphan files have no record, and all three referents are user-deletable (`DeleteDownloadRecord` from the queue's remove button, `PurgeRecordForHash`, `DeleteImportScan`), which would change a file's score when the queue is tidied. So `ContextFromRow` leaves `Title` as the basename **and** sets `EmptyIsUnknown`: the basename is non-empty, so without that arm a title condition was a confident *false* for every file in the library. Blanking `Title` is worse — the file then scores none of remux/vostfr/multi-audio while the release replacing it scores all of them, so **everything on disk becomes upgradable**. Unknown is what lets `ReplacesFile` drop those formats from *both* sides (`comparableTo`); that alone once **stopped upgrades happening at all**, since the upgrade rules were written entirely in title-matched formats, and it works now only because the three stream types below answer the ones carrying the weight. Permanently unanswerable from a file: `vff` vs `vfq` (both are `tags.language: fra`), `repack`/`proper`, `remux`, junk-source — facts about the *upload*, not about the bytes.
- **Three condition types are answerable from both a release name and a probed file: `audio_tracks`, `audio_language`, `subtitle_language`.** They exist because a format written only in `release_title` can never score the file it is being compared against. The idiom is one format with two optional arms — `release_title` for the release, a stream type for the file — exactly the shape `x265` already had by accident. The builtin `multi-audio` was converted to it (`title(multi|dual audio)` OR `audio_tracks >= 2`); `vostfr` and `vff` are user formats and the same rewrite applies (`\bvostfr\b` OR `subtitle_language: fra`). Languages are ISO 639-2/T and are canonicalised on **both** ends — at probe time and at `NewFormat` compile time — through `internal/langcode`, a leaf package `ffmpeg` and `quality` both import because neither may import the other and a duplicated table would drift. This is not cosmetic: a real 5425-file library held 5292 `fre` tags and zero `fra`, so a condition written either way matched nothing without the fold.
- **`ReplacesFile` scores both sides through `comparableTo`, which drops the formats the *file* cannot answer.** A format survives when every `Required` condition is known and at least one condition of any kind is known. "At least one", not all: a vostfr format's title arm is unanswerable for a row, and demanding all of them dropped vostfr entirely — leaving a file that genuinely lacked the French subtitles unable to be upgraded by a release that had them. A format written *only* in `release_title` still drops, which is the point: there the file's non-match is an artifact of the renamer. Dropping a format is not forgiving it — a "never grab this" negative still rejects the incoming release in `Evaluate`, which `qualityctx.Replaces` runs first. Measured on a real install before this: an anime profile paying `vostfr:1000` and `multi-audio:50` left every episode ~1050 below its `upgrade_until_score` of 1200, permanently, since no file could earn those points back — so every episode was upgradable by any VOSTFR release, and 86% of that install's grabs were VOSTFR.
- **`ContextFromRelease` fills the stream fields by regex over the name, and only what the name actually claims** (`applyStreamHints`): `MULTi`/`DUAL AUDIO` → `AudioTracks = 2` (a floor, matching the min-semantics of the condition), `VOSTFR`/`SUBFRENCH` → `SubLangs = [fra]`, `VFF`/`VFQ`/`VFI`/`VF2`/`VOF`/`VQ`/`TRUEFRENCH` → `AudioLangs = [fra]`. A name that says nothing leaves the field **nil**, never a zero. `VOSTFR` deliberately does not imply French *audio* — reading it as a dub is the one mistake that would score a subtitled release and a dubbed one alike. `ContextFromPackFile` applies the same hints over the release title, which is what keeps the pending-proposal preview — where the files are still in the download client and nothing can be probed — reaching the verdict the import will.
- **Band vs score are two different gates, in order.** `Evaluate` first checks resolution against `[min_resolution, preferred_resolution]` — `preferred_resolution` is a hard **ceiling** now, not a target (a release above it is rejected regardless of `upgrade_allowed`, and this reaches the RSS/missing-search feed scanners too, not just interactive search). Only a release inside the band gets its formats summed; the sum is then checked against `min_score`. A release can fail either gate independently, and `RejectReason` says which. Because the ceiling wins, a `min_resolution` above `preferred_resolution` is an empty band that rejects everything — `checkInvariants` refuses it, comparing the two through `quality.CompareResolutions` (the only exported view of `resolutionRank`, so config and the engine rank buckets off one table).
- **A `size` condition's `min_gb`/`max_gb` are per *episode*, and both bounds are multiplied by `ReleaseContext.EpisodeCount`.** One threshold then means the same thing for an episode, a season pack and an integral — the alternative was a cap that either let a 155 GB REMUX season through or rejected every legitimate pack. The count comes from the **library**, never from the release: `library.ParseSeasonSpan` reads the scope the name claims (`S03`, `S01-S05`, `COMPLETE`/`INTEGRALE`) and `SeasonSpan.EpisodeCount` totals it against `db.SeasonEpisodeCounts`, an unfiltered per-season `COUNT(*)`. An indexer never reports a torrent's file count, and the torrent's contents are only knowable after the grab — too late to gate one.
  - `EpisodeCount` of 0 (or negative) means **the library cannot say** and leaves the bounds unscaled, which is how they behaved before they scaled at all. Never read it as an empty pack: `episodeScale()` is the single place that clamps it, and collapsing a bound to zero would reject everything. The scanners' own episode indexes are filtered to what a pass may act on (`ListUpgradeCandidateShows` eager-loads with `eq.Where(candidates...)`), so they are the *wrong* denominator — a pack costs every episode it holds whether or not all of them were wanted.
  - Movies and single episodes pass 1 (`rss.singleRelease`, `restapi.singleReleaseEpisodes`), so nothing about movie scoring changed. Season-scoped searches can use one scalar because `indexer.filterToSeason` drops multi-season and complete packs; the series *browse* cannot, and uses `restapi.spanEpisodes` to size each result by its own name.
- **A release carries the provider ids its tracker published, and `filterProviderIDs` (`internal/indexer/service.go`) is the one filter here that does not guess.** Prowlarr parses `<torznab:attr name="tvdbid">` and friends off each release onto `ReleaseResource`; `parseItems` reads the same attrs (both spellings — `tvdbid`/`tvdb`, `tmdbid`/`tmdb`, as Prowlarr's own `NewznabRssParser` does) so the direct-Torznab path answers too. A non-zero id that disagrees with the search settles the release outright, ahead of `preferTitleMatches`, which keeps its prefer-don't-require job for the unlabelled majority. **Zero is the tracker saying nothing, never "no match"** — the same unknown-vs-false distinction `quality.Condition.eval` turns on — so reading it as a mismatch would empty the result set. Only ids the search itself asked about are compared: a TV search holds no TMDB id, and a series' TMDB id on a release says nothing about the TVDB id the library holds. It runs in `searchAll` **before** the `maxMergedResults` truncation, so a wrong-show release cannot spend one of the 200 slots. A mis-tagged upload is therefore filtered out — the intended reading of a wrong id, not a regression, and the same trust an id-keyed *search* would place in the tracker. `imdbId`/`tvMazeId` ride along undecoded; nothing in the library has a counterpart to compare them against.
- **The Prowlarr client sends the season and episode as `{key:value}` query tokens, and deliberately sends no id token.** `GET /api/v1/search` takes only `query`/`type`/`indexerIds`/`categories`/`limit`/`offset`, so `NewznabRequest.QueryToParams()` parses season and episode back out of the query string — and **only when `type` is `tvsearch` or `movie`** (a `type=search`, which is what shipped, discards every token silently), so `prowlarrSearchType` and `prowlarrQuery` have to agree. The episode token hangs off the season rather than standing alone: Prowlarr renders the pair as one `SxxEyy` string and yields nothing for a season it was not given, so a lone episode narrows a tracker to "episode 3" of no particular season. The id tokens are the ones **not** sent: `HttpIndexerBase.Fetch` drops an indexer from the fan-out *entirely* when handed an id its caps don't declare — an empty result, not a fallback to keyword search — so `{tvdbid:…}` costs whole trackers, while `filterProviderIDs` gets the same precision off the results for free. Season and episode are absent from that guard and never exclude an indexer. `POST /api/v1/search` is not a search at all: it grabs a release into a download client *Prowlarr* owns, bypassing the whole `download.Manager` pipeline.
- **The newznab category root comes from the search's own scope (`SearchParams.Kind`), never from whichever id happens to be set.** It used to be derived from `TMDBID > 0` / `TVDBID > 0 || Season > 0`, and `searchAll`'s retry drops the ids by design — so that pass sent no `categories` at all and keyword-searched every indexer's entire catalogue, which is a share of the "200 releases of Nonnas, Jobs and Macbeth" below. `ReleaseSearchService.Dispatch` drops indexers whose capabilities don't cover the root and `ExpandTorznabQueryCategories` expands it into each tracker's own children, so the root is the granularity worth sending. The retry likewise drops **season and episode**, not just the ids: they were preserved back when nothing forwarded them, but now that they narrow at the tracker, keeping them would re-issue the query that just came back empty. That bare-title pass is also what saves absolute-numbered anime, where the show has no `SxxExx` release at all and only the title can match.
- **Each of the three TV search scopes filters the results to its own scope, in `internal/indexer/service.go`.** Indexers behind Prowlarr routinely ignore the `season`/`ep` params and `searchAll`'s empty-result retry drops the id, so what comes back is a keyword search over the whole series: an episode search answered with every other episode, a series search with single episodes. `filterToEpisode` keeps the exact `SxxExx`, plus a release naming no season and no episode **only when it carries an anime absolute number or a daily air date** — those shows never spell `SxxExx`. Keeping *anything* unnumbered was the first cut and let through the bulk of the noise this exists to remove: a tracker publishing under the bare show title (a real TR4KER shape — 2.5 GB, 0 seeders, no filename, no description), a whole different show, and any pack whose only scope word the parser cannot read. `filterToSeason` keeps season packs of that season only, not single episodes, because both callers size a result against the season's episode count and mark the whole season downloading; `SearchSeries` keeps only `library.IsWholeSeriesPack`. Titles are **preferred, never required** (`preferTitleMatches`, applied to the episode and season scopes **and to `SearchMovie`**; `SearchSeries` applies none): the numbers alone cannot tell one show from another, and a search for an anime's `S04E03` came back offering Reacher, Ted Lasso and Strange New Worlds — any of which can outrank the right release under a profile with no notion of which show it is scoring, after which the importer files it under the record's anchor episode. So a title-naming release wins when one exists, and the whole set survives when none does. Dropping the non-matches is wrong: `TVShow` stores `title` + `original_title` and no aliases, so a show held under a translated title (`Moi, quand je me réincarne en Slime`, original `転生したらスライムだった件`) matches none of the English releases that are most of what its indexers carry. Matching tolerates a prefix in either direction and strips a leading fansub tag, because a parsed title keeps whatever `extractTitle` could not cut. Movies have no scope filter of their own — a film names no season or episode, so the title *is* the whole filter — but they are the same keyword-search noise: a search for `Comme un chef` with a `tmdbid` set came back with 200 releases of Nonnas, Jobs and Macbeth, one of which outscored the film itself on group and codec alone. `SearchMovie` shipped raw indexer output until this was added; the three TV scopes had been hardened and it was not.
  - **The fallback set is stamped `SearchResult.TitleMismatch`, and `rss.rankAccepted` drops it.** "Prefer" is the right answer for a human browsing releases and the wrong one for a pass that grabs the best score unattended: on the homelab a `Détective Conan` season-pack search that nothing named came back holding `The.Shield.S06` and `Monk.S05`, both of which `filterToSeason` kept (they *are* season packs of that season) and the profile scored happily. The flag is per-result rather than a second return value so no interface signature moves, and its **zero value is the permissive one** — a result that never passed through `preferTitleMatches` (an RSS feed item, a whole-series pack) carries no verdict and must not read as a rejected one. `rankAccepted` is the single choke point: all three automatic searchers (`grabSeasonPack`, `grabEpisode`, `scoreBest`) rank through it, and the feed scanners don't use it at all. The cost is that a show whose library title matches none of its releases — the Slime case — stops filling itself automatically; grabbing nothing is the better half of that trade, and interactive search still reaches those releases. Storing TVDB aliases on `TVShow` is what would buy back the coverage.
  - **`normalizeTitle` NFD-decomposes before stripping non-alphanumerics**, so an accented library title is comparable to a scene release, which never carries one. Without it `Détective Conan` normalized to `dtectiveconan` and matched **none of its own releases** — so every French-titled show hit the fallback above on every search, which is how the two wrong packs got in. The existing `[^a-z0-9]+` strip eats the combining marks for free; only the decomposition was missing.
  - `filterToEpisode` reads the pack span **before** its "names neither a season nor an episode" fallback, because a `COMPLETE`/`INTEGRALE` release carries no season token either — read in the other order, the fallback keeps every integral in an episode search.
  - `SearchEpisode`'s second return is how many dropped releases were packs *covering* that episode. It is the only part of the noise an operator can act on (the season/series scopes offer exactly those), so releases for some other episode are never counted — there is nowhere to send anyone for those. `BrowseEpisodeReleases` puts it on `SearchResultList.hidden_packs`, omitted when zero, and `ReleasesTable` renders it **in the empty state too**: telling "nothing exists for this episode" apart from "it only exists inside a pack" is the whole point, and the empty list is where that distinction matters most. The RSS caller discards it.
- Score is **sum of the profile's per-format scores for every matched format**; a format the profile doesn't list contributes 0. There is no global scale — scores are relative order within one profile only. The "never grab this" idiom is a very negative score (e.g. `-1000`) on a format plus `min_score: 0`; there's no separate blocklist feature.
- Builtin/user namespace: `quality.Builtins()`/`BuiltinByName`/`IsBuiltinName` is the compiled-in, read-only library (`internal/quality/builtin.go`, 10 formats: remux, x265, x264, av1, hdr, resolution-2160p/1080p/720p, multi-audio, dubbed). Every builtin **describes** a release; none judges one. `scene-junk`, `bad-group` and `re-encode` shipped in the first cut and were removed — a group blocklist or a "screeners are worthless" rule is user preference, not a fact about the release, and shipping one makes our taste the default for everyone. Anything of that shape belongs in `custom_formats`, and the release-group chips editor exists so writing one is a two-minute job. **Do not re-add opinionated builtins.** `config.CustomFormatEntry` (`custom_formats[]` YAML, name-keyed, hot-editable) is the user layer. `config.Validate` rejects a user entry reusing a builtin name; `Add`/`Update`/`DeleteCustomFormat` re-check that collision plus (delete only) whether any profile still scores the name (`ErrCustomFormatInUse`). REST surfaces both through one list (`GET /custom-formats`, `builtin: true` on the compiled-in ones); `PUT`/`DELETE` against a builtin is 409. A condition that won't compile is `422` with `code: invalid_condition` and the SPA renders that message verbatim (`errorText`, same arm as `connection_failed`) — there is no client-side regex gate, so this message is the only thing naming the offending condition. The create/update handlers call `ToFormat` themselves before `config.Add/UpdateCustomFormat` so the body carries that message rather than the same error wrapped in a config-key path; `quality.NewFormat` drops its `format %q` prefix for an unnamed draft, which is what the tester compiles. `CustomFormatEntry.Description` is optional free text a user format may carry alongside builtins' fixed, server-authored one — both surface through the same `CustomFormat.description` field and the same absent-when-empty convention, so the profile picker's hint (`QualityProfileForm`'s `Select` `Option.hint`) works for either kind.
- **The `release_group` condition is edited as chips, not regex** (`CustomFormatEditor.svelte`). `groupsToPattern` compiles the chip list to `(?i)^(a|b)$` with each name regex-escaped; `parseGroupPattern` is the inverse and is deliberately strict — an unescaped metacharacter, a `\d`-style class or an empty alternative returns `null` and the row falls back to the raw pattern input, which is also what `draftFrom`/`setType` use to decide `groupRaw` for an existing format. Nothing about the engine changed: the anchored regex + `negate` + a negative score already expressed exclusion, and the ruling was that the *authoring* was the problem, not the model. The raw path stays reachable both ways ("Edit as regex" / "Back to the group list"), and the way back is offered only while the pattern still parses, so switching modes can never drop something typed. `ConditionDraft.groupRaw` is editor-only and `toConditions` never emits it.
- Profile presets (`PROFILE_PRESETS` in `QualityProfileForm.svelte`) prefill the **whole** create form — `name` (the preset's own label), both resolutions, `allowed_codecs`, formats and both thresholds — and still only prefill: `applyPreset` calls `setFieldValue` and never submits. Prefilling `name` is what clears the "Name Required" flash when a preset is applied to a form that already failed validation. Codec values are ffprobe's (`hevc`, `av1`), mirroring `lib/media-info.ts` `VIDEO_CODECS`, not the human labels. No preset scores a group blocklist or a junk-source penalty — there is no builtin to name any more, and a preset must apply cleanly to a fresh install with no `custom_formats`.
- **`ResolveScoredProfile` memoises, keyed by the *resolved* profile name and `config.Generation()`.** Assembling a profile compiles every user custom format's conditions through `regexp.Compile`, and `convert.go` resolves one per episode — a 200-episode series detail was ~2,000 compilations per response. The key is the resolved name, not the requested one, because an unknown name falls back to the default and keying on the request would let an arbitrary stored `quality_profile` string grow the map. `config.Generation()` is bumped by **every** assignment to the `current` singleton (three sites in `singleton.go`), which is what makes a hot-edited custom format take effect without a restart; a fourth write site that forgot to bump it would serve the old regexes until reboot. The returned `Profile` is shared — nothing may mutate it.
- `config.ResolveScoredProfile(name)` is the one function that assembles a ready-to-`Evaluate` `quality.Profile` from config: it resolves the named profile (falling back to `quality_default_profile`, mirroring `ResolveQualityProfile`), then for each `formats[]` entry resolves the name against `BuiltinByName` first and `FindCustomFormat` second, compiling user entries via `ToFormat` on the spot. A name that resolves to neither is silently dropped (validated at config load; this only fires on a delete racing a resolve) rather than failing the whole profile.
- **The RSS feed is the only pass that goes *looking* for an upgrade** (`FeedScanner.tryUpgrade` in `internal/rss/feed.go`). Interactive search never upgrades (a manual grab fills a wanted item, or overwrites because the operator asked; `ReplacesFile` is consulted on neither path), and neither does a single-episode missing grab. The missing search's **season-pack** arm is the one other producer of `replace_mode: upgrades`, and only as a rider: `grabSeasonPack` unions in whatever the pack it was already grabbing happens to beat, so nothing here issues a query in order to upgrade. Its upgrade context is `db.UpgradeCandidateShow` — one show, loaded inside the pack arm only once a candidate has ranked and only under `UpgradeAllowed`, so the steady state (every result rejected) pays nothing; a per-grab query is what makes this affordable in a pass whose ticks mostly grab nothing, where a per-tick library index would not be. Movie candidates come from `db.ListUpgradeCandidateMovies`: monitored, has a media file, **status not `downloading`** (a movie mid-re-grab isn't re-evaluated every tick, which would bump `grab_failures` on a healthy movie). Per candidate: skip if `!upgrade_allowed`; evaluate the release and skip if rejected; build the current file's context via `qualityctx.ContextFromRow`; **the `UpgradableFrom` guard runs before the score comparison** — it checks only the *upper* bound: a file at or below `preferred_resolution` (resolved resolution required) is eligible, a file above it or with unresolvable resolution is never replaced. It deliberately does **not** check `min_resolution`: a file below the floor scores 0 (the band rejected it before any format was summed) and is exactly the headline upgrade case. Only a file above the ceiling, or one with no resolvable resolution, also scores 0 while being the file the profile was protecting — the guard is what tells those two 0s apart. Only past it does `ShouldUpgrade(currentScore, releaseScore)` run: `upgrade_until_score` (0 = no cap) as a stop condition, then strictly-greater score.
- **Series upgrade the same way** (`TVFeedScanner.grabUpgrade` in `internal/rss/tv_feed.go`), off `db.ListUpgradeCandidateShows`: monitored episodes holding a file, narrowed to those with no `downloading`/`importing` record — the in-flight check is by record, not by `episode.status`, which only flips back once the import lands. The per-file rules are the movie ones (`UpgradeAllowed` → `UpgradableFrom` → `ShouldUpgrade`), applied over the episodes one release covers.
- **`quality.ReplacesFile(p, existing, incoming) bool`** is the single predicate deciding whether one release replaces one file — `UpgradeAllowed` → `UpgradableFrom` → `ShouldUpgrade`, in that order, for the reason the guard-ordering paragraph above states. The scanners call it directly and the importer through `qualityctx.Replaces` (which runs `Evaluate` first); there is exactly one place this decision is made. `DownloadRecord.replace_mode` (`none | upgrades | all`) is the record-level field it feeds: `none` is a plain gap-filling grab (skip anything that already has a file), `all` is the operator's explicit overwrite (manual replace grab), `upgrades` means "replace what this release beats" and is decided per episode at import time.
- **A season pack is judged per episode, against each episode's own file** — the invariant ("a pack upgrade never lowers any episode's score") is structural rather than something an aggregate has to buy. A `replace_whole_season` profile key once restored the old season-level rule (beat the season's **best** file, take it whole) and was removed 2026-08-27: max was the only aggregate under which the invariant held at the season level, but it bought that safety by freezing a whole season whenever one strong episode was in it. **Do not re-add it** — per-episode comparison keeps the invariant without the cost, and the key forced a second rule through every pack path (`grabUpgrade`, `grabPack`, the importer). Single-episode releases are decided once, by the scanner, and the importer's `!= none` check just carries that decision through — the per-episode predicate and its probe re-check (`takesPackFile`) are pack-path only, since a single file has no second opinion to reach.
- **A pack grabbed to fill a gap also replaces what it beats, in the same grab.** `processItems` still tries the wanted index first and `continue`s on success — that part is unchanged — but the record it grabs carries `replace_mode: upgrades`, so the importer's per-episode plan (below) replaces any existing file the release beats while filling the missing ones. Both branches still share one `grabbed` set, so an episode is never grabbed twice in a tick.
- `file_score` is **detail responses only** — on `MediaFile` for movies, and flat on `Episode` for series (the series *list* carries no episodes at all, so nothing extra is needed to keep it out). Computed on demand from the row, never stored. A rejected/out-of-band file reports `file_score: 0`; there is no `rejected` flag — 0 doubles as both "matched nothing" and "the upgrade logic won't touch this file" by construction.
- `QualityProfile.is_default` marks the profile `quality_default_profile` names, computed in `qualityProfileToAPI`. It exists because a movie or series with an empty `quality_profile` resolves to that profile, and the SPA had no way to name it — both detail sidebars rendered a hardcoded "Server default" string instead of the profile actually in force. `POST /quality-profiles/{name}/default` (`config.SetDefaultQualityProfile`) is what writes the key, and it is **also the only way out of `DeleteQualityProfile`'s 409**: the current default cannot be deleted while it holds the role, so without a setter a fresh install's `default` profile was permanently undeletable. The SPA renders the ★ action on every non-default row and disables delete on the default one.
- `min_score` is omitted from API responses when its value is `0` — deliberate handler code (`if e.MinScore != 0` in `handler_quality_profiles.go`, the field is `*int`), not an encoding artifact. Absent always means `0`.
