# Transcoding

> **Read before touching** `internal/transcoding/`, `internal/ffmpeg/` (CLI/BuildArgs/hardware probe), `quality_profiles[].transcode` in config, `db.CreateMediaFileParams.QueueTranscode`, or the `/transcoding/*` handlers.
>
> **Covers** — the global config block and the per-profile policy, job lifecycle (queue → claim → encode → verify → swap), verification and rejection, boot recovery, hardware (VAAPI) encoding, the SPA surfaces, and the deliberate non-features.
>
> **Not here** — probe columns and the `media-probe` backfill ([`media-lifecycle.md`](media-lifecycle.md)), how a profile scores a release (`quality-scoring.md`).

- **There is one ffmpeg surface, and it is `ffmpeg.path`.** `internal/ffmpeg.CLI` resolves *both* binaries out of that directory (or `$PATH` when it is empty), so `ffprobe` answering says nothing about `ffmpeg` — a `transcoding.ffmpeg_path`/`ffprobe_path` pair was in the older plan and was dropped: two ways to name the same directory is two ways to get it wrong. `Prober` therefore exposes `FFmpegPath()` and `Version(ctx)`, and `GET /config/ffmpeg` reports `version` off `ffmpeg -version` — `found`/`resolved_path` are ffprobe's and cannot stand in for it.
- **`transcoding: {enabled (false), max_concurrent (1, 1–8), max_failures (3, 1–10), hw_accel (auto), hw_device (/dev/dri/renderD128), defer_seeding (false), verify {…}}` is the whole global surface**, all of it runtime-editable through `GET|PATCH /api/v1/config/transcoding` with **no restart** because none is read at boot: `fill` re-reads `enabled` and `max_concurrent` off `config.Get()` on every pass of its claim loop, and `fail` reads `max_failures` at the moment it needs it. Turning the feature off therefore stops the *next* claim rather than waiting out a process lifetime. A worker that had latched the boot-time values would keep encoding after an operator said stop, which is the whole reason the read is per-tick and not per-`Start`.
- **The policy lives on the quality profile, not in the global block** — `quality_profiles[].transcode: {if: {video_codecs, containers, max_video_bitrate, min_video_bitrate}, to: {container, video_codec, crf, preset, audio_codec, audio_passthrough}}`. "What counts as acceptable" is already a per-profile question (band, formats, scores); a second, profile-blind transcode rule would contradict the profile it sits beside on the first anime library. `config.TranscodeEligible(profile)` is the one predicate — the global switch **and** a resolved profile carrying a non-nil `Transcode`. A nil block means the profile's files are never touched.
  - `audio_passthrough` defaults to `[truehd eac3 ac3 dts aac opus flac]` (`config.DefaultAudioPassthrough`) because TrueHD/E-AC-3 carry Atmos and DTS(-HD) cannot survive a re-encode losslessly — copying is the only way they come out the other side. `BuildArgs` emits `-c:a:<i> copy` per *stream*, not one blanket `-c:a`, since the decision is per track and `Info.AudioCodecs` is the stream-ordered list that makes it possible.
  - **A profile that scores a `size` condition's `min_gb` positively must not also carry a `transcode` block.** The transcode's whole point is a smaller file, and the row now carries the encode's real probe — so the shrunk file scores below what the release that produced it did, and every transcode makes its own output look upgradable. Nothing detects the pairing; the two are simply asking for opposite things.
  - The block **rides the profile REST CRUD** (`transcode` on `QualityProfile`), and there is deliberately **no removal over the API**: an absent field on an update leaves the stored policy alone, so clearing one is a YAML edit. The SPA's profile form now edits it, behind a `transcode_enabled` checkbox that is form state and never an API field: the page strips the pair in `toRequest()`, so `transcode` reaches the request whole or not at all — the API takes no half-filled policy. Because the API cannot remove one, the checkbox renders **on and disabled** for a profile that already stores a policy (`policyPersisted`), with a line saying clearing it is a config-file edit; offering an off that silently would not persist is worse than not offering it.
- **A job is created in the same call as the `MediaFile` row** (`db.CreateMediaFileParams.QueueTranscode`, decided by `TranscodeEligible`), on both import paths and the bulk-import committers. Riding the create is what makes a later profile change need no backfill of missed rows — and it means the job and the file cannot disagree about whether one exists. The hygiene **orphan scan does not queue**: those files arrive with no import decision behind them and the manual `POST /transcoding/scan` is the door for them.
- **`transcoding.defer_seeding` (default false) holds a job back while the torrent that produced its file is still `downloading` or `seeding` in its download client — the client's answer is the predicate, nothing on disk is.** Under `library.import_mode: hardlink` the swap is a *rename over the library path*, so the torrent's directory entry keeps the original and seeding survives the transcode — and so does a second full copy of the file for as long as the torrent is kept. The flag is what stops disk carrying the original and the encode at once through a seed window that can run weeks. `runJob` reads the key live (same reason `fill` does), asks `FindSeedingDownloadRecord` for the newest completed record with a torrent hash and a client name that names the file's owner — the movie, or the episode by its edge *or* through `wanted_episodes`, which is how a season pack's other episodes find the one record that carried them — then `Downloader.TorrentStatus` on that client, all before anything is probed. `downloading` or `seeding` puts the row back to `queued` with `deferred_until = now + 1h`; `ClaimNextTranscodeJob` skips a row whose deadline is in the future and clears the stamp on the claim that finally takes it. `DeferTranscodeJob` walks `attempts` back by one — the claim that produced the job bumped it, and a deferral is not an attempt, or a long seed exhausts `max_failures` without ffmpeg ever running.
  - **Everything that is not a live torrent proceeds.** No record (a retroactive `Scan` job, a bulk import, a record already pruned by the completed-record retention sweep), a client name the config no longer has, `ErrTorrentNotFound`, a `completed`/`paused`/`error` status, or a lookup error — all encode now, the error at WARN. A job that cannot be tied to a seeding torrent must not be held forever; the flag defers disk cost while seeding is provably happening and never past that.
  - **Why the client and not the link count.** The first cut used `nlink > 1` as the predicate, and it never released: at the time nothing in streamline dropped the second link when seeding ended — `keep_torrent_seeding: false` removes the torrent *without* its files, and the external clients stop at their ratio and keep the payload — so a deferred job waited until an operator deleted the torrent copy by hand. A builtin torrent is now reaped: `download.RemoveSeedCompleteTorrents` removes it *with* its files on the monitor tick once its seed limit is reached and its record is completed (`downloads-and-imports.md`), and the removal reads here as `ErrTorrentNotFound`, which `runJob` already treats as "no longer live". External clients still keep the payload and still need the operator. The client's status is the question the flag actually asks. For an external client the disk cost still lands once seeding stops and the copy stays; freeing it there is not this worker's call.
- **`Evaluate` never re-encodes HDR/DV video in v1** — a PQ/HLG transfer or a Dolby Vision configuration record suspends the codec *and* bitrate rules; only the container rule survives, so an HDR file in the wrong container still remuxes. Re-encoding HDR without carrying its metadata is how a library ends up with grey, washed-out masters, and carrying it correctly (`hdr: reencode`) is a feature of its own that was not built. The container is judged by the **file extension**, not by ffprobe's `format_name` — `matroska,webm` names two containers and cannot pick one.
- **The output is written beside the original as `<base>.streamline-tmp.<container>`, and the marker is load-bearing.** A rename across filesystems is a copy, so a temp file in `/tmp` would double the I/O of every transcode on a NAS; landing it in the library is what makes the swap an atomic `os.Rename`. The marker is also what `recover` sweeps at boot, over both library roots, through `os.OpenRoot` — the paths come off the filesystem rather than the DB, and a symlink planted in the library would otherwise turn the sweep into a delete anywhere on the host.
- **Verify before swap, always.** The encode's duration must match the source's within two seconds (containers round), and audio the source had must have survived. Both run on a context that outlives the job's own cancel, so a cancel arriving mid-probe reads as a cancel rather than as a corrupt output. Past the swap the row is updated with `path`, `size`, `format`, `size_before`, `transcoded_at` — **and the probe columns, restamped from the encode's own probe**, which `verify` already read and now returns for exactly that. Nulling them instead left `qualityctx.ContextFromRow` falling back to `parsed_codec` until the `media-probe` backfill arrived: an h264→hevc transcode read as x264 for up to a backfill cycle, so the RSS feed could grab an x265 "upgrade" over the file the pipeline had just produced, replace it, and transcode it again.
- **An encode that verifies as worse or broken is `rejected`, not failed, and never swapped.** `verify` runs `checkOutput` (`internal/transcoding/verify.go`): duration ±2 s, equal audio track count, equal width/height, equal subtitle languages on an mkv target (mp4 drops them by design), then the size band from `transcoding.verify` — `max_size_percent` on a **transcode only** (a remux copies the streams and may grow by container overhead), `min_size_percent` on both (an output at a few percent of the source with a matching duration is a dropped stream or a truncated encode, never a transcode; 2160p remux → AV1 legitimately lands near 10 %, which is why the default floor is 5). Two opt-in exec checks follow: `health_check` fully decodes the output with `-xerror`, and `min_vmaf` scores three 60 s windows at 10/50/90 % of the duration against the source (`vmafScore`, mean of the windows, `libvmaf=n_threads=NumCPU`, both sides forced to `yuv420p` so a 10-bit encode can be scored against an 8-bit source). A missing `libvmaf` filter logs once and skips the check rather than failing the job. A rejection is a `*rejection` error, deterministic and therefore **terminal** — `rejected` is its own job status carrying `size_before`/`size_after` and the reason in `error`; `attempts` is not spent. `RetryTranscodeJob` accepts `rejected`, and `ListMediaFilesWithTranscodeOwners` excludes any file holding a rejected job so the scan cannot re-queue what an operator has not asked for again (retry mutates that row, so "has a rejected job" is exactly "rejected and not retried"). A probe *exec* failure on the output, or a health check whose ffmpeg failed to launch (no `*exec.ExitError` behind the error), is still a retryable `fail` — only a non-zero exit is a verdict. Zero on any of the three numeric keys disables that check; `checkInvariants` refuses a floor at or above a non-zero ceiling.
- **The pre-swap checkpoint re-reads the row, and both cancellations are ordered ahead of it.** Shutdown (`ctx.Err()`) is checked *before* the job's own cancel at the probe arm and at the checkpoint, because `canceled` is terminal — nothing retries it and `CreateTranscodeJob`'s dedupe ignores it — so a process going down must leave the row `running` for `recover` rather than spending the file's only chance. Then the row is re-read by id (`stillCurrent`): an encode outlives a replace import, a rename or a re-identify, and on a replace that renders the same name the swap would rename the *old* bytes over the file that replaced them. A moved path, a changed size or a row that is simply gone is treated exactly as a cancel — temp removed, `mf.Path` untouched, WARN naming the reason.
- **`transcode_jobs → media_files` cascades on delete.** Without the annotation `foreign_keys(1)` refuses to delete any file that ever had a job: an upgrade replacing it, drift-check pruning it, a movie delete taking it. That cascade is also what makes `stillCurrent`'s not-found arm reachable.
- **The swap refuses to overwrite a sibling.** On a container change `finalPath` is a path the source does not hold, and `os.Rename` destroys whatever is there without a word — a multi-file movie is enough for that to be another row's file. `os.Lstat` first, and the job fails (retryably, reason naming the path) rather than deleting something no job licensed it to.
- **A panic in an encode fails that job, not the process.** `runJob` defers `observability.RecoverPanic` with an `onPanic` that calls `failTerminal(errJobPanicked)` — terminal because the same input panicking again is a loop, and an operator can retry the row by hand once the cause is fixed. Without it the encode goroutine took the whole binary down (scheduler, downloads, HTTP server) and left the row `running` until the next boot's recover swept it.
- **Every terminal path stamps the span.** `record` is the choke point every outcome funnels through, so the outcome attribute and the error status live there rather than in five helpers; `failWith` and `reject` additionally call `otelx.RecordSpanError` with the cause. `transcoding.run` is opened in `runJob` and closed by a defer, and nothing in between used to touch it — so a failed, rejected or canceled encode traced as OK, and filtering a backend for error spans found no failing transcodes at all.
- **`streamline.transcoding.duration` covers encode *through* verification and swap; `.encode_duration` is the encode alone.** VMAF runs up to three extra decode passes, so the original single histogram could not answer "how long does this codec take to encode". `transcoding.encode` is the ffmpeg span, and progress is logged every 5 minutes (`logProgress` in `runner.go`) — an encode stuck at 0 % on a headless box otherwise showed up only by polling `/transcoding/queue`.
- **Failure is retryable; failure *after* the swap is not.** `attempts` climbs to `max_failures` and then parks the row `failed` with the last 4 KiB of ffmpeg's stderr as `error` — ffmpeg names the reason it gave up in its last lines, and the banner above it is what nobody reads out of a queue row. A DB write failing once the file has already been replaced is terminal instead (`errAfterSwap`): a retry would re-probe a source that no longer exists. It is logged at `observability.LevelCritical` naming **both** paths, because on a container change the row still points at a deleted one and only an operator can reconcile that.
- **Boot recovery is two moves and both are needed.** Rows left `running` by a dead process reset to `queued` (nothing else would ever claim them again), and the stray temp files those encodes left are swept. Neither covers the other: a swept temp file with a `running` row is a job nothing drains, and a requeued row beside a half-written output is an encode that resumes onto its own garbage. The reset also refunds the claim's `attempts` bump, the same way `DeferTranscodeJob` does, because a restart mid-encode is not a failed attempt — a deploy landing during a two-hour encode was otherwise spending one of the job's three tries.
- **Cancel kills ffmpeg; a cancel arriving after the rename completes anyway.** The last honoured checkpoint sits between verification and the swap — nothing has moved there, so the deferred remove drops the encode and the library file is untouched. Past it the work is done, and completing the job is what keeps the row and the bytes on disk saying the same thing. `claim` registers the cancel func under the *same* lock that books the slot: registering it in `runJob` instead left a window where a cancel took the not-running branch, marked the row canceled, and the encode carried on and completed over it.
- **Progress (`percent`, `eta_seconds`, `speed`) lives in worker memory only** — parsed off ffmpeg's `-progress pipe:1`, held in a map keyed by job id, and absent for a `running` row whose encode belongs to a process that has since restarted. Persisting it would be a WAL frame per second per job through the one SQLite connection every API request queues behind, to describe a number that is stale the moment it is read.
- **REST (`admin`, all four):** `GET /transcoding/queue` (newest 200, plus every rejected row regardless of age, **no `status` filter** — the SPA filters client-side), `POST /transcoding/jobs/{id}/cancel|retry` (204; retry accepts `failed` and `rejected`), `POST /transcoding/scan` (202). All four answer **409 while `transcoding.enabled` is false**, which is what the SPA reads as the "feature off" screen — an empty list would read as "nothing queued". Cancel and retry have **no 404**: each store update is one conditional statement, so an unknown id and an already-finished job are the same zero rows affected and there is nothing to tell them apart. Scan additionally 409s when a scan is already walking, and — with `code: worker_unavailable` — when `Ready()` is false (ffmpeg disabled or its binary missing) — queueing rows no worker can claim leaves work nothing drains and nothing explains. The code exists because both SPA Scan buttons read a bare 409 as "already running" and latched into their scan-started state for a scan that never began; `scanWorkerUnavailable` in `lib/transcoding.ts` is the one place that branches on it.
- **`BuildArgs` differs by target container, and mp4 is the reason.** An mp4 target maps **video and audio only** (`-map 0:v -map 0:a`, no `-c:s`, no `-c:t`) on both the transcode and the remux path: `-map 0` hands the muxer the source's SRT/ASS/PGS subtitles and font attachments, which mp4 refuses outright — i.e. most mkv sources, so an mp4 policy failed on nearly everything it was pointed at. mkv holds all of it and keeps `-map 0` + `-c:s copy` + `-c:t copy`. **`av1` also needs its preset translated**: `libsvtav1` takes `-preset <int>` and rejects a name, so `svtPresets` maps the nine x264-style names onto SVT numbers (`medium` → `7`, higher being faster). The names stay the config surface because they are the only spelling the three encoders share.
- **A policy whose output its own `if` rejects is refused at load** (`checkInvariants`): `to.video_codec` must be in a non-empty `if.video_codecs`, `to.container` in a non-empty `if.containers`. Otherwise every job succeeds and the next pass reads its own output as non-compliant — a loop nothing downstream can catch, since nothing failed. A `crf` output can still exceed `max_video_bitrate`, which no invariant can predict; leave the ceiling headroom.
- **The scan re-probes every file** rather than reading the stored probe columns: `HDR` and `AudioCodecs` are what the rules need and neither is a column. That is why it is manual and rare rather than a schedule entry. It **skips rows with a `transcoded_at`** — the pipeline already brought those into compliance, re-encoding an encode is not a v1 operation, and it is the second guard against a policy that fights itself.
- **The bitrate rule reads the video stream's `bit_rate`, falling back to the container's total** (`ffmpeg.Info.VideoBitrateBPS`) — mkv rarely carries a stream `bit_rate`, so the fallback is the common case and it counts the audio tracks too. The rule is documented that way rather than made cleverer: a threshold set with no headroom queues files whose video is already under it. **`min_video_bitrate` reads the same figure**, so on mkv it is being compared against the container total as well and the floor needs the same headroom in the other direction — set at the video rate it will exempt files whose video is comfortably under it.
- **`if.min_video_bitrate` suspends the *codec* rule for a source already below it** (`belowMinBitrate` in `rules.go`); `max_video_bitrate` and the container rule are untouched, so a lean h264 in the wrong container is still remuxed and one above the ceiling is still queued. Constant-quality encoding is bitrate-blind — VAAPI's CQP most of all, since it is handed the profile's `crf` as a flat QP — so re-encoding an already-lean h264 source routinely produces a *larger* file than it started with, and the codec rule alone has no way to notice. The key is the operator saying "leave sources below this alone" rather than a heuristic the evaluator guesses at. `checkInvariants` refuses a floor at or above a set ceiling: the codec rule would then only ever fire on files the ceiling queues anyway, which is a rule that decides nothing.
- SPA: `/activity/transcoding` (its own route, the third row under Operations, admin-only — which is why `activityLinks` is `$derived` rather than constant) and `/settings/transcoding` (save-per-control, no form; it *reads* `/config/ffmpeg` to report `resolved_path · version` rather than duplicating Media probe's controls). "Scan library" sits on both. `queued`/`running`/`succeeded`/`canceled`/`rejected` are five new `StatusKind`s aliased onto existing `--status-*` hues (`failed` already existed, `rejected` aliased onto `--status-failed`) — the same move `importing` made beside `grabbing`, and for the same reason: borrowing the kind outright would have made a queued job's pill read "Wanted" and a canceled one "Paused".
- **Hardware encoding is `transcoding.hw_accel: auto | none | vaapi` plus `transcoding.hw_device` (default `/dev/dri/renderD128`), both runtime-editable through `GET|PATCH /config/transcoding` and Settings → Transcoding.** `auto` probes the device once (an `ffmpeg -encoders` listing, then a half-second synthetic `hevc_vaapi` encode through the device) and falls back to software *per job* when the probe failed or the policy's `to.video_codec` has no VAAPI encoder; `none` forces software; `vaapi` names the Linux backend explicitly. **`vaapi` is required-hardware, and that is the whole difference from `auto`**: when the probe failed, or when the device has no encoder for the policy's `to.video_codec`, the job is **deferred an hour instead of encoded** — `DeferTranscodeJob`, back to `queued` with `deferred_until = now + deferRecheck`, the claim's attempt refunded, one WARN naming the reason (the probe error, or `no <codec> encoder on device`) — and the probe memo is dropped so the next claim re-probes rather than holding every job on one driver hiccup. The fallback it refuses is not a slower encode, it is a bigger process: libx265 needs roughly a gigabyte more RSS than the hardware path, and a 1 Gi pod sized for the GPU its operator chose was OOM-killed by exactly that. Only a transcode is deferred — a remux runs no encoder — and `auto` is unchanged: it falls back per job and keeps its memo, which costs a software encode rather than a stall. The enum still has a slot so VideoToolbox can land beside them without a rename. The probe result is memoised per `(hw_accel, hw_device)` pair, so changing either key re-probes on the next job and nothing here needs a restart; a failed probe logs once at WARN and the view reports it as `hw_status: off|ready|unavailable` with `hw_reason` carrying the probe error (only when unavailable). On the hardware path `BuildArgs` keeps software decode and emits `-vf format=nv12,hwupload` (or `format=p010,hwupload` plus `-profile:v main10` for hevc when the source is 10-bit and the probe's second, p010 test encode passed: the upload format is what decides output depth, the software encoders keep it on their own, and h264 has no 10-bit VAAPI profile so it always lands at 8 bits; `ffmpeg.Info.TenBit` reads `pix_fmt` for it and is not a column), `-c:v hevc_vaapi|h264_vaapi|av1_vaapi`, `-rc_mode CQP -qp <crf>` (VAAPI has no CRF; a constant QP is the closest it offers, so the profile's `crf` is handed over as-is) and `-compression_level` mapped from the preset name (1 slowest/best .. 7 fastest, a table shaped like `svtPresets`). Remuxes never touch it. **CQP is bitrate-blind, so the same number means something else on hardware.** It holds quality roughly constant — VMAF ~99 at qp 22 whatever the source — which makes the output size purely a function of the *source's* bitrate: measured, qp 22 produced **203 %** of a 5 Mbps BluRay x264 and **57 %** of a 10 Mbps WEB source, where libx265 at crf 22 gave 98 % on the first. **26–28 is the sane range on hardware** (qp 28 → 78 %, VMAF 96.7), and `if.min_video_bitrate` is what keeps lean sources out of the queue in the first place. No mapping from `crf` to a qp is done in code on purpose: an offset that fits one GPU and one driver is a guess on every other. Verified on an AMD Phoenix iGPU with all three encoders. Hardware encoders trade size for speed and routinely emit a larger file at equal quality than x265, so `transcoding.verify` (the size band, VMAF) is what keeps a hardware policy honest rather than an optional extra. **The default image cannot do VAAPI**: its `mwader/static-ffmpeg` is a static build with no libva, and no amount of device passthrough changes that. A second image variant is published under a `-vaapi` tag suffix (`ghcr.io/datahearth/streamline:vX.Y.Z-vaapi`), built on `lscr.io/linuxserver/ffmpeg` (ffmpeg 9 with libvmaf and VAAPI compiled in, the Mesa and Intel VA drivers bundled) — no Debian, Ubuntu or Alpine ffmpeg package builds libvmaf, so it is the only image where `transcoding.verify.min_vmaf` is enforced rather than silently skipped; it is not distroless. It needs the render node passed through and the host's `render` group granted (docker `--device` + `--group-add`, compose `devices` + `group_add`, Helm `hwAccel.{enabled,device,resourceName,supplementalGroups}`, the last of which is host-dependent and the resource name of which needs a GPU device plugin on the cluster: no hostPath, no privileged). `docs/wiki/Installation.md` carries the operator-facing version.
- Deliberately **not** built, so nobody rediscovers them: a scan-status endpoint (the queue is the status), `max_failures` on the job payload, `hdr: reencode`, VideoToolbox (no Mac to test on; the `hw_accel` enum has the slot), NVENC/QSV/AMF, full hardware decode (`-hwaccel vaapi`; software decode works on every source codec and the encoder is where the time goes), upconverting 8-bit sources to 10-bit (an x265 banding trick that only costs size on hardware), a per-job "encoder used" field on the API or the UI, `transcoding.ffmpeg_path`/`ffprobe_path`, and `SystemInfo.ffmpeg_version`/`transcoding_warn` (nothing read them).
