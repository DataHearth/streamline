# Extensions

The detail behind the `## Extensions` stub in `CLAUDE.md`. Read it before touching `internal/extension/`, `internal/db/extension_views.go`, `extensions/**`, the `extensions` config family or the `/extensions` handlers.

An extension is a WebAssembly module (Extism on wazero, `internal/extension/runtime.go`) that Streamline loads from `extensions[]` in the config. It mounts URL prefixes, reads a granted slice of the core database through temp views, reads granted folders, and owns a private SQLite file. `extensions/sdk` is the guest side of the contract (its types mirror `internal/extension/contract.go` field for field; `APIVersion` is 1), the OPDS extension is the first one and the reference for how one is written, in a repository of its own that imports the SDK, and `internal/extension/testdata/echo` is the fixture the specs run against (it declares a `credential` and a `settings` card, so the account and user-card endpoints have something to call). The SDK and the fixture are each their own Go module; `task build:extensions` builds the fixture twice with `GOOS=wasip1 GOARCH=wasm go build -buildmode=c-shared`: `echo.wasm`, and `echo-full.wasm` (`-ldflags "-X main.extra=1"`), which also asks for the three folders and the `ffmpeg` and `library_scan` services.

## One instance per request

`Module.Handle` creates a fresh guest instance for every call and closes it after, so a guest holds no state between requests: anything it keeps goes in its own database or its cache folder. `Request.Mount` is the mount prefix (empty under `/api/v1/extensions/<name>/`) and `Request.Origin` is `httputil.RequestOrigin`, the only origin a guest may trust: it cannot tell a trusted proxy from a client that sends `X-Forwarded-Host`. The authorizer allows `REINDEX` on `main`, which SQLite asks for on every `CREATE INDEX`. The dispatcher sets `Cache-Control: no-store, private` itself and `guestCacheControl` lets a guest replace it with a private policy only (one header value, every directive on the allow list, `private` among them), applied by `cacheWriter` on 200, 206 and 304 alone so an error is never kept; a `self` mount takes credentials in the URL, which is why `public` and `s-maxage` are refused. `stream_ffmpeg` answers are never cacheable. Each instance is given `crypto/rand.Reader` as its random source (`WithRandSource`): wazero's default is one fixed stream for every instance, which made every token a guest drew identical. That is why the OPDS extension's `ensureSchema` runs on every request (one cheap marker read once the schema exists). Limits are in `contract.go` and enforced by the host, never the guest: 64 MiB of memory (`MemoryPages` 1024), 30 s per request (`RequestTimeout`), 5 s per SQL statement, a 16 MiB request and response body (`MaxResponseBody`), a 32 MiB module, a 1 GiB cache (`CacheBytes`), 8 ffmpeg processes at once (`MaxFFmpegProcs`) and the last 64 KiB of an ffmpeg run's stderr (`MaxFFmpegStderr`). The module config sets `WithSysWalltime().WithSysNanotime()`; without them wazero reports 2022-01-01 as the time in every guest.

The host functions are `sql_query`, `sql_exec`, `log`, `ffmpeg_run`, `scan_status`, `scan_start` and `http_request` (`hostFunctions`); the host offers all seven to every module, and `ffmpeg_run`, the two scan calls and `http_request` check their service grant when called.

## The store: connection setup order

`OpenStore` gives each extension its own `sqlite.Driver` with a connection hook, run on every pooled connection. The pool is not wrapped in otelsql (each statement already has its `extension.sql` span, and `sqlite.Limit` needs the driver's own connection). The order is load-bearing:

1. `ATTACH` core read-only (`file:<core>?mode=ro`) as `core`. A core path that is in memory fails with `ErrCoreInMemory`, since an attach could not see it.
2. `CREATE TEMP VIEW streamline_<name> AS <view SQL>` for each **granted** view.
3. Register the authorizer (`newPolicy`) **last**. Steps 1 and 2 run statements the authorizer would refuse (reads of `core.*` outside a view, creating a `streamline_` view); installing it first would break the setup, installing it later would leave a window where a connection runs unchecked.

The policy, in one sentence: anything is allowed in `main` (the extension's own file), reads of `core` are allowed only through a granted view, and nothing writes to `core` or `temp`.

- **The `count(*)` rule.** SQLite reports `count(*)` over a table as a column-less read (`arg2 == ""`). It is allowed on the base tables of **granted** views only, never on core in general: that answers "how many rows" for a table the extension was granted a view over, and tells it nothing about a table it was not.
- **Views are temp and unprefixed in core.** They live in `temp` as `streamline_<name>` so an extension's own `main` tables cannot collide with them and nothing is written into the core file. The prefix is also what the policy keys on: a read of `core` is allowed when its `via` is a granted `streamline_` view. A `CREATE VIEW` or `CREATE TRIGGER` in `main` whose name starts with `streamline_` is denied, or a guest could create one that borrows a host view's name and pass the core-read check, reading `core.users.password_hash`.
- A `SQLResult.Error` carries a statement the database refused (including the deadline interrupt); the Go error is for a failed host call only.
- **A result is capped twice.** `Store.Conn` sets `SQLITE_LIMIT_LENGTH` to 16 MiB on the connection it hands out, so one value (`zeroblob(300000000)`, a doubling concatenation) is refused by SQLite before the host allocates it, and `Query` stops with `errResultTooLarge` once the rows it has read pass 16 MiB.
- The `count(*)` rule cannot be narrowed to "through a view": SQLite reports a count over a view as the same column-less read of the base table, with no view name.
- `Release` rolls back a transaction a guest left open, and discards the connection if the rollback fails.

## Grants are exact

An entry's `grants.{mounts,views,services,folders}` must **cover** the manifest's lists (`covers`). Nothing is optional: a manifest asking for more than the entry holds is `needs_approval` and the module is not run. A grant beyond the manifest does not stop it and **stays live** (its view is created), until `POST /extensions/{name}/approve` rewrites the entry's grants to exactly what the manifest it points at asks for (`Manifest.Grants`), re-reading that module and ignoring any body, so an update that adds a view is a new decision. Unknown view, service or folder names (`knownServices`: `serve_file`, `serve_poster`, `ffmpeg`, `library_scan`, `http`; `knownFolders`: `music`, `movies`, `series`, `artwork`, `cache`) fail in the manager (`checkGrants`), not in config, because `internal/db` imports `internal/config`. An unchanged module (same bytes hash, same grants as a set, folders included) keeps its running instance and store across `Reconcile`; a changed one is replaced and the old one is closed when its last in-flight request calls `Release`.

**Every grant confines but one.** A guest reads core through its granted views and files through its granted folders, and has no socket: with `http` it reaches the entry's `hosts` and nothing else (see "The http service"). `ffmpeg` is the exception and is **full trust**: the host runs Streamline's own ffmpeg uncaged, with arguments the guest chooses, so an extension holding it can read and write any file Streamline's user can and reach the network (see "The ffmpeg service"). The SPA's grant text says so (`extensions_service_ffmpeg_help`); nothing in the API asks for a further acknowledgement.

`serve_file` also needs the `book_files` view: the existence check reads `streamline_book_files`, so an extension without it gets a 404 and a WARN naming the cause. `serve_poster` needs the view of the kind it asks for (`books` or `authors`). `send_file` needs no service, only the folder that holds the file.

## Mounts

A manifest mount is `{prefix, auth}` with `auth` either `session` (the ordinary auth middleware runs and the guest sees a `Caller`) or `self` (the middleware lets the path through via `middleware.NewAuth`'s `selfAuth` hook, `Manager.SelfAuthenticated`, and the guest authenticates the request itself). A stopped extension's path passes the middleware too (`SelfAuthenticated` answers true for a `stopped` prefix) **and answers `404`** to everyone, signed in or not, rather than the SPA shell or a redirect to the login page, which a reader app would take for a server: `Reconcile` keeps the prefixes of entries that are not running (their grants' mounts, and their manifest's when it was read) in `stopped`, never a reserved one, or a failed entry granting `/movies` would take that page down.

**The reserved-prefix rule.** A prefix may not be a core route or a first-level SPA route: `reservedPrefixes` in `manager.go`. A spec fails when a directory is missing under `web/app/routes/`, so adding a SPA section forces the decision. `/rest` and `/share` are not on the list: they are the Subsonic extension's. Two extensions cannot hold one prefix; the loser is `failed`.

Two further subtrees are always the host's: `/api/v1/extensions/<name>/cards[/...]` and `/api/v1/extensions/<name>/api[/...]`, both authenticated as the session and dispatched to the module with the path made relative. An API key writes only under `api` (`isExtensionIdentity` in the auth middleware: every other mutation under `/api/v1/extensions`, the management endpoints included, is an identity mutation). A path that reaches either subtree only through a dot segment is a `404`, since the middleware judged its cleaned form.

**`Caller` names the API key, not only the user.** `KeyID` and `KeyName` come from `auth.Claims.APIKeyID`/`APIKeyName`, which `authenticateAPI` sets on the `X-API-Key` path and which no token carries (`json:"-"`); both are zero for a session. A guest keying its devices on `KeyID` needs no device list of its own, and a revoked key simply stops arriving. A session's `jti` is not handed over.

**Account cards.** Core draws one `credential` card per running extension (the first in `account_cards`). `GET /account/extensions` lists them with the caller's state and `/account/extensions/{name}/credential` (GET, POST, DELETE) is the SPA's door to it: the handler calls the module itself (`Manager.Call`, path `/cards/<id>`, the caller as `Caller`) and translates `{set, created_at, last_used_at, last_client}` and `{secret}` into the `AppAccess` and `AppAccessCreated` shapes. A card that does not answer is left out of the list and a `502` on its own endpoint. `settings` cards are the other kind, below.

**The guest never holds a connection while the answer is written.** `Running.call` takes one pooled connection, runs the guest, checks a `serve_file` answer against `streamline_book_files`, and returns the connection before `http.ServeContent` or ffmpeg streams: with a pool of four, four slow downloads would otherwise stall the extension. `serve_file`, `send_file` and `stream_ffmpeg` all push the write deadline 2 min ahead of every write (`slowClientWriter`, `writeChunk`), so a large file to a slow client is served whole and only a client that stops reading is cut; the listener's single 2 min `WriteTimeout` would cut it mid-download.

**What a guest serves cannot script the web UI.** It answers on the app's own origin, so `dispatcher.serve` sets `Content-Security-Policy` (`guestCSP`: `sandbox; default-src 'none'; img-src 'self' data:; media-src 'self'; style-src 'unsafe-inline'`, so a page may play audio from its own origin and run no script) and `nosniff` on every answer, the streamed ones included, and drops the guest's own values for both.

**A cross-origin page reaches an extension through core's allow-list.** `middleware.CORS` answers the preflight of an origin in `server.cors_origins` before auth runs, for every path, so a guest on a `session` mount or the `/api` subtree never sees one and needs no CORS code. A guest on a `self` mount does see the `OPTIONS` of an origin that is not listed, and its own `Access-Control-*` headers are passed through.

Credentials never cross by accident. The `Cookie` header is never handed to a guest; `Authorization` and `X-Api-Key` are withheld on every path that is not a `self` mount (OPDS needs Basic). The guest's `Set-Cookie`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Content-Security-Policy` and `X-Content-Type-Options` response headers are dropped (from `stream_ffmpeg`'s `headers` too), and a status outside 100-599 is a 500.

## Folders

`grants.folders` mounts directories into the guest, per call: `music` (`library.music_path`), `movies` (`library.movie_path`) and `series` (`library.series_path`), each read-only at `/folders/<name>`, `artwork` (`<data_dir>/posters`, read-only, laid out `<kind>/<id>/poster.jpg`) at `/folders/artwork` and `cache` (`<data_dir>/extensions/<name>/cache`, writable) at `/folders/cache`. `Manager.folders` resolves them on **every request**, so an edited library path reaches the next request with no restart. A read-only folder whose directory cannot be stat'ed or is not a directory is left out of `Request.Folders` with a WARN while the extension still answers; `roothealth` is not consulted, so an offline root that still stats as a directory is mounted and its files are simply missing. The cache is created (`0750`) on every request that grants it. A guest maps the host path a view gives it with `Request.GuestPath`; a `music_files.path` or `video_files.path` outside its library folder (a file adopted in place from elsewhere) maps to nothing and cannot be sent.

**Folder access never follows a link out.** The read-only folders are `os.Root`-backed (`mountConfig`), which refuses `..` and any link resolving outside. The cache is `guardFS` over `sysfs.DirFS`: every path is checked through `os.Root.Stat` (a not-yet-existing leaf must not be a dangling link, and its parent must resolve inside), a path that fails the check is `EACCES`, and `Symlink` and `Link` return `EPERM`, so neither a guest nor the host can leave a link there that works. The roots are closed when the call returns.

**The cache** is capped by the `extension-cache-sweep` system job (hourly, `Manager.SweepCaches`, over every `<data_dir>/extensions/*/cache`): past `CacheBytes` (1 GiB) of regular files per extension it deletes the files with the oldest mtime until the total fits; a delete that fails is skipped. It does not look at what is being sent: a file removed while `send_file` streams it stays readable through the open descriptor. Backups never include it (they snapshot `data.db` alone), and `Purge` removes it with the extension's directory.

## send_file

A guest answers `send_file: {path, filename, content_type}` to stream a file from a granted folder. `path` is a host path as the views and `Folder.HostPath` give it; the **host** finds the granted folder holding the cleaned path (`resolveInFolder`), opens it through `os.Root`, and `http.ServeContent` answers ranges. A relative path, a dot segment, a path outside every folder, a link out, a directory or a folder that was not granted is a `404`, with a WARN when no granted folder holds the path. Like `serve_file`, it runs after `Running.call` has returned the store connection. `Content-Type` defaults to `application/octet-stream`; `Content-Disposition: attachment` is set only when `filename` is.

## The ffmpeg service

Service `ffmpeg`. Both forms run Streamline's own binaries, resolved from `ffmpeg.path` by the prober (`Tools`: `FFmpegPath` for ffmpeg, `ResolvedPath` for ffprobe), never one the extension ships. **It is not a sandbox.** The arguments are the guest's, unexamined, and the process runs as Streamline with nothing confining it, so an input or output path, a `file:`/`http:` protocol or a filter reads and writes anything Streamline can and reaches the network. The safeguards below stop accidents and make use visible; they do not confine a hostile extension.

`Running.command` is the one place a process is prepared, in this order of refusal:

1. Not granted: `errFFmpegDenied`, outcome `denied`.
2. A tool other than `ffmpeg` or `ffprobe` (`ffmpeg_run` only): `errFFmpegTool`, `denied`.
3. No binary resolved, or `ffmpeg.enabled: false`: `errFFmpegUnavailable`, `unavailable`. Read per run, so the runtime toggle applies at once.
4. All `MaxFFmpegProcs` (8) slots of this extension in use: `errFFmpegBusy`, `busy`. The slots belong to the `Running`, so a replaced module starts with eight of its own while the old one's runs drain.

Then: arguments are an argv list (`exec.CommandContext`, no shell); the working directory is the extension's cache folder, created for it whether or not `cache` is granted; the environment is Streamline's minus every `STREAMLINE_*` variable (GPU drivers and the locale stay); the process is killed when its context ends (the client went away, a call's deadline, shutdown) and when the extension is retired (disabled, replaced, removed: `Running.retiring`), with `WaitDelay` 5 s for its pipes. Every run, and every refusal, is logged at INFO (`Extension ran ffmpeg`, with the tool, the full argument list, the exit code and the duration), counted on `streamline.extension.ffmpeg{extension,tool,outcome}` (`tool` is `ffmpeg`, `ffprobe` or `unknown`, never the guest's string; `outcome` `ok|failed|killed|unavailable|busy|denied`) and spanned as `extension.ffmpeg` with `ffmpeg.outcome`, the span in error on anything but `ok`.

**`ffmpeg_run`** (`sdk.FFmpeg(tool, args...)`) runs to completion inside the call, under the request's 30 s, while the guest still holds its store connection, so it is for probes and short conversions into the cache. It answers `{exit_code, stdout, stderr, error}`. stdout is capped at `MaxResponseBody` (16 MiB): past it the run is killed and `error` says so; stderr keeps its last 64 KiB. A refusal, a run cut short (`the run was cut short: …`) or a start failure sets `error` with the rest empty; a non-zero exit is not an error, it is `exit_code` with both outputs.

**`stream_ffmpeg: {args, content_type, headers, fallback}`** runs after the guest has returned and its connection is back, and copies ffmpeg's stdout to the client in 32 KiB chunks, flushed, each write pushing the deadline 2 min ahead, so it lives as long as the client reads. Nothing is written until the first byte is in hand, which is what lets a failure become something else:

- Not granted: `404`, whatever `fallback` says.
- Unavailable, busy, or a process that does not start: `fallback` when set, else `503` with `Retry-After: 5`.
- No byte within 30 s (`RequestTimeout`, then killed) or the process ends having written none, whatever its exit code: `fallback` when set, else `502`. The stderr tail goes in the WARN.
- After the first byte the answer is `200` with `content_type` (default `application/octet-stream`) and the guest's headers minus the dropped ones, and no range support. A client that stops reading for 2 min or disconnects kills the process (`killed`); a process that fails mid-stream ends the body short (`failed`).

`fallback` is a `send_file` and is served by the same `sendFile`, so it needs the folder holding it, and it is served after the run's slot is released, so a long download of the original holds none.

## The http service

Service `http`, host function `http_request` (`sdk.Fetch`, `fetch.go`). The host makes one request for the guest and hands back `{status, headers, body}`, or `error` when it made none or got no answer. Two things decide whether it is made, in this order: the `http` grant, then the URL's `host:port` (lower-cased) being in **`extensions[].hosts`**. That list sits on the entry beside `grants`, not in them, and is **file-only**: a manifest cannot name a host (the address is the deployment's, not the module's), `approve` rewrites `grants` alone, and no API writes it, since an API that could add a host could point a guest at anything Streamline reaches. `allowedHosts` reads it from the config on every call. A bad entry in the file is never a failed boot: it simply matches nothing.

**Extism's own guest HTTP (`Manifest.AllowedHosts`) stays off.** It matches the hostname without the port, so `localhost` would open every local service, and it follows redirects through `http.DefaultClient`, so a listed host could send the call anywhere. `guestHTTP` shares `otelx.HTTPClient`'s transport and never follows a redirect (the 3xx is the answer). The call runs under the request's 30 s while the guest holds its store connection, and the answer is capped at `MaxResponseBody` (16 MiB).

## The library scan service

Service `library_scan`, through `Manager.scanner`, wired in `internal/server/library_scan.go` as `libraryScanner`, which is the `drift-check` job (the one that stats every tracked file). `scan_status` (`sdk.ScanStatus`) answers `{scanning, count, last_scan}`: whether `drift-check` is running, the number of tracks holding a file whose `missing_since` is NULL, and the job's `last_finished_at` (null before its first run). `scan_start` (`sdk.StartScan`) is `scheduler.RunNow("drift-check")`, a manual run, and returns once it is started; one already running (`ErrJobBusy`) is not an error. A call without the grant logs a WARN and answers `library_scan is not granted to this extension`; the SDK returns any `error` as a Go error.

## Settings cards

An `account_cards` entry with `kind: settings` carries `fields`, each `{id, kind, label, min, max}` with `kind` `switch` or `number` (`min`/`max` bound a number and mean nothing on a switch). `parseManifest` refuses a settings card with no fields, an empty or repeated field id, another kind or a number with `min > max` (`ErrBadManifest`, so the entry is `failed`). The SPA does not draw them; two admin endpoints read and write them for any account:

- `GET /users/{uid}/extensions` calls `GET /cards/<id>` on every running extension's settings cards, with the admin as `Caller` and the account as `Request.TargetUser`, and lists `{extension, card, title, fields, values}` from each answer's `{"values": {...}}`. A card that errors, answers `>= 300` or answers something else is left out with a WARN. `403` for a non-admin, `404` for an unknown user. Readable with an API key.
- `PUT /users/{uid}/extensions/{name}/cards/{card}` takes `{"values": {...}}`, checks it with `AccountCard.CheckValues` **before** the module is called (every key a declared field, a switch `true` or `false`, a number a JSON integer within `[min, max]`; a key left out is the guest's to leave alone) and sends it as `PUT /cards/<id>` the same way. `204`; `403` non-admin; `404` unknown user, an extension not running or a card it does not declare; `422` `code: card_values_invalid` with the check's message; `502` when the module errors or answers `>= 300`. It is an identity mutation (under `/api/v1/users`), so an API key is refused, and it writes the extension's database, not the config, so a `read_only` instance allows it.

**`TargetUser` is set only by those two endpoints, and they are the only way to a settings card.** `Manager.route` answers `404` for `/api/v1/extensions/<name>/cards/<id>` when `<id>` is a `settings` card (`settingsCardPath`): through that subtree the guest would see any signed-in user as `Caller` with no `TargetUser` and no `CheckValues`, and a guest that forgot to refuse it would let a member write their own limits. A credential card stays reachable there, since it is the caller's own.

## Where things live

- Config: `extensions[]` (`config-surface.md`). Source is an absolute path or an `https` URL with a required `sha256` (checked on API writes and by `resolveSource`, not at config load, so a bad one in the file is a `failed` extension); a URL is fetched once and kept at `<data_dir>/extensions/_sources/<sha256>.wasm` (`_sources` cannot be an extension name), capped at 32 MiB.
- Data: `<data_dir>/extensions/<name>/data.db`, and the cache beside it. `DELETE /extensions/{name}?purge=true` removes the directory (`Manager.Purge`, which refuses a name with a separator or a leading `_`).
- Backups: the `database-backup` job snapshots each configured extension's file, when it exists, with `dbbackup.SnapshotFile` into `<backups>/extensions/<name>`, pruned with `backup.retention.scheduled`, after core's snapshot and under the same skip decision. A failing extension is a WARN and never fails the job.
- Telemetry: spans `extension.reconcile`, `extension.request`, one `extension.sql` per statement, one `extension.ffmpeg` per run; counters `streamline.extension.requests{extension,outcome}` and `streamline.extension.ffmpeg{extension,tool,outcome}`, histogram `streamline.extension.sql.duration{extension,db.operation.name}` (seconds, recorded beside each `extension.sql` span, since the pool has no otelsql wrapper to do it). The extension's name is a metric attribute, never a path or an id.

## The view catalogue

`db.ExtensionViews()` is the only definition (`internal/db/extension_views.go`): each entry has the view's name, the description shown when it is approved, its `Bundle`, the ordered column list a guest may rely on, its SQL and the core tables it reads. **A view's SQL changes in the same commit as the migration that moves the columns it reads**; the integration spec in the same file builds a real core database through `db.Open`, checks every view's columns equal its list in order, checks that no column is named `password_hash`, `password`, `device_email`, `email` or `path`, and checks that no row value carries a seeded email or secret. A new view is a contract: guests read it by name and column, so a column is added, never renamed.

**Three named exceptions**, each its own entry in the spec's `allowed` map, never a pattern: `user_logins.email` (its grant text says it), and `music_files.path` and `video_files.path` (absolute, as Streamline stores it: the guest opens it through the `music`, `movies` or `series` folder and hands it to `send_file` or ffmpeg, so the path is the point). `user_logins` is also the one view the row-value check skips. No view carries a secret.

`ExtensionView.Bundle` groups the views one kind of guest is granted together, and the API returns it on each view (`ExtensionViewInfo.bundle`); the manifest still names views one by one. `music` (`artists`, `artist_members`, `albums`, `album_artists`, `tracks`, `music_credits`, `music_files`, `genres`) `books` (the five book views) and `video` (`movies`, `series`, `seasons`, `episodes`, `video_files`), or empty (`users`, `user_logins`). `music_files` and `video_files` list missing files too, flagged `missing`; a `video_files` row belongs to a movie or an episode, never both, and its probe columns are NULL until the file was probed. `music_files.sample_rate` and `bit_depth` are always NULL: `MediaFile` has no column for either. Adding an identity-adjacent column to `users` is a separate view with its own grant text, not a widening of `users`.

## OPDS and Subsonic are projects of their own

Both are extensions in repositories of their own (`Streamline-HQ/streamline-opds`, `Streamline-HQ/streamline-subsonic`); nothing in this repository builds them, and core holds no column, table or view for either: tokens, passwords and everything else an extension keeps are in its own database. Subsonic's host needs are the folders, the cache, `send_file`, the ffmpeg and library scan services, the settings card and the free `/rest` and `/share` prefixes above.
