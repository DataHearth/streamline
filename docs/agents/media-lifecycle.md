# Media lifecycle & library queries

> **Read before touching** episode/movie status transitions, `internal/events/`, `internal/db` list queries, the `media-probe` job, or the re-identify handlers.
>
> **Covers** — ffprobe columns and what `probed_at` guarantees, the `MediaEvent` table and its hooks, cast ingest and person enrichment, re-identifying a row in place, every path that marks an episode in-flight, and the SQL push-down behind the series list.
>
> **Load-bearing** — a migration adding a probe column nulls `probed_at` in the same file; five places split aired from unaired and all five must agree; every grab path must mark its episodes — adoption included, which lands at `importing` and not `downloading` — and `inFlightEpisodeStatuses` is the one list the orphan sweep reads; person enrichment runs *outside* the credits transaction and is enriched once per person, ever.

## FFmpeg & media probe
- `ffmpeg.enabled` (default true, runtime-toggleable) and `ffmpeg.path` — a **directory** holding the binaries, not a binary path; empty resolves via `$PATH`. `path` is read once at boot into the long-lived `Prober`, so changing it needs a restart; `PATCH /config/ffmpeg` marks the global restart flag only when `path` changes, never for `enabled` alone.
- `internal/ffmpeg` is a leaf package owning discovery of **both** binaries (each optional on its own: `Available()` is ffprobe, `FFmpegPath()` is ffmpeg), `Probe`/`ProbeAudio` via ffprobe and `TranscodeAudio` via ffmpeg (the Subsonic stream); the video transcode worker takes `FFmpegPath()` from it. Enabled but ffprobe missing is a **graceful degrade, never a boot error**: imports proceed on filename parsing as before, nothing is stored, and the health surface reports it via `ffmpeg_warn` on `SystemInfo` (absent when `enabled` is false — the operator opted out). ffmpeg missing raises no `ffmpeg_warn`: the transcode worker logs once at boot and stays idle, and Subsonic streams the original.
- Twelve optional `MediaFile` columns (`container`, `duration_seconds`, `video_codec`, `width`, `height`, `audio_codec`, `audio_channels`, `bitrate`, `audio_tracks`, `audio_langs`, `sub_langs`, `probed_at`). `probed_at IS NULL` means never probed; a *failed* probe still stamps `probed_at` so the row isn't retried forever — which is why `ContextFromRow` gates the stream fields on `probed_at` rather than on the values, an empty `audio_langs` being both "the probe found no tagged track" and "nothing ever looked". `audio_langs`/`sub_langs` are **comma-joined text, not a JSON array**: ent decodes a JSON field on every scanned row — the cost that eventually got `Movie.cast` normalized out into `persons`/`credits` — and these sit on the same list paths. `sub_langs` excludes forced tracks — a forced subtitle carries signs and foreign dialogue, not the script, so counting one reports a dub as subtitled.
- **`dynamic_range` is the one exception to the rule below**: it is nillable and read only by the stats, so NULL says "not read yet" on its own, and the backfill selects it beside `probed_at IS NULL`. Unstamping would have turned every stream column unknown, and quality scoring with them, for the days the backfill takes at 25 rows per 15 minutes. A failed probe writes `""` so the row is not retried forever.
- **A migration adding a probe column nulls `probed_at` in the same file** — precedent `20260902141241_add_media_file_stream_columns`. Every reader takes a stamped `probed_at` as "all twelve columns were recorded", and a schema change is the one thing that can break that: ent maps a NULL text/int column to `""`/`0`, so a row probed before `audio_tracks`/`audio_langs`/`sub_langs` existed read as a confident "one audio track, no languages, no subtitles". The builtin `multi-audio` carries an `audio_tracks >= 2` arm and every real profile scores it, so on the first boot after that migration every MULTi release beat every file in the library by that margin — a library-wide upgrade with no config change behind it. Unstamping returns those rows to never-probed, which reads as unknown (the pre-feature baseline, where `comparableTo` drops the language and multi-audio formats from **both** sides), and the `media-probe` backfill refills the columns at its own pace; the price is `media_info` being absent in the API and the UI until a row's turn comes. `Nillable()` columns with nil-gated readers, a separate `streams_probed_at` marker, and a `video_codec != ''` heuristic in the backfill predicate all buy the same guarantee and are unnecessary next to one `UPDATE`.
- The importer probes the **source** file before transfer and attaches the result. Disabled or a missing binary means the import proceeds exactly as without this feature; a probe *error* now holds the record (see below) instead of importing blind.
- The `media-probe` backfill job (`internal/library/hygiene`, schedule key `schedules.media_probe`, default `15m`, 25 rows/tick oldest-first) fills in every movie and episode row the importer doesn't instrument — adoption, orphan scan, bulk import. Track and book rows are never selected (`ListUnprobedMediaFiles`): the probe reads a video stream, so every audio file failed it with `no video stream`, one WARN per track of each new album, and nothing reads the probe columns outside video. It no-ops when ffmpeg is disabled or the binary is missing, so the runtime `enabled` toggle takes effect without a restart. A file that fails `os.Stat` is skipped and NOT stamped; the drift-check job owns missing files, not this one.
- REST: a nullable `media_info` object on `MediaFile` and `Episode` (absent until probed, and absent when the probe failed); `GET`/`PATCH /api/v1/config/ffmpeg` (admin-only) returns `{enabled, path, found, resolved_path, restart_required}`, where `found`/`resolved_path` are derived from the process's live prober, not the config on disk.
- **Stream data is aggregate, not per-track.** `media_info` carries `audio_track_count`, `audio_languages` and `subtitle_languages` — a count and two language sets, which is what the quality engine can compare. Per-*track* enumeration (each track's codec, channels, title, forced flag) is not in the API and the SPA carries no type for it. The field is `audio_track_count` rather than `audio_tracks` so it never reads as a per-track array.

## Media events
- One table, `MediaEvent` (was `MovieEvent`, renamed with a data migration that carries the rows across — `20260824081500`). Seven **optional** owner edges: `movie`, `episode`, `tv_show`, `artist`, `album`, `book`, `book_series` (the last four added by `20261021083050`, whose down is hand-written: atlas reverses a SQLite rebuild by dropping a temp table that no longer exists); exactly one is set and `events.Record` refuses a row with none. The old table was movies-only with a *required* movie edge, so every series grab, import and drift silently recorded nothing — the hooks bailed by design (`downloadRecordOwner` still walks movie-then-episode, it just no longer gives up).
- The lifecycle types are written by ent mutation hooks (`internal/events/hooks.go`, installed by `Register`); the rest are direct `events.Record` calls. Hooks: `DownloadRecord` create/status → `grabbed`/`download_completed`/`download_failed`/`import_held_for_review`; `MediaFile` create → `imported`, delete → `file_removed`; `Movie`/`TVShow` create → `added`, `monitored` changed → `monitoring_changed`; `ImportScanFile`/`ImportScanShow` outcome=failed → `import_failed`. Direct calls: `drift_*` (drift job), `searched` (searchers), `file_renamed` and `reidentified`/`metadata_refreshed` (`internal/media/{movie,tvshow}`), `transcode_*` (`transcoding.Worker`), `download_cancelled`/`grab_widened` (`download.Manager`), `request_approved` (`request.Service`). `Record` runs inside the caller's transaction.
- **Bulk series operations aggregate to one series-scoped event per operation, not per file or episode.** `file_renamed` (series rename pass), `imported` (bulk-import series commit and season-pack import; the per-episode hook stays quiet under `events.SuppressImported(ctx)`, single-episode imports retain their hook event), `grab_widened`, and `drift_detected`/`drift_confirmed` each record one event with `seasons` (sorted unique season numbers) and `episodes` (episode count) in the payload. Drift folds an album's track files the same way (one event on the album, `tracks`) and one slot's book files (one event on the book, `files`, `book_kind`). `SuppressImported(ctx)` works alongside the existing `SuppressFileRemoved(ctx)` to let the caller choose whether the hook records — bulk operations use it to record their own series event instead. Why: a multi-file series operation (a show re-import, rename pass, or season-pack grab) would otherwise fill the feed with hundreds of identical rows, burying everything else.
- **`download_completed` fires on the transition to `importing`, not to `completed`.** `StatusCompleted` is stamped by `RecordImportSuccess`/`RecordEpisodeImportSuccess` — i.e. once the file is already filed, at the same moment the `MediaFile` create hook records `imported`. Hanging it off `completed` produced two rows for one moment and left the hours between `grabbed` and `imported` — the actual download — with nothing in the feed at all.
- **`file_removed` resolves its owner *before* `next.Mutate`.** A delete hook that waits until after has no row and no edges left to read. `doomedMediaFiles` queries the doomed ids with their movie/episode edges up front; a file whose owner is itself being deleted comes back ownerless and is skipped, since that event would cascade away with the owner anyway. The drift sweep passes `events.SuppressFileRemoved(ctx)` so a disappearance it already diagnosed as `drift_detected`/`drift_confirmed` does not also land as a bare, unexplained removal.
- **`metadata_refreshed` only fires when the provider actually moved something** — a changed title, or episodes added or pruned. `RefreshStale` runs the same code over every stale row on a tick, so an unconditional event would write one row per title in the library and bury a day of real activity.
- **A season or series monitor toggle is one event carrying an episode count, not one event per episode.** `CascadeShowMonitored` and `CascadeSeasonMonitored` return what they touched and `tvshow.Service` records a single row from it; the movie twin stays in `movieHook` because a movie has nothing to cascade to. `tvShowHook` is deliberately create-only — the hook sees the show row's own update and cannot know the count, so leaving monitoring in it would have written a countless row *and* fought the service's. A season has no scope of its own: the row is series-scoped with the number in `seasons`, which is the shape `eventSubject` already renders as *Show · Season 3*. A single-episode toggle is one deliberate action and still gets its own episode-scoped row.
- **A failed event write does not fail the mutation it records.** The hooks run *after* `next.Mutate`, so by the time anything can go wrong the write they describe has already happened. Returning the error made it the mutation's: a locked events table or a bad payload marshal surfaced as "importing this file failed" or "download status update failed", with the real cause wrapped several layers down — an activity-feed problem dressed as a library one. Every hook now goes through `recordAux` / `auxFailure`, which log and let the mutation stand. `events.Record` logs, spans (`events.record`) and counts its own failures on `streamline.events.record.failures`, so the signal is not lost, only moved off the caller's error path.
- `drift_detected` fires on the **first** tick that cannot stat a file, `drift_confirmed` when the grace window expires. `MediaFile.missing_since` carries both: `MarkMediaFileMissing` sets it and reports whether *this* call was the one that did, the grace window counts from it, and `ClearMediaFilesMissing` clears both clocks when a file comes back. **A present file that never went missing gets no write.** The clock used to run from a `last_seen_at` stamped on every row each tick, which rewrote the whole table into the WAL every 15 minutes (over half a million row updates a day on the homelab) and, after downtime longer than the window, let a volume not yet mounted revert the library on the first tick. Past the window the first tick stamps `missing_confirmed_at` (the edge `drift_confirmed` hangs off, since a time comparison cannot say "first tick past"), and the row and its owner's status stay until `library.missing_file_redownload_after` counted from there (`LibraryConfig.MissingFileWait`: `0` confirms and reverts in one tick, `off` and an unreadable value never revert, so a hand-edited typo cannot delete rows). A row with no owner skips the wait: nobody is waiting on it. When the wait ends the row goes in one transaction with its owner's status and `drift_reverted` is recorded after it: a movie and an episode revert to `wanted`, an album only from `available` (a failed or in-flight one keeps its status) and under its file lock, a book slot only from `available` and only once it holds no file, since the importer refuses a grab into a slot holding one (`ErrDestExists`) and a partial audiobook at `wanted` would burn downloads. **An owner holding another file on disk (`HoldsOtherFile`) keeps its status**: the orphan scan adopts a renamed movie during the wait (`MovieHasMediaFile` ignores missing rows for this), and an unconditional revert would download what the title already has. A confirmed file that returns records `drift_recovered`.
- **`missing_since` set means nothing touches the file on its own schedule, in grace or confirmed.** The tag sync and edit check, `TagAlbum`, the transcode worker (deferred, no attempt spent), the unprobed list, OPDS and all four rename plans skip it (an audiobook folder with a missing file is left whole, since it moves whole, and a skipped row keeps its stored path so a returning file heals). **`db.PresentFiles` is the one answer to "does this title hold a file":** the import refusal gates, torrent adoption and the pending preview, the upload gates, the has-file flags of the release previews, the RSS upgrade arms (a better release must not start a download during the wait, and a missing file's quality is no bar to clear), the cover and sidecar folders. Its row is replaced like any other since `setAside` already skips an absent file, and an import finding the row already taken by the wait's end carries on (`unlessGone`). A manual pack grab keeps an episode whose file is missing in its selection (`packEpisodes`) without marking it, so it stays `available`. The manual transcode scan leaves these rows out, and a delete with files does not report one as "not deleted" (`library.RemoveTrackedFile`). The marks read `missing_confirmed_at` only, and `db.AllConfirmedMissing` keeps a title with a present file beside a stale row unmarked. **A confirmed row whose owner holds another file goes at the end of every sweep, whatever the wait says** (`ListReplacedMissingFiles`, one read, an audiobook left out since its slot is a folder and the rest of the book replaces nothing): no status moves and nothing downloads, so there is nothing to wait for, and under `off` it would never go. Reverts leave a title on its way in alone (`revertMovieStatus` and its episode twin skip `downloading`, `importing` and `paused`), since the record's outcome moves it. A path migration re-points a missing row too, or a file returning under the new root could not heal. **`ForgetMediaFile`** removes a row and unmonitors (an episode and an album pinned too, a book only that slot), sharing its status statements with the `DeleteMediaFileAndRevert*` functions and keeping the status of an owner still holding a file; its `file_removed` event is not suppressed, since it is the title's history. `ForgetMissing` refuses an offline root with `*roothealth.OfflineError`, because under one every file reads as gone.
- **A root that looks gone costs nothing** (`internal/library/roothealth`, registered in `wire.go` like `events.Register`; unregistered, every root is online). A root is offline when it has tracked files, by owner type and `book_kind` rather than path prefix, and none of at most 20 sampled rows can be stat'ed, whatever the error. Rows confirmed missing stay out of the sample while any other row exists (`LiveRootFilePathAt`, `CountLiveRootFiles`), or enough of them would read as an outage; when they are all that is left they decide alone, or an unmounted volume would let their wait run out. The sample is spread over the rows in index order, both ends included (the partial owner index, and for a book root the partial `book_kind` index with no `HasBook` term beside it: ordering by id made SQLite scan the table, 509 reads for one `/system/info` on a cold process against 19, and a `HasBook` term did the same on a library holding one kind of book, 746 against 16), so a deleted batch of old files is not an outage, and stops at the first file found, so a healthy root is one query and one stat. No marker file, threshold or timeout, and nothing cached. `drift-check` computes the offline roots once at sweep start and leaves their rows out in SQL, so no clock starts and no revert happens. A clock can still be old, because an outage that began mid-sweep started it and offline ticks never clear it, so the past-grace branch asks again before it reverts; a mount dying mid-sweep starts clocks at most, and they clear when the file is seen again. Every file job, the importer, automatic grabs and by-hand changes ask the same question. The two exits are path migration and `hygiene.AcceptMissing`, which removes only not-found rows, with the drift reverts and events, ignoring grace. It runs one walk at a time, from its response's `Visit` so it can clear the listener's `WriteTimeout`, and outlives a client that gave up. By-hand refusals on books go by the roots that book or series actually holds (`db.BookFileRoots`), and a book import commit by its rows' slots, so an ebook outage never holds an audiobook back. User docs: "A library root is offline" in `docs/wiki/Troubleshooting.md`.
- `searched` is recorded **once per search invocation, at the scope it was issued at** — not once per item. `EpisodeMissingSearcher.searchShow` tallies every season it touched and writes one series-scoped row (`{seasons, episodes_searched, grabbed, packs}`); the SPA renders `Show · Season 3` when exactly one season is in the list. Per-episode rows would be thousands per tick on a real library. Movies record one per `SearchOne`, in the same defer as the outcome metric. **Browse-releases endpoints record nothing** — they grab nothing, and the grab that follows already fires `grabbed`.
- `ActivityEvent` carries `movie` / `episode` (an `EpisodeRef` with `series_id`) / `series` (a minimal `SeriesRef` — never the full `TVShow`, which drags the season tree) / `artist` (`ArtistRef`) / `album` (`ActivityAlbumRef`, with its artist) / `book` (`ActivityBookRef`, its `slot` read from the payload's `book_kind`, its series for a volume) / `book_series` (a `SeriesRef`). `GET /activity` takes `series_id`, matching both the show's own rows and its episodes', and `artist_id`, `book_id`, `book_series_id` the same way (an artist takes in its albums', a book series its volumes').
- **Music and books mirror the series split one level up.** `ScopeAlbum` and `ScopeBook` carry the lifecycle — `downloadRecordOwner` walks movie → episode → album → book → artist, so a discography pack (an `artist` edge plus the `albums` many-to-many) is one `ScopeArtist` row. **The `MediaFile` create hook leaves track and book files alone**: the album importer (`recordAlbumImported`, also once per album a pack fills, `source: pack`), the book importer (`recordBookImported`) and the two bulk-import committers each record one `imported` per album or book slot after the files are written, since an album is a dozen files and an audiobook a folder. The delete hook folds track and book files per owner within one mutation (`files: n`, or `path` for one). `added` comes from `artistHook`, `bookHook` (standalone books only — a series add writes a row for every position, most of them stubs) and `bookSeriesHook`; the stub albums an artist add seeds get none. `searched` is one row per `music.searchAlbum`, per `book.searchSlot` (payload `book_kind`) and per `searchSeriesVolumes` pass (series-scoped, `volumes_searched`/`grabbed`). `download_cancelled` is recorded by `download.Manager.CancelQueueItem` for every owner (`cancelledOwner`, the same walk; `FindActiveDownloadRecordByID` loads the owner ids for it), episodes included. The cancel also reverts the media in the same call — the movie through `RevertMovieToWantedIfNoFile`, every episode, album and book slot through `ReconcileStrandedMedia`, the pass `PurgeRecordForHash` already ran — instead of leaving them `downloading` until the next download-monitor tick, where every search skipped them; a failure there is logged and left to that tick, since the record is already gone. `monitoring_changed` is recorded by the services, never a hook, because the policy re-applies cascade in one statement a hook cannot count: `music.SetArtistMonitor` writes one artist row with `albums` (on + off, which `db.SetArtistMonitor` now returns), `SetAlbumMonitored` one album row, `book.PatchBook` one book row only when a slot's flag actually moved, `PatchSeries` one series row with `volumes` (`db.SetSeriesMonitor` returns the count). `POST /music/monitored-types/apply` records nothing: it is a library-wide settings catch-up, not a choice about any one artist. `importScanAlbumHook`/`importScanBookHook` file a failed music/book bulk-import entry as `import_failed` against its created-or-existing album or book, and a failure that resolved none has nowhere to hang, like the show twin.

## Cast ingest & person enrichment
- Cast is written by `db.ReplaceCast` / `replaceCast` **inside the caller's transaction** — `CreateMovie`, `CreateTVShow` and the two metadata updates each fold the credits into the one they already hold, because SQLite has a single writer and a nested `db.client.Tx` is a different connection blocking on its own caller's lock. An empty incoming list is a **no-op, not a wipe**: cast comes from a different provider call than the rest of a title's metadata, so "no cast" is far more often a failed call than a title with no actors.
- `resolvePerson` resolves identity in order — `tmdb_id`, then `tvdb_id`, then the folded name — and the order is load-bearing: a provider id *is* an identity, a name is only a guess at one. Ids only ever go 0 → non-zero; rewriting a non-zero id would silently re-point every existing credit at somebody else.
- **The biographical fetch runs after that transaction has committed, never inside it.** `Service.enrichPeople` in `internal/media/{movie,tvshow}` is called once the create/metadata-update call has returned — from `Add`, `applyMetadata` (so `RefreshStale` and `Reidentify` both get it) and the series' `RefreshOne`/`Reidentify`. Provider round-trips issued from inside the credits transaction would hold the single write lock across the network and stall every other writer in the process for as long as the slowest one took. `internal/db` deliberately gains no dependency on the providers for the same reason: it exposes the work list (`PeopleNeedingDetails`) and the write (`SavePersonDetails`), and the service layer — which already holds the clients — owns the orchestration.
- **A person is enriched once, ever**, keyed on `Person.details_fetched_at`. `PeopleNeedingDetails` returns only the title's credited people whose stamp is nil, so an actor credited on thirty titles costs one provider call and not thirty. `SavePersonDetails` is the only thing that sets the stamp, and only a *successful* lookup reaches it.
- Provider by id, per service: the movie service holds the TMDB client and enriches people with a `tmdb_id`; the series service holds TVDB and enriches people with a `tvdb_id`. A person carrying only the other provider's id is left to whichever title on that side credits them, and one with neither id has nothing to look up. TVDB supplies no `known_for` and usually no socials — empty there is the provider, not a failure, and nothing is synthesised to fill it.
- **Nothing in the pass can fail the import.** The title and its cast are already committed and matter far more than a biography: a failed work-list query or a failed lookup is logged at warn and the pass carries on, leaving `details_fetched_at` nil so the next metadata refresh retries. The fetch is bounded at `personDetailConcurrency` (4) — a series is ~15 people and strictly serial is a visible pause on the add — and every worker defers `observability.RecoverPanic`, per the repo-wide rule that an unrecovered panic in a background goroutine takes the process down.
- The eight fields (`biography`, `known_for`, `birthday`, `deathday`, `place_of_birth`, `imdb_id`, `instagram_id`, `twitter_id`) ride on both `db.Person` and `db.PersonCredits` through the embedded `db.PersonBio`, mirroring the spec's `PersonBio` component that `Person` and `PersonCredits` `allOf` into. All are optional and **empty is omitted, never `""`** — the SPA treats absent and empty the same. `birthday`/`deathday` stay provider-format strings: providers return partial and malformed dates, and a date column would force a lossy parse at ingest.

## External ids
- `external_ids` (`ent/schema/externalid.go`, `internal/db/external_ids.go`) holds **other sites' ids** for a library row: `source` (an enum, which `metadata.Source*` names the same) and `value`, plus one optional owner column per kind (`movie_id`, `tv_show_id`, `artist_id`, `album_id`), exactly one set by the writer, the `Credit` pattern. **The provider's own id is never a row** (`movies.tmdb_id`, `tv_shows.tvdb_id`, `artists.mbid`, `albums.mbid` stay columns, since they are the identity), and neither are an artist's `wikidata_id`/`deezer_id`, which the overview and the photo read. The artist detail folds them into the same wire object.
- Sources: a movie's IMDb and Wikidata ids (TMDB `GetMovie`, `append_to_response=…,external_ids`), a series' IMDb, TMDB and Wikidata ids (TVDB `remoteIds`, `seriesRemoteIDs`, a value not in its site's shape is dropped), and MusicBrainz url relations (`mbURLIDs`): for an artist from the url-rels `GetArtist` already requested; for an album from the release-group call (`+url-rels`: Wikidata, Discogs master, AllMusic, RateYourMusic) and the release call (`+url-rels` on **both** the heavy and the light inc: Spotify, Deezer, Bandcamp). No request was added for any of it.
- `replaceExternalIDs` runs **inside the caller's transaction** (the creates, the metadata updates, `RefreshArtist`, `SetAlbumHydration`), like `replaceCast`, and replaces the owner's set wholesale, so a re-identified title never keeps the previous one's ids. **A nil map writes nothing**: `storedDetails` re-hydrates an album MusicBrainz no longer knows from its stored facts, and its links stay. A source the enum lacks is logged and dropped, never fatal.
- Each owner column leads a unique `(owner, source)` index, which serves the single read (`TitleExternalIDs`), the batch read (`ExternalIDsFor`: every album of an artist in one query, which the artist detail needs because the SPA stops fetching `GET /music/albums/{id}` once the track credits are in) and the cascade. `(source, value)` is not unique and is there for finding a row by any of its ids.
- **The links backfill** (`music.Service.backfillLinks`, `internal/media/music/links.go`) is how rows stored before the table existed get theirs. `Artist`/`Album.links_fetched_at` is the marker: `CreateArtist`, `RefreshArtist` and `SetAlbumHydration` stamp it whenever their `ExternalIDs` is non-nil, and `NULL` is the backlog. It runs at the end of `music-metadata-refresh`, to the end of the backlog, at `metadata.Background` priority, with `MusicProvider.ArtistLinks` (`/artist?inc=url-rels`) and `AlbumLinks` (`/release-group?inc=url-rels`, then `/release?inc=url-rels` for `release_mbid`, a 404 there keeping the group's links). It never uses the refresh or the hydration, whose release call is the heavy one. The listings page by id after a cursor, so a row that failed is not asked again in the same pass. A `404` stamps the row with its links left alone. A rate limit is waited out (`fetchLinks`, up to 3 times, 5 min a wait), and a longer one ends the pass. Only hydrated albums are listed, since a stub gets its links with its tracks. Movies and series need no backfill: their refresh jobs revisit every title older than 24 h each day.
- They go out as one `external_ids` object (`ExternalIds` in the spec, `toExternalIDs` in `restapi`), which also repeats the row's own provider id (`withOwnID`: `tmdb`, `tvdb`, `musicbrainz`, `hardcover`; `metadata.SourceTVDB`/`SourceMusicBrainz`/`SourceHardcover` are wire-only names, never stored) so a client finds every id in one place. The detail reads always attach it (`GetMovie`, `GetSeries`, `music.Service.Detail`/`AlbumDetail`, `GetBook`, `GetBookSeries`, the lookup details); `GET /movies`, `/series`, `/music/artists` and `/books` only with `with_external_ids=true` (`pageExternalIDs`: one `ExternalIDsFor` over the page; an artist's columns are folded in by `music.ArtistExternalIDs`; the shelf reads `ShelfRow.HardcoverID`, a column of both arms of the union, with no query). A book or a series carries only `hardcover`; its other ids are its editions'.
- **Book editions** are the fifth owner (`book_edition_id`): Hardcover's `book_mappings` hang off editions, never books. `book.Service.backfillEditionLinks` (`internal/media/book/links.go`), at the end of `book-metadata-refresh`, reads them through `BookProvider.EditionLinks` (`hardcover_links.go`) for **only the editions a slot follows** (`db.ListEditionsAwaitingLinks`: `links_fetched_at` NULL and `ebook_of`/`audiobook_of` set — the inverse edges of the slot pointers, no column of their own). A popular book has hundreds of editions, and the batch query is deliberately left alone, since mappings on its ~81 edition rows would multiply its payload. One request per 100 editions, every platform its own aliased `book_mappings` with its own limit and `state: normalized` (Hardcover keeps StoryGraph strings, AbeBooks image URLs and Open Library works in the same column; the shape checks drop them), the platform by `platform_id` (1 Goodreads, 3 Open Library, 18 Wikidata, 20 Google, 32 Audible), depth 2. A verified mapping wins, then the oldest. Audible keeps one mapping per region with different ASINs, so the value is `ASIN:region` for `library.book_language`'s store, else `us`. **An edition is read once, ever**: it is stamped links or none, nothing runs on an add, a refresh or a lookup, a 429 or the scan reserve ends the pass, and the cursor keeps a failed batch out of the rest of the run. `GET /books/{id}` reads every edition's rows in one `ExternalIDsFor`; the SPA links Goodreads and Open Library by id, then by ISBN-13, then by search.
- The SPA builds every URL in `web/app/lib/external-links.ts` and renders them with `ExternalLinks.svelte`, grouped `database | listen | stores | reviews`. A site with no id-keyed address gets a title search with `search: true`, drawn with a magnifier. SensCritique and AlloCiné are only offered in the French locale.

## Re-identifying a library entry
- `POST /{movies,series}/{id}/reidentify` (admin) repoints a row at a different provider id **in place**: same row id, same files, same download history and requests. 409 when the target id is already in the library (`tmdb_id`/`tvdb_id` are unique — merging two entries is a different feature and was deliberately not built), 400 on zero or unchanged, 404 unknown.
- Movies: `SetMovieTMDBID` → refresh metadata → refetch the poster (it is cached by **row id**, so it keeps showing the old title until replaced) → handler runs `renamer.Apply`.
- Series: the files are **detached before the tree is reconciled**, and that ordering is the whole feature. `ReconcileEpisodes` deletes seasons/episodes the provider no longer reports and their `media_file` rows cascade; with a swapped tvdb id that is every episode of the old show, so a naive set-id-then-`RefreshOne` untracks the library it was asked to repair.
- **A metadata refresh never deletes files.** `RefreshOne` logs the paths of pruned episodes' files at WARN and leaves them on disk, untracked. The listing is third-party data a member can trigger a refresh against, and a valid-but-short one used to delete library media; a bulk-import scan re-adopts what is still wanted. Order: fetch the new show (before any write, so a bad id changes nothing) → `DetachEpisodeMediaFiles` → set id → metadata → re-infer `type` → reconcile → re-attach by (season, episode) → rename.
- A file whose S/E has no counterpart in the new show keeps its place **on disk**; only its `media_file` row is dropped, and the path comes back in `unmatched`. A provider numbering seasons differently is not evidence the media is unwanted.
- Re-identify is the one path that **does** re-infer `type` — `UpdateTVShowMetadata` never touches it because an operator may have corrected it, but that correction was about the old show.
- No undo is needed: the inverse is the same call with the old id, files included.
- `db.FindTVShowByTVDBID` reports "not in the library" as a **nil row with a nil error**, unlike its movie twin which returns the ent error. Testing `err == nil` refuses every target; the mock that returned `ent.NotFoundError` hid it through a green suite until the browser hit a 409.

## Episode lifecycle status
- **`movie.status` carries `importing` too**, written by the same monitor tick that flips the record (`CheckStatus` sets the record importing, then the episodes, then the movie off `record.Edges.Movie` — `ListDownloadingRecordsWithMovie` already loads it, so this needs no new Store method). It has no orphan sweep of its own and needs none: `RevertMovieToWantedIfNoFile` and `FailDownloadRecord` both write the movie's status unconditionally, so they cover `importing` exactly as they covered `downloading`. `ListUpgradeCandidateMovies` is the one query that had to learn it (`StatusNotIn(downloading, importing)`) — gating on `downloading` alone would let the RSS feed re-grab a movie whose replacement was already being written to disk. Adding the value needed **no migration** (SQLite stores ent enums as bare text), and `MovieCounts.importing` plus the movies toolbar's Importing tab exist because the value would otherwise be in no tab at all.
- **A series card reads `downloading` and `importing` off `EpisodeCounts`** (`db.episodeCounts`, `TVShow.{downloading,importing}_episodes` — list-only rollups; the detail response carries the episode tree instead). Both tallies **cut across** the have/wanted/unaired buckets rather than replacing one: neither has a file yet, so both stay in `Wanted` and the "missing" filter and its count are untouched. They are also counted **before** the monitored/has-file scope guard, unlike `Total` — a grab that is landing is worth naming whether or not its episode is monitored, or the card stays silent through the whole import. `SeriesGrid.cardStatus` checks `downloading` then `importing` then `wanted`.
- **The in-flight scope is derived from the episode rows, never from the release title** (`EpisodeCounts.widen` → `downloading_scope` + `downloading_season`/`downloading_episode`): first row sets `episode`, a second in the same season promotes to `season`, one in another season to `series`. An operator can grab a pack in two goes, and what the card should say is what is actually landing. `Season`/`Episode` are **cleared** as they stop being true of the whole set, so no caller can read a number the scope disowns — season 0 is the specials, a real season, so only `series` licenses no season at all. This rides the existing counts scan (`season.number`, `episode.number`, `episode.id` added to the same projection): no extra query.
- **`EpisodeCounts.LastAdded` → `last_added` names the show's newest import batch** for the dashboard's arrivals rail: every file that landed within `additionWindow` (1h) of the show's newest `media_files.create_time`, rolled into seasons, episode numbers, a title when it is one episode, and `whole_season` when it filled its season. Files carry no import id, so the window is what tells a pack from a lone episode. Arrival times come from a second lean projection on `media_files` rather than a `MAX()` on the episode scan: an expression column has no declared type, so the driver returns text where a `time.Time` is expected.
- **Both library lists carry a monitoring facet, and it is a facet — not a status.** `monitored=monitored|unmonitored` on `GET /movies` and `GET /series` combines with `status=` rather than replacing it, and `monitored`/`unmonitored` sit on both counts endpoints. The unmonitored tally is **the library total minus monitored**, never its own query: the facet costs one `COUNT` per endpoint. `GET /series?status=` also takes `downloading` and `importing`, whose counts (`CountTVShowsInFlight`) are per-show like `missing` and use the same predicate `FilterTVShows` does — so a tab's count and its contents cannot drift.
- **A monitored flag set by hand is pinned against the library-wide catch-ups, and only a reset clears it.** `Album`, `Season` and `Episode` carry `monitor_pinned`. Set by hand: `SetAlbumMonitored` (album PATCH, album-request approval), `SetEpisodeMonitored`, `CascadeSeasonMonitored` (which pins the season and clears its episodes' pins). Skipped by: `ReapplyMonitorPolicies` (music "Apply to existing"), `CascadeSpecialsMonitored` (series "Apply to existing", a pinned season taking its episodes with it), and the refresh that monitors a placeholder episode once it gets real data. Cleared by the reset of the title it belongs to: `SetArtistMonitor` for an artist, `CascadeShowMonitored` and the preset setters (`SetEpisodesMonitored`/`SetSeasonsMonitored`) for a show. Before the pin, pressing "Apply to existing" silently re-monitored every album an operator had dropped by hand.
- **`Movie.release_date` and `TVShow.first_aired` are display fields, and `release_date` is *not* `digital_release_date`.** The latter is what the release-radar search waits on and is fetched per-region from TMDB's `release_dates` endpoint; `release_date` is the primary/theatrical date off the movie detail, and `first_aired` is TVDB's `firstAired`. The **calendar** (`Store.UpcomingReleases`) is the one place the two are ranked rather than kept apart: it takes `digital_release_date` when set and `release_date` when it is not, and `UpcomingMovie.release_type` tells the SPA which it got. TMDB publishes a type-4 entry only once a title is buyable, so keying the calendar on the digital date alone left the movie half of it permanently empty — a film still in cinemas, which is exactly what an upcoming calendar is for, has a theatrical date and nothing else. The release-radar search is unaffected and still waits on `digital_release_date`. Both providers already returned them, so the work was a nullable column each (migration `20260906140114_add_release_and_air_dates`), `metadata.ParseISODate` on the create and refresh paths, and the API field. There is no backfill job: existing rows fill in as `metadata-refresh` reaches them, and every SPA site falls back to `year` meanwhile. The same endpoint carries sibling `albums` (`Store.ListUpcomingAlbums`: monitored, `[from, to)`, artist eager-loaded) for music and `books` (`Store.ListUpcomingBooks`: `ebook_monitored` or `audiobook_monitored`, `[from, to)`, author eager-loaded) for books.
- **`download_progress` comes from the live queue's cached snapshot, and is optional on purpose** (`restapi.seriesDownloadProgress`). `EpisodeCounts.InFlightEpisodes` carries the ids so the handler can map queue entries to shows without a second query; a pack has one entry on its anchor episode, so the mean is over entries, not episodes. It is asked for **only when some show on the page is downloading** — an idle library pays nothing, and a library page must never be what wakes every download client — and a queue that cannot be read is logged, not fatal: the show keeps its counts and scope and the card falls back to `ProgressBar`'s indeterminate bar. Importing contributes nothing by design; there is no percentage behind it, which is also why movie cards have never passed a progress value.
- `episode.status` is `wanted | downloading | importing | paused | available | skipped`. Only the **in-flight three** (`downloading`, `importing`, `paused`) are owned by a grab; `inFlightEpisodeStatuses` (`internal/db/download_record.go`) is the one list of them, and `RevertOrphanedDownloadingEpisodes` sweeps all three so a row can't strand in any of them. Adding a fourth in-flight state means adding it there, or the sweep silently stops covering it.
- **Every path that grabs must mark its episodes, and there are four.** `grabPackAndMark` (season/series packs), the RSS + missing-search runners (`markEpisodeDownloading`), the single manual grab (`restapi.GrabEpisodeRelease` → `db.MarkEpisodeDownloading`), and the selective-download widen (`download.GrabEpisode` marks the episodes it added). The manual one had no marker at all and the row read `Wanted` from grab until import — the pack path's existence is what made it look covered.
- **Adoption is a fifth path, and it lands at `importing` rather than `downloading`.** An adopted torrent is already complete, so there is no downloading phase to mark: `persistAdoption` calls `db.MarkWantedRecordEpisodesImporting`, which moves only `wanted` — unlike `MarkRecordEpisodesImporting`, which the completion sweep uses and which moves `downloading`/`paused` and would find nothing here. It was missing entirely, and because the series list derives a show's importing state from `episode.status` and never from the record, an adopted import was invisible on the Series page for its whole run while Activity showed it plainly. Retry (`RetryFailedDownloadRecord`) shares the predicate for the same reason: a terminal failure wrote `wanted` back, and the re-run has to undo exactly that.
- `MarkEpisodeDownloading` moves **only from `wanted`**, matching `grabPackAndMark`'s guard. An episode that already has a file is a replace target: marking it downloading and then reverting the grab would leave it `wanted` with the file still on disk, which is the exact shape `RevertOrphanedDownloadingEpisodes`' second arm was written to undo.
- `importing` is set by `db.MarkRecordEpisodesImporting`, called when the monitor flips the *record* to importing — **record-scoped**, over the episodes the record links (`recordEpisodes`, the `DownloadRecord.episodes` many-to-many, which always includes the anchor), exactly like `SyncDownloadStateForRecord`. Both used to walk the anchor's *season* instead, which is wrong in both directions at once: a pack spanning seasons left every season but the anchor's behind, and a season holding two records had each one moving the other's episodes. That second half is what pinned eighteen Narcos episodes at `paused` against a torrent that was never paused — the duplicate grab that paused them was purged, and the integral's own resume only ever swept season 1 (2026-09-20). It moves only `downloading`/`paused` rows, so an `available` replace target isn't dragged in. The SPA renders it in the `grabbing` hue; it is **not** a new colour. It *is* its own `StatusKind` (`importing`, whose `--status-importing` is a CSS alias of `--status-grabbing`) because sharing the `grabbing` kind outright shared its **label** too, and every record the importer already held read "Grabbing" in the queue.
- Adding an enum value to `episode.status` needs **no migration**: SQLite stores ent enums as bare `text` with no CHECK, so the value is enforced in Go only. `task migrate:diff` correctly emits nothing — that is not a missed step.
- **A transport failure never counts toward `grab_failures`** (`rss.transportFailure`, guarding every bump in `missing.go`, `feed.go`, `tv_missing.go`, `tv_feed.go`). `grab_failures` is a strike count against a *release choice* and nothing resets it but a successful grab, while the eligibility queries gate on it — so counting `download.ErrUnreachable`/`indexer.ErrUnreachable` retires the item after `max_grab_failures` (3) unlucky ticks. A flaky Prowlarr did exactly that to the homelab: `fetch torrent: download client unreachable: … timeout` three times, and episodes holding clean 1140-scoring releases stopped being searched at all — no log line, no `searched` event, nothing but a row sitting `wanted` forever. The pack arms are unaffected: they only ever bump on `ErrNoWantedFiles`, which is a statement about the release. `Episode.grab_failures` is on the API (absent at zero) because the counter was otherwise invisible — an operator could not tell a retired episode from an unlucky one without reading the DB.

## Series list performance
- `db.FilterTVShows` applies filter, sort and page in **SQL** and returns the page's shows *without* their season/episode tree, plus a per-show `EpisodeCounts` rollup. The list view needs three numbers, not the tree: eager-loading it was ~121 KB per show, a 2.8 MB response for 23 shows, and — with every query then queued on one connection — a site-wide stall while it ran.
- `missingEpisode` (the `status=missing` predicate) must stay in step with `DeriveSeasonViews`' Missing bucket, or a show matches the filter with nothing missing on its page. `sort=episodes` is a correlated subquery, not a join, so `LIMIT` still applies to shows.
- **An episode with no air date is unaired, never missing.** Five places split aired from unaired and all five must agree: `DeriveSeasonViews`, `db.episodeCounts`, `missingEpisode`, `db.ListEligibleEpisodesForSync` (which feeds *both* the missing search and the TV RSS feed scan) and `restapi.episodeStatus`. They used to read `!AirDate.IsZero() && AirDate.After(now)` — undated fell to the aired side on the theory that an unknown date is not evidence the episode is unreleased. In practice a provider announces a future season as dateless placeholders, often literally titled `TBA`: on a 6859-episode library every one of the 12 undated monitored rows was a future season of a continuing show, each counted as a permanent gap and re-searched every tick. `EpisodeSeed.tba()` (title *and* date both empty → seed unmonitored) does not cover this — TVDB writes the string `"TBA"`, and any monitor cascade or preset re-monitors the row anyway. The status is derived, not stored, so the episode returns to `wanted` on its own the moment the provider publishes a date; there is nothing to migrate.
- **An aired episode's title falls back when the configured language has none.** TVDB's `/episodes/default/{lang}` answers an untranslated episode with an empty name, and translations trail the original airing by weeks, so a French install showed a running English show's downloaded season as a column of blank titles. `TVDB.fillUntranslatedEpisodes` fills an untitled episode **with an air date not in the future** from English, then from the original-language base records (`/episodes/default`, no language), one more page walk per fallback and only while such an episode remains — an announced future episode is often untitled in every language, and checking those would re-fetch every running show on every refresh. A failed fallback keeps the blank. Reconciliation overwrites a changed title, so the translation replaces the fallback on the first refresh after TVDB has it. The SPA names a still-untitled row through `episodeTitle()` (`lib/status.ts`): `Episode N` once it has an air date or a file, the `episode_title_tba` message only for a dateless placeholder with nothing on disk.
- **Specials (season 0) are out of every show-level number and must be out of all of them at once.** `EpisodeCounts` (`Seasons`/`Total`/`Have`/`Wanted`/`Unaired`), `tvShowToAPI`'s detail rollup, `missingEpisode`, `orderByEpisodeCount`, and the detail page's `regularSeasons` derivations all skip them; the specials season itself still renders in the season strip with its own counts. A show whose only gap was an unfollowed specials season read "8/9 eps · 2 missing" with every numbered episode on disk. `EpisodeCounts.Seasons` (`total_seasons`) is counted off the **season** table, not off the episode scan: a season whose episodes are all unmonitored and file-less is still a season the show has, and the detail page counts it as one — deriving it from the scan made the card say 2 where the page said 3. The in-flight tallies are the deliberate exception and still count a special, matching the `downloading`/`importing` filters.
  - **The exclusion makes `have_episodes` a bad "has files on disk" test**, and the series detail page used it as one: a specials-only show reported 0 and greyed out Rename files and Delete all files over an episode set that was not empty. Any UI predicate built from `have_episodes`/`total_episodes`/`wanted_episodes` inherits the specials blind spot — gate on the episode set the action will actually run over.
- **Each sort key carries the direction its menu label promises** (`descending`): `title` ascending, `year`/`rating`/`episodes`/`recent` descending. The SPA's sort menu offers "Year (newest)", "Rating (highest)", "Most episodes" and has no direction toggle, so an ascending default answered none of them — `sort=year` returned oldest-first under both the old Go sort and the first SQL version. The `order` param (`asc`/`desc`) overrides, and exists so the override is reachable at all.
- `orderByEpisodeCount` counts what `EpisodeCounts.Total` counts — monitored **or** on disk. Ranking raw provider rows put a daily soap with 2012 episode rows above shows the card said were bigger, because the card was showing its scoped 26: the order and the number disagreed on the same screen.
- The global search box gates both library queries on the typed threshold (`search-model.svelte.ts`). `SearchField` lives in the global layout, so ungated it pulled the whole library on **every** route for a panel that stays closed until you type.
- ent runs with the `sql/modifier` feature so `Modify` is available for the lean count projection.
- The tree's foreign keys are **explicitly indexed** (`index.Edges(...)` on `Season`/`Episode`/`MediaFile`, migration `20260824093713`). SQLite indexes no FK on its own, so `episodeCounts`' per-episode `EXISTS` over `media_files` was a full scan each: the homelab's series list took 3.9s with the SQL push-down already in place. Any new edge the list path traverses needs the same.
- Movie posters are cached at TMDB `w780`, not `original` (series posters are TVDB artwork URLs, which carry no size) — `original` is ~1.9 MB a card. w780 is ~360 KB and is sized for the largest sharp render, the detail hero’s 260px column at DPR 3; the full-bleed backdrops are `blur-md`, so they set no floor. `posters.Fetch` short-circuits on an existing file, so changing the size only affects new fetches; an existing install has to drop `<data>/posters` to pick it up. `posters.Put` is the one exception: it replaces a cached poster, because an album's own embedded or folder art outranks anything downloaded, and `Fetch` refuses to rename over a file that appeared while it was downloading, so a slower remote fetch can never undo a local one.


## Deleting a title's files

- **`library.RemoveMediaFile` removes the media file by path, and reports an error wrapping `fs.ErrNotExist` when it was not there.** It used to locate the target by scanning the directory listing for an entry equal to `filepath.Base(path)`: a `media_files.path` that had drifted from disk matched no entry, fell through every `continue`, and returned **nil** — so "delete with files" reported the title removed and kept the file. Sidecars and the prune still run when the target is missing; the error is what lets a caller tell the operator's request apart from a deletion that never happened. `movie.Delete`/`tvshow.Delete` log that at **Error** (not Warn) with the path, and record `files.requested`/`files.kept` on their span — the row is gone by then, so this is the only surviving trace of a file that outlived it.
- **`RemoveMediaFile` takes Jellyfin's `<stem>.trickplay/` with the file, and no other directory.** A left-behind one stopped the prune at the season folder (the same thing that kept 51 series folders alive after a bulk rename, which `MoveSidecars` fixes on that side); the removal is recursive, so it is matched by exact name, never by `isSidecar` — a `<stem>-extras/` folder stays.
- **`PruneEmptyDirs` treats a directory holding nothing but `externalMetadata` as empty.** `movie.nfo`, `tvshow.nfo`, `poster.jpg`, `fanart.jpg` and the rest of the Plex/Jellyfin/*arr set carry no relation to the media file's basename, so `isSidecar` (which keys on the stem, deliberately, so one episode's delete never takes another's video) never matched them and the folder survived every prune. On a library migrated from the *arr stack that is nearly every folder — 629 of 1003 on the homelab — so deleting a title left its directory behind forever. Anything else in the directory, including a second episode or a subdirectory, still stops the walk, so a season folder that still has episodes keeps its artwork.
- **`movie.Delete` removes the source torrent before `DeleteMovie`, not after.** The `download_records` edge is `entsql.OnDelete(entsql.Cascade)`, so once the row goes there is nothing left to say which torrent produced the movie — and `AdoptManualTorrents` reads "hash not in `AllDownloadRecordHashes`" as untracked, so a still-seeding torrent came back as an adoption proposal on the next monitor tick. It reuses `removeSourceTorrent` (best-effort, data kept), gated on the same `delete_files` the operator asked for.

## Music and book automation

- Music and book backlog search and metadata refresh are their own jobs — `music-missing-search`, `music-metadata-refresh`, `book-missing-search`, `book-metadata-refresh` — each on its own `schedules.*` key, so MusicBrainz's and Hardcover's limits get their own cadence and a failure lands on the vertical's own row. Their RSS matching still rides `movie-rss-sync`: one pass over the feeds serves every vertical. They share the cap, cooldown and transport-failure rule through `internal/media/searchwindow`, a copy of the logic in `internal/rss/missing.go`. A refresh run handles at most 10 artists, oldest `last_refreshed_at` first, to stay inside MusicBrainz's rate limit. The books pass is bounded by Hardcover's request budget instead: it hydrates series stubs first (twenty per request), then at most 100 stale standalone books in batches of twenty, then at most 5 stale series, stopping when only `hardcoverScanReserve` of the day is left or at the first rate limit (returning nil, the rest waits for the next tick); `RefreshStale` on books returns at once when Hardcover is not configured, and its `scheduler.Progress` total is the stubs, books and series it set out to process.
- **A music album is two lifecycles: stub, then hydrated.** `Add` writes album stubs (`metadata_fetched_at` NULL, no tracks) and the hydration worker (`music/hydrate.go`) writes the tracks; until then the album is not searchable or importable by itself. Every search path (`ListEligibleAlbumsForSync`, `ListWantedAlbums`, `ListArtistAlbumsForSearch`, `ListPackAlbums`) therefore requires `metadata_fetched_at IS NOT NULL` **and** a release date that is null or not after now: an unreleased album is *upcoming*, never missing, and the five-places rule above has its music twin in `db.wantedAlbum`/`db.releasedAlbum`, the API's `albumStatusAt` and the calendar. The album importer and bulk-import adoption call `HydrateAlbum` (synchronous, interactive priority, idempotent) before matching files to tracks; everything else waits for the worker. The credits sweep rides `music.RefreshStale`, whose scheduled refreshes run under `metadata.Background(ctx)` so they queue behind interactive MusicBrainz calls like the worker does.
