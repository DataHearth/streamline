# Streamline

Unified media management platform replacing the *arr stack (Radarr, Sonarr, Lidarr, Readarr) and Seerr. Single self-hosted binary with a slick web UI, REST API for mobile developers, multi-user support with SSO, built-in request system, and automatic media organization. Supports Torznab and Prowlarr indexers, torrent download clients (qBittorrent, Transmission, Deluge, or the built-in engine), and media server notifications (Plex, Jellyfin, Emby). Shipped v1.0.0; music, books and a player are planned (`docs/ROADMAP.md`).

## Stack
- Go monolith: chi + oapi-codegen (OpenAPI → server) + ent ORM + modernc.org/sqlite (CGO-free)
- Config: koanf (file + env + flags, STREAMLINE_ prefix)
- Logging/Observability: slog + OpenTelemetry (traces, metrics, logs via OTel bridge)
- Frontend: Svelte 5 SPA (TypeScript) — Routify v3 file-routing, TailwindCSS v4, TanStack Query + TanStack Form, valibot schemas; bundled by esbuild, embedded via go:embed

## Frontend
- Svelte 5 SPA in `web/app/` (TypeScript everywhere — `<script lang="ts">`, `.ts` lib files). Entry `web/app/main.ts` + `App.svelte`; shell `web/app/index.html` (embedded as `web.SPAShell`).
- Routing: Routify v3 (`routify.config.js`) scans `web/app/routes/` → generated `web/app/.routify/` (gitignored, never hand-edit). A section's wrapping layout MUST be `_module.svelte` — a `_layout.svelte` renders as a sibling route, not a wrapper.
- Data/forms: `@tanstack/svelte-query` (`lib/query.ts`, `lib/api.ts`), `@tanstack/svelte-form`, `valibot` schemas (`lib/schemas.ts`). Toasts: `svelte-sonner` (`lib/toast.ts`). Icons: `@lucide/svelte`. Class merge: `lib/cn.ts` (clsx + tailwind-merge) — never duplicate elements in `{#if}/{:else}` just to swap classes.
- **In-flight work is visible app-wide from one component.** `components/layout/GlobalActivityBar.svelte` sits in `App.svelte` inside the `QueryClientProvider` and shows a 2px indeterminate bar whenever `useIsFetching() + useIsMutating() > 0`, after a 300ms delay so cache hits don't flash. Queries carrying `meta.silent` (sidebar badges, the dashboard's background polls) are excluded from the fetching count so a poll never raises the bar. It is `z-[300]` — above the modal layer (`z-50`) and the `Select` portal (`z-[200]`) — because the case that made it necessary was an indexer search taking ~15s *inside* a modal, which read as a stall. Per-view skeletons stay; this covers everything they don't, including background refetches that leave stale data on screen.
- **`GET /movies` filters, sorts and pages in SQL, and carries a `file_summary` rollup instead of `media_files`.** `movie.FilterList` + `db.FilterMovies` had existed as dead code since the series push-down; the handler still called the unfiltered `List` and the SPA pulled the whole library to filter in the browser. The rollup (`db.MovieFileSummaries`, one lean scan over the page's ids — the same trade `EpisodeCounts` makes for series) carries `file_count`, `size_bytes` and the *largest* file's parsed `resolution`/`codec`, which is everything the grid's size and quality columns, `MovieActionsMenu`'s file count and the bulk-action totals need. `media_files` is now **detail-only**; `MovieActionsMenu` reads `file_summary?.file_count ?? media_files?.length` because it opens from both. `db.ListMovies` and `movie.Service.List` are gone — nothing called them once the handler moved.
- **List projections omit `cast`** (`movieListColumns` / `tvShowListColumns`, derived by *subtracting* from `movie.Columns`/`tvshow.Columns` so a new field lands in the list by default). ent decodes the JSON blob into a `[]CastMember` per scanned row; one page walk of a 610-movie library put 480 MB of garbage on that single `Unmarshal`, for a field no list response emits. `withLeanMovie` applies the same projection to every `WithMovie()` eager-load on the queue/history/activity/drift paths (thirteen in `db`, `ListPendingDownloadRecords` included — it keeps `WithMediaFiles` on top, since the pending row's `has_file` reads them). Detail handlers must not use these projections. `overview` was measured too and deliberately **kept** — it is a plain string column with no decode cost, and it *is* emitted.
- **Both library lists paginate server-side with an appending infinite query** (`routes/{movies,series}/index.svelte`), replacing `apiAllPages` + `IncrementalList`. The typed filter is debounced 250 ms before it reaches the query key. Consequences, all deliberate: the **tri-state monitored filter is gone** (`MonitorFilterTabs`, `MonitorFilter`, `?monitored=`), as is the movies footer's "N GB monitored" — neither survives paging without a `monitored` query param and a wider counts endpoint, and both were dropped rather than rebuilt. Tab counts come from `/movies/counts` and `/series/counts`; the latter grew `upcoming` and `missing` for exactly this, and `missing` reuses `db.missingEpisode` so the tab's count and the tab's contents cannot drift. Bulk selection and the "N of M" line now mean "of what has been loaded", not "of the whole library". The dashboard still walks all pages — its own problem, unmeasured, left alone.
- **The bulk bar's `⋯` covers the per-title kebab minus what the bar already promotes, and minus what has no bulk meaning.** `{Movie,Series}BulkActions` promote Monitor/Unmonitor/Search/Quality to buttons, so the kebab holds only Rename/Refresh/Delete. **Change match** is per-title by construction — it repoints one row at one provider id — and correctly has no bulk form; **Rename files…** was the one real gap, and it is the action a naming-template change needs across a whole library. It applies without a preview (one per selected title is a request each to render a list nobody reads at that length — the per-title kebab keeps its preview modal), behind a confirm, over the subset with files on disk (`file_summary.file_count` / `have_episodes`) so the toast's count is what was acted on. `run()` in both components takes that subset as an optional last argument; everything else still defaults to the whole selection.
- **The dashboard's "Recently added" and "Wanted" rows both mix movies and series, and sort on `added_at`** (`Movie.added_at`/`TVShow.added_at`, ent's `create_time`, added for exactly this). Neither row could order the two kinds before: both list endpoints default to `create_time DESC` *within their own kind*, which says nothing about how they interleave. "Recently added" carried no series at all, and "Wanted" built `[...movies, ...series].slice(0, 6)` — mapping series in, then always truncating them away whenever six wanted movies existed.
- **Settings pages pick one of two save models, never both on a page.** Save-per-control with no form and no Save button (`series`, `media-probe`, `library`, `transcoding`): checkboxes and selects fire on change, text inputs commit on blur, and a `drafts` record keyed by field name is what stops a focus-refetch from overwriting what is being typed. Or a TanStack form with a valibot schema and one Save (`auth`, `metadata`, the resource modals), whose `$effect` re-seeds *only while the form is clean*. `settings/library.svelte` is per-control precisely because it straddles two endpoints (`/config/library` + `/config/download`) that one form could not submit together; `settings/metadata.svelte` is a form because its password fields want an explicit commit. A new page adds its route, a `SETTINGS_TITLES` entry and a `createSettingsNav` item — the sidebar and the touch index read the same list.
- Bundling: `pnpm exec routify build` then `node web/app/esbuild.config.mjs` (esbuild + esbuild-svelte) → `web/static/dist/spa.min.{js,css}`. Scalar API-docs bundle is separate: `web/static/js/docs.js` → `docs.min.js` + `docs.min.css`. `task build:js` emits both.
- **The SPA is installable via `web/static/manifest.json`, and that is the whole PWA.** It is `.json` rather than `.webmanifest` because Go's built-in MIME table has no entry for the latter and the distroless image has no `/etc/mime.types` to fall back on; browsers accept any JSON media type. There is deliberately no service worker (offline was declined; Chrome no longer requires one to install), no install nudge, no push and no share target. `icon-maskable-512.png` is the favicon flattened onto `--bg-deep` so Android's adaptive mask never exposes the tile's transparent corners. `web/embed.go` lists directories one by one, so the manifest needed its own `//go:embed` line — the spec in `spa_test.go` is what catches that line going missing. `TopBar` and `FullScreenPanel` pad `env(safe-area-inset-top)` for the standalone status bar; `SearchScreen` already did.
- TailwindCSS v4 (`@tailwindcss/cli`): `web/static/css/input.css` → `style.css`, scanning `web/app/**/*.svelte` (`task build:css`).
- Frontend deps via pnpm (`package.json` is a manifest only, no scripts). JS/CSS lint+format is Biome (`biome.json`) over `web/static/js` + `web/static/css` only — tabs width 2, double quotes, semicolons.
- Distribution: single binary (frontend `//go:embed`-ed), OCI images, Helm charts.

## Logging
- No `*slog.Logger` plumbing. `cmd/main.go` calls `observability.Setup` then `slog.SetDefault`; every package logs via `slog.XContext(ctx, ...)` (top-level) — never hold a logger field.
- `observability.Setup` returns one `slog.Handler` = `contextEnrichingHandler(multiHandler{stderr, otelslog.Handler})`. stderr is pretty text/json from `log.app.{level,format}`; otelslog bridges to the OTLP logs pipeline (traces/metrics/logs all batch-exported to `otel.endpoint`).
- `contextEnrichingHandler` auto-attaches `request_id` (chi), `user.id`/`user.email`/`user.roles` (auth claims, OTel semconv v1.40.0), `http.route` (chi route pattern). Trace/span IDs come from otelslog. Use `slog.XContext` so ctx flows through.
- `observability.LevelCritical` (= `slog.LevelError + 4`, rendered `CRITICAL`) for panics, invariant violations, unrecoverable conditions. Call via `slog.LogAttrs(ctx, observability.LevelCritical, ...)`.
- OTel semconv pinned at v1.40.0 — use `semconv.<Key>Key` constants (e.g. `semconv.HTTPRouteKey`) over string literals; keep versions aligned across files.

## Observability
- `internal/otelx` is the leaf OTel helper package. Holds `HTTPClient` (otelhttp-wrapped — use for every outbound HTTP call; never `http.DefaultClient`) and `RecordSpanError(span, err) error` (inline: `return ..., otelx.RecordSpanError(span, err)` — no named returns). Must stay dependency-free; `internal/observability` imports `internal/auth`, so anything auth transitively uses must live in `otelx` not `observability`.
- Per-package tracer: `var tracer = otel.Tracer("github.com/datahearth/streamline/internal/<pkg>")`. Span names `<pkg>.<op>` (e.g. `download.grab`, `rss.process_movie`, `indexer.query`).
- DB auto-instrumented via `otelsql.Open` + `RegisterDBStatsMetrics` in `internal/db/client.go`. Add business-logic spans in service methods + `span.SetAttributes` for domain context.
- Prefer semconv helper funcs (`semconv.UserEmail`, `semconv.UserRoles`, `semconv.UserID`, `semconv.DBSystemNameSQLite`) over raw `attribute.String("user.email", …)`.

## HTTP Routes
- `/health` — pre-auth bare JSON endpoint (NOT in OpenAPI), for k8s probes + load balancers. Registered in `internal/server/server.go`.
- `/api/docs` — Scalar UI shell (`web.Handler.APIDocs`). `/api/v1/openapi.yaml` — embedded spec. REST API mounted via `restapi.Mount`.
- SPA fallback: `s.router.NotFound` → `web.Handler.SPAShell`, which writes the embedded `web/app/index.html` for every non-API, non-static path; Routify owns client-side routing incl. its own 404. Static assets served at `/static/*` from `fs.Sub(web.Assets, "static")` (wired in `web.Mount`).
- `/posters/{kind}/{id}/poster.jpg` — poster proxy via `s.posters.Serve`.
- `DELETE /api/v1/torrents/{hash}` also calls `downloads.PurgeRecordForHash`, dropping the live download record behind that torrent and reverting its media. The monitor's orphan sweep would eventually do it, but only after `monitorOrphanGrace` (2 min) — a window that exists to tolerate a client that hasn't caught up with its own listing, which a removal issued through streamline is not. The Torrents page invalidates `["activity","queue"]` on success for the same reason.
- The auth middleware's `excludePaths` list is assembled in `internal/server/wire.go` and handed to `middleware.NewAuth` (`/health`, `/api/docs`, `/api/v1/openapi.yaml`, `/static/`, `/login`, `/register`, `/auth/login`, `/auth/register`, `/auth/config`, `/auth/invite/`, `/auth/oidc/`); matcher in `internal/server/middleware/auth.go`, paths ending `/` match as prefix.

## Auth & Sessions
- Middleware splits transport by path prefix (`internal/server/middleware/auth.go`):
  - `/api/v1/*` accepts `Authorization: Bearer <jwt>`, `X-API-Key`, or — for a request the browser proves same-origin — the `streamline_session` cookie. 401 JSON on failure. The cookie path is what lets the SPA call the API without ever handing a JWT to JavaScript; `sameOriginAPIRequest` gates it on `Sec-Fetch-Site: same-origin`, falling back to a single `Origin` matching the request host, then (GET/HEAD only) a single matching `Referer`. A *present* `Sec-Fetch-Site` of any other value is refused outright, so `Origin` cannot override it. The fallbacks exist because Fetch Metadata is only sent for potentially-trustworthy URLs — a plain-http LAN install, the default self-hosted shape, sends none of it.
  - Everything else authenticates via the `streamline_session` cookie (httpOnly, SameSite=Lax, Secure when the request is TLS, a trusted proxy forwards `https`, or `config.PublicURL()` is https). 302 to `/login?next=<escaped>` on failure. Bearer ignored.
- API keys equal a session on media + config endpoints but are **read-only on the identity band**: any non-GET/HEAD request under `/api/v1/auth/me`, `/auth/password`, `/auth/invites`, `/auth/jwt`, or `/users` is refused with 403 (`identityMutationForAPIKey` in `middleware/auth.go` — the single chokepoint, not metered since the credential is valid). `/auth/jwt` is on the list because rotate re-issues a bearer token, so a key reaching it would bootstrap the very session credential the list denies it. `CreateMyApiKey` keeps its own `claims.JTI` check as defense-in-depth. This is a fixed policy — per-key scopes were considered and rejected. Anything new added under those prefixes inherits the denial; a new identity-ish endpoint *outside* them must be added to `identityPrefixes`.
- Webui auth routes (`internal/server/web/auth.go`, registered via `web.Mount` → `registerWebAuthRoutes`): `GET /auth/config`, `GET /auth/invite/{token}`, `POST /auth/login`, `POST /auth/register`, `POST /auth/logout`, `GET /auth/oidc/{name}/start`, `GET /auth/oidc/{name}/callback`. There is no `GET /login`/`/register` handler — those fall through to the SPA shell (Svelte renders `login.svelte`/`register.svelte`). Login/register take JSON, set the `streamline_session` cookie, and return `204` on success / `4xx` JSON on failure — no server-rendered HTML.
- Login + register rate-limited per IP (5 attempts / 15 min) via `auth.Limiter`. `/api/v1` has its own budget (20 / 15 min, `server.apiFailureLimiter`) charged **only when authentication fails** — a valid key or session is never metered, so bulk consumers need no exemption. The hidden `auth.api_failure_limit` key overrides the count; `0` turns metering off, which is what `e2e/apptest` sets so the every-operation anonymous sweep is not itself throttled.
- An admin is seeded on a fresh install (`auth.Manager.BootstrapSeedAdmin` — `Manager` is the interface, the implementation is the unexported `auth` struct), so the DB is normally non-empty at request time and there is no first-user-registration special case. One exception: a configured `password_file` that reads back empty seeds *nobody* (see below), leaving an empty DB with `registration_mode: disabled` — unreachable until the secret materialises and the process restarts. `IsFirstUser` has no caller outside bootstrap, and `/auth/config` exposes no `first_user` field.
- `auth.registration_mode` (runtime-toggleable via `config.Update`): `disabled | open | invite`.
- **`auth.default_role` serves both self-registration paths, which is why it is no longer called `oidc_default_role`.** It is the role an anonymous `POST /auth/register` lands on in `open` mode (`web/auth.go` → `RegisterOpen` → `role.SelfRegistered`) *and* the fallback an OIDC login provisioning a new account falls back to when no claim maps (`oidc.go` → `role.Federated`). The old name described half of what it did, so an operator reading it as OIDC-only could set `admin` for an IdP they trust and hand the same role to anyone who registers with a password — which is exactly what `role.SelfRegistered`'s clamp exists to stop, and a clamp is a poor substitute for a name that does not mislead. It is only ever a **fallback**: an invite carries its own role (`role.Invited`, uncapped — a direct decision about one account) and a matched claim outranks it.
- **The rename is a clean break — `auth.oidc_default_role` is gone, not aliased.** It shipped briefly as a `renamedKeys` entry and was removed deliberately: an old config naming it now has that key dropped by koanf like any other unknown, so the role falls back to `member` **silently**. That is the cost of the break and it is the operator's to handle at upgrade; `Describe("with the removed auth.oidc_default_role")` in `config_test.go` pins it so nobody re-adds the alias by accident. Nothing on `/config/auth` carries the old name either — the view emits `default_role` alone and a patch naming `oidc_default_role` is ignored as an unknown field.
- **`renamedKeys` + `applyRenamedKeys` (`internal/config/config.go`) is the deprecated-key mechanism**, holding the pre-media-split `schedules` renames. koanf silently drops a key the struct no longer has, so without it an old config keeps parsing while the renamed job reverts to its default interval. It copies the old key's value onto its replacements, skipping any replacement whose value already differs from the default (that reads as "the operator set it themselves" in both the merged and the file-only koanf), and runs against **both** layers so a file naming the old key keeps its value when write-back reverts an environment-supplied one. It stays general rather than schedules-specific so the next rename does not rebuild it — but reaching for it is a choice, not the default: `auth.default_role` deliberately did not.
- Seed admin via `auth.seed_admin.{email, password, password_file}` — file wins if both provided; trimmed of whitespace. No-op if users already exist. An empty `email` resolves to `admin@streamline.local`, and that account gets a generated password when no password *and no `password_file`* was configured (a configured file reading back empty is an unmaterialised secret, not a request to generate — generating would flip `IsFirstUser` and the real file could never apply). The generated password is printed once to stdout on the single greppable `default admin credentials — email: … password: …` line and is never written to the config nor passed to slog (stderr + OTLP). `BootstrapSeedAdmin` never mutates `auth.seed_admin`; a stored plaintext left by an older release is the operator's to delete.
- Session TTL via `auth.session_ttl` (default `168h`, Go duration string). JWT HMAC signing secret (`auth.session_secret`, or `session_secret_file`) auto-generated on first boot and persisted via atomic YAML write-back (`config.Update`). Ephemeral fallback when the write-back fails `ErrNoPath` (dev/tests) or `ErrReadOnly` (a read-only compose/k8s mount — the production case).
- Invite lifecycle: admin creates via `POST /api/v1/auth/invites` (raw token shown once). The SPA fetches `GET /auth/invite/{token}` and prefills the email (readonly) when the invite has a bound email. `LookupInviteForPrefill` skips email match; `RegisterWithInvite` checks it up front (`validateInvite`), then creates the user and consumes the invite in one transaction.
- Registration failures are mapped to user-safe messages (`userFacingRegisterError` in `internal/server/web/auth.go`) and returned as JSON; raw service errors are only logged, never sent to the client.

## OIDC
- Multi-provider via `auth.oidc[].{name, issuer, client_id, client_secret | client_secret_file}`. `OIDCManager.Init` discovers each at startup; a discovery failure is logged at ERROR and the entry is skipped.
- Flow: state + nonce + PKCE (S256) held in short-lived `_oidc_*` cookies scoped to `/auth/oidc/`. Redirect URI = `<STREAMLINE_PUBLIC_URL or http://server.host:port>/auth/oidc/<name>/callback` (see `config.PublicURL`).
- Provider trust is **two independent axes**, one key each, both defaulting closed: `auth.oidc[].email_linking` (which accounts it may adopt) and `auth.oidc[].allow_admin` (whether it may grant `admin`). They were one key; tightening the adoption tier could then *raise* the role ceiling. Keeping them apart is what makes each axis monotone — no move on one can add capability on the other. Never re-merge them.
- Linking policy (`auth.Manager.LoginOIDC`):
  1. Existing `(provider, subject)` → log the linked user in, re-syncing the claim-mapped role through `role.Federated` → `syncOIDCRole`. The re-sync writes through `db.UpdateUserRole`, whose guarded UPDATE refuses to demote the last admin (login still succeeds, the role is kept, and the refusal is logged); the demotion resumes on the next login once another admin exists.
  2. `email_verified=false` → `ErrOIDCEmailUnverified` (reject).
  3. Existing user by email → adoption is **opt-in per provider** via `email_linking` (`disabled` default / `non_admin` / `all`); when permitted, link identity and promote `auth_method` `local` → `both`, otherwise `ErrOIDCLinkNotAllowed`. A matching email is not proof of account ownership — an IdP that lets users self-assert a verified address would otherwise mint a login for any local user, seeded admin included. The adoption itself never writes a role; claim-mapped roles resume syncing on the next login, via step 1.
  4. New user → apply `registration_mode`. `invite` mode consumes the earliest unused+unexpired invite bound to the email and feeds its role to `role.Federated` as the fallback; no match → `ErrOIDCNoInvite`. `disabled` → `ErrOIDCRegDisabled`. `open` → falls back to `auth.default_role`.
- `email_linking` governs **adoption only** (`emailLinkingAllowed`): `disabled` adopts nothing, `non_admin` adopts non-admin accounts (the migration setting — turn on, have users sign in once, turn off), `all` adopts any account including admin. It never affects a role.
  - It gates the adoption, not its result. Step 1 matches on the identity an adoption linked and never reads the key, so a provider set back to `disabled` still signs in as every account it adopted while it was open — including local-password accounts it did not create. That is what makes the README's migration procedure work; there is no unlink, so deleting the user is the only way to drop the identity.
- `allow_admin` is the **admin ceiling**, enforced by the single choke point `role.Federated` in `internal/role/` (imported as `approle` inside package `auth`). False (default) means no login through the provider yields admin, with **no exception**: not a claim mapped to `admin`, not a `default_role` of `admin`, not an invite-carried `admin`. Among claim candidates admin is *dropped* (so an admin-only claim set leaves the existing role untouched, and an admin+member set lands on member); a configured fallback of admin is *clamped* to member, because provisioning has to land somewhere.
  - `role.Federated` reads no auth_method, no `email_linking`, and no claim of the request being served. Each of those moved with an attacker or an operator, and each of rounds 1-3 died to a different ordering that exploited exactly that.
  - **The ceiling is a compile error to skip, not a lint.** `role.Value` wraps an unexported field and the package exports no setter; its only constructors are five named authorities — `Operator` (admin API), `Seed` (first boot), `Invited`, `SelfRegistered` (open local registration, which clamps admin to member exactly as `Federated` does for a provider without `allow_admin`, so posting `/auth/register` first can never outrank a federated login) and `Federated` (the one OIDC door, which applies the ceiling itself). `db.CreateUserParams`/`UpdateUserParams` take a `role.Value`, so a bare `entuser.Role` no longer compiles into a params struct: composite literal, field assignment, a params type invented next year all fail to build. The zero value is the safe one ("no role decided", every write path skips it), and `Ent()`/`EntPtr()` are the only exits to an ent role. What the boundary cannot express is "only this package may call `Operator`", so the residue is code on an OIDC login's path calling one of the four non-OIDC constructors instead of `Federated` — named, greppable calls, which is what the specs below check. `Federated` also takes the provider's **name**, not its config — a `config.OIDCConfig{AllowAdmin: true}` written at a call site would otherwise be an escalation spelled entirely in blessed calls; named, the ceiling can only be what the operator configured, and an unknown name (or an unloaded config) confers nothing.
  - Four rounds of AST guard preceded that and four rounds were bypassed, each by a shape the previous round had not enumerated — most recently `var esc oidcRole; esc.role = string(entuser.RoleAdmin)`, which needed no new API at all because the field was in the same package. **Do not move the type back into `auth` and do not export the field.**
  - What is left for `Describe("OIDC role writes")` in `oidc_test.go` is a backstop over the surface the compiler does not reach: a role field filled by hand. It **type-checks** every non-test file of package `auth` — `go/packages` resolves the imports, `go/types` checks the package — and reports each place that names a role field: a `Role:` key in *any* composite literal (no type filter: round 5's suffix-match on `*UserParams` is exactly how `UserPatch{Role: &esc}` slipped past), an assignment to a `.Role` field, an ent `SetRole`/`SetNillableRole`. It fails on any whose value the compiler does not vouch for and whose function is not allow-listed. Vouched means exactly two things: the receiver of `Ent()`/`EntPtr()` **is the type** `role.Value`, or the value is `string(<x>.Role)` off an `*ent.User` row. **A name is not a type, and round 6 is the proof**: its walker trusted anything *spelled* `<x>.EntPtr()`, so a five-line `shadowRole` declared in package `auth` and dropped into `syncOIDCProfile` — not allow-listed, on an OIDC login's path — landed an admin row, an admin JWT and an admin session with every spec green.
  - A second spec builds package `auth`'s call graph, also type-resolved, and fails if `LoginOIDC` can reach any `roleWriters` entry — which is what makes the allow-list's "no OIDC login reaches it" a checked fact rather than a sentence. Every *reference* to a package function is an edge, not only a call in call position: round 6's name-keyed graph saw `up := s.UpdateUser; up(…)` as a call to `up` and reported `UpdateUser` unreached. Types also drop `s.db.UpdateUser` and `tx.CreateUser` on their own, where the name-keyed version needed a hand-maintained list of receiver names to tell them from the service's own methods.
  - Three fixed-point specs fail if the walker stops seeing the known writes, the known calls, or the one write it vouches for by shape, so none can pass by going blind. Injections are **spliced into the real source before it is type-checked**, so an escalation is judged in the function it would really have to live in, against the package's real types, by exactly the code that judges the tree.
  - `roleWriters` names the seven functions that decide a role over an authenticated non-OIDC path (bootstrap seeding, local/invite registration, invite creation, admin CRUD) and is held to its claim by the reachability spec; `roleCarriers` names one (`ListUsers`' filter) and is the one allow-list nothing checks. Adding a name to `roleCarriers` is how this gets reopened — reach for `roleWriters` first and let the reachability spec argue. `issueToken` used to be the second entry: exempting the whole function left `Claims{Role: "admin"}` — a JWT forgery an OIDC login reaches — invisible, so it is held to the row-mirror shape instead and that literal is now caught. The walker scans package `auth` only, so `internal/role` is unscanned by design: it is the one package allowed to decide a role, and its own specs cover the ceiling.
  - What none of it covers, stated so the next round does not have to rediscover it:
    - reflection or `unsafe` — `unsafe.Pointer` rewrites the very field the package boundary protects, and the forged value then leaves through the real exit on the real type;
    - **a write inside a `roleCarriers` function** — `ListUsers` is exempt by name, and nothing checks that a login cannot reach it;
    - a `role.Federated` call naming a *different* provider than the one being authenticated, which is capped by that provider's ceiling rather than by none;
    - the residue of the JWT mirror: `string(<x>.Role)` proves the value came off *a* user row, not off the row this login authenticated, so `claims.Role = string(other.Role)` inside `issueToken` still passes. Closing it means the session's role stops being a free-standing string — `Claims.Role` would have to become a type only a constructor taking the authenticated `*ent.User` can fill, which is `internal/server`'s middleware and RBAC as much as `auth`'s — and it would still not cover `s.issueToken(ctx, someOtherRow, meta)`, which mints a whole session for the wrong user without naming a role at all.

    The `leave uncovered, on purpose` table injects each of these four and watches nothing happen; it fails if one starts being caught, which is a docs fix. Do not restate this list without injecting the shape and watching it fail. A role decided in another package and returned into `auth` is uncovered too, but only asserted here — it has no injection.
- Provider names are unique per config — `Config.Validate` rejects a duplicate `auth.oidc[].name` (the other name-keyed lists get this from a `unique=Name` tag). Two entries sharing a name split trust from authentication: `oidcManager.Init` keys its map by name so the *last* entry's verifier and client_id authenticate the callback, while `findOIDCProvider` returns the *first* entry's `allow_admin`/`email_linking` — a token from the weaker issuer capped by the stronger entry's ceiling.
- `role_claim` accepts a dotted path into nested claims (`realm_access.roles` for Keycloak); a claim literally named with a dot wins over the path reading. `oidcClaimRoles` returns the mapped candidates *uncapped* — ranking and the ceiling are `role.Federated`'s, so there is one place to audit. The privilege ordering lives in `internal/role` too (`AtLeast`, which `auth.RoleAtLeast` delegates to) so RBAC and the ceiling rank roles off one table.
- Both trust keys are config-file only: the REST provider CRUD (`/api/v1/config/oidc`) neither reads nor writes them, so API-created providers get `disabled` + no admin, and `UpdateOIDCProvider`'s in-place patch preserves whatever the file set. `Config.Validate` spells the `email_linking` zero value out as `disabled` so the write-back never emits `email_linking: ""`, which `api/config.schema.json` rejects; `allow_admin` is a bool, so the write-back always emits it and the schema has to know the key.
- OIDC callback failures `302`-redirect to `/login?error=<code>` (`internal/server/web/auth.go`); the SPA's client-side `oidcErrorMessage` (`web/app/lib/auth_api.ts`, used by `routes/login.svelte`) maps codes to human-facing text.

## Runtime config surface (`/config/*`)
- Seven sections are readable and patchable: `/config/{auth,library,ffmpeg,download,metadata,system,transcoding}`, all admin-only, all partial-patch (a nil field is left alone), all echoing the section's new state. Everything else in the config is file-only and needs a restart. `docs/wiki/Configuration-Reference.md` holds the operator-facing table of which key lives on which settings page; keep it in step when a key moves in or out of this surface.
- **What is deliberately *not* here.** The trust boundary — `auth.mode`, `auth.trusted_networks`, `auth.trusted_role`, `server.trusted_proxies` — is file-only for the same reason `oidc[].allow_admin`/`email_linking` are: a key an attacker could reach through the API is a key the API can be made to grant. So are the seed-admin block and every session/API secret. `data_dir` and server host/port are out because they decide what the process opened before it could serve a request.
- **`/config/system` is the one section spanning three config blocks** (`log`, `otel`, `events`) because it is one question — what the server records about itself — and none of the three is big enough to be its own endpoint. It also mixes hot and cold: `events.retention` is read per cleanup tick, while the log handlers and OTLP exporters are built once by `observability.Setup`. `UpdateConfigSystem` therefore compares `Log` and `OTel` **struct-wise** against the pre-update config and only then calls `restart.Mark()` — a retention-only patch must not ask for a restart it does not need. `LogConfig` is one all-optional schema serving both the view and the patch (like `ProbeConfig`), so `logPatchFromAPI` is what keeps a `{"log":{"app":{"level":...}}}` body from flattening its siblings.
- **`torrent_listen_port` is not on this surface and must not be added.** It is authored by a VPN tunnel, not by an operator: `PUT /torrents/listen-port` moves the running engine's sockets and persists nothing, so a restart falls back to `STREAMLINE_TORRENT_LISTEN_PORT`. The SPA affordance lives on the Torrents page (live engine state) rather than a settings form for exactly that reason — and it exists because gluetun's `VPN_PORT_FORWARDING_UP_COMMAND` fires once per rotation with no retry, so a partial move needs a human re-issue.
  - **`DownloadClient.listen_port_override` is what stops the builtin form from lying.** Three keys name the peer port, and `BuiltinDownloadClient` resolves `torrent_listen_port` over the entry's own `listen_port` — but `ListDownloadClients` converts the raw `c.DownloadClients` entries, so the form was showing, and saving with a 200, a value the engine never binds. On the deployment the override exists for. The view now reports the override (builtin only, non-zero only) and the form goes read-only behind it. `port_bound` is a different signal and both are wanted: it is the live socket off `client.LocalPort()`, present only while the engine runs, while the override names the *cause* and survives the engine being down.
- **The file-only keys are reported read-only on `SystemInfo`, not left invisible.** `sysinfo.Snapshot` carries the trust boundary, the bootstrap block and the generated values so Settings → General can say what is in force — otherwise the only way to know is reading the YAML on the host, which a container deploy makes awkward. `GetSystemInfo` is already `roleAdmin`, which is what makes this safe; it must stay that way. Secrets are never reported as a value: the seed-admin password as a **source** (`sysinfo.secretSource` → file/config/unset, applied in `sysinfo.Collect`), the session and provider secrets as their `*_file` path or nothing. `fillFileOnlySettings` is the one place the Snapshot's file-only block reaches the API.
- **`library.{movie,series,download}_path` are read-only in `LibraryConfigView` and absent from `LibraryConfigPatch`.** `config.LibraryPatch` still carries them because `pathmigrate` writes them — it rewrites every stored path in the DB and repoints the root afterwards. A second, plain-PATCH door would strand every path the library already recorded. The view carries them anyway so the settings page can show where the library lives and link to Advanced.
- **`narrowUint8` is the guard on every bounded counter** (`max_grab_failures`, `import_max_attempts` 1–255; `drift_grace_ticks`, `lockout.threshold` 1–20/255). Nothing validates a request body against the spec's `minimum`/`maximum` — there is no request-validation middleware — and `uint8(300)` is 44, a value the config's own `min=1` / `max=…` tags then happily accept. The narrowing has to reject before the conversion, not after.
- **`checkDuration` guards every Go-duration key** (`session_ttl`, `lockout.{window,duration}`, `no_match_cooldown`, `selection_grace`, `events.retention`). `Config.Validate` marks these `required`, which is only non-empty — it never parses one. A typo written through the API therefore lands on disk and surfaces much later, as a job silently falling back or not running at all.
- **`/config/metadata` writes are restart-required and the handler says so.** `metadata.NewTMDB`/`NewTVDB` read the four keys once, when `wire.go` constructs the clients, so `UpdateConfigMetadata` calls `restart.Mark()` on a real change (comparing the whole struct — re-sending stored values raises nothing) and the view reports `restart_required` off the same process-wide flag ffmpeg and OIDC use. Keys are write-only: the view carries `*_set` and `*_file_managed` booleans, a blank key preserves the stored one (so there is no way to *clear* a key over the API), and setting one inline while the matching `*_file` is configured returns `ErrSecretFileManaged` — mirroring `UpdateIndexer`.

## Config-backed resources
- Media servers, download clients, indexers, and quality profiles live in the YAML config (NOT ent/SQLite), name-keyed and hot-editable — mirroring `auth.oidc[]`. Top-level lists: `media_server.servers[]`, `download_clients[]`, `indexers[]`, `quality_profiles[]` + `quality_default_profile`. Global grab knobs moved to `library.no_match_cooldown` / `library.max_grab_failures` (the old `library.default_quality` block is gone).
- Helpers in `internal/config/resources.go` (`Find*`/`Enabled*`/`PickDownloadClient`/`ResolveQualityProfile`) + per-family CRUD in `internal/config/mutate_*.go` (`Add*`/`Update*`/`Delete*`, secret-preserve on blank). REST handlers (`internal/server/restapi/handler_{download_clients,indexers,media_servers,quality_profiles}.go`) call config directly — no service CRUD; the indexer/download/mediaserver services keep only behavioral methods (`Test`/`TestByName`/`Grab`/`Feed`/`DiscoverSections`/Plex PIN). Read views hide secrets behind `api_key_set`/`password_set` booleans.
- Endpoints are name-keyed (`/api/v1/<resource>/{name}`); media-server update is `PATCH`, the others `PUT`. Movies reference a profile by `quality_profile` string (empty resolves to the default). DownloadRecord/Movie carry `download_client_name`/`indexer_name`/`quality_profile` string columns instead of FK edges.
- **`torrent_listen_port` is a top-level scalar that overrides the builtin entry's `listen_port`, resolved in `BuiltinDownloadClient()`.** It is top-level *only* so the environment can reach it: the env layer maps `STREAMLINE_A__B` onto `a.b` with a single underscore staying literal, so `STREAMLINE_TORRENT_LISTEN_PORT` names it exactly, while nothing inside `download_clients[]` is addressable at all. It exists because the value is authored by a VPN tunnel rather than by git — a per-session forwarded port rotates on every reconnect, so a read-only ConfigMap cannot carry it and a `config.Update` write-back would fail `ErrReadOnly` anyway. Resolving it in config rather than in the engine is what keeps the engine reading nothing but `entry.ListenPort` (`newPeerSockets` binds it; `newClientConfig` leaves `cc.ListenPort` alone); the engine has no env awareness and no ctx plumbing for it. Read at wiring for the *initial* bind, but no longer the ceiling: `PUT /api/v1/torrents/listen-port` moves the running engine's peer sockets, because the engine owns them rather than letting anacrolix create them. The endpoint persists nothing — a rotation is authored by the tunnel, and the deployments that need this run a read-only config where `config.Update` fails `ErrReadOnly` — so a restart still falls back to `STREAMLINE_TORRENT_LISTEN_PORT`. A ProtonVPN tunnel rotates its forwarded port on roughly every reconnect, measured at about one per 2.5 days on the homelab. Builtin engine only; external clients own their own listening port. Adding it meant `defaults()` *and* `config.schema.json`, and the `DumpDefaults` spec fails loudly if the first is missed.

## Builtin torrent engine
- **The peer pool is capped by `applyMemoryBounds` (`internal/bittorrent/bounds.go`), and the caps are constants on purpose.** anacrolix's defaults — 50 established conns per torrent, 100 total half-open, 500 known peers per torrent, 64 MiB of unverified piece data — are sized for a desktop. Each established conn is a 128 KB bufio read buffer + up to 32 KB write + 2 goroutines + 2 timers, so ten seeding torrents at stock is ~500 conns ≈ 80 MB of buffers and a thousand goroutines, against a 256 MB target. Config keys were considered and rejected: raising them past what the host has does not buy throughput, it buys the OOM killer, and a machine with room to spare should run an external client that owns its own limits. `bounds_test.go` asserts each value is *below* the upstream default, so a future anacrolix bump cannot silently turn a cap into a widening.
- **Uploaded bytes are persisted per torrent (`TorrentSession.uploaded`) and ratio is read off `uploadedBase + this process's counter`.** anacrolix's `BytesWrittenData` starts at zero every boot, so a ratio built on it alone forgave everything a torrent had already given back and a `seed_ratio` target receded on every restart — `completed_at` had always been persisted, so the seed-*time* limit worked and only ratio silently didn't. `enforceOnce` writes the total **before** its `Info()`/`wantedMissing`/paused/seedStopped gates, since incomplete and paused torrents upload too and this minute tick is the only pass that runs. `Engine.Close` flushes the counters, so only a hard kill loses up to a minute of upload; the alternative is a write on every stats read.
- `e.rates` keeps working on the **session** counter — it is a delta, so folding a constant base in would change nothing but the first sample after boot.
- **The engine owns its own peer sockets — `DisableTCP` + `ListenPacket` — instead of letting anacrolix create them**, because `Client.LocalPort()`, and every tracker announce behind it, reads `cl.listeners[0]`: an anacrolix-created listener has no removal path (`AddListener` only appends), so adding a replacement on a new port would leave the announce still naming the old one. `rebindablePacketConn` and `rebindableListener` are always rebound in step, both landing on the same port — the design leans on that agreement, not on `cl.listeners` ordering staying stable. `rebindablePacketConn.ReadFrom` must swallow the `net.ErrClosed` a rebind produces on the retired socket and retry on the replacement, because `utp.Socket` reads this conn in a loop and treats any error as a dead socket, tearing the uTP stack down for good. A rebind is otherwise selective in what it disrupts: TCP peer connections are each their own kernel socket and survive it; uTP connections all ride the one packet conn and don't.
- **`client.Close()` does reach the packet conn.** anacrolix wraps the `net.PacketConn` handed to `ListenPacket` inside a `utp.Socket` and appends that socket's `Close` to `cl.onClose`, so `Engine.Close`'s own `packetConn.Close()` call is a genuine double-close — safe only because `rebindablePacketConn.Close`/`rebindableListener.Close` are idempotent. The TCP listener is different: `AddListener` only appends to `cl.listeners`, and its doc says the caller owns closing what it registers that way, so `Engine.Close`'s `listener.Close()` is the only thing that ever closes it. `rebind` binds the replacement socket before closing the retired one, so asking a socket to rebind to the port it already holds is a real `EADDRINUSE` — `movePeerSockets` (the locked half of `SetListenPort`) guards each socket individually rather than checking only whether the pair is already correct, which is what lets a *manually retried* call converge on a partial failure (listener moved, packet conn still stuck) instead of wedging on the already-correct socket. Nothing retries automatically, though: the only caller is gluetun's `VPN_PORT_FORWARDING_UP_COMMAND`, fired once per port rotation with no retry of its own, so a partial failure persists — announcing the old port while the TCP listener sits on the new one — until the next rotation or a restart. It's logged at `observability.LevelCritical` with both ports for that reason.
- **A completed port move forces a DHT re-announce; trackers get nothing.** `SetListenPort` ends in `announceToDHT`, which calls `Torrent.AnnounceToDht` for every torrent on every `Client.DhtServers()` entry. That reads the peer port live (`incomingPeerPort`) at announce time, so an announce issued after the rebind carries the new port with no extra plumbing — and unlike the tracker side it is a *real* forced announce. There is none for regular trackers in the pinned anacrolix: `ModifyTrackers` used to force one and no longer does (`torrentRegularTrackerAnnouncer.Stop` is a no-op, and both `modifyTrackers` and the client-level dispatcher key their state by infohash, so restarting a running announcer is a no-op too — measured at 0 announces in 5s against a local tracker). A private tracker can therefore advertise the dead port for up to its whole interval; DHT is the half that can be refreshed at once. The locked rebind lives in `movePeerSockets` **so the announce runs with `e.mu` released** — `AnnounceToDht` takes the anacrolix client lock, and this file otherwise never holds `e.mu` across a call into anacrolix. An empty `DhtServers()` (`entry.DisableDHT` → `cc.NoDHT`) is a configured no-op, and a nil client is the shape `SetListenPort`'s own specs build.
- **`DisableTCP` means the engine must supply its own TCP dialers, on both paths.** `New` calls `client.AddDialer` right after construction: source-bound to `bindIP` (`tcp4`/`tcp6` picked by `bindIP.To4()`) when `bind_interface` is set, a plain unbound `tcp4` + `tcp6` pair otherwise. `cl.dialers` is populated only from sockets anacrolix itself created, so skipping either branch leaves every outbound peer connection uTP-only, silently — no error anywhere names the missing dialer.
- **The unbound path additionally sets `cc.DisableIPv6 = true`** so exactly one UDP network exists — one `ListenPacket` call, one `utp.Socket`, one DHT server, rather than two racing to read the same packet conn. The cost: anacrolix rejects every inbound IPv6 peer and skips `udp6://` trackers, while the unbound `tcp6` dialer above still dials IPv6 peers outbound.

## Selective file download
- `download.selective_files` (default **false**, runtime-toggleable) gates the feature; off is bit-for-bit today's whole-torrent grab. `download.selection_grace` (default `10m`) bounds how long a magnet-sourced selection may sit `pending` before giving up and downloading whole. `schedules.file_selection` (default `30s`) is the pass that resolves `pending` records. **The 5s resolution cadence lives inside the run, not in the schedule** (`jobs.FileSelection`): the job re-runs the pass every `selectionBusyInterval` for as long as it keeps finding pending records, capped at `selectionBusyBudget` (1 min) per run so the scheduler stays in charge. Registering it at 5s instead was thousands of ticks a day finding nothing — the query is indexed and cheap, but a *tick* never is, since the state hook commits a WAL frame through the one SQLite connection every API request queues behind. Folding it into the 30s `download_monitor` tick is still wrong for the opposite reason: that would waste up to 30s of bandwidth per magnet with no fast path at all.
- **The wanted set follows `replace_mode`**, computed one tick earlier by the same predicate the importer uses at import time (`quality.ReplacesFile`), so grab-time and import-time never disagree about what a release is *for*:

  | `replace_mode` | producer | wanted set |
  |---|---|---|
  | `none` | single-episode missing grab (`grabEpisode`), manual grab without replace | missing (`wanted` + aired) episodes only |
  | `upgrades` | RSS gap-fill (`grabPack`), RSS upgrade (`grabUpgrade`), missing-search pack (`grabSeasonPack`, per-grab `UpgradeCandidateShow` context) | missing episodes **∪** episodes whose file the release beats (`beatEpisodes`/`quality.ReplacesFile`) — this union is what keeps "a pack grabbed to fill a gap also replaces what it beats, in the same grab" true once bytes stop being free |
  | `all` | manual replace grab (`grabPackAndMark` with `replaceExisting`) | every episode in the grab's scope — the operator said replace |

  Two producers sit outside the keep-set story and are documented in their own sections: `ReplacePending` stamps `upgrades` (adoption), and the movie feed's `tryUpgrade` stamps `all` (a movie has one file and no keep-set).

  `wantedAiredEpisodes` is what the status-marking loop may ever flip to `downloading` in either mode — a pack can't contain an unaired episode regardless of what was asked to replace — while the `GrabEpisode` wanted-set itself is wider under `all`, since that mode is about the selective-download keep-set, not about which episodes get marked.
- **An anime group may write the absolute number in `SxxExx` form, and the keep-set has to read it.** TLC and Tsundere-Raws list a release as `S02E03` and name the file inside the torrent `S02E15` — TVDB's absolute 15. `library.Parse` reads a real season and episode there, so `AbsoluteNumber` is 0 and `MatchEpisodeInSeason`'s anime arm never fires; the season+episode lookup then finds no `S02E15` in a 12-episode season and `computeKeepSet` returns zero matches, failing the grab with `ErrNoWantedFiles` **before any client is contacted**. The episode is then unfillable no matter how many acceptable releases exist — measured on a homelab where the only non-rejected release for two episodes was refused this way every pass. The fallback runs **only after** the exact season+episode found nothing, so a season that genuinely holds that episode still wins, and it is anime-only.
- **Flow A (`.torrent`)**: `grab` (`internal/download/manager.go`) decodes the metainfo before `AddTorrent` and matches files to episodes with the importer's own matcher (`library.MatchEpisodeInSeason`) — anything the selector can't match, the importer can't match either, so there is no "grab it anyway" fallback. Zero matched episodes fails the grab with `ErrNoWantedFiles` **before any client is contacted** (bumps `grab_failures`, nothing to remove). Every automatic caller counts that against the anchor episode — the RSS/missing single-episode paths, the magnet pass, **and both season-pack arms** (`rss.grabPack`, `rss.grabSeasonPack`); the manual REST grabs surface it as a 422 `grab_rejected` and bump nothing; a season whose only packs all mismatch would otherwise be re-tried every tick and never reach `max_grab_failures`. The pack arms count `ErrNoWantedFiles` only, since any other grab error is the pack's alone and says nothing about the episode. Every candidate matching a wanted episode collapses the grab back to `selection_state: skipped` (not selective, take it whole) rather than applying a no-op selection.
- **Flow B (magnet)**: the file list is unknowable at grab time, so `grab` marks the source `Selective` and parks the record `selection_state: pending`; `RunSelectionPass` (`internal/download/selection_pass.go`) resolves it once `client.ListFiles` reports something. A zero-match resolution here removes the torrent **with its files**, fails the record, and bumps `grab_failures` — same outcome as Flow A's zero-match, one tick later. Past `selection_grace`, an empty or persistently-erroring `ListFiles` gives up and downloads whole (`finalizePending`) rather than hanging the record forever.
- **`selection_mode` is the invariant that keeps a restart from undoing a selection.** The builtin engine's `startWhenReady` calls `applyFilePriorities(t, mode, wanted)` every time a session is (re)armed, including every process restart (sessions restore from `TorrentSession`). `mode` gates what gets bumped off `PiecePriorityNone`: `all` bumps everything (today's behavior — manual adds, adopted torrents, every non-selective grab), `pending` bumps **nothing** (a magnet whose keep-set hasn't resolved — this is also how the builtin engine wastes zero bytes on a selective magnet with no paused-add dance, since anacrolix fetches metadata independently of piece priority), `explicit` bumps exactly `TorrentSession.wanted_files`. Both `pending` and `explicit` are persisted on `TorrentSession` and therefore **survive a restart** — the bug this exists to prevent is a `None`-priority skip (indistinguishable from "nobody decided yet") getting silently bumped back to `Normal` on the next boot, quietly re-downloading everything a selection had excluded.
- **`wantedBytes`/`wantedCompleted`** (`internal/bittorrent/wanted.go`) sum `f.Length()`/`f.BytesCompleted()` over files at priority `!= None` and are the completion/progress/ratio denominator throughout the builtin engine — anacrolix's `BytesMissing` counts every incomplete piece regardless of priority (skipped pieces included) and never reaches zero once a file is skipped, so completion would never fire without this. With nothing skipped these equal the full torrent, so full-torrent behavior needs no special case.
- **Mode `pending` means zero demand, and two places had to stop reading zero demand as "done".** `Engine.status` returns `StatusFetching` for a `pending` torrent before the `wantedMissing == 0` branch — with no file wanted that sum is 0 the instant metadata resolves, which reported a torrent that had downloaded nothing as seeding, i.e. ready to import. `CheckStatus` mirrors the same guard on the record's `selection_state` so a client that scopes progress the same way can't flip a pending record to `importing` either.
- **`ResumeTorrent` is the give-up exit from mode `pending`, for the builtin engine.** Nothing else ever writes mode `all` onto an existing session, so a `pending` torrent that is merely resumed keeps every file at `PiecePriorityNone` and runs forever asking for nothing. Resume therefore persists mode `all`, updates the in-memory state and re-runs `applyFilePriorities` (metadata unresolved is fine — `startWhenReady` reads the state it just wrote). Both callers want exactly that: `finalizePending`'s arms (grace expired on an empty or erroring listing, `ErrNotSupported`, every candidate matched) and a human clicking resume on the Torrents page. `pending` is not a paused state, so nothing is lost by the conflation.
- **§4.6 widen, not duplicate-add.** A re-grab that lands on a hash a **live selective** record already holds (`selection_state` `pending` or `applied`, `selective_files` still on, a non-empty wanted-episode list — it need not add anything new) widens instead of adding: union the new episodes into `wanted_episodes`, recompute the keep-set over the client's own file list, `SetWantedFiles`. A completed record flips back to `downloading` (the `wantedBytes` denominator grew, so the completion predicate stops holding on its own — no un-completion logic needed); the builtin additionally clears `TorrentSession.seed_stopped` and resets `completed_at` so a stale seed-time limit doesn't immediately re-stop the re-completed torrent. `grab_failures` is **never** bumped on a widen — the grab succeeded, it just landed on a torrent already held. Every caller stamps `replace_mode` through `SetDownloadRecordReplaceMode`, which only ever **raises** (`none < upgrades < all`) and silently no-ops a lower: a widen hands the caller a record somebody else's grab created, so an automatic pass stamping `upgrades` onto a hash an operator's replace-grab already holds must not revoke that `all`. Gating on `selection_state` rather than "has `wanted_episodes`" is deliberate: `wanted_episodes` is written unconditionally by every `GrabEpisode` caller, so the state check is what keeps a non-selective duplicate (a plain whole-torrent grab, an `unsupported`/`skipped` client) as an ordinary duplicate-add hit instead. A hash hit on a completed, non-widen-eligible record falls through to a normal grab. The **whole** pre-check — `localInfoHash` + `FindWidenableDownloadRecordByHash`, not just the widen arm — sits behind `selective_files`: its duplicate rejection is behavior this feature introduced, and off has to be the pre-feature path where `AddTorrent` is what detects a duplicate hash.
- **qBittorrent cannot select at add time — this was tried and rejected.** qBittorrent 5.x answers 400 ("Cannot specify filePriorities when uploading torrent files") when `filePriorities` accompanies a `.torrent` upload (container-proven against a real 5.2.1 daemon). The shipped path is **add stopped → `filePrio` (0/1) → start**: `AddTorrent` sends `stopped`/`paused` alongside a selective `.torrent`, `applySelectionAndStart` then issues `filePrio` computed from the locally-decoded metainfo (not a round-tripped `ListFiles`, which can legitimately answer empty while metadata is still settling) and starts the torrent only once every priority call has succeeded. A magnet gets the real mechanism instead — add with `stopCondition=MetadataReceived`, select, start — which is why `selection_state: pending` must suppress the paused-torrent mirror onto episode badges (`CheckStatus`/`SyncSeasonDownloadStateForRecord`) or every qBittorrent magnet grab flashes "paused" for a second.
- **Transmission's `files-wanted`/`files-unwanted` treat an empty array as "everything"** — for all five RPC-spec file fields, not just these two. `SetWantedFiles` and `AddTorrent` both compute the skip-complement and **omit the key entirely** when nothing needs skipping; sending `files-unwanted: []` to mean "skip nothing" would instead mean "skip everything." Transmission has no stop-on-metadata mechanism for a magnet, so it's the one client that relies entirely on the `file_selection` pass — waste is bounded by the pass interval, not zero.
- **Deluge's `set_torrent_options({"file_priorities": ...})` silently succeeds against a pre-metadata torrent and downloads everything** — `torrent.py`'s `set_file_priorities` returns early with no error when the torrent has no metadata yet. `SetWantedFiles` guards this by calling `ListFiles` first and refusing (a plain retryable error, not a client call) when it comes back empty. Deluge's magnet path avoids the trap a different way: `core.prefetch_magnet_metadata` resolves the metainfo **without ever admitting the torrent into the session**, so the keep-set is known and passed in `options.file_priorities` on the same `add_torrent_magnet` call — Flow B collapses into Flow A for Deluge specifically. `manager.go`'s `MagnetMetadataFetcher` interface is how `grab` opportunistically takes this path before falling back to `pending`.
- **The keep-set is written by `CreateDownloadRecord`, not only by the post-add confirmation.** `applied` is decided at create for a Flow A grab, so `selected_files`/`selected_bytes` are stored in the same insert — a confirmation call that fails for any reason other than `ErrNotSupported` leaves the record `applied` and the SPA would otherwise render "0 B of 24 GB selected". The post-add call only *corrects* the pair.
- **Every client refuses an empty keep-set before doing any work** (`SetWantedFiles` with `len(wanted) == 0`): a selective record never wants zero files, and each client's "skip the complement" arithmetic would read it as "skip everything". Same wording across all four (`<client> set wanted files: refusing to skip every file`); the builtin's guard also runs before any state or priority is touched.
- `unsupported` (`ErrNotSupported` from `ListFiles`/`SetWantedFiles`) exists for a client that cannot select at all — none of the four shipped clients' real implementations return it today (only test doubles do), so it's reachable only via edge paths, not the normal four-client surface.
- `selection_state` (`pending | applied | unsupported | skipped`) is omitted from `QueueEntry` API responses when `skipped` — "not a selective download" is the default and the common case. `selected_files_count`/`selected_bytes` are present only when `applied`; the SPA queue row reads "X of Y selected" off them, an "unsupported" hint when the client couldn't select, and renders `pending` unchanged (no special affordance — it's a transient state the pass clears within one tick under normal conditions).

## Quality scoring
- `internal/quality` is the pure scoring engine (no config/db imports): `Format`/`Condition` (Radarr-compatible matching — every `required` condition must pass, and if any non-required conditions exist at least one of those must pass too; `negate` inverts a single condition; **input that was never recorded matches nothing, negated or not**), `Profile`/`Evaluate` (band check → sum matched-format scores → `min_score` check), `ShouldUpgrade`/`UpgradableFrom`. Context builders (`ContextFromRelease`/`ContextFromRow`/`ContextFromFile`, wrapping `library.Parse` + probe data) live one level up in `internal/quality/qualityctx`, not in `quality` itself — `library` imports `config`, so `config` (which needs `quality.Profile` to build `ResolveScoredProfile`) can only import the leaf `quality` package, not anything that pulls `library` in behind it. `ContextFromRelease` reports `HasSeeders` as `seeders > 0`, not as an unconditional true: Torznab leaves the attribute at 0 when the indexer omits it, and a `negate: true` seeders condition would otherwise score every silent indexer's results as confirmed-low.
- **`Condition.eval` returns `(ok, known)`, and `known` is the whole point.** `negate` inverts only a known result, so a condition reading a field nobody filled in matches nothing rather than scoring a positive out of ignorance. The idiomatic `no-release-group` format (`release_group`, pattern `.`, `negate: true`) is what forced it: `mediaFileScore` scored a file by re-parsing `filepath.Base(f.Path)`, which the renamer wrote from the naming template — the default keeps only `{quality}` — so every imported file parsed as group-less and took the format's -100, on a real library, on every file, while `release_group` had been on the row all along. `ReplacesFile` compares that number against a full release score, so the RSS scanner read the entire library as upgradable. **Unknown is a property of how the context was built, not of the field being empty**: `ReleaseContext.EmptyIsUnknown` is set by `ContextFromRow` only. A release parse looked at the whole name, so an empty `Group` there is a real absence and still matches; a column is empty both when the release had none and when nothing filled it in. `HasSeeders` was already this flag for seeders and now reads as unknown rather than false. A `required` condition that is unknown fails the format (it cannot be proven); an unknown optional counts toward neither the quorum nor against it.
- **`ContextFromRow(*ent.MediaFile)` is how a file already in the library is scored** — `release_group` + `parsed_source`/`parsed_resolution`/`parsed_codec` + `size`, with the probe's `width`/`video_codec` winning where non-zero (so an ffmpeg-off install degrades to what the release name claimed), plus the three stream fields below. Eight of the ten condition types answer off the row; `seeders` is meaningless for a file, and `release_title` is the one that should answer but cannot. `ContextFromFile`/`ContextFromPackFile` survive for files *inside* a torrent, which have no row, and take a `*ffmpeg.Info` rather than loose width/codec so those files answer the stream types too. All six library-file call sites use `ContextFromRow`: `restapi.mediaFileScore`, `rss.feed`/`tv_feed` ×3, `importer.takesPackFile`, `restapi.replacesEpisodeFile`.
- **`release_title` is the one condition type a library file cannot answer, and `ContextFromRow` now says so.** A `release_name` column was built and reverted: the release name *is* already in the DB (`DownloadRecord.title`, `ImportScanFile.source_path`, `TorrentSession.name`), just not reachable from an arbitrary file — a pack has one record and one `.Unique()` episode edge, so episodes 2..N reach nothing; wizard/orphan files have no record; and all three referents are user-deletable (`DeleteDownloadRecord` from the queue's remove button, `PurgeRecordForHash`, `DeleteImportScan`), which would make a file's score change when the queue is tidied. `ContextFromRow` therefore leaves `Title` as the basename **and** sets `EmptyIsUnknown`, which `eval` reads as "a title condition is unanswerable here" — the basename is non-empty, so without that arm it was a confident *false* for every file in the library. Blanking `Title` instead was tried and is worse: a file then scores none of remux/vostfr/multi-audio while the release replacing it scores all of them, so **everything on disk becomes upgradable**. Reporting them unknown is what lets `ReplacesFile` drop those formats from *both* sides (see `comparableTo`). That alone once **stopped upgrades happening at all**, because the upgrade rules were written entirely in title-matched formats; it works now because the three stream condition types below answer the ones carrying the weight. What is still unanswerable from a file, permanently: `vff` vs `vfq` (both are `tags.language: fra`), `repack`/`proper`, `remux`, junk-source — facts about the *upload*, not about the bytes.
- **Three condition types are answerable from both a release name and a probed file: `audio_tracks`, `audio_language`, `subtitle_language`.** They exist because a format written only in `release_title` can never score the file it is being compared against. The idiom is one format with two optional arms — `release_title` for the release, a stream type for the file — exactly the shape `x265` already had by accident. The builtin `multi-audio` was converted to it (`title(multi|dual audio)` OR `audio_tracks >= 2`); `vostfr` and `vff` are user formats and the same rewrite applies (`\bvostfr\b` OR `subtitle_language: fra`). Languages are ISO 639-2/T and are canonicalised on **both** ends — at probe time and at `NewFormat` compile time — through `internal/langcode`, a leaf package `ffmpeg` and `quality` both import because neither may import the other and a duplicated table would drift. This is not cosmetic: a real 5425-file library held 5292 `fre` tags and zero `fra`, so a condition written either way matched nothing without the fold.
- **`ReplacesFile` scores both sides through `comparableTo`, which drops the formats the *file* cannot answer.** A format survives when every `Required` condition is known and at least one condition of any kind is known. "At least one", not all: a vostfr format's title arm is unanswerable for a row, and demanding all of them dropped vostfr entirely — leaving a file that genuinely lacked the French subtitles unable to be upgraded by a release that had them. A format written *only* in `release_title` still drops, which is the point: there the file's non-match is an artifact of the renamer. Dropping a format is not forgiving it — a "never grab this" negative still rejects the incoming release in `Evaluate`, which `qualityctx.Replaces` runs first. Measured on a real install before this: an anime profile paying `vostfr:1000` and `multi-audio:50` left every episode ~1050 below its `upgrade_until_score` of 1200, permanently, since no file could earn those points back — so every episode was upgradable by any VOSTFR release, and 86% of that install's grabs were VOSTFR.
- **`ContextFromRelease` fills the stream fields by regex over the name, and only what the name actually claims** (`applyStreamHints`): `MULTi`/`DUAL AUDIO` → `AudioTracks = 2` (a floor, matching the min-semantics of the condition), `VOSTFR`/`SUBFRENCH` → `SubLangs = [fra]`, `VFF`/`VFQ`/`VFI`/`VF2`/`VOF`/`VQ`/`TRUEFRENCH` → `AudioLangs = [fra]`. A name that says nothing leaves the field **nil**, never a zero. `VOSTFR` deliberately does not imply French *audio* — reading it as a dub is the one mistake that would score a subtitled release and a dubbed one alike. `ContextFromPackFile` applies the same hints over the release title, which is what keeps the pending-proposal preview — where the files are still in the download client and nothing can be probed — reaching the verdict the import will.
- **Band vs score are two different gates, in order.** `Evaluate` first checks resolution against `[min_resolution, preferred_resolution]` — `preferred_resolution` is a hard **ceiling** now, not a target (a release above it is rejected regardless of `upgrade_allowed`, and this reaches the RSS/missing-search feed scanners too, not just interactive search). Only a release inside the band gets its formats summed; the sum is then checked against `min_score`. A release can fail either gate independently, and `RejectReason` says which. Because the ceiling wins, a `min_resolution` above `preferred_resolution` is an empty band that rejects everything — `checkInvariants` refuses it, comparing the two through `quality.CompareResolutions` (the only exported view of `resolutionRank`, so config and the engine rank buckets off one table).
- **A `size` condition's `min_gb`/`max_gb` are per *episode*, and both bounds are multiplied by `ReleaseContext.EpisodeCount`.** One threshold then means the same thing for an episode, a season pack and an integral — the alternative was a cap that either let a 155 GB REMUX season through or rejected every legitimate pack. The count comes from the **library**, never from the release: `library.ParseSeasonSpan` reads the scope the name claims (`S03`, `S01-S05`, `COMPLETE`/`INTEGRALE`) and `SeasonSpan.EpisodeCount` totals it against `db.SeasonEpisodeCounts`, an unfiltered per-season `COUNT(*)`. An indexer never reports a torrent's file count, and the torrent's contents are only knowable after the grab — too late to gate one.
  - `EpisodeCount` of 0 (or negative) means **the library cannot say** and leaves the bounds unscaled, which is how they behaved before they scaled at all. Never read it as an empty pack: `episodeScale()` is the single place that clamps it, and collapsing a bound to zero would reject everything. The scanners' own episode indexes are filtered to what a pass may act on (`ListUpgradeCandidateShows` eager-loads with `eq.Where(candidates...)`), so they are the *wrong* denominator — a pack costs every episode it holds whether or not all of them were wanted.
  - Movies and single episodes pass 1 (`rss.singleRelease`, `restapi.singleReleaseEpisodes`), so nothing about movie scoring changed. Season-scoped searches can use one scalar because `indexer.filterToSeason` drops multi-season and complete packs; the series *browse* cannot, and uses `restapi.spanEpisodes` to size each result by its own name.
- **Each of the three TV search scopes filters the results to its own scope, in `internal/indexer/service.go`.** Indexers behind Prowlarr routinely ignore the `season`/`ep` params, and `searchAll`'s empty-result retry drops the id entirely, so what comes back is a keyword search over the whole series: an episode search answered with every other episode, and a series search with single episodes. `filterToEpisode` keeps the exact `SxxExx`, plus a release naming no season and no episode **only when it carries an anime absolute number or a daily air date** — those shows never spell `SxxExx`, and dropping them would hide every release they have. Keeping *anything* unnumbered was the first cut and it let through the bulk of the noise the filter exists to remove: a tracker that publishes under the bare show title (a real TR4KER shape — 2.5 GB, 0 seeders, no filename, no description, nothing that says what is inside), a whole different show, and any pack whose only scope word the parser cannot read. `filterToSeason` keeps season packs of that season only, not single episodes, because both callers size a result against the season's episode count and mark the whole season downloading; `SearchSeries` keeps only `library.IsWholeSeriesPack`. Titles are **preferred, never required** (`preferTitleMatches`, applied to the episode and season scopes **and to `SearchMovie`**; `SearchSeries` keeps whole-series packs only and applies no title preference): the numbers alone cannot tell one show from another, and a search for an anime's `S04E03` came back offering Reacher, Ted Lasso and Strange New Worlds — any of which can outrank the right release under a profile with no notion of which show it is scoring, after which the importer files it under the record's anchor episode. So a title-naming release wins when one exists, and the whole set survives when none does. Dropping the non-matches was tried and is wrong: `TVShow` stores `title` + `original_title` and no aliases, so a show held under a translated title (`Moi, quand je me réincarne en Slime`, original `転生したらスライムだった件`) matches none of the English releases that are most of what its indexers carry. Matching tolerates a prefix in either direction and strips a leading fansub tag, because a parsed title keeps whatever `extractTitle` could not cut. Movies have no scope filter of their own — a film names no season or episode, so the title *is* the whole filter — but they are the same keyword-search noise: a search for `Comme un chef` with a `tmdbid` set came back with 200 releases of Nonnas, Jobs and Macbeth, one of which outscored the film itself on group and codec alone. `SearchMovie` shipped raw indexer output until this was added; the three TV scopes had been hardened and it was not.
  - `filterToEpisode` reads the pack span **before** its "names neither a season nor an episode" fallback, because a `COMPLETE`/`INTEGRALE` release carries no season token either — read in the other order, the fallback keeps every integral in an episode search.
  - `SearchEpisode`'s second return is how many dropped releases were packs *covering* that episode. It is the only part of the noise an operator can act on (the season/series scopes offer exactly those), so releases for some other episode are never counted — there is nowhere to send anyone for those. `BrowseEpisodeReleases` puts it on `SearchResultList.hidden_packs`, omitted when zero, and `ReleasesTable` renders it **in the empty state too**: telling "nothing exists for this episode" apart from "it only exists inside a pack" is the whole point, and the empty list is where that distinction matters most. The RSS caller discards it.
- Score is **sum of the profile's per-format scores for every matched format**; a format the profile doesn't list contributes 0. There is no global scale — scores are relative order within one profile only. The "never grab this" idiom is a very negative score (e.g. `-1000`) on a format plus `min_score: 0`; there's no separate blocklist feature.
- Builtin/user namespace: `quality.Builtins()`/`BuiltinByName`/`IsBuiltinName` is the compiled-in, read-only library (`internal/quality/builtin.go`, 10 formats: remux, x265, x264, av1, hdr, resolution-2160p/1080p/720p, multi-audio, dubbed). Every builtin **describes** a release; none judges one. `scene-junk`, `bad-group` and `re-encode` shipped in the first cut and were removed — a group blocklist or a "screeners are worthless" rule is user preference, not a fact about the release, and shipping one makes our taste the default for everyone. Anything of that shape belongs in `custom_formats`; the release-group chips editor (Part 2 of this feature) exists so writing one is a two-minute job. Do not re-add opinionated builtins. `config.CustomFormatEntry` (`custom_formats[]` YAML, name-keyed, hot-editable) is the user layer. `config.Validate` rejects a user entry reusing a builtin name; `config.AddCustomFormat`/`UpdateCustomFormat`/`DeleteCustomFormat` re-check the same collision plus (`DeleteCustomFormat`) whether any profile still scores the name (`ErrCustomFormatInUse`). REST surfaces both through one list (`GET /custom-formats`, `builtin: true` on the compiled-in ones); `PUT`/`DELETE` against a builtin is 409. A condition that won't compile is `422` with `code: invalid_condition` on create/update/test, and the SPA renders that message verbatim (`errorText` in `web/app/lib/api.ts`, same arm as `connection_failed`) — there is no client-side regex gate, so this message is the only thing naming the offending condition. The create/update handlers call `ToFormat` themselves before `config.Add/UpdateCustomFormat` so the body carries that message rather than the same error wrapped in a config-key path; `quality.NewFormat` drops its `format %q` prefix for an unnamed draft, which is what the tester compiles. `CustomFormatEntry.Description` is optional free text a user format may carry alongside builtins' fixed, server-authored one — both surface through the same `CustomFormat.description` field and the same absent-when-empty convention, so the profile picker's hint (`QualityProfileForm`'s `Select` `Option.hint`) works identically for either kind.
- **The `release_group` condition is edited as chips, not regex** (`CustomFormatEditor.svelte`). `groupsToPattern` compiles the chip list to `(?i)^(a|b)$` with each name regex-escaped; `parseGroupPattern` is the inverse and is deliberately strict — an unescaped metacharacter, a `\d`-style class or an empty alternative returns `null` and the row falls back to the raw pattern input, which is also what `draftFrom`/`setType` use to decide `groupRaw` for an existing format. Nothing about the engine changed: the anchored regex + `negate` + a negative score already expressed exclusion, and the ruling was that the *authoring* was the problem, not the model. The raw path stays reachable both ways ("Edit as regex" / "Back to the group list"), and the way back is offered only while the pattern still parses, so switching modes can never drop something typed. `ConditionDraft.groupRaw` is editor-only and `toConditions` never emits it.
- Profile presets (`PROFILE_PRESETS` in `QualityProfileForm.svelte`) prefill the **whole** create form — `name` (the preset's own label), both resolutions, `allowed_codecs`, formats and both thresholds — and still only prefill: `applyPreset` calls `setFieldValue` and never submits. Prefilling `name` is what clears the "Name Required" flash when a preset is applied to a form that already failed validation. Codec values are ffprobe's (`hevc`, `av1`), mirroring `lib/media-info.ts` `VIDEO_CODECS`, not the human labels. No preset scores a group blocklist or a junk-source penalty — there is no builtin to name any more, and a preset must apply cleanly to a fresh install with no `custom_formats`.
- **`ResolveScoredProfile` memoises, keyed by the *resolved* profile name and `config.Generation()`.** Assembling a profile compiles every user custom format's conditions through `regexp.Compile`, and `convert.go` resolves one per episode — a 200-episode series detail was ~2,000 compilations per response. The key is the resolved name, not the requested one, because an unknown name falls back to the default and keying on the request would let an arbitrary stored `quality_profile` string grow the map. `config.Generation()` is bumped by **every** assignment to the `current` singleton (three sites in `singleton.go`), which is what makes a hot-edited custom format take effect without a restart; a fourth write site that forgot to bump it would serve the old regexes until reboot. The returned `Profile` is shared — nothing may mutate it.
- `config.ResolveScoredProfile(name)` is the one function that assembles a ready-to-`Evaluate` `quality.Profile` from config: it resolves the named profile (falling back to `quality_default_profile`, mirroring `ResolveQualityProfile`), then for each `formats[]` entry resolves the name against `BuiltinByName` first and `FindCustomFormat` second, compiling user entries via `ToFormat` on the spot. A name that resolves to neither is silently dropped (validated at config load; this only fires on a delete racing a resolve) rather than failing the whole profile.
- **The RSS feed is the only pass that goes *looking* for an upgrade** (`FeedScanner.tryUpgrade` in `internal/rss/feed.go`) — interactive search never *upgrades* (a manual grab fills a wanted item, or overwrites outright because the operator asked for it, and `quality.ReplacesFile` is consulted on neither path), and neither does a single-episode missing grab. The missing search's **season-pack** arm is the one other producer of `replace_mode: upgrades`, and only as a rider: `grabSeasonPack` unions in whatever the pack it was already grabbing for that season's gaps happens to beat, so nothing here issues a query in order to upgrade. Its upgrade context is `db.UpgradeCandidateShow` — one show, loaded inside the pack arm only once a candidate has ranked and only under `UpgradeAllowed`, so the steady state (every result rejected, no pack worth grabbing) pays nothing. A per-grab query is what makes this affordable in a pass whose ticks mostly grab nothing; a per-tick index over the library, the shape the feed scanner can justify because every tick has releases to score, would not be. Movie candidates come from `db.ListUpgradeCandidateMovies`: monitored, has a media file, **status not `downloading`** (a movie mid-re-grab isn't re-evaluated every tick, which would bump `grab_failures` on a healthy movie via the normal grab-failed path). Per candidate: skip if `!upgrade_allowed`; evaluate the incoming release and skip if rejected; build the current file's `ReleaseContext` via `qualityctx.ContextFromRow`; **the `UpgradableFrom` guard runs before the score comparison** — it checks only the *upper* bound: a file at or below `preferred_resolution` (resolved resolution required) is upgrade-eligible, a file above it or one whose resolution is unresolvable is never replaced. It deliberately does **not** check `min_resolution`: a file below the floor scores 0 (the band rejected it before any format was summed) and is exactly the headline upgrade case — 0 there means "worth replacing", not "leave alone". Only a file *above* the ceiling, or one with no resolvable resolution, also scores 0 while being the file the profile was protecting; the guard is what tells those two 0s apart. Only past that guard does `ShouldUpgrade(currentScore, releaseScore)` run: `upgrade_until_score` (0 = no cap) as a stop condition, then strictly-greater score.
- **Series upgrade the same way** (`TVFeedScanner.grabUpgrade` in `internal/rss/tv_feed.go`), off `db.ListUpgradeCandidateShows`: monitored episodes holding a file, narrowed to those with no `downloading`/`importing` record — the in-flight check is by record, not by `episode.status`, which only flips back once the import lands. The per-file rules are the movie ones (`UpgradeAllowed` → `UpgradableFrom` → `ShouldUpgrade`), applied over the episodes one release covers.
- **`quality.ReplacesFile(p, existing, incoming) bool`** is the single predicate deciding whether one release replaces one file — `UpgradeAllowed` → `UpgradableFrom` → `ShouldUpgrade`, in that order, for the reason the guard-ordering paragraph above states. The scanners call it directly and the importer through `qualityctx.Replaces` (which runs `Evaluate` first); there is exactly one place this decision is made. `DownloadRecord.replace_mode` (`none | upgrades | all`) is the record-level field it feeds: `none` is a plain gap-filling grab (skip anything that already has a file), `all` is the operator's explicit overwrite (manual replace grab), `upgrades` means "replace what this release beats" and is decided per episode at import time.
- **A season pack is judged per episode, against each episode's own file** — the invariant ("a pack upgrade never lowers any episode's score") is structural rather than something an aggregate has to buy: each episode is compared to its own file, so none of them can go backwards, no season-wide aggregate needed. A `replace_whole_season` profile key once restored the old season-level rule (beat the season's **best** file, take it whole) and was removed 2026-08-27 — max was the only aggregate under which the invariant held at the season level, but it bought that safety by freezing a whole season whenever one strong episode was in it, and nobody wanted that trade. Do not re-add it: per-episode comparison keeps the invariant without the cost, and the key forced a second rule through every pack path (`grabUpgrade`, the gap-filling `grabPack`, the importer). Single-episode releases are decided once, by the scanner, and the importer's `!= none` check just carries that decision through — the per-episode predicate and its probe re-check (`takesPackFile`) are pack-path only, since a single file has no second opinion to reach.
- **A pack grabbed to fill a gap also replaces what it beats, in the same grab.** `processItems` still tries the wanted index first and `continue`s on success — that part is unchanged — but the record it grabs carries `replace_mode: upgrades`, so the importer's per-episode plan (below) replaces any existing file the release beats while filling the missing ones. Both branches still share one `grabbed` set, so an episode is never grabbed twice in a tick.
- `file_score` is **detail responses only** — on `MediaFile` for movies, and flat on `Episode` for series (the series *list* carries no episodes at all, so nothing extra is needed to keep it out). Computed on demand from the row, never stored. A rejected/out-of-band file reports `file_score: 0`; there is no `rejected` flag — 0 doubles as both "matched nothing" and "the upgrade logic won't touch this file" by construction.
- `QualityProfile.is_default` marks the profile `quality_default_profile` names, computed in `qualityProfileToAPI`. It exists because a movie or series with an empty `quality_profile` resolves to that profile, and the SPA had no way to name it — both detail sidebars rendered a hardcoded "Server default" string instead of the profile actually in force. `POST /quality-profiles/{name}/default` (`config.SetDefaultQualityProfile`) is what writes the key, and it is **also the only way out of `DeleteQualityProfile`'s 409**: the current default cannot be deleted while it holds the role, so without a setter a fresh install's `default` profile was permanently undeletable. The SPA renders the ★ action on every non-default row and disables delete on the default one.
- `min_score` is omitted from API responses when its value is `0` — deliberate handler code (`if e.MinScore != 0` in `handler_quality_profiles.go`, the field is `*int`), not an encoding artifact. Absent always means `0`.
- Deliberately deferred (do not rediscover): **cutoff-unmet backlog search** (a scheduled sweep for upgrade-eligible items — today upgrades only happen when the RSS feed happens to see a better release, or when a missing-search season pack beats what is on disk; the predicate "file score < upgrade_until_score" already exists via `UpgradableFrom`/`ShouldUpgrade`, only the scheduler entry + rate budgeting is missing); **per-file score caching** (no `score` column on `MediaFile` — on-the-fly scoring is microseconds, caching only pays once something needs to query by score in SQL, which arrives with the backlog search above); **community format import/sync** (TRaSH Guides, Dictionarry — out of scope, everything here is local).

## FFmpeg & media probe
- `ffmpeg.enabled` (default true, runtime-toggleable) and `ffmpeg.path` — a **directory** holding the binaries, not a binary path; empty resolves via `$PATH`. `path` is read once at boot into the long-lived `Prober`, so changing it needs a restart; `PATCH /config/ffmpeg` marks the global restart flag only when `path` changes, never for `enabled` alone.
- `internal/ffmpeg` is a leaf package owning binary discovery and `Probe` via ffprobe (the future player's transcoder lands here too). Enabled but the binary missing is a **graceful degrade, never a boot error**: imports proceed on filename parsing as before, nothing is stored, and the health surface reports it via `ffmpeg_warn` on `SystemInfo` (absent when `enabled` is false — the operator opted out).
- Twelve optional `MediaFile` columns (`container`, `duration_seconds`, `video_codec`, `width`, `height`, `audio_codec`, `audio_channels`, `bitrate`, `audio_tracks`, `audio_langs`, `sub_langs`, `probed_at`). `probed_at IS NULL` means never probed; a *failed* probe still stamps `probed_at` so the row isn't retried forever — which is why `ContextFromRow` gates the stream fields on `probed_at` rather than on the values, an empty `audio_langs` being both "the probe found no tagged track" and "nothing ever looked". `audio_langs`/`sub_langs` are **comma-joined text, not a JSON array**: ent decodes a JSON field on every scanned row (the `Movie.cast` cost) and these sit on the same list paths. `sub_langs` excludes forced tracks — a forced subtitle carries signs and foreign dialogue, not the script, so counting one reports a dub as subtitled.
- **A migration adding a probe column nulls `probed_at` in the same file** — precedent `20260902141241_add_media_file_stream_columns`. Every reader takes a stamped `probed_at` as "all twelve columns were recorded", and a schema change is the one thing that can break that: ent maps a NULL text/int column to `""`/`0`, so a row probed before `audio_tracks`/`audio_langs`/`sub_langs` existed read as a confident "one audio track, no languages, no subtitles". The builtin `multi-audio` carries an `audio_tracks >= 2` arm and every real profile scores it, so on the first boot after that migration every MULTi release beat every file in the library by that margin — a library-wide upgrade with no config change behind it. Unstamping returns those rows to never-probed, which reads as unknown (the pre-feature baseline, where `comparableTo` drops the language and multi-audio formats from **both** sides), and the `media-probe` backfill refills the columns at its own pace; the price is `media_info` being absent in the API and the UI until a row's turn comes. `Nillable()` columns with nil-gated readers, a separate `streams_probed_at` marker, and a `video_codec != ''` heuristic in the backfill predicate all buy the same guarantee and are unnecessary next to one `UPDATE`.
- The importer probes the **source** file before transfer and attaches the result. Disabled or a missing binary means the import proceeds exactly as without this feature; a probe *error* now holds the record (see below) instead of importing blind.
- The `media-probe` backfill job (`internal/library/hygiene`, schedule key `schedules.media_probe`, default `15m`, 25 rows/tick oldest-first) fills in every row the importer doesn't instrument — adoption, orphan scan, bulk import. It no-ops when ffmpeg is disabled or the binary is missing, so the runtime `enabled` toggle takes effect without a restart. A file that fails `os.Stat` is skipped and NOT stamped; the drift-check job owns missing files, not this one.
- REST: a nullable `media_info` object on `MediaFile` and `Episode` (absent until probed, and absent when the probe failed); `GET`/`PATCH /api/v1/config/ffmpeg` (admin-only) returns `{enabled, path, found, resolved_path, restart_required}`, where `found`/`resolved_path` are derived from the process's live prober, not the config on disk.
- **Stream data is aggregate, not per-track.** `media_info` carries `audio_track_count`, `audio_languages` and `subtitle_languages` — a count and two language sets, which is what the quality engine can compare. Per-*track* enumeration (each track's codec, channels, title, forced flag) is not in the API and the SPA carries no type for it. The field is `audio_track_count` rather than `audio_tracks` so it never reads as a per-track array.

## Transcoding
- **There is one ffmpeg surface, and it is `ffmpeg.path`.** `internal/ffmpeg.CLI` resolves *both* binaries out of that directory (or `$PATH` when it is empty), so `ffprobe` answering says nothing about `ffmpeg` — a `transcoding.ffmpeg_path`/`ffprobe_path` pair was in the older plan and was dropped: two ways to name the same directory is two ways to get it wrong. `Prober` therefore exposes `FFmpegPath()` and `Version(ctx)`, and `GET /config/ffmpeg` reports `version` off `ffmpeg -version` — `found`/`resolved_path` are ffprobe's and cannot stand in for it.
- **`transcoding: {enabled (false), max_concurrent (1, 1–8), max_failures (3, 1–10)}` is the whole global surface**, all three runtime-editable through `GET|PATCH /api/v1/config/transcoding` with **no restart** because none is read at boot: `fill` re-reads `enabled` and `max_concurrent` off `config.Get()` on every pass of its claim loop, and `fail` reads `max_failures` at the moment it needs it. Turning the feature off therefore stops the *next* claim rather than waiting out a process lifetime. A worker that had latched the boot-time values would keep encoding after an operator said stop, which is the whole reason the read is per-tick and not per-`Start`.
- **The policy lives on the quality profile, not in the global block** — `quality_profiles[].transcode: {if: {video_codecs, containers, max_video_bitrate}, to: {container, video_codec, crf, preset, audio_codec, audio_passthrough}}`. "What counts as acceptable" is already a per-profile question (band, formats, scores); a second, profile-blind transcode rule would contradict the profile it sits beside on the first anime library. `config.TranscodeEligible(profile)` is the one predicate — the global switch **and** a resolved profile carrying a non-nil `Transcode`. A nil block means the profile's files are never touched.
  - `audio_passthrough` defaults to `[truehd eac3 ac3 dts aac opus flac]` (`config.DefaultAudioPassthrough`) because TrueHD/E-AC-3 carry Atmos and DTS(-HD) cannot survive a re-encode losslessly — copying is the only way they come out the other side. `BuildArgs` emits `-c:a:<i> copy` per *stream*, not one blanket `-c:a`, since the decision is per track and `Info.AudioCodecs` is the stream-ordered list that makes it possible.
  - The block **rides the profile REST CRUD** (`transcode` on `QualityProfile`), and there is deliberately **no removal over the API**: an absent field on an update leaves the stored policy alone, so clearing one is a YAML edit. The SPA's profile form does not edit it at all — deferred by the design round, so YAML and the API are the only authors.
- **A job is created in the same call as the `MediaFile` row** (`db.CreateMediaFileParams.QueueTranscode`, decided by `TranscodeEligible`), on both import paths and the bulk-import committers. Riding the create is what makes a later profile change need no backfill of missed rows — and it means the job and the file cannot disagree about whether one exists. The hygiene **orphan scan does not queue**: those files arrive with no import decision behind them and the manual `POST /transcoding/scan` is the door for them.
- **`Evaluate` never re-encodes HDR/DV video in v1** — a PQ/HLG transfer or a Dolby Vision configuration record suspends the codec *and* bitrate rules; only the container rule survives, so an HDR file in the wrong container still remuxes. Re-encoding HDR without carrying its metadata is how a library ends up with grey, washed-out masters, and carrying it correctly (`hdr: reencode`) is a feature of its own that was not built. The container is judged by the **file extension**, not by ffprobe's `format_name` — `matroska,webm` names two containers and cannot pick one.
- **The output is written beside the original as `<base>.streamline-tmp.<container>`, and the marker is load-bearing.** A rename across filesystems is a copy, so a temp file in `/tmp` would double the I/O of every transcode on a NAS; landing it in the library is what makes the swap an atomic `os.Rename`. The marker is also what `recover` sweeps at boot, over both library roots, through `os.OpenRoot` — the paths come off the filesystem rather than the DB, and a symlink planted in the library would otherwise turn the sweep into a delete anywhere on the host.
- **Verify before swap, always.** The encode's duration must match the source's within two seconds (containers round), and audio the source had must have survived. Both run on a context that outlives the job's own cancel, so a cancel arriving mid-probe reads as a cancel rather than as a corrupt output. Past the swap the row is updated with `path`, `size`, `format`, `size_before` and `transcoded_at`, and **every probe column is nulled** alongside `probed_at` — the bytes changed, so a stamped `probed_at` would be a confident lie and the `media-probe` backfill re-reads them at its own pace (the same guarantee the stream-column migration bought).
- **Failure is retryable; failure *after* the swap is not.** `attempts` climbs to `max_failures` and then parks the row `failed` with the last 4 KiB of ffmpeg's stderr as `error` — ffmpeg names the reason it gave up in its last lines, and the banner above it is what nobody reads out of a queue row. A DB write failing once the file has already been replaced is terminal instead (`errAfterSwap`): a retry would re-probe a source that no longer exists. It is logged at `observability.LevelCritical` naming **both** paths, because on a container change the row still points at a deleted one and only an operator can reconcile that.
- **Boot recovery is two moves and both are needed.** Rows left `running` by a dead process reset to `queued` (nothing else would ever claim them again), and the stray temp files those encodes left are swept. Neither covers the other: a swept temp file with a `running` row is a job nothing drains, and a requeued row beside a half-written output is an encode that resumes onto its own garbage.
- **Cancel kills ffmpeg; a cancel arriving after the rename completes anyway.** The last honoured checkpoint sits between verification and the swap — nothing has moved there, so the deferred remove drops the encode and the library file is untouched. Past it the work is done, and completing the job is what keeps the row and the bytes on disk saying the same thing. `claim` registers the cancel func under the *same* lock that books the slot: registering it in `runJob` instead left a window where a cancel took the not-running branch, marked the row canceled, and the encode carried on and completed over it.
- **Progress (`percent`, `eta_seconds`, `speed`) lives in worker memory only** — parsed off ffmpeg's `-progress pipe:1`, held in a map keyed by job id, and absent for a `running` row whose encode belongs to a process that has since restarted. Persisting it would be a WAL frame per second per job through the one SQLite connection every API request queues behind, to describe a number that is stale the moment it is read.
- **REST (`admin`, all four):** `GET /transcoding/queue` (newest 200, **no `status` filter** — the SPA filters client-side), `POST /transcoding/jobs/{id}/cancel|retry` (204), `POST /transcoding/scan` (202). All four answer **409 while `transcoding.enabled` is false**, which is what the SPA reads as the "feature off" screen — an empty list would read as "nothing queued". Cancel and retry have **no 404**: each store update is one conditional statement, so an unknown id and an already-finished job are the same zero rows affected and there is nothing to tell them apart. Scan additionally 409s when a scan is already walking, and when `Ready()` is false (ffmpeg disabled or its binary missing) — queueing rows no worker can claim leaves work nothing drains and nothing explains.
- **The scan re-probes every file** rather than reading the stored probe columns: `HDR` and `AudioCodecs` are what the rules need and neither is a column. That is why it is manual and rare rather than a schedule entry.
- SPA: `/activity/transcoding` (its own route, the third row under Operations, admin-only — which is why `activityLinks` is `$derived` rather than constant) and `/settings/transcoding` (save-per-control, no form; it *reads* `/config/ffmpeg` to report `resolved_path · version` rather than duplicating Media probe's controls). "Scan library" sits on both. `queued`/`running`/`succeeded`/`canceled` are four new `StatusKind`s aliased onto existing `--status-*` hues (`failed` already existed) — the same move `importing` made beside `grabbing`, and for the same reason: borrowing the kind outright would have made a queued job's pill read "Wanted" and a canceled one "Paused".
- Deliberately **not** built, so nobody rediscovers them: a scan-status endpoint (the queue is the status), `max_failures` on the job payload, the profile-form `transcode` section, `hdr: reencode`, hardware encoders (`-c:v h264_vaapi` and friends — device plumbing, per-host capability probing, and a fallback path, for a feature whose bottleneck on a homelab is usually the disk), a `-ffmpeg` image variant (the runtime image already ships static ffmpeg/ffprobe), `transcoding.ffmpeg_path`/`ffprobe_path`, and `SystemInfo.ffmpeg_version`/`transcoding_warn` (nothing read them).

## Bulk import matching
- `library.Parse` takes the **last** year token and never one at offset 0, and `extractTitle` cuts at that token's recorded byte offset. Taking the first, and cutting by re-searching the year's *text*, left numeric titles (`1917`, `2001 A Space Odyssey`) with an empty title and no candidates, and ate year-like suffixes (`Blade Runner 2049`, `Fantasia 2000`).
- **`seasonEpRe` takes a third episode digit** (`S(\d{2})E(\d{2,3})`). A season past 99 episodes is rare but real — Kaamelott's first four Livres are 100 shorts each — and pinned at two digits `S01E100` parsed as episode **10**: silently, since nothing about the name looks malformed, so the file matched the wrong episode or none at all and the real one stayed `wanted` forever. The season stays at two digits; widening it makes `S1E1` ambiguous against a regex that carries no `\b` anchor.
- **A release group may carry its own dash**, and `groupRe` stops at the last one — `…x264-tsundere-raws` parsed as `raws`. `expandHyphenatedGroup` walks left from the captured group over further dash-joined words, stopping at a word holding a `.` or a space (a separate token: `WEB-DL.x264-GRP`, `Blu-Ray x264-GRP`) or at a known technical tag. Widening `groupRe`'s character class instead was tried on paper and is wrong: leftmost-match then starts inside `WEB-DL` and `cleanGroup` rejects the whole tail, losing the group entirely.
- **Resolution is normalised at parse time** (`normalizeResolution`: lowercased, `4K` → `2160p`). `quality.resolutionRank` is a plain switch, so a group's `1080P` ranked 0 and `Evaluate` rejected the release as "resolution outside profile band" — a whole release lost to the case of one letter, on a real TR4KER listing. `extractTitle` therefore re-finds the *original* token via `resolutionRe` for its cut marker, the same dance `Source` already does, since the stored value no longer appears in the name as written.
- **A multi-season chain is joined by more than a dash.** `seasonRangeRe`'s separator class covers `-.,+&` and space, because `Demon Slayer S01 & S02 & S03` is a real shape and, read as one season, it surfaced in a season-1 search offering every season. `ParseSeasonSpan` bounds a range with `seasonRangeBounds`, which reads *every* `Sxx` token rather than the pair the regex matched: pairwise matches cannot overlap, so a chain matches `S01 & S02`, resumes past it, and sizes the pack two seasons short.
- **The season token has three spellings and "complete" qualifies whichever noun the name gives it.** `longSeasonRe` reads `Season 4` / `Saison 04` alongside scene's `S04`: without it a French pack (`Breaking Bad Saison 04 Complète Multi …`) named no season at all, which reads as "single episode of nothing" and walked through every scope filter. And `IsWholeSeriesPack` no longer fires on a bare `complete`/`complète`/`intégrale` tag when the name *also* names one season — `Breaking Bad S05 Complete Multi 1080p` is a season-5 pack, and reading it as whole-series dropped it from a search for exactly the season it holds. A season *range* still wins over both, since `COMPLETE S01-S05` spans five. `ParseSeasonSpan` ranks the same way (range → single season → bare complete) and its complete arm moved below the season check for it.
- **A season pack's title is cut at the bare season token**, not at the resolution. `extractTitle`'s marker list only ever held the `SxxExx` match, which is empty for a pack, so everything between the season and the resolution was glued onto the title — `Good.Omens.S03.MULTi.VF2.1080p…` parsed as `Good Omens S03 MULTi VF2`, which `TitleMatches` can never equal the library's `Good Omens`. Manual-torrent adoption dropped every such pack silently (at the time `AdoptManualTorrents` `continue`d on no match; today it would land as an `unidentified` proposal). `rss.releaseShowKey` had been trimming a trailing ` sNN` off its key to compensate; that only covered packs with nothing between the season and the resolution, and the trim is gone now that the parser is right (the function survives to trim an anime absolute number, which `extractTitle` still leaves in the title).
- **Bare `WEB` normalizes to `WEB-DL`**, not to a third source value. Groups spell the same untranscoded stream rip both ways and the *arr parsers fold it the same; kept apart, a `source` custom-format condition written against one scored nothing from the other, in both directions. `WEBRip` stays its own value — that one is a re-encode. The editor's source picker no longer offers `WEB`, and an existing `custom_formats` condition spelling it that way now matches nothing (six values in a dropdown, no migration).
- `library.ParseEmbeddedIDs` lifts `{tmdb-N}`/`{tvdb-N}` out of a path. Both classifiers consult it **first** and treat it as authoritative — the path was rendered from that id, so a title parsed back out of it can only lose information.
- Both classifiers **rank before truncating** (`rank.go`: exact title/alias > year agreement > prefix > provider order). TVDB returns the right series for "Dororo" at index 15 and `showCandidateLimit` is 5; slicing the provider's order first threw away the entry the scoring was meant to find.
- **Identification comes before the existing-library lookup**, in both `Classify` and `ClassifyShow`. Scanning candidates for a tracked id up front resolved ambiguities by whichever tracked row ranked higher: two rows normalising to "Spiral" (TVDB writes the 2017 one's year *inside* its title) made a 2005 folder come back `existing` against the 2017 row, and 76 files were adopted into it as a **success**.
- `normalizeTitle` strips a trailing `(YYYY)` — TVDB's in-title disambiguator — so a disambiguated entry can equal the folder it belongs to. `TitleMatchesAny` also matches TVDB aliases + translations, which is the only way a romaji folder (`Kimetsu no Yaiba`) reaches an entry stored under its English title.
- Confirmation needs **exactly one** match: a unique year among title-matches, else a unique title match. Requiring a parsed year left every year-less series folder ambiguous (104 of 104 across two real scans; the fix confirms 74).
- `ApplyTemplate` runs substituted values through `SanitizePath`. The rendered string is a path whose `/` are structural and callers split on them, so a title carrying its own (`In/Spectre`, `Face/Off`) became two directories — which sanitising the *split segments* afterwards can no longer see.
- `SanitizePath` collapses whitespace runs and trims after replacing: `":" -> " -"` and the outright deletions each double a space they already had beside them (`2001 : L'Odyssée` -> `2001  - L'Odyssée`, `A | B` -> `A  B`). Both rename services `PruneEmptyDirs` the source directory after a move, so a re-rename pass over an existing library doesn't leave one empty folder per affected title.
- **Both rename services read the release facts off the `MediaFile` row (`library.ParsedFromMediaFile`), never off the current basename.** The renamer *writes* that basename from the naming template, and the default template keeps only `{quality}` — so the first rename dropped the source, the codec and the group, every pass after it re-parsed a name that no longer carried them, and a file whose quality was never in the name re-rendered `[]` forever while `release_group`, `parsed_resolution` and a full probe sat on the row untouched. This is the naming half of the defect `qualityctx.ContextFromRow` fixed on the scoring side; same shape, same fix. Precedence is probe → stored parse → basename, the basename last but not dropped because it is the only evidence for a row the importer never instrumented (orphan scan, adoption, a bulk import the `media-probe` backfill has not reached). The probe wins outright for **resolution** and only backfills the **codec**: 2160p is 2160p however it was measured, while ffprobe's `hevc` and a release's `x265` are different vocabularies and `{codec}` in a template means the second — so a measurement fills that field only when nothing claimed it, rather than rewriting every name that has one.
- **An empty token wrapped in a bracket pair takes the pair, and the whitespace before it, with it** (`templateTokenRe` captures `(\s*)([\[(])?…([\])])?`; `bracketPair` requires the two halves to match). Punctuation in a template delimits a value and with no value there is nothing to delimit — without this, fixing the paragraph above still left `13 Hours (2016) [].mkv` for every file that genuinely has no quality anywhere, and the name never converged because the next pass re-planned it. A **bare** token is deliberately left alone: `{title}-{group}` has no pair to remove and inventing a rule for the separator would rewrite names nobody complained about. One unmatched half is literal text the template author wrote for some other reason and survives untouched.
- `commitAttach` honours `scan.Mode`: a rename scan relocates `existing` entries too. Attaching them where they lay split the library across two roots and took an inode sweep to find.
- Commit **re-resolves against current state** instead of trusting scan-time classification: `addOrFindMovie` / `resolveShow` return the existing row when the tmdb/tvdb id is already in the library. Otherwise a scan that sat in review while another added the title failed with a UNIQUE violation, and pointing a row at an existing show — the normal way to fix a bad match — was impossible.
- `commitShow` matches the **whole folder before anything moves** (`planEpisodes`), and fails the entry when at most half the files match an episode. Adopting anyway is what wrote 7 of 76 files into the wrong series. A show already in the library reports `outcome: attached`, not `created`.
- Episodes have their **own size floor**, `library.MinEpisodeSize` (5 MiB) against `MinMediaSize`'s 50 MiB. The feature floor is a movie-shaped assumption: Kaamelott's first four seasons are 3-minute shorts, so it hid 228 of a 248-file folder and the scan reported `file_count: 20` — which then failed `planEpisodes` because the survivors weren't episodes. `findMediaFile` takes the floor as a param, `placement.minSize` carries it per media kind, and `ListVideoFilesRecursive` (four series-only callers: the bulk-import scanner and committer, the hygiene series scanner, the importer's pack path) uses the episode one. `file_count` and the `only N of M` denominator are the same list, so anything that filters one moves the other.
- The zero-match guard also fires on a **re-numbered release** — `S02E23` for a season with 22 episodes — and is right to. `have=212/214` is not evidence the two files are the missing pair; check the season rows.
- `TVDB.SearchSeries` retries an **empty** result with each half of the query (`queryHalves`, ≥4 words, leading then trailing). TVDB's scorer returns nothing for a show's own full title while returning it for substrings — `Zom 100 Bucket List of the Dead` finds nothing, `Zom 100 Bucket List` and `Bucket List of the Dead` both find it, and no rule separates the substrings that work. Native-script titles rank best (15/15 in a real sample, `日常` first of 44) but aren't known before matching. A query that returns *junk* rather than nothing (`Baki` → `Bali`) is not helped: the show is absent from the result set, so ranking can't recover it.
- **Season names need one request each** (`TVDB.translateSeasons`). The extended series record carries season names only in the series' original language, and its `?meta=translations` covers the series, not its seasons — so an anime's arc names stayed Japanese (`柱稽古編`) on a French install while everything around them was translated. `GET /seasons/{id}/translations/{lang}` is the only form TVDB offers, hence the per-season cost and hence capturing `seasons[].id` from the extended payload. A miss is ordinary and comes in two shapes — 404 for a language TVDB holds no record for, and a record holding only an overview (`"name": null`) — and both keep the original name, so the error is dropped rather than surfaced: one untranslated season must not fail a refresh.
- Series searches query **both** `show.Title` and `show.OriginalTitle`, mirroring movies — all four call sites (`BrowseEpisodeReleases`/`BrowseSeasonReleases`/`BrowseSeriesReleases`, `rss.searchShow`). `show.Title` is the *local* title, so on a non-English install it is the name a scene release is least likely to carry; `dedupTitles` collapses the pair when a show has no language override, so a translated show costs one extra query per indexer and an untranslated one costs nothing.
- Series `type` is inferred by `metadata.inferAnime`: the literal `anime` genre, **or** an animation genre plus a Japanese origin language/country. It drives absolute-number matching, so a miss silently mis-matches every file. `PATCH /series/{id}` takes a `type` override and `UpdateTVShowMetadata` deliberately **does not refresh** `type`, so the override survives.
- `POST /library/imports/{id}/decisions` applies one decision across a scan, narrowed by `classification` and/or `ids`, dispatching on the scan's kind. Reviewing a 465-file scan through the per-row PATCH cost 465 requests.
- Every list endpoint bounds `limit` to `[1, 100]` (200 for activity) and **400s** a value outside it (`pagination.go` `limitOr` — there is no request-validation middleware, so the spec's bounds are enforced there). The SPA's `apiAllPages` (`web/app/lib/api.ts`) walks pages at `PAGE_LIMIT = 100` against `total`; the handlers used to clamp silently, and asking for `limit=500` — which nine call sites did — showed 100 of 621 movies with no indication anything was missing.
- `pathmigrate.WarnOnDrift` logs CRITICAL at boot for a root whose stored paths all sit elsewhere. Nothing else notices a remount. For movies/series the message warns of pruning (`drift-check` deletes those records after `drift_grace_ticks`); the downloads root warns about imports instead — nothing prunes download rows on drift — and counts only **live** rows (downloading/importing/held/pending), because terminal rows (dismissed adoption tombstones included) keep their creation-time save_path forever and would hold the warning on for a legitimately moved root.
- Movie matching compares the parsed title against **both** `Title` and `OriginalTitle` (`TitleMatchesAny`), mirroring the series alias path. TMDB answers in `metadata.language`, so a French install is offered `2001 : L'Odyssée de l'espace` and nothing else — the right film under a title an English folder can never equal.
- `otelx.RecordSpanError(span, nil)` returns nil and leaves the span alone. It used to deref the error for `SetStatus`, so a missing `if err != nil` was a panic the handler reported as a 500 nowhere near the mistake — which is exactly how `BulkDecide` shipped and how the dev server caught it.
- Connection-test 422s carry `code: connection_failed` and the SPA renders their message verbatim — it is composed by our own client code and is the only place the upstream status appears. A plain 422 reads "some of those values weren't accepted", which blames credentials that are fine.
- **A refused grab answers `422` with `code: grab_rejected`**, and the SPA renders that message verbatim (`errorText`, same arm as `connection_failed`). All four grab handlers share it — `GrabMovieRelease`, `GrabEpisodeRelease`, `GrabSeasonRelease`, `GrabSeriesRelease` — over `download.ErrUntrustedSource` and `ErrNoWantedFiles`. Without a code the SPA falls through `BY_CODE` to `byStatus(422)` and shows its generic "some of those values weren't accepted", which blames the request body: on the homelab, two anime episodes refused for `ErrNoWantedFiles` (the `SxxE<absolute>` keep-set gap) were indistinguishable from a malformed release payload, and the message naming the actual reason — the sentinel plus the caller's own release title — was discarded before it reached the screen. `errUnprocessable` still has no code by design; a 422 whose message is a *diagnostic* rather than field validation needs one, or the message never renders.

## Import verification & holds
- The importer verifies a probed source against the release claim before any transfer (`verifyFile` in `internal/importer/verify.go`, a pure function) and parks a failing record at `download_record.status = held` with a `hold_reasons` JSON column, returning **nil** — a hold is an outcome, not a failed attempt, so `import_attempts` doesn't move.
- Four checks, each producing one `{file, check, expected, actual}` reason: `corrupt` (probe error — nothing else is evaluable, so it is reported alone), `resolution`, `duration`, `codec`. Plus `always_ask` (`library.probe.always_ask`), which holds an otherwise-clean import and needs no probe, so it fires with ffmpeg off. A source that cannot even be resolved (`ErrNoMedia`) fails the import as a counted attempt instead of holding.
- **Resolution is bucketed by WIDTH**, not height: scope aspect ratios crop height (1920×800 is 1080p). ≥3200 → 2160p, ≥1800 → 1080p, ≥1200 → 720p, else 480p. Only a bucket *below* the claim holds; higher never does, and the claim parses from the payload basename with the release title as fallback — only when both parse nothing is the check skipped. `4K` and odd casing normalize to their bucket.
- `duration` compares against the metadata runtime (movie `runtime`, episode = its show's) scaled by `library.probe.min_duration_ratio` (default `0.5`); runtime `0` skips it. `codec` holds when the profile's `allowed_codecs` is non-empty and the probed video codec isn't in it (case-insensitive); empty = any codec.
- A probe that never ran (ffmpeg disabled/missing) verifies **nothing** — nil info with a nil error must not read as corrupt.
- Season packs are verified **before anything moves**, but only over the files the import actually plans to take: the importer builds a per-file plan first (episode match, existing-file lookup, then probes every matched file — the probe result feeds the `replace_mode` decision via `quality.ReplacesFile` under `upgrades`, since the incoming width/codec come from it) and only runs the verdict/hold-reason pass over the files that plan marked for import — a corrupt file belonging to an episode the import was never going to touch doesn't hold the record. A file matching no episode isn't probed at all. Under `replace_mode: all` the planned set is every matched file, so that mode verifies whole exactly as before. Any planned file's reasons still hold the entire record, reasons itemised per file — importing part of the *planned* set and holding the rest would split a season across two states.
- `POST /api/v1/downloads/{id}/resolve` (admin) takes `{action: import|regrab|delete}`. `import` sets `verification_bypassed` and re-enqueues, so the re-run imports as-is; `regrab` and `delete` both remove the torrent **with its files** and fail the record, differing only in whether the movie goes back to `wanted` for another search. Episodes revert to `wanted` on both. An unknown or missing action is a 400, and 409 when the record exists but isn't held; the queue verbs (pause/resume/cancel) answer 409 on a held record, pointing at resolve. Single-file replace imports verify **before** the existing file is replaced, like packs.
- Held records appear in the live queue (`ListActiveDownloadRecords` includes them) with `status: "held"` and `hold_reasons`, which is what the SPA's ResolveDialog renders.
- Deliberate limits: no release blocklist, so a re-grab may re-find the same release; holds are per-record even for packs; `hold_reasons` is cleared on resolve rather than archived.
- Runtime image ships static `ffmpeg`/`ffprobe` binaries (`mwader/static-ffmpeg`, digest-pinned) copied into `/usr/local/bin` — the distroless final stage has no package manager to `apt`/`apk` install into, and static-ffmpeg's binaries have no external deps so a bare `COPY --from=` is enough.

## Adopting a manually-added torrent
- `download.AdoptManualTorrents` (`internal/download/adopt.go`, run on the `download_monitor` tick) matches every untracked seeding/completed torrent the enabled clients report against the library, and either auto-imports or files a `pending` proposal. qBittorrent's `ListTorrents` filters to the `streamline` category and the builtin engine only holds what streamline added, so nothing an operator didn't put there can reach this pass.
- **A release matching nothing in the library becomes an `unidentified` proposal, not a silent skip.** It is the one proposal carrying **no media edge** (both `DownloadRecord` edges are optional and `events.hooks` skips an owner-less row rather than failing the mutation, so the row inserts cleanly). That last part was a claim before it was true: `downloadRecordOwner` fell through to `m.IDs(ctx)`, which ent refuses outright on `OpCreate`, so the hook failed the insert and *every* unidentified adoption was dropped with one `adopt: persist failed` line at WARN. A create carries its edges in the mutation or not at all — there is no stored row to fall back to — so `OpCreate` now returns the empty owner before that query. Dropping it was what made adding a torrent for an untracked title a dead end: no record, no proposal, nothing above debug in the log, and no way to point at it afterwards. Every `ok == false` from either classifier lands here, so no path through the loop is silent any more.
- `POST /activity/pending/{id}/identify` `{kind, provider_id}` (admin) is how it gets a title: add the movie/series when the library lacks it, then link the record. **Both `movie.GetByTMDBID` and `db.FindTVShowByTVDBID` report "not in the library" as a nil row with a nil error** — testing the error instead of the row is a nil deref, and a mock returning `ent.NotFoundError` hides it through a green suite (it did, and the panic surfaced on the first real click). The anchor episode comes from `download.AdoptionEpisode`, shared with `classifyEpisodeAdoption` so a hand-identified pack lands on the same episode the automatic path would have picked. 409 when the proposal already carries media; 422 when the chosen show has no counterpart for the season the name claims.
- **A pack proposal links one anchor episode, and `GET /activity/pending/{id}/preview` is what stops that from being the whole story.** `AdoptionEpisode` picks the first episode the release can *fill* (a whole-series pack names no season, so `parsed.Season` is 0 — the specials, not "unknown" — `AdoptionEpisode` orders the numbered seasons first with specials last, and `packAnchor` takes the first episode holding no file, falling back to the first episode in scope when every one already does — the pack is then an upgrade); the preview then reads the torrent's own file list off its download client and buckets every file the way the importer will: `imports` (holds no file), `upgrades` (holds a file this release beats), `keeps` (its file wins, or no profile ranks it), `unmatched` (a count — extras, or a name the parser cannot read). It applies the importer's ext/size/sample filters and reaches the per-file verdict through the *same* `qualityctx.Replaces` `takesPackFile` uses, so the counts cannot promise what the import then skips. What it cannot mirror is the probe — the files are still in the client — so `upgrades`/`keeps` are a name-and-size estimate and the SPA says so. 409 for a proposal with no episode edge, 422 `connection_failed` when the client cannot be listed.
- **The preview decides the pack row's label and its actions**, which is also what repairs a record identified before the anchor fix without migrating anything. The label drops the anchor episode (`Kaamelott · S03`, or `· N seasons`), since naming one episode read as a proposal to import that episode. And the two actions stop being alternatives: a pack can both fill gaps and beat files, so **Import** shows when `imports` is non-empty and **Replace** when `upgrades` is, each hidden when it would do nothing. `has_file` is not consulted for a pack at all — it is the *anchor's*, so it once offered Replace on a pack that was purely filling gaps. Both buttons are disabled while the preview is in flight so neither changes under the cursor; a single-episode record keeps the old `has_file` either/or.
- **`ReplacePending` raises `replace_mode` to `upgrades` and deletes no media file** (it may still remove the *old torrent* when the body asks with `remove_old_torrent`, best-effort and only for a distinct hash). It used to pre-delete the matched media's file in the handler, which was wrong three ways: on a pack it deleted the *anchor's* file — a handle, not necessarily anything the torrent holds — while the record stayed `replace_mode: none`, so the importer then skipped every other episode that had a file; and on every shape the delete ran before anything was probed, so a held import had already destroyed the only copy on disk, the exact ordering `importSingleEpisode`/`importMovieRecord` go out of their way to avoid. `upgrades` rather than `all` because a pack proposal is not a release anyone inspected: `quality.ReplacesFile` decides per episode against that episode's own file, so a better file already there is kept. A movie or single episode has no second opinion to reach, so the importer's `!= none` check reads it as the plain overwrite it is. Replace can therefore legitimately do nothing — which is why the row hides it when `upgrades` is empty.
- Identify leaves the record `pending` — naming it is not accepting it — so the existing Import/Replace/Ignore still decide. `ImportPending`/`ReplacePending` answer **409** on a record with no media edge, since there is nothing to import into or replace. `PendingItem.media` is absent for these and is what the SPA keys the Identify action off; `parsed_title` rides along (present only then) because the raw release name is a useless search seed.
- Adding a series through identify uses `tvshows.Add` exactly as a hand-add does, so the show arrives monitored and the missing-episode search will start filling its other seasons. That is the same consequence as adding it yourself, deliberately not special-cased.
- The RBAC table (`internal/server/restapi/rbac.go`) is **deny-by-default and keyed by operationId** — a new endpoint 403s with `operation missing from the RBAC table, denying` until it is listed there.

## Media events
- One table, `MediaEvent` (was `MovieEvent`, renamed with a data migration that carries the rows across — `20260824081500`). Three **optional** owner edges: `movie`, `episode`, `tv_show`; exactly one is set and `events.Record` refuses a row with none. The old table was movies-only with a *required* movie edge, so every series grab, import and drift silently recorded nothing — the hooks bailed by design (`downloadRecordOwner` still walks movie-then-episode, it just no longer gives up).
- The lifecycle types are written by ent mutation hooks (`internal/events/hooks.go`, installed by `Register`); `drift_*` and `searched` are direct `events.Record` calls from the drift job and the searchers (below). Hooks: `DownloadRecord` create/status → `grabbed`/`download_completed`/`download_failed`; `MediaFile` create → `imported`; `ImportScanFile`/`ImportScanShow` outcome=failed → `import_failed`. A `Record` failure fails the mutation and runs inside the caller's transaction.
- `drift_detected` fires on the **first** tick that cannot stat a file, `drift_confirmed` when the grace window expires. The edge needs `MediaFile.missing_since`: `last_seen_at` just stops advancing, so it cannot tell the first missing tick from the fifth. `BumpMediaFilesLastSeen` (batched — one UPDATE per tick, not one per row through SQLite's single connection) clears it; `MarkMediaFileMissing` sets it and reports whether *this* call was the one that did.
- `searched` is recorded **once per search invocation, at the scope it was issued at** — not once per item. `EpisodeMissingSearcher.searchShow` tallies every season it touched and writes one series-scoped row (`{seasons, episodes_searched, grabbed, packs}`); the SPA renders `Show · Season 3` when exactly one season is in the list. Per-episode rows would be thousands per tick on a real library. Movies record one per `SearchOne`, in the same defer as the outcome metric. **Browse-releases endpoints record nothing** — they grab nothing, and the grab that follows already fires `grabbed`.
- `ActivityEvent` carries `movie` / `episode` (an `EpisodeRef` with `series_id`) / `series` (a minimal `SeriesRef` — never the full `TVShow`, which drags the season tree). `GET /activity` takes `series_id`, matching both the show's own rows and its episodes'.

## Media server refresh
- The importer calls `mediaserver.Dispatcher.RefreshAll(ctx, kind, libraryPath)` after every successful import, `kind` being `movie` or `series`. Jellyfin/Emby ignore both args and refresh everything; Plex rescans one section, so the kind picks between `library_section` and `library_section_tv`. Passing only the path meant an episode import poked the *movie* section, and `library_section_tv` was dead config outside the play-on deeplink.
- **Plex's path match is a fallback, not the mechanism.** `findSection` compares `libraryPath` against the section locations Plex reports, which are Plex's *own* mount paths: in any containerised install ours is `/srv/streamline/movies` and Plex's is `/data/movies`, so the match finds nothing and the refresh used to fail with `no section found for path …` — imports landed and nobody's library ever saw them. On a miss it now WARNs and refreshes every section, matching what Jellyfin already does. Setting `library_section`/`library_section_tv` skips the lookup and scopes it back to one.
- Both keys are reachable from the settings form; discovery reports each section's Plex type, so each picker only offers sections of the type it names.
- **Discovery has two endpoints, and the saved-server one is not optional.** `POST /media-servers/discover` takes `{server_type, host, api_key}` and serves the *create* form, where the row does not exist yet. A saved server's token never reaches the browser (the read view carries only `api_key_set`), so the edit form has no key to send and that endpoint would be handed an empty one — which is why `POST /media-servers/{name}/discover` (`DiscoverSectionsByName`, mirroring `TestByName`) runs against the stored secret instead. Before it existed the edit form's Discover button was permanently disabled behind `!api_key`, so section keys were unobtainable for any configured Plex server.
- Discovery always fills the pickers — `discover.onSuccess` only assigns `sections`, and the section `Select`s are marked `readOnlyExempt` so they stay usable under `read_only` even though the rest of the form is locked. What `read_only` blocks is *saving*, not picking, so the pickers stay useful for figuring out which section is which. A separate "Show config snippet" button (visible once `lock() && sections.length > 0`) opens `PlexSectionsModal`, which shows the section keys the operator picked plus a paste-ready YAML block to commit by hand — same shape as `PlexCredentialsModal` for the PIN token. Discovery and PIN sign-in deliberately skip `readOnlyLock` — they only read remote state (see the note on the function itself).

## Re-identifying a library entry
- `POST /{movies,series}/{id}/reidentify` (admin) repoints a row at a different provider id **in place**: same row id, same files, same download history and requests. 409 when the target id is already in the library (`tmdb_id`/`tvdb_id` are unique — merging two entries is a different feature and was deliberately not built), 400 on zero or unchanged, 404 unknown.
- Movies: `SetMovieTMDBID` → refresh metadata → refetch the poster (it is cached by **row id**, so it keeps showing the old title until replaced) → handler runs `renamer.Apply`.
- Series: the files are **detached before the tree is reconciled**, and that ordering is the whole feature. `ReconcileEpisodes` deletes seasons/episodes the provider no longer reports and returns their paths for deletion from disk; with a swapped tvdb id that is every episode of the old show, so a naive set-id-then-`RefreshOne` wipes the library it was asked to repair. Order: fetch the new show (before any write, so a bad id changes nothing) → `DetachEpisodeMediaFiles` → set id → metadata → re-infer `type` → reconcile → re-attach by (season, episode) → rename.
- A file whose S/E has no counterpart in the new show keeps its place **on disk**; only its `media_file` row is dropped, and the path comes back in `unmatched`. A provider numbering seasons differently is not evidence the media is unwanted.
- Re-identify is the one path that **does** re-infer `type` — `UpdateTVShowMetadata` never touches it because an operator may have corrected it, but that correction was about the old show.
- No undo is needed: the inverse is the same call with the old id, files included.
- `db.FindTVShowByTVDBID` reports "not in the library" as a **nil row with a nil error**, unlike its movie twin which returns the ent error. Testing `err == nil` refuses every target; the mock that returned `ent.NotFoundError` hid it through a green suite until the browser hit a 409.

## Episode lifecycle status
- **`movie.status` carries `importing` too**, written by the same monitor tick that flips the record (`CheckStatus` sets the record importing, then the episodes, then the movie off `record.Edges.Movie` — `ListDownloadingRecordsWithMovie` already loads it, so this needs no new Store method). It has no orphan sweep of its own and needs none: `RevertMovieToWantedIfNoFile` and `FailDownloadRecord` both write the movie's status unconditionally, so they cover `importing` exactly as they covered `downloading`. `ListUpgradeCandidateMovies` is the one query that had to learn it (`StatusNotIn(downloading, importing)`) — gating on `downloading` alone would let the RSS feed re-grab a movie whose replacement was already being written to disk. Adding the value needed **no migration** (SQLite stores ent enums as bare text), and `MovieCounts.importing` plus the movies toolbar's Importing tab exist because the value would otherwise be in no tab at all.
- **A series card reads `downloading` and `importing` off `EpisodeCounts`** (`db.episodeCounts`, `TVShow.{downloading,importing}_episodes` — list-only rollups; the detail response carries the episode tree instead). Both tallies **cut across** the have/wanted/unaired buckets rather than replacing one: neither has a file yet, so both stay in `Wanted` and the "missing" filter and its count are untouched. They are also counted **before** the monitored/has-file scope guard, unlike `Total` — a grab that is landing is worth naming whether or not its episode is monitored, or the card stays silent through the whole import. `SeriesGrid.cardStatus` checks `downloading` then `importing` then `wanted`.
- **The in-flight scope is derived from the episode rows, never from the release title** (`EpisodeCounts.widen` → `downloading_scope` + `downloading_season`/`downloading_episode`): first row sets `episode`, a second in the same season promotes to `season`, one in another season to `series`. An operator can grab a pack in two goes, and what the card should say is what is actually landing. `Season`/`Episode` are **cleared** as they stop being true of the whole set, so no caller can read a number the scope disowns — season 0 is the specials, a real season, so only `series` licenses no season at all. This rides the existing counts scan (`season.number`, `episode.number`, `episode.id` added to the same projection): no extra query.
- **Both library lists carry a monitoring facet, and it is a facet — not a status.** `monitored=monitored|unmonitored` on `GET /movies` and `GET /series` combines with `status=` rather than replacing it, and `monitored`/`unmonitored` sit on both counts endpoints. The unmonitored tally is **the library total minus monitored**, never its own query: the facet costs one `COUNT` per endpoint. `GET /series?status=` also takes `downloading` and `importing`, whose counts (`CountTVShowsInFlight`) are per-show like `missing` and use the same predicate `FilterTVShows` does — so a tab's count and its contents cannot drift.
- **`Movie.release_date` and `TVShow.first_aired` are display fields, and `release_date` is *not* `digital_release_date`.** The latter is what the release-radar search waits on and is fetched per-region from TMDB's `release_dates` endpoint; `release_date` is the primary/theatrical date off the movie detail, and `first_aired` is TVDB's `firstAired`. Both providers already returned them, so the work was a nullable column each (migration `20260906140114_add_release_and_air_dates`), `metadata.ParseISODate` on the create and refresh paths, and the API field. There is no backfill job: existing rows fill in as `metadata-refresh` reaches them, and every SPA site falls back to `year` meanwhile.
- **`download_progress` comes from the live queue's cached snapshot, and is optional on purpose** (`restapi.seriesDownloadProgress`). `EpisodeCounts.InFlightEpisodes` carries the ids so the handler can map queue entries to shows without a second query; a pack has one entry on its anchor episode, so the mean is over entries, not episodes. It is asked for **only when some show on the page is downloading** — an idle library pays nothing, and a library page must never be what wakes every download client — and a queue that cannot be read is logged, not fatal: the show keeps its counts and scope and the card falls back to `ProgressBar`'s indeterminate bar. Importing contributes nothing by design; there is no percentage behind it, which is also why movie cards have never passed a progress value.
- `episode.status` is `wanted | downloading | importing | paused | available | skipped`. Only the **in-flight three** (`downloading`, `importing`, `paused`) are owned by a grab; `inFlightEpisodeStatuses` (`internal/db/download_record.go`) is the one list of them, and `RevertOrphanedDownloadingEpisodes` sweeps all three so a row can't strand in any of them. Adding a fourth in-flight state means adding it there, or the sweep silently stops covering it.
- **Every path that grabs must mark its episodes, and there are four.** `grabPackAndMark` (season/series packs), the RSS + missing-search runners (`markEpisodeDownloading`), the single manual grab (`restapi.GrabEpisodeRelease` → `db.MarkEpisodeDownloading`), and the selective-download widen (`download.GrabEpisode` marks the episodes it added). The manual one had no marker at all and the row read `Wanted` from grab until import — the pack path's existence is what made it look covered.
- `MarkEpisodeDownloading` moves **only from `wanted`**, matching `grabPackAndMark`'s guard. An episode that already has a file is a replace target: marking it downloading and then reverting the grab would leave it `wanted` with the file still on disk, which is the exact shape `RevertOrphanedDownloadingEpisodes`' second arm was written to undo.
- `importing` is set season-wide by `db.MarkRecordEpisodesImporting`, called when the monitor flips the *record* to importing — season-scoped like `SyncSeasonDownloadStateForRecord` because a pack imports the whole season behind its single episode link. It moves only `downloading`/`paused` rows, so an `available` replace target isn't dragged in. The SPA renders it in the `grabbing` hue; it is **not** a new colour. It *is* its own `StatusKind` (`importing`, whose `--status-importing` is a CSS alias of `--status-grabbing`) because sharing the `grabbing` kind outright shared its **label** too, and every record the importer already held read "Grabbing" in the queue.
- Adding an enum value to `episode.status` needs **no migration**: SQLite stores ent enums as bare `text` with no CHECK, so the value is enforced in Go only. `task migrate:diff` correctly emits nothing — that is not a missed step.
- **A transport failure never counts toward `grab_failures`** (`rss.transportFailure`, guarding every bump in `missing.go`, `feed.go`, `tv_missing.go`, `tv_feed.go`). `grab_failures` is a strike count against a *release choice* and nothing resets it but a successful grab, while the eligibility queries gate on it — so counting `download.ErrUnreachable`/`indexer.ErrUnreachable` retires the item after `max_grab_failures` (3) unlucky ticks. A flaky Prowlarr did exactly that to the homelab: `fetch torrent: download client unreachable: … timeout` three times, and episodes holding clean 1140-scoring releases stopped being searched at all — no log line, no `searched` event, nothing but a row sitting `wanted` forever. The pack arms are unaffected: they only ever bump on `ErrNoWantedFiles`, which is a statement about the release. `Episode.grab_failures` is on the API (absent at zero) because the counter was otherwise invisible — an operator could not tell a retired episode from an unlucky one without reading the DB.

## Series list performance
- `db.FilterTVShows` applies filter, sort and page in **SQL** and returns the page's shows *without* their season/episode tree, plus a per-show `EpisodeCounts` rollup. The list view needs three numbers, not the tree: eager-loading it was ~121 KB per show, a 2.8 MB response for 23 shows, and — with `SetMaxOpenConns(1)` — a site-wide stall while it ran.
- `missingEpisode` (the `status=missing` predicate) must stay in step with `DeriveSeasonViews`' Missing bucket, or a show matches the filter with nothing missing on its page. `sort=episodes` is a correlated subquery, not a join, so `LIMIT` still applies to shows.
- **An episode with no air date is unaired, never missing.** Five places split aired from unaired and all five must agree: `DeriveSeasonViews`, `db.episodeCounts`, `missingEpisode`, `db.ListEligibleEpisodesForSync` (which feeds *both* the missing search and the TV RSS feed scan) and `restapi.episodeStatus`. They used to read `!AirDate.IsZero() && AirDate.After(now)` — undated fell to the aired side on the theory that an unknown date is not evidence the episode is unreleased. In practice a provider announces a future season as dateless placeholders, often literally titled `TBA`: on a 6859-episode library every one of the 12 undated monitored rows was a future season of a continuing show, each counted as a permanent gap and re-searched every tick. `EpisodeSeed.tba()` (title *and* date both empty → seed unmonitored) does not cover this — TVDB writes the string `"TBA"`, and any monitor cascade or preset re-monitors the row anyway. The status is derived, not stored, so the episode returns to `wanted` on its own the moment the provider publishes a date; there is nothing to migrate.
- **Each sort key carries the direction its menu label promises** (`descending`): `title` ascending, `year`/`rating`/`episodes`/`recent` descending. The SPA's sort menu offers "Year (newest)", "Rating (highest)", "Most episodes" and has no direction toggle, so an ascending default answered none of them — `sort=year` returned oldest-first under both the old Go sort and the first SQL version. The `order` param (`asc`/`desc`) overrides, and exists so the override is reachable at all.
- `orderByEpisodeCount` counts what `EpisodeCounts.Total` counts — monitored **or** on disk. Ranking raw provider rows put a daily soap with 2012 episode rows above shows the card said were bigger, because the card was showing its scoped 26: the order and the number disagreed on the same screen.
- The global search box gates both library queries on the typed threshold (`search-model.svelte.ts`). `SearchField` lives in the global layout, so ungated it pulled the whole library on **every** route for a panel that stays closed until you type.
- ent runs with the `sql/modifier` feature so `Modify` is available for the lean count projection.
- The tree's foreign keys are **explicitly indexed** (`index.Edges(...)` on `Season`/`Episode`/`MediaFile`, migration `20260824093713`). SQLite indexes no FK on its own, so `episodeCounts`' per-episode `EXISTS` over `media_files` was a full scan each: the homelab's series list took 3.9s with the SQL push-down already in place. Any new edge the list path traverses needs the same.
- Movie posters are cached at TMDB `w780`, not `original` (series posters are TVDB artwork URLs, which carry no size) — `original` is ~1.9 MB a card. w780 is ~360 KB and is sized for the largest sharp render, the detail hero’s 260px column at DPR 3; the full-bleed backdrops are `blur-md`, so they set no floor. `posters.Fetch` short-circuits on an existing file, so changing the size only affects new fetches; an existing install has to drop `<data>/posters` to pick it up.

## Testing
- Framework: Ginkgo (Describe/Context/It/By) + Gomega assertions
- Mocks: Mockery (`go tool mockery`) — config in `.mockery.yaml`, generated to `internal/<pkg>/mocks/`
- Run tests: `task test:unit` / `task test:integration` / `task test:e2e` / `task test` / `task test:coverage` — all `go tool ginkgo run -r --keep-going`; the first three and `test:coverage` (`!e2e`) carry a label filter, `task test` runs everything unfiltered (e2e capped at `--timeout=1m15s`); forward extra args via `CLI_ARGS`, narrow with `LABEL_FILTER=`
- `task test:e2e:containers` — container-backed e2e (Docker + `STREAMLINE_E2E_CONTAINERS=1`, 5m timeout); hermetic `test:e2e` excludes `containers`-labeled specs.
- Run single suite: `task test:unit -- ./internal/metadata/...`
- Each Ginkgo suite has a dedicated `<pkg>_suite_test.go` (the three `internal/utils/*` packages inline it in their single test file) with `TestX` + `RunSpecs` + `BeforeSuite(func() { DeferCleanup(testutil.InstallSlog()) })` — `testutil.InstallSlog()` routes `slog.Default` to GinkgoWriter for the suite's lifetime.
- Mocks emit to `internal/<pkg>/mocks/mock_<Name>.go` — type `Mock<Name>`, constructor `NewMock<Name>(GinkgoT())`
- Regenerate mocks after interface changes: `go tool mockery`
- Span-instrumented funcs wrap ctx via `tracer.Start(...)`, breaking exact-ctx mock matchers. Use `mock.Anything` for the ctx param in `.EXPECT().Fn(mock.Anything, ...)` calls.

## Multi-agent fix workflows
Convention for landing a batch of independent fixes (audit findings, review comments, a bug list). Iterate on this as we learn.

- **Group findings by file ownership first.** Two agents editing one file is the failure mode; disjoint file domains are what make the rest safe. One group per domain (e.g. `restapi/`, `download+importer`, `middleware+web`, `auth+db+ent`).
- **One workflow per group, one agent per finding.** Each fix agent runs with `isolation: 'worktree'` so it can never see or clobber another's tree. Agents fix *only* their assigned finding — no drive-by refactors, no fixing things they notice.
- **Seed every worktree before the agents build.** A fresh worktree cannot compile *anything* importing `web`: all four `go:embed` inputs are gitignored — `web/static/css/style.css`, `web/static/css/docs.min.css`, `web/static/js/docs.min.js`, `web/static/dist/`. The failure reads `pattern static/css/docs.min.css: no matching files found`, which looks like broken code and is not. Copy them in from the main checkout right after launch (they stay gitignored, so they never pollute a patch); re-run the copy as assemble-phase worktrees appear. Building them per-worktree instead costs a full pnpm+esbuild+tailwind cycle per agent.
- **Agents commit; they do not emit patches.** Every fix agent ends by committing its work on its worktree's own branch, one commit per finding, with a real Conventional Commits subject. Integration is then a merge/cherry-pick against a shared ancestor — a proper 3-way merge that understands moved and adjacent hunks. Patch files were the earlier convention and they mangle exactly this: a flat diff has no base, so two agents editing neighbouring lines of one file produce hunks that apply cleanly in isolation and silently mis-stack when combined. Commits carry the base; diffs don't.
  - Inside a harness worktree the agent uses `git commit` (the worktree is a git worktree, not a jj workspace — this is the "raw git plumbing" exception, not a licence to use git elsewhere). The integrating session brings the work across with jj, which sees those commits after its automatic import.
  - If a patch file is ever unavoidable, generate it with `git diff --no-ext-diff`: this machine sets `diff.external = difft`, so a bare `git diff > x.patch` writes difftastic's *rendered* output — diff-shaped, no `---`/`+++`/`@@`, and `git apply` rejects it with "No valid patches in input". Applying is unaffected; only generation.
- **Agents never write to the main working copy.** A per-workflow assemble agent merges the group's commits in its own worktree, resolves intra-group overlap, verifies `task build:go`, and leaves a single reviewable branch.
- **The main session integrates.** Workflows finish in any order; the session reviews each group's commits, brings them into the working copy, and verifies — serialized, so nothing races on the tree. Never let a workflow write to main itself.
- **Codegen runs once, at the end, in the main tree.** `task generate` / `task migrate:diff` rewrite `ent/*` and `internal/*/mocks/*`; per-workflow codegen produces conflicting generated files against a partial tree. Agents may run it inside their worktree to compile-check, but must keep generated output out of the commits they hand over. Migrations from `task migrate:diff` *are* handed over, unedited.
- **Verification is the session's, after integration** — `task build:go`, `task lint:go`, `task test:unit` over the merged result. A group that passed alone can still break the merge.
- **Clean up after integration.** Remove each group's worktrees and their `worktree-*` branches once its work is in and verified. They live under `.claude/worktrees/` *inside* the repo, so until they go the editor/LSP indexes every half-finished agent tree and reports its errors as if they were yours.
- Agents get no history rewriting and no publishing: no `jj`, no rebase/amend of anything they did not create, no push, no `task dev`, no `task release:*`.

## Docs & Spec Upkeep
- Any change to `/api/v1` behavior — routes, auth/authz, status codes, security schemes, request/response shapes — updates `api/openapi.yaml` in the same change, then `task generate` to regenerate `gen.go` (the spec itself is served from `api/embed.go`'s `//go:embed openapi.yaml`). A handler and its spec entry must never disagree.
- When a feature or behavior changes, update the affected CLAUDE.md section **and the wiki** (`docs/wiki/` — user-facing pages like `REST-API.md`, `Authentication-and-SSO.md`) in the same change — stale docs describing the old behavior are worse than none.
- `docs/wiki/` is the source of truth for the GitHub wiki; `.github/workflows/wiki.yaml` mirrors it to `DataHearth/streamline.wiki.git` on every push to `main` touching it. Filename = page title (dashes become spaces), `_Sidebar.md` is the nav. Never edit through the wiki UI — the next sync overwrites it.

## Code Generation
- API: `go tool oapi-codegen --config api/oapi-codegen.yaml api/openapi.yaml` → `internal/server/restapi/gen.go` (package `restapi`) — regenerate after spec changes
- ORM: `go generate ./ent` — regenerate after schema changes
- All codegen: `task generate` (runs `go tool oapi-codegen`, `go generate ./ent`, `go tool mockery`). Versioned migrations: `task migrate:diff -- NAME` diffs the ent schema into a new migration.
- Prefer the narrowest integer type on ent schema fields (`field.Uint8` for bounded counters like `grab_failures`, `field.Uint16` for small ranges like `number`/`year`) — sqlite storage is identical but Go structs stay memory-efficient.
- After ent regen the LSP may report "undefined" for new fields/methods briefly; `task build:go` is the source of truth.

## Build
- Task runner: [Taskfile.yaml](Taskfile.yaml) — sole build orchestrator (no npm scripts).
- **Always** invoke operations via `task <target>`. Raw `go build`/`go test`/`ginkgo`/`golangci-lint`/`pnpm exec` bypass the Taskfile and drift from CI.
- Go tooling runs via the Go `tool` directive: `go tool {ginkgo,golangci-lint,oapi-codegen,mockery,air,govulncheck}` (`task vulncheck` runs the last, as CI does) — not system-installed; the flake devshell only ships `go`, `pnpm`, `go-task`, `biome`, etc.
- Full build: `task` (= `build:app` → `build:go`, which depends on `build:js` + `build:css` because assets are `//go:embed`-ed) → `go build -o streamline ./cmd`.
- Frontend: `task build:js` (Scalar docs bundle + Paraglide message compile + `routify build` + esbuild SPA) and `task build:css` (TailwindCSS v4).
- Dev server: `task dev` — live reload via `go tool air` (`.air.toml`; rebuilds with `task build:app`, runs `streamline --config ./tmp/config.yaml`).
- Lint: `task lint` (`lint:go` golangci-lint + `lint:frontend` biome + `lint:ts` svelte-check). Format: `task fmt` (`golangci-lint fmt` + `biome format --write`) — Biome, not prettier.
- Clean: `task clean`.

## Release
- App and chart version independently. App release: `task release:changelog VERSION=vX.Y.Z` (regenerates the CHANGELOG, commits it on its own revision and advances `main`) → `task release:tag VERSION=vX.Y.Z` (tags `main`, push fans out to `.github/workflows/{release,image}.yaml`). Chart release: bump `version` in `deploy/helm/streamline/Chart.yaml` → commit → `task chart:tag` (tags `chart-vX.Y.Z`, triggers `.github/workflows/chart.yaml`).
- Artifacts come from goreleaser (`.goreleaser.yaml`): CGO-free binaries for linux/darwin/windows × amd64/arm64, archives carry `config.example.yaml`, `checksums.txt` is cosign-signed (bundle format), one SPDX SBOM per archive. Images are cosign-signed keyless + SBOM-attested + grype-scanned in `image.yaml`.
- `release:tag` / `chart:tag` / `release:image` / `release:helm` publish for real and have no dry-run. Never run one to "test" it — only exercise a precondition's failure path.

## Version Control
- Repository uses jj (Jujutsu) with a git backend. Commit a task with `jj new -m "msg"` (creates empty child, auto-snapshots subsequent work). Seal a task by starting the next with `jj new -m "..."`.
- Don't re-run `jj describe` on a commit you're already working in — message is set once per task.
- If working copy holds unrelated leftover edits (e.g. settings.json), describe them into their own commit *before* `jj new` for feature work.
- Abandon empty working-copy commits after no-artifact steps (smoke tests, manual verification): `jj abandon @`.
- Commit messages: Conventional Commits `type(scope): msg` — add a `(scope)` where it clarifies, omit it when it doesn't. Bundle related changes; avoid single-file revisions.

## Project Structure
- `api/openapi.yaml` — OpenAPI spec (source of truth for REST API)
- `internal/` — all application code
- `ent/schema/` — ent ORM schemas
- `web/app/` — Svelte 5 SPA (`routes/`, `components/`, `lib/`); `web/static/` — CSS/JS/fonts/images; `web/embed.go` `//go:embed`s the built assets + SPA shell
- `docs/plans/` — design docs and plans (gitignored, local only)
- `docs/ROADMAP.md` — public, user-facing feature status (Shipped / In progress / Planned). Not an internal phase list; update it when a feature ships or starts.
- `CHANGELOG.md` — generated from conventional commits by git-cliff (`task release:changelog VERSION=vX.Y.Z`); don't hand-write entries.
- `deploy/` — Dockerfile + Helm charts + `compose.yaml` (local test stack: gluetun VPN + qBittorrent + Prowlarr + Plex, builds from source — *not* a user deployment template)
- `deploy/helm/streamline/` — streamline chart (installs to `streamline` ns). Optional subchart `charts/observability/` installs upstream alloy/VM/VL/VT/grafana into `observability` ns via `namespaceOverride`.
- `deploy/helm/streamline/kubeconfig.yaml` — kind cluster kubeconfig (auto-exported by `task helm:kind:up`; flake devshell sets `KUBECONFIG` to this path).

## Helm Gotchas
