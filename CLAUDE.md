# Streamline

Unified media management platform replacing the *arr stack (Radarr, Sonarr, Lidarr, Readarr) and Seerr. Single self-hosted binary with a slick web UI, REST API for mobile developers, multi-user support with SSO, built-in request system, and automatic media organization. Supports Torznab and Prowlarr indexers, torrent download clients (qBittorrent, Transmission, Deluge, or the built-in engine), and media server notifications (Plex, Jellyfin, Emby). Movies, TV, music and books are all shipped; Usenet and a player are planned (`docs/wiki/Roadmap.md`).

## Stack
- Go monolith: chi + oapi-codegen (OpenAPI → server) + ent ORM + modernc.org/sqlite (CGO-free)
- Config: koanf (file + env + flags, STREAMLINE_ prefix)
- Logging/Observability: slog + OpenTelemetry (traces, metrics, logs via OTel bridge)
- Frontend: Svelte 5 SPA (TypeScript) — Routify v3 file-routing, TailwindCSS v4, TanStack Query + TanStack Form, valibot schemas; bundled by esbuild, embedded via go:embed

## Frontend

Svelte 5 SPA in `web/app/` (TypeScript everywhere), Routify v3 file-routing over `web/app/routes/`, TanStack Query + Form, valibot, TailwindCSS v4, bundled by esbuild and `//go:embed`-ed. A section's wrapping layout MUST be `_module.svelte` — `_layout.svelte` renders as a sibling route, not a wrapper. Both library lists paginate server-side, and their toolbars read **faceted** counts — each facet counted against the *other* filters, each with its own `*_total` "all" row. Detail-page tabs swipe on touch screens below `lg` (`lib/swipe-tabs.ts`). On a touch screen and below `md` search is a page (`/search`), not an overlay, so Back closes it; from `md` a mouse's search bar (CSS `pointer-fine`, never a JS check) and Ctrl/⌘+K on any pointer open the command palette; and Back/Forward restore `#main`'s scroll (`lib/scroll-restore.ts`). A page's filters, search, sort and tab live in its query string through one helper, `syncRouteQuery` (`lib/url-state.svelte.ts`), with one parameter vocabulary across pages and old names still read. Every bottom sheet and full-screen layer calls `closeOnBack` (`lib/close-on-back.svelte.ts`): Android's Back closes the topmost one through `CloseWatcher`, and any open layer closes when the route's path changes. Settings pages pick save-per-control **or** one TanStack form, never both on a page, and either way the page must call `markConfigForm()` or nothing on it locks on a read-only instance.

## Logging
- No `*slog.Logger` plumbing. `cmd/main.go` calls `observability.Setup` then `slog.SetDefault`; every package logs via `slog.XContext(ctx, ...)` (top-level) — never hold a logger field.
- `observability.Setup` returns one `slog.Handler` = `contextEnrichingHandler(multiHandler{stderr, otelslog.Handler})`. stderr is pretty text/json from `log.app.{level,format}`; otelslog bridges to the OTLP logs pipeline (traces/metrics/logs all batch-exported to `otel.endpoint`).
- **`log.app.enabled` gates the stderr sink only**; the OTel pipeline is gated on `otel.endpoint` alone. It used to return early with a `DiscardHandler`, so quieting local logs silently stopped traces and metrics as well — an instance exporting nothing, for a reason nowhere near the OTel config.
- `contextEnrichingHandler` auto-attaches `request_id` (chi), `user.id`/`user.email`/`user.roles` (auth claims, OTel semconv v1.40.0), `http.route` (chi route pattern). Trace/span IDs come from otelslog. Use `slog.XContext` so ctx flows through.
- On an authenticated request `user.*` is therefore the **caller**. A log line about another account (admin CRUD, unlock, session revoke) names it `target.user.*` — writing `user.id` there emits the key twice, target and actor, and a filter on `user.id` matches both people.
- `observability.LevelCritical` (= `slog.LevelError + 4`, rendered `CRITICAL`) for panics, invariant violations, unrecoverable conditions. Call via `slog.LogAttrs(ctx, observability.LevelCritical, ...)`.
- OTel semconv pinned at v1.40.0 — use `semconv.<Key>Key` constants (e.g. `semconv.HTTPRouteKey`) over string literals; keep versions aligned across files.

## Observability
- `internal/otelx` is the leaf OTel helper package. Holds `HTTPClient` (otelhttp-wrapped — use for every outbound HTTP call; never `http.DefaultClient`; every response body is capped at `MaxResponseBody` inflated bytes, a backstop against a hostile remote's gzip bomb, so a caller streaming something larger needs its own client; a call that knows its answer is small decodes through `otelx.DecodeJSON(body, max, out)` with a per-package ceiling) and `RecordSpanError(span, err) error` (inline: `return ..., otelx.RecordSpanError(span, err)` — no named returns). Must stay dependency-free; `internal/observability` imports `internal/auth`, so anything auth transitively uses must live in `otelx` not `observability`.
- Per-package tracer: `var tracer = otel.Tracer("github.com/datahearth/streamline/internal/<pkg>")`. Span names `<pkg>.<op>` (e.g. `download.grab`, `rss.process_movie`, `indexer.query`).
- DB auto-instrumented via `otelsql.Open` + `RegisterDBStatsMetrics` in `internal/db/client.go`. Add business-logic spans in service methods + `span.SetAttributes` for domain context.
- Prefer semconv helper funcs (`semconv.UserEmail`, `semconv.UserRoles`, `semconv.UserID`, `semconv.DBSystemNameSQLite`) over raw `attribute.String("user.email", …)`.
- **Never put a row id in a metric attribute** — `movie.id`, `episode.id`, a request path with an id in it. That is one time series per row in the library. Ids belong in the log line and on the span; a metric attribute is a low-cardinality dimension (`outcome`, `kind`, `status`, an indexer or client *name*).
- **A span that can fail must record the failure.** Every terminal path funnels its error through `otelx.RecordSpanError` or, where a helper owns the exits, through one choke point (`transcoding.record`, `scheduler.executeJob`). A span left untouched by its own failure paths reports OK, and filtering a backend for error spans then finds nothing wrong.
- **Every goroutine started with `go` defers `observability.RecoverPanic(ctx, what, onPanic)`.** `middleware.Recoverer` covers the request path and nothing else; an unrecovered panic in a background worker takes the whole process down. `onPanic` is the caller's policy — a scheduled job records `errJobPanicked` and retries next tick, a transcode fails terminally, a boot goroutine calls `stop()` for a clean shutdown.
- Sampling is `otel.sample_ratio` (default `0.05`), overridden by `OTEL_TRACES_SAMPLER` — `Setup` skips its own `WithSampler` when that variable is set, because passing the option at all makes the SDK ignore the env. `otel.insecure` is needed for an `http://` collector; `otel.environment` fills `deployment.environment`.
- `otel.SetErrorHandler` routes SDK export failures into the stderr handler **only** — never the full handler, or a failing log exporter is fed its own error records.

## HTTP Routes
- `/health` — pre-auth bare JSON endpoint (NOT in OpenAPI), for k8s probes + load balancers. Registered in `internal/server/server.go`.
- `/api/docs` — Scalar UI shell (`web.Handler.APIDocs`). `/api/v1/openapi.yaml` — embedded spec. REST API mounted via `restapi.Mount`.
- SPA fallback: `s.router.NotFound` → `web.Handler.SPAShell`, which writes the embedded `web/app/index.html` for every non-API, non-static path; Routify owns client-side routing incl. its own 404. Static assets served at `/static/*` from `fs.Sub(web.Assets, "static")` (wired in `web.Mount`).
- `/posters/{kind}/{id}/poster.jpg` — poster proxy via `s.posters.Serve`; `kind` is `movies`, `tvshows`, `artists`, `albums`, `books`, `authors` or `people`. A person's photo is fetched on its first miss from the provider link the row keeps (`fetchPersonPhoto`); the metadata refresh jobs copy every credited person's, which is what extensions read. An artist with no photo is served the cover of its newest released album that has one (`artistPosterSource`, `db.ArtistCoverAlbums`), and a 404 only when none does, which is the SPA's cue for the monogram.
- `/posters/lookup/{kind}/{key}/poster.jpg` — the **only** proxy for art of a title that is not in the library (`internal/artwork`, behind the session middleware, not in OpenAPI): `kind` is `artists` or `albums` (an MBID, the latter a release-group) or `books` (a Hardcover book id), 404 means no art and the SPA draws its placeholder. The client never supplies a URL or a name: the lookup services remember the provider's own reference as they serve a payload (`artwork.Remember(kind, key, artwork.Source{URL | DeezerID | Name})`, a bounded in-memory map, 2000 entries, 24 h, lost on restart) and the proxy resolves from that — an artist by a Deezer name search accepted only with **exactly one** hit that folds equal (no MusicBrainz request), else through what MusicBrainz links for **that** artist (`ArtistLinks`: one `url-rels` call, since a search hit never carries them, at `metadata.Prefetch` priority): its Deezer page unless another MusicBrainz artist links the same page (`DeezerArtistShared`, one `/url` call memoised 24 h per page — Deezer files namesakes under one page, and MusicBrainz links the grunge Nirvana and the 60s UK band to the same 415), else its own Commons `image` rel; a namesake gets no face rather than a wrong one. An album resolves through the Cover Art Archive front, a book through the Hardcover image URL the payload already carried. It **never spends a Hardcover request**. Every fetched URL and every redirect hop must be https on `dzcdn.net`, `coverartarchive.org`, `archive.org`, `assets.hardcover.app`, `commons.wikimedia.org` or `upload.wikimedia.org` (Wikimedia refuses Go's default User-Agent, so the fetch sends streamline's); a key that is already a library row serves that row's file instead; a copy older than 24 h is refetched (and served stale if the refetch fails); the on-disk cache under `posters/lookup/` drops its 200 oldest entries past 2000; a failed resolve is remembered for an hour in memory, keyed on the key **and the source it was tried with** (a MusicBrainz `rate_limited` miss is not remembered at all), so a Deezer link a detail lookup remembers later is tried at once (and `Remember` keeps a live entry's fields a new source leaves empty, so a search listing the artist again does not forget it); concurrent requests for one key share one fetch. The metric label is `lookup-artists|lookup-albums|lookup-books` on the existing `streamline.posters.*` counters.
- `POST /api/v1/schedules/{name}/run` marks its run with `scheduler.Manual(ctx)`, and the throttled jobs waive their own windows on it — the missing searches take `unthrottledWindow()` (no cooldown, no failure cap), the metadata refreshes take a cutoff of now. Without it a manual run walked the list, touched nothing, and read as a trigger that did not fire.
- `GET /api/v1/schedules/events` is the one streaming endpoint: `text/event-stream`, a full `ScheduleList` frame on connect and on every `scheduler.Subscribe` nudge, coalesced to 250ms, keepalive comment every 15s. It is a strict-handler response type (`scheduleStream`) that writes the stream from its own `Visit` method, and it clears the listener's 2min `WriteTimeout` on its connection via `http.ResponseController`. The other code that moves that deadline: an upload's body (`idleBody` in `internal/server/middleware/body_limit.go`), which pushes the read and write deadlines 2min ahead of every read, so a long upload can still be answered and a stalled one is still cut; the library path browser (`handler_library_paths.go`), which clears it; and an extension's file and ffmpeg answers, which push it 2min ahead of every write. A job reports progress with `scheduler.Progress(ctx, done, total)` on the ctx the scheduler handed it (a no-op on any other ctx); `total` 0 means "counting without a known size" and the SPA shows a bare count with no bar.
- `DELETE /api/v1/torrents/{hash}` also calls `downloads.PurgeRecordForHash`, dropping the live download record behind that torrent and reverting its media. The monitor's orphan sweep would eventually do it, but only after `monitorOrphanGrace` (2 min) — a window that exists to tolerate a client that hasn't caught up with its own listing, which a removal issued through streamline is not. The Torrents page invalidates `["activity","queue"]` on success for the same reason. `blocklist=true` keeps the record instead, rejected (`RejectRecordForHash`), so the automatic picks skip that release for the title; the removal otherwise sends the title back to `wanted` with nothing against the release, and a dead release that still scores best is grabbed again. With `delete_files=true`, a torrent that has no metadata answers `409 code: files_unknown` and stays: the engine places data by the info name, so the removal used to answer 204 and leave the folder. `DELETE /api/v1/activity/queue/{id}` (`CancelQueueItem`) runs the same `ReconcileStrandedMedia` pass after deleting the record, so a cancelled episode, album or book is back to `wanted` in the same request, like a movie.
- **Cross-origin access is one file-only allow-list**, `server.cors_origins` (exact `scheme://host[:port]`, checked by `checkInvariants`): `middleware.CORS` sits just before auth, answers a listed origin's preflight with `204` itself (a preflight carries no credentials, so auth would refuse it) and stamps `Access-Control-Allow-Origin` on every answer to that origin, extension mounts included. It never sends `Access-Control-Allow-Credentials`: the session cookie stays same-origin (`sameOriginAPIRequest`), so a cross-origin page signs in with Bearer or `X-API-Key`. An empty list installs nothing.
- The auth middleware's exclude list is the package-level `authExcludePaths` in `internal/server/wire.go`, handed to `middleware.NewAuth` (`/health`, `/api/docs`, `/api/v1/openapi.yaml`, `/static/`, `/login`, `/register`, `/auth/login`, `/auth/register`, `/auth/config`, `/auth/invite/`, `/auth/oidc/`); matcher in `internal/server/middleware/auth.go`, paths ending `/` match as prefix and everything else exactly. A path under a live extension mount whose `auth` is `self` passes the middleware through its fourth parameter, `selfAuth` (`extension.Manager.SelfAuthenticated`).

## Extensions

WebAssembly modules (Extism on wazero) loaded from `extensions[]` in the config: each mounts URL prefixes, reads a granted slice of core through **temp views** over a read-only `ATTACH` behind a SQLite authorizer, reads granted **folders** (`music`, `movies`, `series`, `artwork` read-only through `os.Root`; its own `cache`, writable, 1 GiB swept hourly by `extension-cache-sweep`, links refused) and sends a file from one (`send_file`), and owns `<data_dir>/extensions/<name>/data.db`. A fresh guest instance handles every request, so nothing survives in memory. The manager (`internal/extension`) reconciles the config on boot and on every API change; states are `running | disabled | needs_approval | failed`, and a failed one never fails the boot; a reconcile started by an API change outlives its request (`reconcileExtensions`), since the config is already saved and a client hanging up mid-compile left the entry `failed`. **Grants must cover the manifest**: an entry missing any of the manifest's `mounts/views/services/folders` is `needs_approval` and does not run, and approving sets them to exactly the manifest's. **The `http` service reaches only `extensions[].hosts`**, exact `host:port` pairs written in the config file and nowhere else (never a grant, never the API), through a host function that follows no redirect; a guest has no socket otherwise. **The `ffmpeg` service is full trust**: Streamline's own ffmpeg runs uncaged with the guest's arguments (`ffmpeg_run`, `stream_ffmpeg`), so an extension holding it reads and writes any file Streamline can and reaches the network; every other grant confines it to its views and folders. A stopped extension's mount answers `404`; a bad `source` in the config file is a `failed` extension, never a failed boot; everything a guest serves carries a host-set CSP (`sandbox`, no script, `media-src 'self'`), `nosniff` and `Cache-Control: no-store, private`, which a guest may relax only to a `private` policy on a successful answer (`guestCacheControl`), never `public`; an API key writes nothing under `/api/v1/extensions` but an extension's own `/api` subtree. The view catalogue is `db.ExtensionViews()`, and **a view's SQL changes in the same commit as the migration that moves its columns**; `users.locked` is 1 while the account is locked out, and a guest that checks credentials of its own refuses such an account; no view exposes a secret, an email outside `user_logins`, or a file path other than `music_files.path` and `video_files.path`. **Every extension is served under `/extensions/<name>`**, one prefix core owns, so none can shadow a route core adds later; its manifest's mounts (contract version 2) are relative to that path, `/` or one plain segment, and a request goes to the longest one, the guest seeing the path below it plus `Request.BasePath`/`Mount`. The credential headers never reach a guest on a non-`self` mount. OPDS is the first extension and lives in a repository of its own, released from there; core holds no column, table or view for it or for Subsonic, and whatever an extension keeps is in its own database. This repository keeps the guest SDK (`extensions/sdk`, its own Go module, what an extension imports) and the echo fixture, built with `task build:extensions`, which the unit and integration tests depend on.

The SPA manages them at Settings → Extensions and draws each running extension's credential card on the account page through `/account/extensions[/{name}/credential]`. A `settings` card is read and written for another user by an admin through `/users/{uid}/extensions[/{name}/cards/{card}]`, the host checking the values against the declared fields first; `Request.TargetUser` is set there only, and the signed-in `/api/v1/extensions/{name}/cards/{id}` subtree answers `404` for a settings card.

## Stats

`GET /stats?range=7d|30d|90d` (admin, `db.GetStats`) is computed on demand from existing tables, with no table of its own, and the SPA polls it every 5 minutes. `library` is always now; the range bounds the pipeline and the requests, and `previous` is the same totals over the stretch before. Two figures are read rather than recorded: **`failures` classifies the free-text `failure_reason`** (`failureCode`: `stalled`, `verification`, `no_match`, `tracker`, `no_space`, `unpack`, else `other`), and **the two request medians read `update_time`**, so an approved request that later went available loses its decision time. `hdr` is the probe's `MediaFile.dynamic_range`, never the path: renaming drops the release's HDR tag, and `unknown` is a file the backfill has not reached. Each of the largest files shows the resolution the probe measured, else what the import recorded. The pipeline leaves out an `imported` event whose source is an adoption (`wizard`, `orphan`, `bulk_import`), which has no grab behind it. Days are UTC. User docs: "Stats" in `docs/wiki/Activity-and-Calendar.md`.

## Auth, sessions & OIDC

The middleware splits transport by path prefix: `/api/v1/*` takes Bearer, `X-API-Key`, or a same-origin `streamline_session` cookie; everything else is cookie-only and 302s to `/login`. API keys are read-only on the identity band, and each carries a `scope` (`read` keys send GET/HEAD only, refused in the middleware before RBAC, so no role widens them) and an optional `expires_at` (an expired key gets the unknown-key 401; the `purge-api-keys` system job drops it a week later). OIDC is multi-provider, and provider trust is **two independent axes** — `email_linking` (which accounts it may adopt) and `allow_admin` (whether it may grant admin).

`role.Federated` in `internal/role/` is the single admin ceiling, enforced by a package boundary that makes skipping it a compile error, plus type-resolved specs over package `auth`. **Never merge the two trust keys, never export the role field, never move the type back into `auth`** — four rounds of weaker guards were each bypassed.

**Linking policy, the API-key denial list, seed admin, registration modes and what the guards deliberately do not cover: [`docs/agents/auth-and-oidc.md`](docs/agents/auth-and-oidc.md) — read it before touching `internal/auth/`, `internal/role/`, or the auth middleware.**

## Config surface

Seven sections are readable and patchable at runtime (`/config/{auth,library,ffmpeg,download,metadata,system,transcoding}`, admin-only, partial-patch); everything else is file-only and needs a restart. The trust boundary and every secret are deliberately file-only — a key the API can reach is a key the API can be made to grant. Media servers, download clients, indexers and quality profiles live in the YAML config, name-keyed and hot-editable, not in ent/SQLite. A blank secret on their update keeps the stored one **unless the update moves the entry to another scheme, host or port**: then the secret must be sent again (422 `secret_required`; a `*_file` secret refuses the move, 403 `secret_file_managed`).

A missing `--config` file is written at boot from `config init`'s defaults (`config.Seed`), with only `data_dir` and the library paths taken from `STREAMLINE_*` — never a secret.

**Adding or removing a config field means `defaults()` AND `api/config.schema.json`.** Bounded ints go through `narrowUint8` and durations through `checkDuration` — both must reject *before* conversion, since nothing validates a request body against the spec.

**The full section-by-section rules and the resource CRUD contract: [`docs/agents/config-surface.md`](docs/agents/config-surface.md) — read it before touching `internal/config/` or the `/config/*` handlers.**

## Database connections

`db.Open` returns one ent client over **two pools** (`internal/db/router.go`): a single connection for every write and every transaction, and four `query_only` connections for autocommit statements starting with `SELECT` (`isRead`), all kept idle-open (`database/sql` closes all but two by default, and a reopened reader starts with an empty page cache and re-reads the schema). The split is by statement, not by method, because ent sends `INSERT … RETURNING` through `Query`; a write that reaches the read pool fails on `query_only`. A read never queues behind a write: on the homelab's Ceph volume a write waits on three replicas 25–30 ms apart and some take seconds, which with one shared connection made every page wait behind them. WAL keeps the readers consistent (each sees what was committed before it started), and nothing reads outside its own transaction while it is open — on one connection that deadlocked, which is why the `withTx` rule exists. Both pools are named on their spans and connection metrics (`db.client.connection.pool.name` `write|read`). Each connection has its own page cache, so `readConns` multiplies `cache_size`. Before `db.Open`, boot reads the database file, its WAL and the builtin engine's bolt piece completion (`bittorrent.PieceCompletionPath`) into the OS page cache (`prewarm` in `internal/server`, eight ranges at once, at most 2 minutes in all): boot queries read rows spread across the database, and re-adding torrents reads the bolt file for every piece. On network storage each cold page read is a round trip (about 26 ms on a Ceph RBD volume reached over a WAN, up to 200 ms on CephFS, where every random read pulls a readahead window), minutes in all, while large reads pay one round trip per window.

## Database backups

`internal/dbbackup` owns every copy of the database: `VACUUM INTO` snapshots in `<data_dir>/backups` (dir `0700`, files `0600` — they hold password, API-key and session hashes), named `streamline-<kind>-<schema version>-<UTC time>.db` so a listing and the retention pass read nothing but the directory. It never imports `config` or `db` (the migration runner calls it from inside `db.Open`). Four kinds, retention per kind (`backup.retention.{scheduled,pre_migration,manual}`, 0 keeps all; `pre-restore` is never pruned). **`runMigrations` snapshots before applying anything** — only when a migration is pending on a versioned, clean database — and a failed snapshot fails the boot with nothing migrated (`backup.pre_migration: false` opts out); with automated image updates nobody else is there to take the copy. A snapshot is written under a hidden `.partial` name and renamed once synced. The `database-backup` job (`24h`) snapshots through its **own connection** (`SnapshotFile`), never the server's own pools, and an automatic run skips when a scheduled backup from within 90% of the job's *current* interval exists, or every restart would rotate the week out. `streamline backup` never goes through `db.Open` (which would migrate); `streamline restore` validates first (opens, `quick_check`, clean `schema_migrations`, version ≤ `db.LatestSchemaVersion()`), detects a running server by switching the live database out of WAL (SQLite refuses while another connection is open — `ErrInUse`), keeps the replaced file as `pre-restore`, and needs `--force` where no database exists. User docs: "Backups" in `docs/wiki/GitOps-and-Kubernetes.md`.

## Downloads, imports & adoption

The builtin engine owns its own peer sockets, caps its peer pool with constants (not config keys), and reads pieces itself past the page cache (`uncachedPiece`), since anacrolix's mmap reads let seeding evict the database. A torrent holding every piece of its wanted files closes its connections to seeders every 10 s (`dropRedundantSeeders`), which anacrolix does only for one holding every piece, so never for a torrent with skipped files. Its limit enforcer only stops uploading; removing a seed-complete torrent **with its files** is the download manager's call on the monitor tick, and only for a builtin torrent whose record the importer already completed. **A removal with files never loses them to a failed delete**: the engine records a `TorrentDataRemoval` row before dropping the torrent, answers the removal as done, and retries the delete at boot and every minute until the files are gone or another torrent has taken the name; what is still owed is `pending_removals` on `GET /torrents`, a banner on the Torrents page and the gauge `streamline.bittorrent.pending_data_removals`. **A grab that finds the engine full rotates one out** (`download.addRotating`): the imported torrent with the oldest import day, the highest ratio within a day, removed with its files — only a hash with a completed record and no unfinished one (`db.ImportedTorrentTimes`), else the grab is refused as before. The importer verifies a probed source against the release claim before any transfer and parks a failing record `held` rather than counting an attempt. Rejecting a held release (resolve `regrab` or `delete`) marks its record `rejected`, and **every automatic pick — missing searches and feeds, all four verticals — drops what that blocklist matches before choosing** (`db.RejectedReleases`); manual search and grab never consult it. Untracked torrents the clients report are matched against the library each monitor tick and either auto-imported or filed as a `pending` proposal. Every successful import, bulk-import commit, transcode swap, rename and file delete dispatches a media-server refresh (movies, series, music and books alike) — the last two through `mediaserver.RefreshInBackground`, off the request path. A refresh names the paths it changed and the dispatcher rescans only their folders, mapped through the server entry's `path_mappings` (`from` Streamline's prefix, `to` the server's), falling back to the whole library when a folder lies outside everything the server reports; refreshes coalesce for 30 s into one request per server, and shutdown flushes the queue.

A record is filed under one `anchor_episode` and links every episode its download is for through the `episodes` many-to-many (anchor included, upgrade targets too) — **every status write over that set filters on the status it moves from**, and every grab path links every episode it marks `downloading`, since the orphan sweep spares exactly what an in-flight record links.

**A record's `save_path` is resolved on disk, never sent.** Streamline never sends a save path on add — qBittorrent gets `category: "streamline"` and nothing else — so the location contract is `<library.download_path>/<torrent name>` and lives in the client's category configuration, which qBittorrent applies only under Automatic Torrent Management (Manual, its default, ignores it). Two torrents named alike share that folder, so **an import keeps only the files the record's own torrent lists** (`Worker.sourceFilter`; unfiltered only when the client cannot list it). **Both a completed grab and an adoption stat the payload before the import starts** (`payloadPaths` + `locate` in `internal/download/payload.go`): the convention path first, then the client's own `Torrent.SavePath` through `download.path_mappings`. At neither, adoption files a `pending` proposal and the completion sweep holds the record (`downloading → held`, one `location` reason naming both paths, no attempt counted), which every monitor tick re-checks and releases to `importing` from the path it finds (`ReleaseLocatedRecord`); `resolve import` answers 409 on it. An unverified path reaches the importer as a *retryable* ENOENT, burns all `import_max_attempts`, and lands `failed`. `POST /activity/history/{id}/retry` is the only exit from `failed` — `resolve` takes `held` only and the importer's scan takes `importing` only.

**An automatic movie or episode grab is refused while the title has a download in flight** (`download.Automatic(ctx)`, set by every `internal/rss` pass; `ErrAlreadyDownloading`, no strike): a pass grabs from the list it read at its start, and two passes otherwise each take a release of one episode. A grab by hand is not held to it.

**Every grab checks free space first** (`download.space_check`, default on, `space_reserve_gb` 10): the release plus what the client's torrents still have to write plus the reserve must fit in the free space the **client** reports, else `ErrNoSpace` — `grab_rejected` by hand, no `grab_failures` strike automatically. A check that cannot be made lets the grab through.

**Uploads** (`POST …/upload` on an album, track, artist or book, previewed by `…/upload/preview`) are client-less `uploaded` download records imported by `copy` from `<download_path>/.uploads`, whatever `library.import_mode` says; a target with a live record is refused `409 upload_conflict`.

**Engine internals, port rebinding, hold/resolve semantics, the free-space check, uploaded records and their staging sweep, the adoption proposal lifecycle, the retry contract and Plex section discovery: [`docs/agents/downloads-and-imports.md`](docs/agents/downloads-and-imports.md) — read it before touching `internal/bittorrent/`, `internal/importer/`, `adopt.go`, or `internal/mediaserver/`.**

Two flows — a `.torrent` decodes the metainfo before add, a magnet parks the record `selection_state: pending` until `RunSelectionPass` resolves it. `replace_mode` decides the wanted set; `selection_mode` on `TorrentSession` is what survives a restart.

## Quality scoring

`internal/quality` is the pure scoring engine (no config/db imports); context builders live in `internal/quality/qualityctx`. A release is gated by resolution **band** first (`preferred_resolution` is a hard ceiling), then by summed custom-format score against `min_score`. `quality.ReplacesFile` is the single predicate deciding whether one release replaces one file. Builtins describe a release and never judge one — opinionated rules belong in `custom_formats`.

Every `indexer.Manager` search takes **two name sets**: `titles` is queried (one request per title per indexer) and `aliases` is only matched against. `Movie.aliases`/`TVShow.aliases` hold the providers' translated and alternative titles, which is what stops a library holding a work under its localized title from discarding every release named in another language. **Never pass an alias list as `titles`** — that multiplies every search by its length against rate-limited trackers.

## Native indexers (Cardigann definitions)

`internal/cardigann` reads the Cardigann YAML definitions Prowlarr and Jackett describe trackers in, so a stack can drop both. **Today it is the converter, a catalog read from upstream at run time, and the engine** (`internal/cardigann/engine`) — nothing of upstream ships in the binary or the repository: a `protocol: cardigann` indexer — added from the catalog (`GET /cardigann/catalog[/{file}]`, Settings → Indexers → Add built-in, a form generated from the definition's settings) or the YAML; **secret settings never leave the API** (`secrets_set` names them; an edit sending one empty keeps it, unless the definition changes), and any setting may instead be read from `<name>_file` (`CardigannIndexer.Resolved()`, the only form the engine, the check and `config_hash` read), which is **file-only** — the API refuses a `_file` key, a value for a file-held setting and a `site`/`proxy` move while a file holds a secret; on a read-only instance *Add built-in* still opens the form and shows the entry as YAML to paste — **is pinned to the upstream commit of the definition it runs** (`cardigann.commit`, written by the API from the catalog on create or definition change, never taken from a request; the converted JSON is kept per commit under `<data_dir>/cardigann/v<convert.Version>/`, read by `definitions.Pinned`, which never reaches the network and is what `config` checks against, and `definitions.Resolve`, which fetches that commit's tarball when it is not kept — every caller that pins or edits an entry keeps or resolves first), **logging in when it says to** — the engine runs one login (`post`/`form`/`get`/`oneurl`/`cookie`), `internal/indexer` decides when: before the first request without a live `IndexerSession` row, again once on `ErrLoginRequired`, never during a failure's backoff (a wrong password retried per RSS tick bans the account), and a captcha only through a person (`POST /indexers/{name}/captcha` → `/login`). A browser challenge (Prowlarr's Cloudflare/DDoS-Guard detection, in `Engine.do`, so every request) goes to the FlareSolverr-compatible `cardigann.solver_url` once, its cookies and user agent kept in the session; `cardigann.proxy` routes a tracker (and the solver's browser) through one egress. The `cardigann-update` job (boot, then 24h) reads Prowlarr/Indexers' newest commit (`snapshot.Latest`/`Fetch`, a GitHub tarball) into the **in-memory** catalog (`definitions.Install`; `update.Ensure` fetches on demand when nothing was read yet, `catalog_unavailable` when GitHub cannot be reached) and moves each entry to the catalog's version of its definition: a change that alters the hosts it names or its login is **held** (in memory, forgotten on restart and found again by the next run) until `POST /cardigann/updates/{file}/approve`, anything else is kept and pinned (`config.PinCardigann`), a version equal to the catalog's stays on its commit, and the kept commits no entry names are pruned; on a **read-only config every change is held** and the SPA offers the new `commit` to copy into the file. A definition upstream drops or the converter refuses leaves entries on the version they are pinned to. There is no format version on a kept definition: it sits under `convert.Version`, so a converter change re-converts each pinned commit on first use. Its ids follow the definition's search mode and an id search leaves the term out, its links resolve through the download block at grab time and are **fetched by the engine itself** (`indexer.ResolveDownload`, owner found by host first — the indexer's proxy, solver, pacing and session, never the shared client), and `checkReleaseSource` admits its site's host. **A definition the entry can no longer run is a warning at `Load` and a failed search, never a failed boot**: `CheckCardigann` (decode, `convert.Check`, site, settings) runs on API writes and pins only. An edit moving an entry's `site` or `proxy` asks for its secret settings again (`secret_required`), and the trust hold reads scheme-relative `//host` paths as hosts too. A session row carries `config_hash` (definition, site, proxy, settings) and one earned under other settings is read as none, so no edit `Forget`s it; a parallel login adopts the session the first stored; `keep` is best effort. A fetch reads `definitions/v12` with `v11` as the per-file fallback (Prowlarr's own, the newest copy of a file winning) and rewrites .NET spellings through `internal/cardigann/convert` — keyed by upstream **file name**, not id; `convert.Version` moves with any change to what the converter emits. Tests use three unmodified upstream fixtures (`internal/testutil/cardiganntest`); the whole upstream catalog goes through the engine only in the weekly `cardigann-upstream` workflow (`STREAMLINE_CARDIGANN_UPSTREAM=1`), so `task test` never needs the network. **Compiling on RE2 is not the bar — meaning the same is**: `\w \d \s` are spelled as the Unicode sets .NET means, and what RE2 cannot express with .NET's meaning (lookarounds, `\b`, `$`, …) is tagged `engine: regexp2` at conversion, never chosen by trial at runtime. Templates are re-quoted and validated by Go's parser, so the engine must pass `.Config`/`.Result` as maps; dates are parsed with `cardigann.ParseDate`, never bare `time.Parse` (a layout without a year takes the current one, as in .NET). Prowlarr's load-time defaults are baked in by `convert.clean`; what cannot be (null renders as `""`, Newtonsoft's JSON stringification, URL-encoding only substituted values) is the file's **engine contract**. Each converted definition keeps its `source` block (upstream path, sha256, modification notice).

**Fetching and updates, the regex/date/template rewrites, secret flagging and the licensing basis: [`docs/agents/cardigann.md`](docs/agents/cardigann.md) — read it before touching `internal/cardigann/**`.**

## Media lifecycle & library queries

Twelve optional probe columns hang off `MediaFile`; `probed_at` stamped means all twelve were recorded, so **a migration adding a probe column nulls `probed_at` in the same file**. `MediaEvent` has seven optional owner edges (movie, episode, tv_show, artist, album, book, book_series) and exactly one is set; an album import is one event on the album, never one per track, and every detail page's History tab reads its owner's slice of `GET /activity`. `episode.status` is `wanted | downloading | importing | paused | available | skipped`, and every path that grabs must mark its episodes — **adoption included, which lands at `importing` and needs its own record-scoped mover** (`MarkWantedRecordEpisodesImporting`), since the completion sweep's one only moves `downloading`/`paused`. The series list filters, sorts and pages in SQL with a per-show counts rollup — never the episode tree — and derives a show's downloading/importing state from `episode.status`, so an unmarked episode is a show missing from those filters entirely.

An episode with no air date is **unaired, never missing**, and five places split aired from unaired — they must agree or a show matches a filter with nothing missing on its page. Specials (season 0) are out of every show-level number — seasons, episodes, the missing filter, the episode sort — and must be out of all of them at once; the specials season still renders with its own counts.

Cast is written inside the title's transaction; the **person biography fetch is not** — it runs after the commit, from the service layer that holds the providers, and `internal/db` stays free of any provider dependency. A person is enriched **once, ever**, keyed on `Person.details_fetched_at`, and no failure there may fail the import.

**A library root that looks gone costs nothing** (`internal/library/roothealth`): it is offline when it has tracked files and none of a sample of at most 20 can be stat'ed. `drift-check`, the orphan scans, tag sync, transcoding, imports and automatic grabs leave it alone, by-hand changes to its files answer `409 code: library_offline`, and `GET /system/info` carries `library_offline` for the pill and the Settings → Library banner. The ways out are path migration (music and book roots re-point only) and `POST /library/roots/{root}/accept-missing`.

**A file gone from disk keeps its row** (`MediaFile.missing_confirmed_at`): past the grace window the title stays `available` with a "missing from disk" mark until `library.missing_file_redownload_after` (default `168h`, `0` at once, `off` never) and a file that returns heals. While `missing_since` is set nothing touches the file on its own schedule, every question of "does this title hold a file" answers through `db.PresentFiles` (imports, adoption, uploads, RSS upgrades), a confirmed row whose owner holds another file goes on the next tick whatever the wait says, and `POST /library/missing-files/forget` removes the row and stops monitoring the title. One word everywhere: missing.

**Probe semantics, the event hooks, cast ingest and person enrichment, re-identify ordering, the in-flight marking paths and the list push-down: [`docs/agents/media-lifecycle.md`](docs/agents/media-lifecycle.md) — read it before touching status transitions, `internal/events/`, or `internal/db` list queries.**
## Music

Third vertical, mirroring TV: `Artist → Album → Track`, `MediaFile.track` the file edge. Metadata is MusicBrainz and an album is a **release-group**; one limiter (`metadata/mblimiter.go`) serves three classes — interactive first, then `metadata.Prefetch`, then `metadata.Background` — and a rate limit holds the last two. **`Add` is two-phase**: the request writes the artist and one stub per release group (`hydrating: true`), a process-wide worker fills the tracks, and **`metadata_fetched_at` NULL is the one "tracks not here yet" marker** — an unhydrated or unreleased album is never searched. A release group is one album however many artists it credits (`Album.artist` the owner, `co_artists` the rest; listings read owned ∪ co, policy and renames are owner-only). Monitoring is a policy (`Artist.monitor`), `Album.monitored` the only flag searches read. Every status write filters on the status it moves from, and a terminal import failure parks an album `failed`, never re-grabbed automatically. Music profiles are their own config family (`/music/quality-profiles`, never `/config/*`), tiers classified only in `internal/quality/audio.go`. A WAV converts to FLAC at import (`library.ConvertsWAV`); a CUE disc image is refused before it is downloaded wherever the name or file list says so.

## Music tags

Streamline writes what the library knows into every music file through TagLib (`go.senan.xyz/taglib`, WebAssembly on wazero, CGO-free; only `internal/library/audiotags` imports it). `audiotags.Write` **never modifies a file in place** — it writes a sibling copy, reads it back, and renames it over the original — and gives the copy the original's mode, extended attributes and owner (`ErrOwnership` when it cannot, the original untouched); **every change to an album's track files — a tag write, the importer's transfers, a rename, a delete — holds `library.LockAlbumFiles(albumID)`**, and the writer re-reads its row under it, or a copy taken before an upgrade or delete is renamed back over the path. It replaces only the keys it is given (empty deletes), deletes `library.music_tags.strip`, and never touches `preserve`, which wins over everything; the key set is `library.AlbumTrackTags`, pure, every owned key present. **The `music-tag-sync` job is the only writer after an import**; the importer records files `pending` and tags them through the same engine (`TagAlbum`) before it refreshes the media servers. `MediaFile.tags_state`/`tags_hash` carry the state; an equal hash settles a file without opening it, and an empty one forces the write. **A file a listed torrent serves is never written**, and under `seeding: defer` neither is a hardlink whose torrent is still listed — every client's listing is the only seeding signal, since only the builtin engine reports a stopped torrent. `mode` is `off`, `import` (once) or `managed` (re-queued on hydration, refresh and settings changes); only albums with `Album.tags_managed` are ever re-queued, which a music import review sets per commit (`write_tags`) and which adopted-only albums start without. **Artwork rides the same write**: `audiotags.WriteWithArt` embeds the cached cover (scaled to `art_max_px`) as the front picture and the pass leaves `cover.jpg` beside the album and the artist photo as `folder.jpg` in a folder named after the artist; **ownership is a SHA-256 on the row** (`MediaFile.tags_art_hash`, `Album`/`Artist.art_sidecar_hash`), never a picture description (MP4 keeps none), so art Streamline did not write is never replaced and its own copies are never read back as the album's art. The album's **tag panel** (`GET /music/albums/{id}/tags`) compares each file with the write through `audiotags.Compare`, which shares the writer's own `plan`; `Album`/`Track.tag_overrides` layer hand-set tags over the library's (`desiredTags`), and under `managed` the job's **outside-edit check** stats written files in rotation and queues one whose owned keys were changed elsewhere.

**The write contract, the key mapping and where each value comes from, the tag state, the job and its triggers, the seeding guard, `albumImportMode`, the artwork rules, the panel, overrides and the edit check: [`docs/agents/music-tags.md`](docs/agents/music-tags.md) — read it before touching `internal/library/audiotags/`, `internal/media/music/tags.go`, the album importer's tagging, or `library.music_tags`.**

## Books

Fourth vertical, **book-first**: `Book` is a shelf item alone or a volume of a `BookSeries`; `Author` rows join through `BookContribution` and there is no author-follow. A book has two independent **slots**, ebook and audiobook, each pointing at a `BookEdition`; the slot state on the wire (`book.SlotState`) and the shelf SQL derive it the same way — change one and the other. A refresh fills a slot with no edition but never re-points one. Metadata is Hardcover (key optional: without it the handlers answer `503 hardcover_not_configured`), called in **batches of twenty** under a 5,000/day budget whose scan reserve every background pass stops at. **Series add is two-phase** and a stub volume is never searched, grabbed or imported. The shelf (`GET /books`) is one raw-SQL `UNION ALL`, faceted like the other lists. Nothing is ever written into a book file; the OPDS extension serves ebooks only.

## API conventions
- **A change to the files of an offline library root answers `409` with `code: library_offline`**, built in `responseError` from `*roothealth.OfflineError`, so a handler only returns the error. The message names the root and never its path, which is admin-only. Book and series operations go by the roots they actually hold (`db.BookFileRoots`). The SPA renders it verbatim.
- **The upload endpoints carry three codes the SPA renders verbatim**: `422 upload_rejected` (a bad path, wrong-kind media, no media, a stub book, nothing in a discography matched), `409 upload_conflict` (the target already has a live download record) and `422 no_space` (the download volume cannot hold it). `no_quality_profile` applies as on a grab. Like `grab_rejected`, they need a code or the SPA falls through to the generic 422 line.
- Every list endpoint bounds `limit` to `[1, 100]` (200 for activity) and **400s** a value outside it (`pagination.go` `limitOr` — there is no request-validation middleware, so the spec's bounds are enforced there). The SPA's `apiAllPages` (`web/app/lib/api.ts`) walks pages at `PAGE_LIMIT = 100` against `total`; the handlers used to clamp silently, and asking for `limit=500` — which nine call sites did — showed 100 of 621 movies with no indication anything was missing.
- `otelx.RecordSpanError(span, nil)` returns nil and leaves the span alone. It used to deref the error for `SetStatus`, so a missing `if err != nil` was a panic the handler reported as a 500 nowhere near the mistake — which is exactly how `BulkDecide` shipped and how the dev server caught it.
- Connection-test 422s carry `code: connection_failed` and the SPA renders their message verbatim — it is composed by our own client code and is the only place the upstream status appears. A plain 422 reads "some of those values weren't accepted", which blames credentials that are fine.
- **A search result's `download_url` is a sealed handle, not the indexer's link** (`restapi/release_handle.go`): AES-GCM under a key derived from the session secret, prefixed `slr1.`, opened by `toIndexerResult` on the way back in. The link carries the indexer's API key and search is a member endpoint. A plain link in a grab body still passes, held to the indexer allowlist by `checkReleaseSource`; `info_url` goes out through `otelx.RedactURL`. Rotating the JWT secret retires every outstanding handle; a grab carrying one answers `grab_rejected` saying to search again, not the missing-field 422.
- **A refused grab answers `422` with `code: grab_rejected`**, and the SPA renders that message verbatim (`errorText`, same arm as `connection_failed`). All six grab handlers share it — `GrabMovieRelease`, `GrabEpisodeRelease`, `GrabSeasonRelease`, `GrabSeriesRelease`, `GrabMusicAlbumRelease`, `GrabBookRelease` — over `download.ErrUntrustedSource`, `ErrNoWantedFiles` (video only; album and book grabs take the whole torrent), `ErrClientFull` (the builtin engine at its `maxTorrents` constant with no imported torrent left to rotate out), `ErrNoSpace` (the free-space check, `download.space_check`), `ErrUnsafeTorrentName` (a `.torrent` whose name the engine's path guard refuses) and `ErrTorrentAlreadyExists` (the client already holds the torrent, or a live record tracks its hash; `errAlreadyInClient` names the release — it fell through to a bare 500 "internal error" until a re-grab of a season the queue showed downloading surfaced it). Without a code the SPA falls through `BY_CODE` to `byStatus(422)` and shows its generic "some of those values weren't accepted", which blames the request body: on the homelab, two anime episodes refused for `ErrNoWantedFiles` (the `SxxE<absolute>` keep-set gap) were indistinguishable from a malformed release payload, and the message naming the actual reason — the sentinel plus the caller's own release title — was discarded before it reached the screen. `errUnprocessable` still has no code by design; a 422 whose message is a *diagnostic* rather than field validation needs one, or the message never renders.
- **`replace_existing: true` on a music or book grab sets the record's `replace_mode = all`** (the field the importer already honours; the RSS upgrade arm sets `upgrades`). The old files go only **after** the new ones are placed and verified: per matched track for an album, per linked album that already had files for an artist pack, every file of the grabbed slot for a book (a replaced audiobook folder is removed whole, the other slot is never touched). A held or failed import leaves the originals. Accepted and a no-op on a title with no files.
- **A list response must be an inline `type: array` schema, not a `$ref`'d `components/responses` array.** oapi-codegen turns the `$ref` form into a struct embedding the slice, which encodes as `{"TypeName": [...]}` rather than a bare array — `/music/quality-profiles` and `/books/quality-profiles` shipped answering an object until the spec was inlined.
- **`GET /requests/{id}/metadata` for an artist, book or series calls the same handler method as its lookup detail** (`GetMusicArtistLookup`, `GetBookLookup`), so the request panel and the add flow share one cache and one provider budget; 429 and 503 pass through and the SPA falls back to the title without retrying.
- **A release search no enabled indexer answered answers `502` (`504` when every one timed out) with `code: indexers_unavailable`**, never an empty `200`: the search handlers hand `indexer.Unavailable` errors to `responseError`, which builds the response, and the SPA renders the message (indexer names and what went wrong) verbatim. An indexer failing while another answers costs only its own results. The automatic missing searches stop their pass at the first such search and stamp no cooldown. A caller that hung up (the SPA aborts a release search nothing is watching) is logged as `499` at debug, not as a 500. Rules in `docs/agents/quality-scoring.md`.
- **A 422 for a title with no usable quality profile carries `code: no_quality_profile`** (`errNoQualityProfile`), for the same reason: the album and book-slot search/grab endpoints would otherwise fall to the SPA's generic 422 line.
- **A Hardcover `503` carries `code: hardcover_not_configured` or `code: hardcover_key_rejected`**, distinct from `rate_limited` (429). One helper builds it (`errHardcoverUnavailable`); a handler that returns the book provider's 503 with `errServiceUnavailable` leaves the SPA unable to tell a missing key from a refused one from an outage. Approving a book or series request answers the same codes (and `429`) and the request stays pending.

## Testing
- Framework: Ginkgo (Describe/Context/It/By) + Gomega assertions
- Mocks: Mockery (`go tool mockery`) — config in `.mockery.yaml`, generated to `internal/<pkg>/mocks/`
- Run tests: `task test:unit` / `task test:integration` / `task test:e2e` / `task test` / `task test:coverage` — all `go tool ginkgo run -r --keep-going`; the first three and `test:coverage` (`!e2e`) carry a label filter, `task test` (and `test:e2e`) build the frontend first (`build:js` + `build:css`, skipped when unchanged), then `task test` runs every spec exactly once in two passes over disjoint package sets with no label filter (`E2E_PACKAGES` first and alone, then `REST_PACKAGES`, every other package holding a spec; one JUnit file each under `JUNIT_DIR`), so its reports list as skipped only specs that skip themselves — a label-filtered pass would list every spec it filtered out as skipped, and the two-filter split reported 362 phantom skips; forward extra args via `CLI_ARGS`, narrow with `LABEL_FILTER=` (not on `task test`)
- `task test:e2e` is capped at `--timeout=1m15s` (`E2E_TIMEOUT` overrides it; CI's frontend-only path sets `4m` for a cold build cache) and points ginkgo only at the packages holding a spec whose `Label(` line names `"e2e"` (`E2E_PACKAGES`, derived by grep, so keep that label on the `Label(` line). A build counts against the timeout, and building every suite stalled the API suite's SQLite fsyncs until it failed in `BeforeSuite`. `CLI_ARGS` replaces the package list. `apptest.Start` also sets `TMPDIR` to `/dev/shm` where it exists, so the app's database and config are in memory: on disk, building the whole tree stalled a request past the e2e client's 10 s timeout. A browser click under the same load timed out too, which is why `task test` runs e2e apart from those builds.
- `task test:e2e:containers` — container-backed e2e (Docker + `STREAMLINE_E2E_CONTAINERS=1`, 5m timeout); hermetic `test:e2e` excludes `containers`-labeled specs. `task test` selects them and they skip themselves unless `STREAMLINE_E2E_CONTAINERS` is set and Docker answers; CI's `test` job sets it and installs ffmpeg (the `ffmpeg`/`transcoding` e2e specs skip without it on PATH), so on CI the only skips left are the upstream Cardigann specs (`STREAMLINE_CARDIGANN_UPSTREAM`, the weekly workflow) and the ones that need root.
- Run single suite: `task test:unit -- ./internal/metadata/...`
- Each Ginkgo suite has a dedicated `<pkg>_suite_test.go` (the three `internal/utils/*` packages inline it in their single test file) with `TestX` + `RunSpecs` + `BeforeSuite(func() { DeferCleanup(testutil.InstallSlog()) })` — `testutil.InstallSlog()` routes `slog.Default` to GinkgoWriter for the suite's lifetime.
- Mocks emit to `internal/<pkg>/mocks/mock_<Name>.go` — type `Mock<Name>`, constructor `NewMock<Name>(GinkgoT())`
- Regenerate mocks after interface changes: `go tool mockery`
- Span-instrumented funcs wrap ctx via `tracer.Start(...)`, breaking exact-ctx mock matchers. Use `mock.Anything` for the ctx param in `.EXPECT().Fn(mock.Anything, ...)` calls.

## Multi-agent fix workflows
Convention for landing a batch of independent fixes (audit findings, review comments, a bug list). Iterate on this as we learn.

- **Group findings by file ownership first.** Two agents editing one file is the failure mode; disjoint file domains are what make the rest safe. One group per domain (e.g. `restapi/`, `download+importer`, `middleware+web`, `auth+db+ent`).
- **One workflow per group, one agent per finding.** Each fix agent runs with `isolation: 'worktree'` so it can never see or clobber another's tree. Agents fix *only* their assigned finding — no drive-by refactors, no fixing things they notice.
- **Seed every worktree before the agents build.** A fresh worktree cannot compile *anything* importing `web`: all four `go:embed` inputs are gitignored — `web/static/css/style.css`, `web/static/css/docs.min.css`, `web/static/js/docs.min.js`, `web/static/dist/`. The failure reads `pattern static/css/docs.min.css: no matching files found`, which looks like broken code and is not. Copy them in from the main checkout right after launch (they stay gitignored, so they never pollute a patch); re-run the copy as assemble-phase worktrees appear. Building them per-worktree instead costs a full pnpm+esbuild+tailwind cycle per agent.
- **Agents commit; they do not emit patches.** Every fix agent ends by committing its work on its worktree's own branch, one commit per finding, with a real Conventional Commits subject. Integration is then a merge/cherry-pick against a shared ancestor — a proper 3-way merge that understands moved and adjacent hunks. Patch files were the earlier convention and they mangle exactly this: a flat diff has no base, so two agents editing neighbouring lines of one file produce hunks that apply cleanly in isolation and silently mis-stack when combined. Commits carry the base; diffs don't.
  - Inside a harness worktree the agent uses `git commit` (the worktree is a git worktree, not a jj workspace — this is the "raw git plumbing" exception, not a licence to use git elsewhere). The integrating session brings the work across with jj, which sees those commits after its automatic import.
  - If a patch file is ever unavoidable, generate it with `git diff --no-ext-diff`: this machine sets `diff.external = difft`, so a bare `git diff > x.patch` writes difftastic's *rendered* output — diff-shaped, no `---`/`+++`/`@@`, and `git apply` rejects it with "No valid patches in input". Applying is unaffected; only generation.
- **Agents never write to the main working copy.** A per-workflow assemble agent merges the group's commits in its own worktree, resolves intra-group overlap, verifies `task build:go`, and leaves a single reviewable branch.
- **The main session integrates.** Workflows finish in any order; the session reviews each group's commits, brings them into the working copy, and verifies — serialized, so nothing races on the tree. Never let a workflow write to main itself.
- **Codegen runs once, at the end, in the main tree.** `task generate` / `task migrate:diff` rewrite `ent/*` and `internal/*/mocks/*`; per-workflow codegen produces conflicting generated files against a partial tree. Agents may run it inside their worktree to compile-check, but must keep generated output out of the commits they hand over. Migrations from `task migrate:diff` *are* handed over, unedited.
- **Verification is the session's, after integration** — `task build:go`, `task lint:go`, `task test:unit` over the merged result. A group that passed alone can still break the merge.
- **Clean up after integration.** Remove each group's worktrees and their `worktree-*` branches once its work is in and verified. They live under `.claude/worktrees/` *inside* the repo, so until they go the editor/LSP indexes every half-finished agent tree and reports its errors as if they were yours.
- Agents get no history rewriting and no publishing: no `jj`, no rebase/amend of anything they did not create, no push, no `task dev`, no `task release:*`.

## Docs & Spec Upkeep
- Any change to `/api/v1` behavior — routes, auth/authz, status codes, security schemes, request/response shapes — updates `api/openapi.yaml` in the same change, then `task generate` to regenerate `gen.go` (the spec itself is served from `api/embed.go`'s `//go:embed openapi.yaml`). A handler and its spec entry must never disagree.
- When a feature or behavior changes, update the affected CLAUDE.md section — **or the `docs/agents/` file its stub points at, when the change lands in one of those subsystems** — **and the wiki** (`docs/wiki/` — user-facing pages like `REST-API.md`, `Authentication-and-SSO.md`) in the same change — stale docs describing the old behavior are worse than none.
- `docs/agents/` holds the subsystem detail — one file per area, each behind a `##` stub above. `docs/agents/README.md` is the index and states the upkeep rule. A stub and its file must never disagree: the stub carries the shape and the load-bearing invariants, the file carries the rules and the reasons.
- **A code comment describes the code as it is, never as a diff against what it replaced.** "No longer", "used to", "instead of X", "not `total`" only make sense to someone who saw the earlier version, and the next reader did not: the comment says what the code does and why it has to, and how it got there belongs in the commit message and the PR.
- `docs/wiki/` is the source of truth for the GitHub wiki; `.github/workflows/wiki.yaml` mirrors it to `DataHearth/streamline.wiki.git` on every push to `main` touching it. Filename = page title (dashes become spaces), `_Sidebar.md` is the nav. Never edit through the wiki UI — the next sync overwrites it.

## Code Generation
- API: `go tool oapi-codegen --config api/oapi-codegen.yaml api/openapi.yaml` → `internal/server/restapi/gen.go` (package `restapi`) — regenerate after spec changes
- ORM: `go generate ./ent` — regenerate after schema changes
- All codegen: `task generate` (runs `go tool oapi-codegen`, `go generate ./ent`, `go tool mockery`). Versioned migrations: `task migrate:diff -- NAME` diffs the ent schema into a new migration.
- App icons: `task generate:icons` (`go run ./web/icons`, one file, filling through `golang.org/x/image/vector`; deliberately not part of `task generate`: run it only when the logo changes) renders every icon in `web/static/images` from `web/icons/logo.svg`. The outputs are committed, since `deploy/unraid/streamline.xml` links `favicon-512.png` on main by URL, and never edited by hand; the colours in `web/icons/main.go` are hardcoded copies of `--accent` and `--bg-deep`. Details in `design-system/MASTER.md` §8.
- **Let the generator write a migration whenever it can, and hand-write only what it cannot.** A schema change ent can diff is `task migrate:diff`, its output kept as generated, the down step included. A migration the diff cannot carry — moving rows between columns or tables (`20260824081500`'s `movie_events` copy), a backfill, a down that folds data back — is written by hand, in the generated file or one of its own, with `atlas.sum` rehashed after. `ent/migrate/main.go` runs every new down file on the replayed history and checks it restores the previous schema. Atlas's own reverse of a SQLite table rebuild (any change `ALTER TABLE` cannot express — an added column that carries an index included) is just `DROP TABLE new_<table>`, a table that no longer exists on the way down; when the check fails the generator replaces the down with Atlas's plan from the new schema back to the old one, checks that too, and says so in its output. `task migrate:check` runs the same check over the whole history (it regenerated ten downs that could never run, the init one included) and keeps every down that passes — which is why `replace_mode`'s hand-written down stays: it folds `replace_mode = 'all'` back into `replace_existing`, data a schema-only plan cannot carry. The `down migrations` spec in `internal/db/migrations_test.go` rolls a populated database all the way back through the real runner, so a down that cannot run fails CI.
- **A removed ent schema's table is dropped by the same generator.** ent's plan keeps table creations and modifications only, so `ent/migrate/main.go` (`dropUnknownTables`) appends the drop of every table the replayed history holds and `migrate.Tables` no longer declares to the new up file, before the down check. It runs only when the diff wrote a file: removing a schema nothing else references needs another schema change in the same diff.
- Prefer the narrowest integer type on ent schema fields (`field.Uint8` for bounded counters like `grab_failures`, `field.Uint16` for small ranges like `number`/`year`) — sqlite storage is identical but Go structs stay memory-efficient.
- After ent regen the LSP may report "undefined" for new fields/methods briefly; `task build:go` is the source of truth.

## Build
- Task runner: [Taskfile.yaml](Taskfile.yaml) — sole build orchestrator (no npm scripts).
- **Always** invoke operations via `task <target>`. Raw `go build`/`go test`/`ginkgo`/`golangci-lint`/`pnpm exec` bypass the Taskfile and drift from CI.
- Go tooling runs via the Go `tool` directive: `go tool {ginkgo,golangci-lint,oapi-codegen,mockery,air,govulncheck}` (`task vulncheck` runs the last, as CI does) — not system-installed; the flake devshell only ships `go`, `pnpm`, `go-task`, `biome`, etc.
- **A tool-directive module needs its full `h1:` in go.sum, and only the tool jobs notice when it doesn't.** `build`/`test`/`lint-go` never build those packages, so a `go.sum` carrying just the `/go.mod` hash resolves fine for them and fails in `vulncheck` (`go tool govulncheck`) and in `nix`, where the `streamline-lint` goModules derivation runs `go mod download` over the whole set — as a builder error inside a fixed-output derivation, which reads like broken code. `renovate.json` sets `postUpdateOptions: ["gomodTidy"]` so renovate can't open a PR in that state; a hand-edited go.mod needs `go mod tidy`, not `go get` alone.
- Full build: `task` (= `build:app` → `build:go`, which depends on `build:js` + `build:css` because assets are `//go:embed`-ed) → `go build -o streamline ./cmd`.
- Frontend: `task build:js` (Scalar docs bundle + Paraglide message compile + `routify build` + esbuild SPA) and `task build:css` (TailwindCSS v4).
- Dev server: `task dev` — live reload via `go tool air` (`.air.toml`; rebuilds with `task build:app`, runs `streamline --config ./tmp/config.yaml`).
- Lint: `task lint` (`lint:go` golangci-lint + `lint:frontend` biome over the SPA and the static JS/CSS + `lint:ts` svelte-check). Format: `task fmt`, which is treefmt (configured in `flake.nix`): `golangci-lint fmt`, `biome format` over the static JS/CSS only — Biome's formatter changes what Svelte markup renders — and nixfmt. Biome, not prettier.
- Clean: `task clean`.
- README screenshots: `task docs:screenshots` (`e2e/demoshots`) boots a throwaway instance, seeds a demo library through a fake Torznab indexer and a fake qBittorrent with ffmpeg-made files, so imports and the held import are real, and shoots the twenty pages into `docs/assets/`. Only the calendar's release dates and the browser's view of `/system/info` (disk, public URL) are staged. Needs ffmpeg, a Chromium and the TMDB/TVDB/Hardcover keys; `CONTRIBUTING.md` has the usage.
- **CI runs a section only when its inputs change.** The `changes` job at the top of `.github/workflows/ci.yaml` holds one path filter per section (`go`, `frontend`, `biome`, `helm`, `chart`, `nix`), and every other job is skipped at the job level unless its filter matched. A frontend-only change runs the SPA jobs, `build`, the web e2e specs (`./e2e/web`) and the unit specs over the embedded assets (`./internal/server/web`), not the whole Go tree; `vulncheck` also runs on every push to main, since advisories arrive without a change. A new top-level file a section reads must be added to its filter, or a change to it runs nothing. **The jobs run in three stages, each waiting on the one before**: `vulncheck`, then the lints, `format` (`nix fmt -- --ci`, on every change, no filter) and `build`, then `test` and `nix`; a failure skips every later stage. Each later job's `if` starts `!cancelled() && !failure()`, so a job skipped by its own filter does not skip what follows it — a new job needs the same guard and the `needs` of its stage. **The Go jobs restore one cache that `build` and `test` save on main, under a key each** (`actions/cache/restore` in each job, `setup-go`'s own cache off): an entry is never rewritten once saved, and under `setup-go`'s shared key the first job to finish owned it, so `test` never got its modules or test binaries back. Every job asks for `test`'s entry first (every module, every test binary, saved after a whole-tree run), then `build`'s for the same `go.sum` set — saved a stage earlier and only while neither exists, which is what a run finds when the tests on main fail — then the newest `test` entry for that Go version and last the newest `build` one, so a PR that moves `go.sum` downloads only what it changed. The kind sits before the hash in the key (`go-<os>-<go version>-test-<hash>`) because keys match by prefix only. The key names the three `go.sum` files by path, never `**`, which would read `node_modules` after the pnpm install; a new Go module's `go.sum` goes in that list. **`ci-ok` is the one check branch protection requires**: a job skipped by its `if` reads as passing, and so does every job when `changes` itself fails, so it fails unless `changes` succeeded and every other job passed or was skipped — add a new job to its `needs`. CI and Helm E2E have **no concurrency group**: each CI run tests only its own diff, so a run cancelled or replaced by a newer one would leave its commit untested for good. The frontend-only path runs `task test:e2e E2E_TIMEOUT=4m`, since the timeout counts the build: on a 4-vCPU runner the web suite takes about 28s from a warm Go build cache and about 2m from a cold one, past the 1m15s default. `e2e/web` skips its whole suite when `CHROME_PATH` is unset; the `test` job points it at the runner's Chrome and fails when there is none. Biome runs at the version `biome.json`'s `$schema` names.

## Issue triage
- `.github/labels.yml` is every label the repo carries, grouped `type | status | area | maintainer | renovate`; `labels.yaml` syncs it on push to main (create, update, rename an `aliases` entry in place — never delete). **Add or rename a label in that file, never through the UI**: the triage allowlist is derived from it, and a description doubles as Claude's guidance for when the label fits (100 characters max).
- `issue-triage.yaml` runs `anthropics/claude-code-action` (Haiku, `CLAUDE_CODE_OAUTH_TOKEN`) on `issues: opened`, and on `workflow_dispatch` as a backfill (given numbers, or every issue). Anyone who can open an issue starts it with the Claude token, so the job holds an issues-only `GITHUB_TOKEN`, a `.github/`-only sparse checkout, and **no tool but three wrappers** in `.github/scripts/triage/`: `gh.sh` (read-only), `edit-issue.sh` (labels of the permitted groups only, at most two `area/*`, `needs-info` never on a maintainer's issue) and `comment-issue.sh` (one per run, new issue from an outside author only, no @-mention). Every limit comes from the event payload or `labels.yml`, never from an argument. A backfill touches `type` and `area` only and never comments.
- `needs-triage` is the workflow's own marker: set at the start, cleared by `finish.sh` after a successful run — an issue still carrying it is one the run failed on. **Native Issue Types are not set**: they are an organization feature and this repository belongs to a personal account — the `type` update answers 200 and keeps nothing for the Actions token (with or without `contents: write`) and for the owner's token alike. The type labels carry it. Should the repo move to an organization, setting a type takes push access: give it its own job, **never** repository write in the job holding the Claude token.

## Release
- App and chart version independently, but they release the same way, so both live in one `release` namespace (`.taskfiles/release.yaml`). App: `task release:app VERSION=X.Y.Z`, which is `release:app:changelog` (regenerates the CHANGELOG **and rewrites `version ? "X.Y.Z"` in `nix/package.nix`** — `nix build` has no tag to read, so a nix install would otherwise report the previous release forever; `app:tag` refuses to tag until both are on main — commits them on their own revision and advances `main`) then `release:app:tag` (tags `main`, push fans out to `.github/workflows/{release,image}.yaml`). Chart: `task release:chart VERSION=X.Y.Z`, which is `release:chart:bump` (rewrites `version` in `deploy/helm/streamline/Chart.yaml`, regenerates `deploy/helm/streamline/CHANGELOG.md`, commits both, advances `main`) then `release:chart:tag` (tags `chart-vX.Y.Z`, triggers `.github/workflows/chart.yaml`); run the two apart to review the bump commit before the tag goes out. **A chart change lands without a bump**: only a `chart-v*` tag publishes and `release:chart:bump` writes the version it tags, so the version moves once, at release time, against the whole diff since the last chart tag. lint-helm refuses only a version *below* main's on a pull request (a stale branch overwriting `Chart.yaml`). Both take `VERSION` as bare semver; a leading `v` is accepted and stripped, so the same string works for either. The tag prefix is the task's business — `v` for the app, `chart-v` for the chart. The shared halves are `release:_changelog` and `release:_tag`, internal and the only place the jj-vs-git commit dance and the tag push are written. **`_changelog` fetches and cuts its revision from `main@origin`, never from `@`** — `jj new` on `@` sealed the empty working-copy commit into released history — and **`_tag` pushes `main` with the tag** (`jj git push --remote origin -b main --tag`): pushing the tag alone left `main` local, renovate moved origin's underneath it, and the next fetch made `main` conflicted. `_tag` is all-jj since jj 0.45 — the tags it writes are lightweight, not annotated, which nothing here reads.
- Artifacts come from goreleaser (`.goreleaser.yaml`): CGO-free binaries for linux/darwin/windows × amd64/arm64, archives carry `config.example.yaml`, `checksums.txt` is cosign-signed (bundle format), one SPDX SBOM per archive. Images are cosign-signed keyless + SBOM-attested + grype-scanned in `image.yaml`.
- **PR images live in their own package, `ghcr.io/datahearth/streamline-pr`**, so nothing that deletes them can reach a release tag. `pr-image.yaml` builds each same-repo, non-Renovate PR's **head** commit (not the merge commit) whenever the PR touches an image input. It builds `linux/amd64` only, with `provenance: false` and `sbom: false` so each push is one package version. It pushes `pr-<n>` and `pr-<n>-<sha7>`, each with a `-vaapi` twin. It reads main's build cache and never writes one, and grype only reports. `pr-image-cleanup.yaml` runs on `closed` and in a daily sweep. It uses `.github/scripts/pr-image/prune.sh` from the default branch: a version goes only when **every** tag on it is `pr-<n>` or starts with `pr-<n>-`, which is why each push also carries a commit tag (the next push moves `pr-<n>` off the old version). The sweep also deletes untagged versions older than a day. The script never deletes the package's last tagged version, which GHCR refuses. The two workflows share the concurrency group `pr-image-<n>`, so closing a PR cancels its running build. Fork PRs are deliberately unsupported: their `pull_request` token is read-only, and building under `pull_request_target` is ruled out. A new GHCR package is private, so `streamline-pr` has to be made public by hand once, after its first publish.
- Both tags publish a GitHub release, and both bodies come from `.github/actions/release-notes` (composite): it extracts the version's CHANGELOG section, pipes it to the Claude CLI to rewrite as operator-facing notes (installed from `claude.ai/install.sh`, run from `RUNNER_TEMP` with the section on stdin and no tool granted — no file writes, no repo access), then appends the caller's install/verify footer. **Both workflows run it in a separate `notes` job** (`contents: read`, `persist-credentials: false`, workflow-level `permissions: {}`) and hand the file to the publishing job as an artifact: the installer is an unpinned `curl | bash`, and in the publishing job it ran beside the checkout's persisted token, cosign's OIDC token and the tree GoReleaser signs. `anthropics/claude-code-action` is deliberately *not* used: it rejects `push` outright (`Unsupported event type: push`) and both release lines are tag-push triggered, so the step never once ran under it. **The model is never load-bearing**: the step is `continue-on-error` and skipped entirely without `CLAUDE_CODE_OAUTH_TOKEN`, and empty output falls back to the raw changelog section — which is exactly what shipped before. A *missing* changelog section still fails the release, since that is our mistake and not the model's. The chart release is created with `--latest=false` so it does not displace the app release on the releases page.
- `release:app` / `release:app:tag` / `release:chart` / `release:chart:tag` / `release:image` / `release:helm` publish for real and have no dry-run. Both end-to-end targets commit *before* they reach the half that pushes, so a dry check must be `task --dry`, never a real run with a deliberately bad VERSION. Never run one to "test" it — only exercise a precondition's failure path.

## Version Control
- Repository uses jj (Jujutsu) with a git backend. Commit a task with `jj new -m "msg"` (creates empty child, auto-snapshots subsequent work). Seal a task by starting the next with `jj new -m "..."`.
- Don't re-run `jj describe` on a commit you're already working in — message is set once per task.
- If working copy holds unrelated leftover edits (e.g. settings.json), describe them into their own commit *before* `jj new` for feature work.
- Abandon empty working-copy commits after no-artifact steps (smoke tests, manual verification): `jj abandon @`.
- Commit messages: Conventional Commits `type(scope): msg` — add a `(scope)` where it clarifies, omit it when it doesn't. Bundle related changes; avoid single-file revisions.

## Helm Gotchas
- VM/VL/VT charts: at v0.35/0.12/0.0.7 the selector used `app: server` but the template labels dropped it, so `server.podLabels.app: server` is set in each subchart's values. The charts pinned in `charts/observability/Chart.yaml` derive pod labels from the selector labels, so the workaround is likely removable — verify against a rendered template before dropping it.
- Cross-namespace k8s DNS requires FQDN: `<svc>.<ns>.svc.cluster.local`. Streamline→alloy uses `alloy.observability.svc.cluster.local:4318`.
- OTel SDK defaults to HTTPS. The chart renders `otel.insecure: true` into the config for the subchart's Alloy (plain HTTP), and for any `config.otel.endpoint` written as `http://…` — it strips the scheme, since the exporters take `host:port` via `WithEndpoint`.
- The Grafana dashboard is rendered by the **parent** chart (`templates/grafana-dashboard.yaml`) for both the subchart's Grafana and `grafanaDashboard.enabled` (an existing Grafana's sidecar) — a subchart can't read its parent's files. `task helm:prep` copies `deploy/grafana/dashboards/streamline.json` into `deploy/helm/streamline/dashboards/` (gitignored). Panels use `$datasource`/`$logs` variables, never a datasource uid; the logs panel's plugin type and query are picked at render time (`grafanaDashboard.logs.type`), since a datasource variable is bound to one plugin type.
